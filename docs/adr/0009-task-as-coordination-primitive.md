# ADR-0009: The task is the coordination primitive

**Status:** accepted (v2.5, 2026-02-08)
**Supersedes / superseded by:** —

## Context

Through v2.4, coordination was unidirectional and reactive: only humans could create work for agents; `request_human_input` modeled "agent needs a human" as blocking-and-waiting rather than as a real handoff; `spawn_agent` modeled "agent needs another agent" the same ad hoc way. When a conversation ended, whatever understanding the agent had built died with it — a follow-up event (PR review, CI failure, user reply) started a blank conversation with no memory of the prior work.

## Decision

A task (`agents.tasks` + `agents.task_handoffs`) is a first-class entity, independent of any conversation and of any external artifact it may reference — "a task is the agent's (or human's) understanding of what needs to be done and why," never a wrapper around a Linear issue or a PR. `creator_type`/`assignee_type` are polymorphic (`agent` | `human`) from the schema's first version, so all three coordination directions — human→agent, agent→agent, agent→human — use the same primitive without a future migration, even though v2.5 itself only exercises human→agent triggering plus an agent creating and working its own task. Task creation is agent-initiated, not framework-imposed: the agent calls `create_task` as its own first action when starting meaningful work, and conversations without a task continue to work unchanged (`task_id` is nullable). Handoffs are agent-authored structured records written at conversation boundaries (`summary` required, ~4KB cap, optional `key_decisions`/`artifacts`/`open_questions`/`next_steps`) — never auto-generated, because the agent knows which of fifty messages actually mattered and an auto-summary would treat all of them as equally important. `handoff_type` (`completion` | `pause` | `delegation` | `escalation`) is metadata the framework stores and delivers but never pattern-matches on, so new handoff types are addable by prompt guidance alone. Whether to create a task is placed in an agent's `<domain_knowledge>`, not its `<constraints>` — it's a judgment about whether the conversation will produce something needing follow-up, not a safety boundary. Events for the same task are serialized through a Postgres advisory lock (`pg_advisory_xact_lock(hashtext(task_id))`), in a lock space kept separate from conversation-level `SKIP LOCKED` with a fixed lock order (task, then conversation) to avoid deadlock between the two — one problem at a time, matching how a human would work the same queue. Hierarchy guardrails cap delegation depth at 5 levels and subtasks per parent at 10, and reject circular delegation (A→B→A) while explicitly allowing self-decomposition (A→A, which is task breakdown, not a cycle) — enforced as guard checks inside the `create_task` tool itself, not as a separate service or middleware layer. Event-to-task correlation is owned by each integration, not the router: every integration maintains its own `task_correlations` table (a plain `TEXT` column, no foreign key into `agents.tasks`, so integrations stay independent), written on outgoing artifact-creating MCP calls and read on incoming webhooks — the integration processes both sides of an artifact's lifecycle and has the most information to make the correlation reliably.

## Consequences

- `request_human_input` and `spawn_agent`'s separate, ad hoc semantics are subsumed by one primitive with a creator and an assignee, though the agent→agent and agent→human delegation directions this enables don't ship until v2.7.
- The `created` task status and the `assignee_type: "human"` branch exist in the schema from v2.5 but are exercised by no v2.5 tool — a deliberate two-step (schema now, behavior later) that costs nothing at this milestone.
- Task-scoped event routing becomes an early-exit branch ahead of the existing `EventRouter`: presence of a correlated `taskId` skips fast-path/slow-path classification entirely and routes straight to the task's active or newest conversation.
- Stale tasks are framework-flagged (a scheduled job, mechanically similar to a `wait_for` timeout) but agent-decided what to do about it (follow up, discard, retry) — a hybrid, not an auto-close.
- Worker sub-agents (coder, researcher, tester) do not receive task tools at all: they share the parent orchestrator's `correlationId`, so a worker calling `create_task` or `complete_task` would corrupt the orchestrator's own task state rather than create anything meaningful of its own.
