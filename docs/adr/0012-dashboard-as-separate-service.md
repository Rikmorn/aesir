# ADR-0012: The dashboard is a separate, read-mostly service

**Status:** accepted (v2.4, 2026-02-05)
**Supersedes / superseded by:** —

## Context

v2.3 (ADR-0006) gave the platform a unified event log with rich observability data, but the only way to see any of it was direct SQL or log tailing: reconstructing why an agent made a specific tool call meant hand-filtering and joining `agent_events`, a tool returning `isError: true` was invisible until it produced bad output downstream, and "what can this agent do?" required reading YAML files, code, and three separate permission tables.

## Decision

The dashboard runs as its own Next.js 15 service (`packages/dashboard/`, port 3005) rather than embedded in the agent service, because it has a different deployment lifecycle (dashboard changes shouldn't force agent-service restarts), a different resource profile (SSR and static assets versus background agent loops), and a clean dependency boundary — it reads from Postgres and the agent-service API and nothing else. It connects to the existing Postgres instance read-only, with no write paths and no new tables in v2.4; dashboard-specific data, when needed, gets its own `dashboard.*` schema rather than touching `agents.*`. The original design called for importing the agents package's own Drizzle table definitions directly ("shared Drizzle schema... no schema duplication," per the raw spec's Detailed Requirements) — what shipped instead is the opposite: `packages/dashboard/src/lib/schema.ts` maintains its own local Drizzle definitions that mirror the agents schema, specifically to avoid pulling the full `@aesir/agents` dependency tree (`@anthropic-ai/sdk`, `@slack/bolt`, `pg-boss`, and the rest) into the Next.js build. Real-time updates use Server-Sent Events, not WebSockets: the data flow is unidirectional (server → browser, "watch what's happening"), SSE works through standard HTTP proxies with no special configuration, and the browser's `EventSource` handles reconnection on its own — a new `/api/sse/events` endpoint on the agent service bridges the existing in-memory `EventLog.subscribe()` mechanism out to the browser. All database access goes through a service layer (`src/services/*.ts`) that returns dashboard-shaped types rather than raw rows, deliberately positioned as the seed of a future API boundary: when a REST/GraphQL layer is added, the service functions become its implementation and components don't change. Runtime state that doesn't live in the database — tool registry, worker loop status, integration health — is exposed by new endpoints under a separate `/api/` prefix on the agent service, distinct from its existing operational endpoints (`/events`, `/conversations/:id`), so different auth policies can apply to management versus operational traffic; this prefix is deliberately designed, per the spec's own rationale, as the first iteration of a broader management API. The whole dashboard is built auth-ready rather than retrofitted: a passthrough `middleware.ts`, a `ServiceContext` parameter threaded through every service function (currently empty), and `NEXTAUTH_*` env stubs — structured for auth before it's required, on the reasoning that this class of requirement is near-certain and near-zero cost to anticipate versus expensive to bolt on later.

## Consequences

- The schema mirror is a maintenance liability by design, not by accident: `packages/dashboard/src/lib/schema.ts`'s own header states "schema changes are infrequent; if the agents schema changes, update this file" — drift is caught by inspection, not by a shared-type guarantee.
- No dashboard-specific tables shipped in v2.4; when one is needed it goes in a `dashboard.*` schema of its own rather than the mirrored `agents.*` tables.
- Static configuration data (agent definitions, tool registry, MCP permissions) deliberately gets no real-time SSE treatment — it changes only on service restart or database seed.
- v2.4 shipped strictly read-only; write operations (retry, cancel, reassign) and an external API were reasoned as a distinct future concern requiring its own design, not an oversight. Per `docs/history/specs/design-vision.md`'s Dashboard to Management API expansion path, those steps remain unbuilt as of v2.9.
