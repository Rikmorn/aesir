# ADR-0008: Intent-based communication: reply, ask, notify

**Status:** accepted (v2.6, 2026-02-09)
**Supersedes / superseded by:** —

## Context

Through v2.5, agents communicated outbound through integration-specific tools (`slack:send_message`, `slack:reply_to_thread`; `linear:create_comment` existed in the Linear MCP server but was never registered for agent use; no GitHub PR-comment tool existed at all). This scaled as O(agents × integrations) — every new channel meant updating every agent's tool list and prompt guidance — and it left agents reasoning about channels instead of intent: dev-agent's escalation behavior was hardcoded to Slack regardless of where the triggering signal actually came from. Inbound events were already normalized through adapters into domain-language signals (`approval`, `pr_review`, `user_reply`); outbound had no symmetric counterpart, so an agent replying to a Linear comment still had to know it was Slack and hardcode a channel ID.

## Decision

The design principle is "classify by intent, reply by origin": the semantic meaning of a signal (approval, feedback, question) is independent of the channel it arrived on, so agents reason in domain language while infrastructure handles channel translation in both directions. A `ReplyContext` discriminated union (Slack `{teamId, channelId, threadTs?}` / Linear `{issueId}` / GitHub `{owner, repo, prNumber, commentId?}`) is attached by inbound adapters wherever an originating channel exists, carried opaquely through `IncomingEvent` → `Signal` → the user message the agent sees, and passed straight through — untouched — to three new tools: `communication:reply` (respond to whoever is talking to you), `communication:ask` (request input, with any options pre-rendered into plain text — `- **label**: reply "value"` — before dispatch, so no channel gets native interactive buttons), and `communication:notify` (broadcast to an explicit target, with no auto-resolution or conversation-derived fallback). A single outbound denormalizer dispatches on `replyContext.channel` to the matching integration MCP call (Slack `reply_to_thread` when `threadTs` is present else `send_message`; Linear `create_comment`; GitHub `create_pr_comment`) — the denormalizer receives plain text and routes it; it never formats, which stays the tools' job. Echo prevention is filtered at the point closest to the source: the integration that owns the OAuth/bot identity for a channel drops its own agent-generated webhooks before they reach the agent service's adapters or router at all, because burning a slow-path LLM call to classify the agent's own output back to itself is wasteful and because a downstream adapter-level check is an unreliable safety net compared to filtering where the actor identity is actually known. Linear's `create_comment` becoming agent-reachable for the first time in v2.6 is what turns this from a theoretical gap into a required filter — before v2.6, agents never wrote to Linear, so there was nothing to echo.

## Consequences

- Adding a new integration channel is an adapter change plus a denormalizer case — zero agent changes, collapsing what used to be O(agents × integrations) tool surface into three fixed tools.
- `defaultNotifyTarget` on an agent definition lets an agent call `notify()` without hardcoding a channel, but the tool itself still requires an explicit target every time — there is no implicit "wherever this conversation is happening" fallback.
- Options rendered as text rather than native buttons is a deliberate consistency trade: every channel behaves the same way, at the cost of losing Slack's native interactive affordance.
- v2.8 extended the same denormalizer pattern to failure paths: a single channel-agnostic `notifyFailure()` call at all terminal error paths replaced a Linear-only `emitErrorActivity()`, so agents fail consistently regardless of where the conversation started.
- `docs/history/decisions-log.md`'s "Echo filter at adapter level" row and `docs/history/specs/design-vision.md`'s "Echo filtering at integration layer only" row name the same mechanism (actor-identity comparison against the agent's own OAuth/bot user, done cheaply with no extra API call) but disagree on which layer name to attach to it — this ADR follows the raw spec's unambiguous language (`### Agent Echo Prevention`: filtering happens at the integration, "before they reach adapters or router," with explicitly "no adapter safety net") rather than either summary row's label.
