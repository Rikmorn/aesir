# ADR-0008: Intent-based communication: reply, ask, notify

**Status:** accepted (v2.6, 2026-02-09)
**Supersedes / superseded by:** —

## Context

Through v2.5, agents communicated outbound through integration-specific tools (`slack:send_message`, `slack:reply_to_thread`; `linear:create_comment` existed in the Linear MCP server but was never registered for agent use; no GitHub PR-comment tool existed at all). This scaled as O(agents × integrations) — every new channel meant updating every agent's tool list and prompt guidance — and it left agents reasoning about channels instead of intent: dev-agent's escalation behavior was hardcoded to Slack regardless of where the triggering signal actually came from. Inbound events were already normalized through adapters into domain-language signals (`approval`, `pr_review`, `user_reply`); outbound had no symmetric counterpart, so an agent replying to a Linear comment still had to know it was Slack and hardcode a channel ID.

## Decision

The design principle is "classify by intent, reply by origin": the semantic meaning of a signal (approval, feedback, question) is independent of the channel it arrived on, so agents reason in domain language while infrastructure handles channel translation in both directions. A `ReplyContext` discriminated union (Slack `{teamId, channelId, threadTs?}` / Linear `{issueId}` / GitHub `{owner, repo, prNumber, commentId?}`) is attached by inbound adapters wherever an originating channel exists, carried opaquely through `IncomingEvent` → `Signal` → the user message the agent sees, and passed straight through — untouched — to three new tools: `communication:reply` (respond to whoever is talking to you), `communication:ask` (request input, with any options pre-rendered into plain text — `- **label**: reply "value"` — before dispatch, so no channel gets native interactive buttons), and `communication:notify` (broadcast to an explicit target, with no auto-resolution or conversation-derived fallback). A single outbound denormalizer dispatches on `replyContext.channel` to the matching integration MCP call (Slack `reply_to_thread` when `threadTs` is present else `send_message`; Linear `create_comment`; GitHub `create_pr_comment`) — the denormalizer receives plain text and routes it; it never formats, which stays the tools' job. Echo prevention is designed as filtering by actor identity at the integration or adapter layer: the integration, which knows its own OAuth/bot identity, filters as early as possible and drops an agent-generated webhook before it emits a `NormalizedEvent`; the adapter is a safety net if an echo leaks through, checking for agent-generated indicators and returning `null`/`AdapterIgnore`; the router is never meant to see an agent's own echo, because burning a slow-path LLM call to classify the agent's output back to itself is wasteful and unreliable. Linear's `create_comment` becoming agent-reachable for the first time in v2.6 is what turns this from a theoretical gap into a required filter — before v2.6, agents never wrote to Linear, so there was nothing to echo, and the spec calls out actor-ID-based filtering on the `Comment` webhook as the new work needed.

## Consequences

- Adding a new integration channel is an adapter change plus a denormalizer case — zero agent changes, collapsing what used to be O(agents × integrations) tool surface into three fixed tools.
- `defaultNotifyTarget` on an agent definition lets an agent call `notify()` without hardcoding a channel, but the tool itself still requires an explicit target every time — there is no implicit "wherever this conversation is happening" fallback.
- Options rendered as text rather than native buttons is a deliberate consistency trade: every channel behaves the same way, at the cost of losing Slack's native interactive affordance.
- v2.8 extended the same denormalizer pattern to failure paths: a single channel-agnostic `notifyFailure()` call at all terminal error paths replaced a Linear-only `emitErrorActivity()`, so agents fail consistently regardless of where the conversation started.
- v2.8's Phase 75 ("Echo Elimination") replaced the v2.6 per-integration echo design with a single, stateless, router-level layer instead: `packages/agents/src/router/webhook-filter.ts` suppresses any `IncomingEvent` whose `actorInfo.isBot === true`, uniformly across channels, ahead of routing — one mechanism instead of an integration-by-integration filter each maintaining its own actor check. Linear's own webhook handler subsequently dropped its echo filter entirely, on the separate, Linear-specific reasoning that agent activity and user comments are structurally distinct paths (`create_agent_activity` vs. `comment`) that can't collide, not because filtering moved elsewhere.
