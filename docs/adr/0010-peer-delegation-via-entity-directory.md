# ADR-0010: Peer delegation through an entity directory with a negotiation handshake

**Status:** accepted (v2.7, 2026-02-13)
**Supersedes / superseded by:** —

## Context

Through v2.6, work reached agents only via external systems with a human in the loop at every handoff: product-agent creates a Linear ticket, a human assigns it, dev-agent picks it up via webhook. Agent-to-agent coordination without going through that human-mediated artifact didn't exist. ADR-0009 had already framed `spawn_agent` and `request_human_input` as ad hoc versions of the same underlying operation, but v2.5 shipped only the human→agent and agent-self-tasking directions — agent→agent and agent→human delegation were explicitly deferred.

## Decision

Orchestrator agents discover and delegate to each other directly, with no central orchestrator, through an entity directory: a table seeded from each agent's `definition.yaml`, keyed by a new `capabilities` field (natural-language, intent-level descriptions — "implement code changes and open pull requests," not a tool list), queried via `directory:find`/`directory:get`. Delegation goes through a handshake rather than fire-and-forget: `task:delegate` creates the task and starts the target's conversation; the target evaluates and calls `task:respond` with accept-plus-estimate or reject-plus-reason; the delegator, having separately called `wait_for` (`wait_for_task` from v2.9 on), decides to proceed, cancel, or try someone else. The handshake ships as accept/reject only, deliberately scoped down from an original counter-propose requirement, specifically because the protocol is built as a swappable strategy interface so richer negotiation can be added later without touching `task:delegate` itself. What crosses to the target is a focused brief — task description, expectations, and knowledge references — never the delegator's message history, so the target queries shared memory independently instead of inheriting the delegator's context wholesale. Completion closes the loop: `TaskSignalDispatcher` fires a signal when a task reaches a terminal status (`completed`/`failed`), resolves the callback to the parent task's current active conversation — not a fixed conversation ID, so it survives the conversation being re-triggered — and, if that conversation is no longer active, logs the completion as orphaned rather than losing it, because `completion_result` is persisted as JSONB on the task itself, independent of whether delivery succeeds. `wait_for_task` is a distinct tool from `wait_for` that auto-registers for every task-lifecycle signal type (completion, failure, timeout) in one call, so a delegator cannot forget to listen for the failure or timeout path and get stuck indefinitely. Delegation and hand-off share the same infrastructure — `task:delegate`, directory lookup, handshake — and differ only in whether the delegator calls `wait_for_task` afterward, which is a prompt-level decision the agent makes based on whether it needs the result to continue, not a framework distinction. Completion obligations follow the same split: triggered work needs no `task:complete_task` call; delegated work must call it to unblock the delegator; delegated work with external side effects must finish those external updates first, because `task:complete_task` resumes the delegator and both sides touching shared state at once risks a race. The QA agent validates this whole system as a delegation-only agent — no triggers of its own, started exclusively via `task:delegate`, running on Haiku for cost efficiency — proving that some agents exist purely to be delegated to rather than to initiate work.

This tier of collaboration is scoped to orchestrators only. The companion principle — orchestrators are autonomous peers with directory presence, budgets, and handshakes; sub-agents (coder, researcher, tester) are internal workers spawned within an orchestrator's conversation, sharing its budget, and never appear in the directory or receive delegated tasks — draws that line in the same milestone.

## Consequences

- v2.9 (phases 80–81) extended the handshake with a third response — counter-propose, implemented as a discriminated union on a `type` field replacing the earlier `response` enum specifically for extensibility — and added task groups with `all_required`/`any_sufficient`/`majority` completion policies for parallel delegation, both delivered without changing `task:delegate`'s core contract, which is exactly what the v2.7 strategy interface was built to allow.
- Maximum delegation depth is 5, not the 3 the milestone spec proposed. `task:delegate` enforces `MAX_DELEGATION_DEPTH = 5` (`packages/agents/src/shared/tools/task/types.ts`), the same figure as the task primitive's general guardrail (ADR-0009) rather than a tighter one, and that value is unchanged since the `v2.7` tag. `docs/history/specs/2.7-agent-collaboration.md`, DEL-09, called for reducing it to 3 for this milestone (orchestrator → orchestrator → sub-agent, the natural maximum); it was never implemented as written, so the tighter bound exists only in the spec. What binds is 5.
- Human-targeted delegation, materialization-as-policy (internal signal vs. Linear ticket), and bidirectional mid-task clarification were all designed into the schema (`reach_via` JSONB, a materialization dispatch interface, multi-type `wait_for`) but explicitly deferred — the shapes exist so each can be added later without refactoring the directory or handshake.
- Graceful degradation is a stated cross-cutting constraint: if the directory is unreachable, agents fall back to solo execution; if completion signaling fails, delegators eventually time out rather than hang forever.
