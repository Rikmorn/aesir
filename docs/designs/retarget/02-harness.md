# Topic 2: the harness and the manifest

Status: seeded 2026-09-16, not started. Roberto flagged this as a core concept needing its own discussion. This file holds the positions taken so far so the discussion starts from them.

## Roberto's position (2026-09-16)

Quoting the brief and the follow-up: the harness is "an executable that provides tools for the LLM to use", like Claude Code is to the model. The manifest "declares what tools the agent has access to, memory strategies, context management strategies, skills, hooks", and "during build time we bundle or configure mcp config as necessary". On Managed Agents' feature list (hosted loop, per-session sandbox, MCP, skills, scheduling, multi-agent rosters, memory stores): "our manifest should allow for all (or most) of these to be defined per agent/container, with the harness doing whatever setup needed at build time and docker providing the environment for them to run on. That build process can grow as we need it to; token budgets could be an extension."

## Points raised in reply, to be argued properly here

**Declare versus provide.** Build-time, image-local items (tools as code, MCP configuration, skills, guidance layers, model choice, resource limits) the manifest defines and the build bakes. Cross-agent services (memory store, scheduler, roster, the paused conversation) the manifest can only declare; the cluster provides them. Analogy and likely pattern: a pod spec declares volumes, secrets and schedules; the cluster fulfils them. Precedent in aesir: the YAML `tools:` list is a declaration bound by the ToolRegistry against a per-conversation context (`packages/agents/src/framework/tool-registry.ts`). The manifest is that mechanism moved from process start to image build plus container start. The build can emit the cluster objects the declarations imply (a schedule line becomes a CronJob), which is where "the build process can grow" lands.

**Build-time versus runtime.** Budgets, iteration caps, heartbeats and timeouts are runtime enforcement by the harness. Declare them in the manifest; bind environment-specific values (budgets, endpoints, secrets) at deploy as env or mounted config so a budget change is not a rebuild.

**Guidance layers are image layers.** Claude Code's layering is files in a filesystem; a container is a filesystem. Base harness image, organisation layer (shared guidance, shared MCP configuration, shared skills), agent layer (role guidance, tool selection, manifest) map onto a `FROM` chain. Cost: a base change rebuilds everything above it; per-conversation state is not in any layer and needs its own home.

**Sprawl risk.** "All per agent" must not mean each agent owns its own MCP server and memory store instances. The organisation layer owns shared instances; agents declare use. Where that line sits is a decision for this topic.

## Questions this topic must answer

1. What the harness owns: the loop, context management (pruning, summarisation, compaction), memory strategy, tool exposure (all listed versus exposed by phase or by search), hooks, skills, the message API it exposes to receive work.
2. Build or reuse: own loop on the Messages API, the SDK Tool Runner, or the Claude Agent SDK as the harness inside the image. What each gives and takes (model-agnosticism, control over context, built-in tools, permissions). Research thread 1 feeds this.
3. The manifest schema: fields, which are build-time, which are deploy-time, which are declarations of cluster-provided services. Compare with the precedents the research thread finds (A2A Agent Card, kagent CRDs, Docker cagent, AGENTS.md).
4. Tool exposure: finding 2 in `00-as-is.md` (every listed tool on every call). What the manifest can express about when a tool is available.
5. How a running harness receives a message and how it pauses: the contract between the harness and the durable conversation store (topic 3 decides where the store is).
6. Build or reuse, sharpened by the product statement: "the loop is yours" implies model choice. Wrapping the Claude Agent SDK gets Claude Code's loop, compaction and built-in tools but binds the harness to Claude. An own loop on the Messages API (or the SDK Tool Runner) keeps model choice and costs the loop, compaction and caching work. Decide whether model-agnosticism is a requirement of the first workload or a later extension.

## Model agnosticism (Roberto, 2026-09-16)

"Model agnostic is important as a principle. I don't mind doing it all with the Claude SDK, but the harness should be usable with OpenAI or any of the open-source models, so the behaviours would eventually need to be cloned or the SDKs packaged so they can be bundled at build time (some form of DLL maybe?). There is a question of where the model is; I assume somewhere on the internet, but I don't see why we couldn't in the future create a network tunnel for agents to talk to private LLMs."

### Two SDKs, two different commitments

"Claude SDK" names two products, and the choice decides whether agnosticism is a swap or a rewrite:

| SDK | What it is | Agnostic later means |
|---|---|---|
| `@anthropic-ai/sdk` (Messages API client, optional Tool Runner) | An HTTP client; the loop is yours | Add an adapter behind your port; the loop does not change |
| `@anthropic-ai/claude-agent-sdk` (Claude Code as a library) | The loop, compaction, permissions, hooks, subagents, built-in tools; Claude-only | Write a second harness; "clone the behaviours" is that rewrite |

Verified as-is: the loop imports the Messages client directly and calls `messages.create` (`packages/agents/src/shared/agent-loop/run-agent-loop.ts:17`, `:223`, `:286`, `:368`); the only model dependency is `@anthropic-ai/sdk` (`packages/agents/package.json:31`). No Agent SDK, no OpenAI client, no abstraction library is present.

### The pattern: port and adapter for the model

- **Pattern:** port and adapter (hexagonal architecture, Cockburn). The harness talks to a `ModelPort` (send system, messages and tools; receive content blocks, tool calls, stop reason, usage; stream). One adapter per provider family: Anthropic Messages; OpenAI Responses or Chat Completions; OpenAI-compatible for vLLM, Ollama and llama.cpp servers, which all expose that wire format.
- **Problem it solves and why here:** the loop's logic (tool execution, budgets, pause, compaction policy) must not depend on one provider's wire format. Here because the principle is stated and the second provider is known.
- **Where it already appears in aesir:** the embedding service. `packages/agents/src/shared/embedding/factory.ts` switches on `config.provider` and returns an Ollama or Voyage adapter behind the `EmbeddingService` interface in `types.ts`. Same shape, one level up.
- **What it costs and when not:** the intersection problem. Prompt caching, adaptive thinking, compaction blocks, server tools and mid-conversation system messages are Anthropic-shaped; OpenAI's reasoning items and Responses state are theirs. A port that exposes only the intersection loses the cost and context levers. A port where each adapter declares capabilities and the harness degrades or fails at build (the manifest asks for compaction; the adapter lacks it) keeps them. Do not use it when only one provider will ever exist; that is not this case.

A second reason to build the port even before a second provider: a fake adapter makes the loop deterministically testable without LLM-judged scenarios (testability lens, `.claude/skills/design-pass/SKILL.md`).

### Options for the adapters

| Option | What it gives | What it costs | Note |
|---|---|---|---|
| A. Own thin port; official SDK per provider inside each adapter | Full access to each provider's features; no lag | You write and maintain each adapter | Anthropic first; OpenAI-compatible second, when a workload needs it |
| B. A provider-abstraction library (Vercel AI SDK, `ai` 7.0.x, provider spec `LanguageModelV4`) | Adapters for many providers at once; the Anthropic provider exposes nearly the whole surface today: explicit caching, adaptive thinking, compaction, context editing, tool search and `defer_loading`, mid-conversation system and tool changes, task budgets, server tools | A new major every six to eight months (v5 2025-07, v6 2025-12, v7 2026-06) and per-feature documentation lag; `providerOptions` and `providerMetadata` are real, layered escape hatches | Checked 2026-09-27: the lag argument was weaker than written and the churn argument stronger (`research/2026-09-27-tool-exposure-and-model-port.md` §5) |
| C. A translation proxy (LiteLLM, Bifrost, or agentgateway's LLM fronting) | Two routes under one name: passthrough keeps every lever and swaps nothing; translation swaps providers and keeps the intersection of two dialects plus hand-mapped fields | Another process; LiteLLM needs Postgres and Redis for its features and shipped a credential stealer on PyPI on 2026-03-24 through a compromised CI action; Claude Code turns off `tool_reference` behind a gateway, a measured instance of a proxy costing a lever | Checked 2026-09-27: an egress concern in passthrough mode, not the port (same file §6) |
| D. Claude Agent SDK as the harness now, clone later | The most capable harness on day one | Agnosticism becomes a second harness | Conflicts with the principle unless the principle is explicitly deferred |

"Bundled at build time" needs no DLL mechanism in a container: the adapter is code in the image, selected by the manifest's model declaration, installed at build. Runtime pluggability without a rebuild is option C.

### Where the model is

Egress, not a harness feature. The harness makes outbound HTTPS to a base URL. A private model on GPU nodes in the cluster is a Service; one on another network is a VPN peer or a tunnel; both are environment configuration. The manifest declares the model endpoint and a credential reference; the environment provides the route. The model API key is then a vault credential like any other, substituted at egress, so the harness container holds no provider key. Implementation shape to weigh in topic 3: an egress sidecar or gateway the container talks to over plain HTTP, which adds credentials and forwards over TLS. This is the realistic version of the parked "bundle the model" idea: the model runs in the cluster, not in the agent's image.

## Execution structure: loop, or a planned graph (added 2026-09-16)

Roberto's "graph engineering" points at arXiv 2604.11378 (Hu Wei, 13 Apr 2026), "From Agent Loops to Structured Graphs". Read from the abstract and HTML this session; the dedicated session reads it properly.

**What it claims (verified from the paper's text).** The Agent Loop, "an iterative cycle where a single language model decides what to do next by reading an ever-growing context window", has three structural weaknesses: implicit dependencies (a step's dependence on an earlier one "exists only in the context window"), unbounded recovery (the model "autonomously decides whether to retry, skip, or replan" with no contract and no bound), and mutable execution history (a revised plan overwrites the original, so "it is impossible to reconstruct a faithful audit trail"). Its answer, the Structured Graph Harness: a planning layer produces and validates a static DAG of executable units before execution; an execution layer dispatches the ready set in topological order; a recovery layer escalates retry, local patch, full replan. A plan version is immutable. The survey of 70 open-source systems places agent loops at 60 percent, event-driven 15, state machine 10, graph/flow 5, hybrid 10, on a controllability versus expressiveness axis; SGH takes maximum controllability and gives up competitive parallelism, recursive expansion and dynamic topology. Formal termination is for the scheduler, not for model outcomes. The paper states it contributes "a theoretical framework, a design analysis, and an experimental protocol, not a production implementation or empirical results".

**Three scales of "graph", so the word stops blurring.**

| Scale | Who authors the structure | Example | Aesir today |
|---|---|---|---|
| Hand-authored flow graph | the developer, in code | LangGraph, the thirteen-node v2.1 graph | Rejected by ADR-0002 |
| Planned DAG inside one run | a planner (usually the model), before execution; immutable per plan version | SGH, plan-and-execute, LLMCompiler | Absent; the loop is the pure Agent Loop (`run-agent-loop.ts`) |
| Work tree across agents | agents, through delegation at run time | task trees, delegation graphs | Present: `TaskTreeNode`, tree budgets, task groups, the dashboard's delegation graph (`packages/dashboard/src/components/tasks/`) |

The repository's graph vocabulary (tree budget, subtree allocation, delegation graph, task groups) is the third scale. The paper is the second. The retarget question for this topic is whether the harness should support the second as a declared execution strategy, and what that costs.

**Where aesir already answers the paper's critique, and where it does not (believed; code not re-read this session).** Mutable history: the event log is append-only and is the audit trail; history pruning and summarisation change what the model sees, not the record (`docs/reference/design-vision.md`, "events as ground truth"). Unbounded recovery: `maxIterations` and `tokenBudget` bound the loop but there is no contract of which recovery is allowed for which failure. Implicit dependencies: nothing; ordering lives in the context window, as the paper says.

**Questions for the dedicated session.** Whether "execution strategy: loop | planned DAG | hybrid" is a manifest field; who produces the graph and when; how a durable pause (wait for a review for three days) fits a static DAG whose nodes are supposed to run to completion; whether the graph is stored beside the conversation and shown in the dashboard; what Anthropic's "A harness for every task: dynamic workflows in Claude Code" (claude.com blog, 2 Jun 2026, found by the research thread) does that SGH forbids; and what evidence, if any, exists beyond the paper's own untested predictions.

### Roberto's observation: aesir already has the graph runtime, unnamed (2026-09-16)

"It honestly feels like it's something we do implicitly with our job and delegation/handoff system we made way back when, except it grew organically based on what the agent needed."

Mapping, from ADR-0010 and the tool list; the code was not re-read this session:

| Structured Graph Harness | Aesir's implicit version | Status |
|---|---|---|
| Node: executable unit | a task, run by a conversation | present, persisted |
| Edge: dependency | `task:delegate` plus `wait_for_task`; parent and child on the task row | present, created at run time |
| Join | task groups: all-required, any-sufficient, majority (ADR-0010 consequences) | present; any-sufficient is the "first of" join SGH excludes |
| Resources | tree budgets flowing down the task tree (`tree-budget.ts`) | present |
| Scheduler and ready set | `TaskSignalDispatcher` resumes the parent on a terminal child status | partial: signal-driven, no ready set from a plan |
| Bound on recursion | `MAX_DELEGATION_DEPTH = 5` | present |
| Planning layer: validated plan before execution | none; nodes appear when an agent decides to delegate | absent |
| Recovery contract: retry, patch, replan | the delegator's model decides on failure; handoff types (completion, pause, delegation, escalation) are continuation, not recovery levels | absent as a contract |
| Immutable plan version and audit | append-only event log and task rows; no plan object to version | audit present, plan absent |

**Consequences.** The paper's DAG lives inside one run; aesir's lives across agents; a harness with an explicit graph model could serve both scales. This is a fork for the harness session, not a settled point. And the collaboration layer's fate is no longer "drop or keep": decide which parts are graph-essential (nodes, edges, joins, budgets, signals, bounds, audit) and which are not (the negotiation handshake, peer discovery through the directory, human handoff), and whether a planning layer and a recovery contract earn their place. The as-is caution stands: this runtime was validated by scenario agents, never by a real workload.

### The manifest (question 3)

**What ships.** Ten products read from schema files or API references; no two share a schema, but seven fields recur in seven or more: name and description, model, instructions, a tools list, MCP server references, skills, a delegation list (manifest §4). A version field is universal and means three unrelated things: a server-incremented integer (Managed Agents), an artefact digest (kagent, Docker Agent), a free string (A2A). Triggers never live inside the agent object: Managed Agents deployments, Foundry routines and kagent scheduled runs are siblings; Docker's scheduler is a session-only tool (manifest §3). Nobody has a field for layered guidance; kagent's `promptTemplate.dataSources` (ConfigMap includes) and Docker's `add_prompt_files` are the nearest seams. Hooks exist in four products; context-management knobs in four.

**The correction.** kagent v1.0.0-alpha1 (2026-09-18) shipped `Harness` (digest-pinned image, compaction, memory, substrate, env with `credentialRef`), `AgentTemplate` (model ref, prompt, tool bindings, immutable skill sources) and an `Agent` that pairs them, plus a `WorkerPool` per namespace and per-revision snapshots (manifest §1.2; shape §1). The 2026-09-16 research had these on an unreleased branch with a label selector; the shipped API dropped the selector for the pairing object. This is the only product that gives the runtime its own object, and it is the shape this note's "declare versus provide" argued for. Its `status.capabilities` (controller-written: `approvals`, `structuredOutput`, `maxNativeAgentDepth`, `resume`, `checkpoint`) and `warnings[]` are the only shipping precedent for reporting harness-to-behaviour compatibility.

**Three candidates**, each drafted as a commented skeleton with per-field precedent and the cluster objects a build would emit (manifest §5):

| | A. One document | B. Three objects | C. Services graph |
|---|---|---|---|
| Shape | Docker Agent's YAML: everything in one file, `${env}` and `flavors` as the only deploy seams | kagent v1alpha3 and Managed Agents' agent / environment / session: `Harness` (image and runtime policy), `AgentTemplate` (behaviour against references), `Agent` (the pairing plus deploy facts: overrides, version policy, triggers, scaling, card) | Foundry `azure.yaml`: sibling services (model, connection, toolbox, memory store, routine) wired by `uses`; the agent is one service with a referenced definition file |
| Harness upgrade rebuilds | every agent image | the Harness image only | every agent with a Dockerfile |
| Prompt edit rebuilds | the agent image | a template revision, no image | the definition; a new version |
| Who checks fit | nobody; runtime errors | a controller writes `status.capabilities` and `warnings` | the platform validates protocols at deploy |
| Cost to start | lowest | highest: three schemas and a resolver; a controller later | medium |

**Position (proposal).** Candidate B, because it is the shape the two products designed for this exact problem converged on, it decouples the harness upgrade from the prompt edit (the guidance-layers-as-image-layers idea above had the cost that a base change rebuilds everything; B removes it), and it is the only shape with a place to report that a template asks for a lever the harness lacks, which the tools-and-port research says the port needs (below). Start with B's three schemas and a `ko`-shaped build (G4); the controller comes when GitOps or a second operator asks. What B borrows: `Harness.env[].credentialRef` and `substrate.workerPoolRef` from kagent; `agent_with_overrides` as full replacement and the cents-string budget from Managed Agents; `maxTurns` from Claude Code; triggers as a sibling list on the `Agent` object, which is Managed Agents' deployment and Foundry's routine; the card from A2A and Foundry's `agentCard`. Assumption: the harness is the platform's own, so `Harness.kind` has one value at first; kagent's `codex`, `claude` and `byo` kinds show where a second harness would plug in.

### Tool exposure (question 4, G8)

The question "by phase or by search" has a shipped answer at both vendors (tools and port §1): Anthropic's tool search tool with `defer_loading` (public 2025-11-24, no beta header; regex or BM25; deferred definitions stripped from the cached prefix, discoveries appended at the tail so the cache survives; up to 10,000 deferred tools); OpenAI's `tool_search` with namespaces (gpt-5.4 and later; Azure ships the same). Claude Code defers MCP tools by default once their descriptions pass 10% of the context window (`auto:N`, `alwaysLoad` per server). Measured degradation (§3): 8 to 19 points lost when about three similar tools are added; 7.59% to 85.58% lost from about 49 to 741 tools; Anthropic's own 79.5% to 88.1% on Opus 4.5 with search on. Token cost: at 35 tools and 800 tokens per schema, about 28k tokens per call, 14% of a 200k window; caching removes most of the money, not the window share or the selection loss (§3).

Three manifest shapes (§4): A static list; B pinned core plus searchable rest, every schema still built into the image, `pinned` mapping to non-deferred and the rest to `defer_loading`; C named toolsets with phase gates, a phase switch being a `tool_addition` or `tool_removal` system message on Anthropic and a namespace on OpenAI. **Position:** B is the floor for a 30-to-40-tool agent; C composes on top when a workload shows edit-phase tools misfiring during planning. One evidence point for the egress design: Claude Code disables `tool_reference` behind a third-party gateway (2.1.70), so an egress proxy must be transparent at the wire level or the harness loses levers it never asked the proxy to touch.

### The model port (question 2), corrected

The options table rows B and C above were corrected on 2026-09-27. The intersection is now measurable (tools and port §8): Anthropic-only levers today are the memory tool, context editing, `input_examples`, `eager_input_streaming`, programmatic tool calling, task budgets, the advisor, mid-conversation system and tool changes, client toolsets, citations, explicit cache breakpoints with the 1-hour TTL, on-demand compaction, `pause_turn`, `speed`, `inference_geo`; both vendors share, in different shapes, tool search, compaction (signed block versus encrypted item), reasoning (both as opaque items passed back unchanged), automatic or explicit caching, structured outputs, server tools, PDF and files; universal across Anthropic, OpenAI and the open-weights servers are system prompt, text and images, JSON Schema tools, tool calls and results, SSE streaming, max tokens, stop sequences, usage. Sampling parameters are no longer universal: GPT-6 and the Fable 5 family reject `temperature`.

So option A is smaller than assumed: the port is built on the primitives both vendors now share (opaque round-trip blocks, deferred tools with tail expansion, dated server-tool types, a normalised stop reason keeping the raw value) plus a **capability declaration per adapter**, for which LiteLLM's 43 `supports_*` keys and OpenRouter's `supported_parameters` are a ready vocabulary (§7). A manifest that asks for compaction against an adapter that lacks it fails the build, which is kagent's `warnings[]` from the other side. Recommendation criteria (§"Recommendation criteria"): A wins when the manifest names Anthropic-shaped levers and a fake adapter for deterministic tests matters; B when provider breadth on day one outweighs interface stability; C as an egress concern in passthrough mode for the first-party provider and translation only for open-weights servers. **Position:** A, with C's passthrough as the egress shape (G3), unchanged from the earlier proposal but now for measured reasons.
