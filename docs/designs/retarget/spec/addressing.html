Specification

Addressing: reaching one agent among a hundred

Two components that are always separate in what ships: a registry that lists and governs, and a gateway that routes by the address the caller supplies and enforces policy. No model in either. Search returns a handful; choosing happens over the handful.

Who may call whomNetworkPolicy at the network layer; the gateway's policy at the request layerYes, at the gateway, not in DNS
What agent X isNot in DNS; the card carries itNo; the Service only locates the card
Which agent can do YNot a discovery primitive anywhereNo; the search tier over cards

The trap. Service discovery equates healthy with "has ready endpoints". A claimed-loop agent scaled to zero has no endpoints and is fully available: its paused conversations are in the store and the next claim scales it up. Availability is the card's status plus the store, never the endpoint count. An A2A call to a zero-replica agent needs the gateway to buffer while it scales, which is one more reason in-platform delegation ships first. In the shared-pool shape the trap is moot: availability was never an endpoint count, and the A2A endpoint is served by the gateway on the agent's behalf.

Two cautions

  • Cards are authored in the manifest and signed, never generated from the prompt. A generated card leaked a system prompt into a discovery endpoint in one shipped project.
  • A card's description is text the caller's model reads. Registry write access is the build pipeline only; a card another team can edit is a prompt-injection path.

What is not built

A chat surface. An organisation-wide orchestrator agent. Capability routing by a model over the full catalogue. A registry API of aesir's own: the record is the card, and when A2A settles a registry API the registry exposes it.
