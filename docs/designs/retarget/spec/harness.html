Specification

The harness and the container

The harness is the executable inside the agent's image: the loop, context management, tools, hooks, skills, the MCP client and the store client. The container is its environment. Tool execution runs in a separate sandbox pod the harness calls, and no credential ever enters either.

What the harness owns

Candidate B: three objects

Ten products compared on 2026-09-27; kagent v1.0.0-alpha1 (2026-09-18) and Managed Agents' agent / environment / session converged on the same split, and it is the only shape with a place to report that a template asks for a lever the harness lacks. A harness upgrade rebuilds one image; a prompt edit is a template revision and rebuilds nothing.

Positions the research supports

QuestionPosition
Execution familyKeep the claimed loop: stateless replicas claim from Postgres. Move to a durable engine or actors only on a named signal (resume latency dominated by history load; a need for live per-conversation connections)
Where a paused conversation livesIn the store, never on a volume; a volume only for a sandbox working tree
Unit of the imageOne harness image by digest with per-agent bundles on top; image-per-agent only for native tooling the base lacks
Unit of computeThe session, not the agent; every surveyed platform provisions per session. The shape the evidence points at is a shared harness pool per trust tier, with a dedicated Deployment only for a bundle with native dependencies; kagent abandoned one Deployment per agent in its v1 alpha line this month. Version across a pauseRecord the image digest and template revision on the conversation at start; pinned by default, auto-upgrade as the manifest opt-in. Cheap only in the pool, where a retained version is a registry artefact loaded beside the new one; per-agent Deployments need one per (agent, version), drained by a zero-open count as Temporal's Worker Controller does
CredentialsInjected by the gateway after the request leaves the container (agentgateway backendAuth: static keys, SigV4, cloud identities). OAuth refresh tokens and GitHub App installation tokens are handled by no gateway anywhere: a vending step holds the long-lived secret and writes the short-lived token where the gateway reads keys. Per-agent identity as a ServiceAccount token requested per claimed row; SPIRE later
Health and drainLiveness probes the loop's heartbeat; no readiness probe for a poller; on SIGTERM stop claiming, cancel the tool call, write its error, release the claim
Scale to zeroKEDA Postgres scaler on a count of claimable rows; measure wake latency before choosing between a long-running replica and a per-session worker
PackingSmall CPU request, honest memory, Burstable, MostAllocated bin packing. Measured 2026-09-27: a Node 22 hello-world container idles at 16 to 23 MiB; with HTTP and Postgres clients loaded, 58 MiB on the researcher's machine. The earlier 150 to 300 MB figure was an overestimate
Transcript storageOne row per message with JSONB payloads; large tool results to object storage; compaction bounds the live window (about 0.7 MB at 200K tokens). Never one document per conversation rewritten on append, which is what exists today
Tool exposureA pinned core of three to five tools, the rest deferred and searched; toolsets with phase gates only when a workload shows edit-phase tools misfiring during planning
Model portAn own port on the shared primitives with a capability declaration per adapter; the Vercel AI SDK's coverage is near complete but it ships a major every six to eight months; a translation proxy keeps the levers only on passthrough, so it is an egress shape, not the port
