# Connector tiers and OAuth brokering: what makes an integration "free"

Date: 2026-09-27. Research brief for the retarget conversation (no issue yet). Extends `../04-events.md` (the three-part split and "first-party integrations use the public extension API") and `2026-09-21-harness-container-gaps.md` §3 (cited as *gaps §3*: egress substitution, gateway-held credentials). The sibling brief on inbound webhooks owns signature verification and fan-out; this one covers credentials, OAuth, provider identity, and tiering. Written from pages fetched this session. `[V]` means verified from a fetched page listed in Sources. `[S]` means taken from a search-result summary of a page that could not be fetched. `[I]` means inferred. No repository code was read.

**Summary.** "Free" decomposes into nine items, and only three of them can be owned by anyone other than the party who registered the app with the provider: the client code, the inbound adapter, and rate-limit handling. Everything else follows the app registration, and providers pin that to one owner: a GitHub App has one owner account, a Slack app belongs to the workspace that created it and must be installed per workspace, a Linear OAuth app gets a distinct app user per workspace. Every managed-auth broker surveyed that ships a vendor-owned OAuth app calls it a development convenience and pushes production users to register their own, because a shared app shares rate limits, brands the consent screen with the vendor, has fixed scopes, and can be revoked by the provider. Agent platforms tier connectors on three levers, label, gate, and default-off, and none of them forbids the bottom tier. The MCP authorization spec (2026-07-28) dissolves the provider-app problem only where the provider itself runs a remote MCP server; where it does not, someone still registers an OAuth client with the provider and holds a refresh token, and the spec says where that token must not go (through the MCP server to the upstream API) rather than where it should live. Anthropic's Managed Agents makes the customer register the client and run the flow, then holds and refreshes the tokens and injects them when the connector opens the server; that is the closest shipped precedent for a container that never holds a credential. For a self-hosted platform the "vendor app" is the operator's app, so a platform-native tier is free for the builder but costs the operator one registration per provider per installation. The GitHub App Manifest flow and Slack's `apps.manifest.create` turn that registration into a guided form.

## 1. Decomposing "free"

**Conclusion.** The item that decides everything is the provider-side app registration. Whoever owns it owns the redirect URI, the webhook secret, the bot identity, the app-review relationship, and the rate-limit pool. The platform can own the flow UI, the callback, token storage, refresh, and egress injection regardless of who owns the app, because those are functions of the callback host, not of the registrant. Installation into a tenant's workspace is always a tenant-admin action that the platform can only initiate.

| Item | Who can own it | Why (provider constraint) | Precedent |
| --- | --- | --- | --- |
| Registered OAuth client or app (client id, secret, scopes) | Platform vendor, operator, or builder, but exactly one of them per app | GitHub: "You can register a GitHub App under your personal account or under any organization you own" [V]; Slack: the app is created in one workspace and "Activate Public Distribution" is needed before others can install [V]; Linear: created at the OAuth2 Application settings page, "highly recommended" to create a dedicated workspace to own it because "each admin user will have access" [V] | Nango shared apps "may be revoked by the provider at any time" and "have fixed scopes" [V]; Arcade's built-ins "share any rate limits from those providers with other Arcade customers" [V] |

| Rate-limit handling | Whoever owns the app | GitHub App limits "scale with the number of repositories and number of organization users"; OAuth App tokens get the "user's rate limit of 5,000 requests per hour" [V]; a shared broker app pools limits across customers [V, Arcade] | Arcade: "your auth provider will take precedence over the arcade-provided auth provider" [V] |
| App review or marketplace listing | The app owner, and usually only if it owns the service | Copilot: a verified publisher "Owns the underlying service"; an independent publisher may certify without owning it [V]; GitHub Marketplace paid plans need "an organization that is a verified publisher" and "a minimum of 100 installations" [V]; Slack Marketplace: "installed on 10 or more active workspaces" [V]; Linear: "built by formal companies", "do not accept scripts, low-effort/vibe coded or apps built by hobbyists" [V] | Claude directory: "Anyone on a paid Claude plan can submit"; listed "as a Community connector" by default [V] |

What the platform must own for "free" to be true, read off the table: the registered app for that provider (or a guided flow that creates one per tenant), the callback URL and flow UI, the vault with refresh and revocation, the egress injection so the container never holds the value, the webhook registration under the app, and the client code and adapter. What a builder must bring for a provider the platform does not support: its own registered client (client id, secret, scopes) pointed at the platform's redirect URI, or a static credential; its client code; its adapter; and, if the provider needs an app review, the relationship with the provider. The tenant admin still performs the install in both cases.

Two provider mechanisms make registration scriptable, which matters for §6 and §7. GitHub's App Manifest flow: "A GitHub App manifest is a way to share a preconfigured GitHub App registration with other users"; the platform redirects the user to GitHub with the manifest, the user approves, and the conversion endpoint returns `id`, `slug`, `client_id`, `client_secret`, `webhook_secret`, and `pem` [V]. The manifest carries `hook_attributes.url`, `redirect_url`, up to 10 `callback_urls`, `public`, `default_permissions`, `default_events` [V]. Slack manifests are "reusable configurations" in JSON or YAML; `apps.manifest.create` creates apps from them, using an app configuration token that is "unique to a user and a workspace, but not an app" and expires after 12 hours [V]. Linear has no equivalent; the app is created in the settings UI [V].

Google is the counter-example on review: apps requesting "sensitive or restricted" scopes "must complete Google's OAuth app verification", which needs a homepage on "a verified domain you own", a privacy policy on that domain, a demo video of "the complete OAuth Consent Screen", and for restricted scopes "an annual security assessment from a Google empanelled group of security assessors" [V]. A provider like that makes a shared platform app the only practical route for small builders, which is the opposite pressure from GitHub and Slack.

## 2. Managed-auth brokers for agents

**Conclusion.** Two families. Outbound token brokers hold provider tokens for your users and either hand them to your code or proxy the call. Inbound authorization servers make your own product an OAuth issuer so MCP clients can sign in to it. Only WorkOS does both, as separate products. Every outbound broker with a vendor app frames it as "get started" and recommends your own for production; three (Nango, Paragon, Composio) say so in as many words. Klavis is the exception where the vendor app is the product and white-labelling is the upgrade.

A broker that exposes MCP moves the provider-app question into its own authorization server, which is the §5 dissolution with the broker as the "provider".

Three observations for the design. First, "does the builder's code see the token" splits the brokers: Arcade (`context.authorization.token`), Auth0, and WorkOS Pipes hand it over; Nango, Composio (`proxyExecute`), and Pipedream (proxy) offer a mode where they call the API for you and the token stays with the broker. Second, a per-user connection keyed by the customer's own user id (`external_user_id`, `user_id`, `connection id`) is universal, and Managed Agents copies it as vault `metadata.external_user_id` (*gaps §3*). Third, none of these brokers registers the provider app for you in production; the "free" tier is a shared app with stated risks.

## 5. The MCP authorization spec and whether it dissolves the problem

**Conclusion.** The spec version is 2026-07-28 [V]. It settles the client side: the MCP client is the OAuth client, Client ID Metadata Documents are the SHOULD, Dynamic Client Registration is "deprecated and retained for backwards compatibility", pre-registration must remain an option, and resource indicators are mandatory. It dissolves the provider-app problem only when the provider runs the remote MCP server, because then the provider's own authorization server owns the app and the harness registers itself as a client. It does not dissolve it for a builder's own MCP server that fronts GitHub or Slack: that server is an OAuth client to the provider, must hold a separate upstream token, and inherits every item in §1.

What the spec fixes [V]:

- Roles: "A protected *MCP server* acts as an OAuth 2.1 resource server"; "An *MCP client* acts as an OAuth 2.1 client"; the authorization server "may be hosted with the resource server or a separate entity".
- Registration priority: pre-registered credentials first, CIMD when `client_id_metadata_document_supported` is advertised, DCR "as a fallback", then "Prompt the user to enter the client information". Clients "SHOULD support an option for static client credentials", including "Present a UI to users that allows them to enter these details".
- Tokens: `resource` "MUST be included in both authorization requests and token requests"; "MCP servers MUST NOT accept or transit any other tokens"; "The MCP server MUST NOT pass through the token it received from the MCP client"; "Clients and servers MUST implement secure token storage".
- Confused deputy: "MCP proxy servers using static client IDs MUST obtain user consent for each dynamically registered client before forwarding to third-party authorization servers". This binds a platform that fronts a provider with one client id.
- Extensions repository: "Enterprise-Managed Authorization" is Stable and "Client Credentials" is Draft. Claude's docs describe the former as connecting enterprise users "through their organization's SSO without a consent screen".

Where the token lives, and the "container never holds a credential" rule. The spec places the access and refresh tokens in the MCP client and says nothing about which process that is. Three shipped placements:

| Placement | Who holds the token | Container sees it | Precedent |
| --- | --- | --- | --- |
| MCP client inside the agent process | The process; keychain or credentials file | Yes | Claude Code: "stored securely in your system keychain (macOS) or a credentials file"; refresh on `401`, retry once; `--client-id --client-secret --callback-port` for pre-registered servers; CIMD "discovers these automatically" [V] |
| MCP client at the platform, token injected when the connection opens | The platform's vault | No | Managed Agents: credential "keyed by an `mcp_server_url`. When the agent connects to a server at that URL at session runtime, the token is injected automatically"; "First matching vault wins" [V] |
| Builder's MCP server as OAuth client to the upstream | The MCP server's store | No, but the builder's server does | Cloudflare: upstream token "in the encrypted props so the MCP client never sees it" [V] |

What Claude does today for remote MCP OAuth [V]:

- Claude Code: DCR by default, CIMD "discovers these automatically", pre-registered credentials via `--client-id --client-secret --callback-port`, a random loopback port unless pinned, tokens and the client secret in the keychain or a credentials file, refresh on `401` with one retry, `claude mcp login` and `logout`, and `--header "Authorization: Bearer ..."` for static tokens. Its own CIMD is hosted at `https://claude.ai/oauth/claude-code-client-metadata`.
- Claude apps (web, Desktop, mobile, Cowork): one fixed redirect URI, `https://claude.ai/api/mcp/auth_callback`; CIMD only when the server advertises `client_id_metadata_document_supported` and `none` in `token_endpoint_auth_methods_supported`, otherwise DCR; Anthropic-held client credentials for directory listings; customer-entered client id and secret for custom connectors; `static_headers` in beta; a `401` is required to start sign-in; refresh "proactively up to five minutes before the stored expiry".
- Managed Agents and the Messages API MCP connector: no flow at all; the caller supplies the tokens, Anthropic refreshes (vaults) or does not (connector).

The second placement is the only one compatible with the rule, and it is the *gaps §3* gateway pattern applied to MCP: the harness's MCP client terminates at a platform component that holds the token, or the platform runs the client and the container speaks an unauthenticated internal transport. Either way the platform still needs a vault, a callback, and refresh, which is exactly the list Managed Agents implements. What the spec removes is the provider-side registration, and only for providers that ship a remote MCP server; the vault docs' own examples are `https://mcp.slack.com/mcp` and `https://mcp.linear.app/mcp` [V]. Claude Code shows the cost of the first placement in a container: the token is on the disk the agent can read.

## 6. Bring-your-own provider app

**Conclusion.** Every broker makes BYO a form: client id, client secret, scopes, and a redirect URI the platform prints. Two make adding a *new provider* config rather than code (Nango's provider definitions, Arcade's generic OAuth 2.0 provider); Composio makes a new provider code-only with no OAuth; Copilot and Zapier are forms for the auth and code for the API. The redirect URI is always under the platform's domain, the secret is always write-only in the platform's store, and the client is per platform by default with per-tenant as an explicit option.

| Platform or broker | Form or code | Redirect URI | Where the secret lives | Per tenant or per platform |
| --- | --- | --- | --- | --- |
| Nango [V] | Form per integration; new provider by contributing a definition | `https://api.nango.dev/oauth/callback` | Nango, per environment | Per platform (one integration per environment) |

| Arcade [V] | Form (Custom Provider) or `engine.yaml` with `HOOLI_CLIENT_ID` env vars when self-hosted | Generated: "This must be set as the redirect URL in the external service's configuration" | Arcade Engine | Per platform; tools bind by provider `id` |
| Pipedream Connect [V] | UI or API; `oauthAppId` on connect | "a unique `redirect_uri`" per custom client | Pipedream; "The client secret is write-only" | Per client; per tenant possible by creating one per customer [I] |

Provider-side constraints on BYO [V]:

- GitHub Apps: the private key is "downloaded to your computer" once and "GitHub only stores the public portion"; "Private keys do not expire"; up to 25 keys, "Consider storing the key in a key vault ... and making it sign-only". A webhook URL is optional ("deselect **Active**"). The manifest flow lets a platform create a tenant-owned app and receive `pem`, `webhook_secret`, `client_id`, `client_secret` in one call, within one hour of the redirect. Installation scope is "Only on this account" or "Any account".
- Slack: HTTPS redirect URLs; distribution must be activated for other workspaces; a manifest plus `apps.manifest.create` and a 12-hour configuration token creates the app programmatically; request URLs for events and interactivity are part of the manifest.
- Linear: client id and secret from the settings page, "Rotate secret" available; `actor=app` for agents; tokens "valid for 24 hours", refresh tokens for all apps since 2026-04-01; webhooks and agent session events are enabled on the app.
- Google: brand verification for sensitive scopes and an annual third-party assessment for restricted scopes, as §1 states.

Per-tenant versus per-platform. A per-platform app shares one rate-limit pool and one consent brand across tenants and needs one registration; a per-tenant app isolates limits and identity and needs a registration per tenant, which the GitHub and Slack manifest flows reduce to a redirect and an approval click. Claude's advice to "Scope what each user can reach with your service's own per-user permissions rather than with a per-tenant OAuth app" [V] is the per-platform position; Arcade's rate-limit warning [V] is the case for per-tenant.

## 7. A tier model for the operator to argue with

**Conclusion.** Three tiers, with the same runtime underneath (the Claude and Docker precedent) and the platform owning the vault, callback, refresh, and egress injection at every tier (the Managed Agents precedent). The tiers differ in who registers the provider app, who wrote and reviewed the client code and adapter, and whether the builder declares or builds. In a self-hosted platform the "vendor" is the operator, so the top tier is free for the builder and costs the operator one registration per provider per installation.

| | Tier 0: bring your own | Tier 1: reviewed | Tier 2: platform-native |
| --- | --- | --- | --- |
| Platform provides | Vault (write-only secrets), callback URL under its domain, authorization flow UI, refresh, egress substitution or gateway injection, ingress URL, delivery persistence | Tier 0 plus review, listing, signed bundle, and optionally a platform-held client for the builder's app | Tier 1 plus the provider app registration, the bot identity, webhook registration, client code, adapter, rate-limit handling; the builder writes `uses: <provider>` and a scope list in the manifest |
| Builder provides | Client code, adapter, and either a static credential or its own OAuth client (client id, secret, scopes) registered with the redirect URI the platform prints | The same, plus tool annotations, tests, a test account, a privacy and support link, and evidence it owns or may use the API | Nothing provider-side; the tenant admin performs the install |
| Builder can | Reach any provider, including ones nobody else supports; run the adapter in its own container if it wants | Be discovered and enabled by tenant admins without a warning | Ship an agent against GitHub, Slack, or Linear with zero provider-side work |
| Builder cannot | Skip the warning label; use a platform-held client; appear in the catalogue | Change tools without re-review of annotations | Choose scopes outside the platform app's set (Nango's "fixed scopes" cost) |
| Does the builder's code see a token | Not if it calls through egress substitution with a placeholder; yes if the provider needs signing or an exchange (*gaps §3* limit) | Same as Tier 0 | No; the platform's client code runs in the platform's trust zone, or in the container with placeholders |
| Promotion | Review of tools and scopes, tests, ownership or permission for the API, a maintenance commitment | Adoption and the operator's decision to own the app; the platform team rebuilds nothing, it re-homes the registration | n/a |
| Precedent | Claude Custom and `custom_connection`; Zapier private; Copilot custom connector; Home Assistant custom with its logged warning; Docker self-provided image | Claude Verified; Copilot independent publisher; Terraform Partner; Grafana Community signing; Docker-built image | Copilot Standard connectors; Claude Anthropic-built; Composio managed toolkits (with the shared-app caveats) |

Recommendation criteria, not a decision:

1. The `04-events.md` principle holds if Tier 2 is a Tier 1 bundle whose provider app happens to be operator-registered. Nothing in Tier 2 should need a private platform path; Claude's "same infrastructure" and Docker's "same catalogue, different signature" show the shape.
2. Make the operator's registration a guided flow, not a runbook: GitHub's manifest conversion and Slack's `apps.manifest.create` return every secret the vault needs in one response. Linear stays manual. Count the operator's cost honestly: one app per provider per installation, plus renewal of any secret the provider expires, which Copilot's "one month before your client ID and client secret expire" rule shows is an ongoing duty.
3. Decide per provider whether the Tier 2 app is per platform or per tenant. GitHub App limits scale with installation size, so per platform is fine; a Slack app is per workspace by construction; Google's verification cost argues for per platform.
4. Keep the Tier 0 label honest and the gate with the tenant admin, as Slack and Claude do; do not make Tier 0 impossible, or builders route around the platform with static tokens in images.
5. If a Tier 0 builder brings a remote MCP server, the platform is the MCP client and needs pre-registration, CIMD, and DCR in that order, plus a platform-side client store. The container must not be the MCP client if the credential rule stands.

Assumptions this rests on: (a) the egress-substitution or gateway mechanism from *gaps §3* exists, otherwise Tier 0 code always sees tokens; (b) provider installation is a tenant-admin act the platform cannot perform, true for all three first-workload providers [V]; (c) the platform hosts the callback, so the redirect URI is stable across builders; (d) the operator, not a vendor, registers the Tier 2 apps, because the platform is self-hosted; (e) a shared broker app is not a route for GitHub or Slack in production, per Nango's own warning [V], but Klavis and Composio ship it, so this is a judgement, not a fact.
