# Support services and security pass inputs: retention, cost, redaction, injection, sandbox, approvals

Date: 2026-09-27. Research brief for the retarget conversation (no issue yet). Extends `2026-09-16-scaling-containerised-agents.md` §4 (sandboxes) and §5 (observability), cited as *scaling §n*, and answers gap rows G6, G20, G22 and G25 of `02-harness.md`. Written from pages fetched this session; no repository code was read. `[V n]` means verified from source n in the list at the end. `[S n]` means taken from a search summary or a secondary page because the primary could not be fetched. `[I]` means inferred by me. Two sections (§5, §6) were researched by subagents that returned verbatim quotes with URLs; I spot-checked the load-bearing quotes against the primary pages and mark them `[V]` on that basis.

**Summary.** Every vendor that keeps a transcript keeps it until someone deletes it; only compute and local caches expire on a timer. Managed Agents transcripts "persist until you delete them", Foundry deletes a *session* after 30 idle days but keeps the *conversation*, AgentCore keeps memory events for a configured 3 to 365 days, OpenAI's stateful endpoints are excluded from zero data retention, and Claude Code sweeps local transcripts after 30 days by default, a default that has cost users work. Regulators found in February 2026 that controllers confuse masking with erasure and have no procedure for back-ups; a June 2026 paper shows soft-deleted embeddings are reconstructible. For cost, the OpenTelemetry GenAI conventions are still "Development" with no tagged release; metrics carry `gen_ai.agent.name` and nothing about the conversation or user, so per-session cost must come from spans or from the platform's own usage events. Managed Agents is the only surveyed system that attributes a delegated thread's spend to the caller: threads carry `parent_thread_id` and roll up to one session `list_cost`. Redaction in every trace backend is client-side and irreversible; the one server-side shape that a model can still resume from is a typed placeholder block, which Managed Agents (`type: "redacted"`), Anthropic thinking (`signature`) and OpenAI (`encrypted_content`) all use in different forms. On security, the MCP specification now says clients "MUST consider tool annotations to be untrusted"; tool-description poisoning, rug pulls and cross-server shadowing are demonstrated, and the 2025 to 2026 CVE record is dominated by command injection through MCP configuration. A2A cards can carry JWS signatures but verification is only a SHOULD, and a generated card has leaked a system prompt in the field. Sandboxes split into three credential postures: plaintext in the sandbox (E2B, Modal, Codex), placeholder swapped at an egress proxy (Managed Agents cloud, Daytona, Claude Code's mask mode), and a vended identity (Foundry). Shipped approval gates converge on the same list of gated actions; only Managed Agents records the decision as a typed event on the transcript, and the default is drifting toward classifier approval.

## Part 1: support services

### 1. Retention and deletion

**Conclusion.** The precedents agree on one shape: the transcript is a stateful resource with explicit delete and an archive state that blocks writes; compute and its filesystem expire on an idle timer; only local caches and trace stores use a TTL. No surveyed vendor deletes a transcript on a timer without the customer asking. The one that does (Claude Code's local cache) drew two bug reports about silent data loss [V 15][V 16]. Policy is declared at the platform (vendor defaults), the resource (memory store `eventExpiryDuration`, Langfuse project retention) or the tenant (Anthropic workspace-level 30-day retention toggle); none of the surveyed systems declares retention in the agent definition [I].

**What erasure means when a transcript is also an embedding or a summary.** The EDPB's coordinated enforcement report on Article 17, adopted 10 February 2026 across 32 authorities and 764 controllers, names two structural failures that apply directly to an agent store. Controllers "only apply basic pseudonymisation or partial masking, although such a process would not fulfil the requirements of the GDPR regarding deletion" [V 34, §4.2.7]. On back-ups, "Many controllers were found not to have specific procedures", and the recommendation is to "Verify that erasure has been carried out and be able to demonstrate such erasure" [V 34, §4.2.6]. The Ghost Vectors paper (arXiv 2606.18497, submitted 2026-06-16) shows why the embedding store is a back-up in disguise: three HNSW implementations "only mark the record as deleted, leaving the embedding on disk physically unchanged", and Vec2Text inversion recovers the text; the proposed fix is per-epoch encryption keys discarded on deletion, with a signed proof of the deletion event [V 35]. The report does not mention embeddings or language models by name [V 34]; the inference that a compaction summary is a derived copy of the deleted content, and needs the same treatment, is mine [I]. Vendor mechanics for "delete this user's data from memory" are per-record: AgentCore `DeleteEvent` and `DeleteMemoryRecord` [V 22]; Anthropic redacts a memory *version* and keeps the row with its actor attribution, so the audit trail survives the content [V 5]; Langfuse deletes by trace id and warns that datasets are not covered [V 28].

**Proposal from the precedents.** A transcript row carries one of four states. *Active*: readable, writable, resumable. *Archived*: readable, resumable only by an explicit un-archive, no new events (the Managed Agents archive semantics [V 2]). *Deletion pending*: unreadable by agents and the dashboard, scheduled for purge, with the request recorded as an event so the EDPB's "demonstrate such erasure" test can be met [V 34]. *Purged*: the row keeps only its id, the actor who requested deletion and the timestamp (the Anthropic redacted-version shape [V 5]). Derived artefacts (summaries, embeddings, sandbox files, trace-backend copies) are enumerated on the row so the purge job can reach them; the Langfuse and Ghost Vectors findings are what happens when they are not [V 28][V 35]. Policy lives in three places, in precedence order: tenant (a retention ceiling and a legal-hold flag), agent manifest (a default TTL for sessions this agent starts, which no surveyed vendor has, so this is a gap the design can fill [I]), and platform (the floor, such as "compute idle 15 min" and "trace backend 14 days"). Deletion is explicit or by TTL, never silent on a default: the two Claude Code issues are the failure pattern [V 15][V 16].

### 2. Cost attribution

**Conclusion.** The conventions cannot carry the attribution the acceptance test needs. Spans can carry agent, version and conversation ids, but only as "Conditionally Required", only at "Development" stability, and no metric carries any of them. Every trace backend attributes cost to a trace, a session and a user by attributes the *client* sets; none attributes a delegated job to its caller unless the client threads a parent id. Managed Agents does thread it, and that is the shape to copy: usage is a domain event per turn, thread cost rolls up to the session that spawned it, and the dashboard reads the event log rather than the trace backend.

**The OpenTelemetry GenAI conventions today.** They live in their own repository, `open-telemetry/semantic-conventions-genai`, which has "no releases" as of this session [V 39]. The README, the metrics document and the agent-spans document each carry "Status: Development" [V 36][V 37][V 38]. Agent spans define `create_agent`, `invoke_agent`, `invoke_workflow`, `plan` and `execute_tool`; `gen_ai.agent.id`, `gen_ai.agent.name`, `gen_ai.agent.version` and `gen_ai.conversation.id` are all "Conditionally Required" and all "Development" [V 38]. No end-user attribute appears in either document [V 37][V 38]. The metrics document lists `gen_ai.client.operation.duration`, time-to-first-chunk, server-side latencies, `gen_ai.invoke_agent.duration`, `gen_ai.invoke_agent.inference_calls`, `gen_ai.invoke_agent.tool_calls` and `gen_ai.execute_tool.duration`; `gen_ai.agent.name` is the only agent attribute on any of them, and `gen_ai.agent.id`, `gen_ai.conversation.id` and user ids appear on none [V 37]. The README links a separate "inference token metrics" document [V 36]; I did not fetch it, so whether the token-usage metric carries agent attributes is unverified [I], and the G6 finding that it carries none stands as recorded in the 2026-09-21 research.

**Attributing a delegated job to its caller.** Managed Agents runs each delegated agent as a session thread; the thread list carries `parent_thread_id`, `null` for the primary thread [V 6]; thread usage is priced per thread and "exclude[s] the session's running-time cost, so they don't sum exactly to the session's `list_cost`"; the session figure is the one the budget is enforced against, and a multiagent session "has a single budget shared across all of its threads" [V 3][V 6]. Advisor consultations "appear in the advisor thread's usage and in the session's usage totals" [V 6]. That is caller attribution by construction: the session that delegated pays. Helicone's `Session-Path` gives the same hierarchy for a proxy-based setup [V 45]. Langfuse and Phoenix attribute by whatever ids the client stamps; a delegated agent that runs as its own trace is invisible to the caller's session unless the caller's `sessionId` or a parent trace id is propagated, and the Metrics API cannot group by `sessionId` in any case [V 31][I]. None of Langfuse, Phoenix, Helicone or Portkey distinguishes "who asked" from "who ran" as a first-class field [I].

**What follows for the design.** Keep the G6 position: usage is a domain event per turn in the conversation store, in the `session.usage` shape, carrying tokens, list cost, active seconds and the ids the conventions lack (conversation, agent, agent version, tenant, originating human, and the parent conversation when the turn was delegated) [I]. Spans carry `gen_ai.agent.id`, `gen_ai.agent.version` and `gen_ai.conversation.id` so the trace backend can join, and `session.id` and `user.id` as OpenInference attributes if Phoenix is the backend [V 38][V 42]. The dashboard reads cost from the event log and reads traces from the backend by id; the Langfuse Metrics API's inability to group by session and its Hobby-tier 100 requests per day make it the wrong source for a live per-conversation view [V 29][V 31].

### 3. Redaction in transcript stores

**Conclusion.** Every trace backend masks on the client before export and cannot recover the original; that is the right property for a log and the wrong one for a transcript the model must resume from. The precedents for a resumable redaction are typed placeholder blocks: an opaque token whose plaintext is recoverable only by a party with the key, or a marker whose plaintext is recoverable by nobody but whose position and provenance survive. Who can see the unredacted form is, in every surveyed case, either nobody or the platform that produced it.

Anthropic's own guidance on logging is indirect: the retention page says message-content attributes are opt-in because they are "likely to contain PII" (*scaling §5*), and the prompt-leak page says to "Avoid unnecessary proprietary details" in prompts and to filter outputs by regex or a prompted model rather than to leak-proof the prompt [V 9]. Nothing in the Managed Agents reference documents a client-requested redaction of a transcript event; the only redaction primitive an operator can call is on memory versions [V 4][V 5].

**Proposal from the precedents.** Represent a redacted span of a transcript as a typed block, not as edited text: `{type: "redacted", ref, policy, sha256, redacted_at, redacted_by}`. `ref` points at a vault-scoped store that holds the original under the tenant's key, which is Presidio's `encrypt` operator applied at the store rather than the client [V 48]; `policy` names why (PII class, secret pattern, operator request); `sha256` lets a later reader prove what was there without reading it, the Anthropic memory-version shape [V 5]. The model sees the block rendered as a short placeholder sentence, which is how the Managed Agents redacted block and the omitted thinking block are resumed [V 4][V 8]. Trace export applies the same block, so the backend never holds the original and no Langfuse-style deletion of "other objects" is needed [V 28][V 32]. Access to `ref` is a separate permission from reading the transcript, held by the tenant's operator role and by no agent, which is the "agents do not have a redact capability" asymmetry in reverse [V 5]. Purge of the original under §1 turns the block into the irreversible Managed Agents memory form: `ref` nulled, hash and provenance kept [V 5].

## Part 2: security pass inputs

### 4. Prompt injection through descriptions

**Conclusion.** A tool description or an agent-card description is model-visible text authored by a party the operator does not control. The demonstrated attacks (April 2025 onwards) are all this: hidden instructions in a description, a description that changes after approval, and a description that redirects a *different* server's tool. The specification now names the trust rule but gives no mechanism; the shipped mitigations are approval-at-add, default ask for MCP tools, output size caps and server-side intent evaluation. Pinning by hash and showing a diff on change exist as recommendations and scanners, not as behaviour of the clients I could verify. A2A cards have a signature field and a SHOULD; kagent shows what an unsigned, generated card can leak.

**The MCP record.** Invariant Labs' notification of 1 April 2025 defined a Tool Poisoning Attack as "malicious instructions ... embedded within MCP tool descriptions that are invisible to users but visible to AI models", demonstrated on Cursor with a poisoned `add` tool that read `~/.cursor/mcp.json` and SSH keys behind a confirmation dialog that "showed only simplified tool names", named the rug pull ("a malicious server can change the tool description after the client has already approved it") and shadowing ("poison tool descriptions to exfiltrate data accessible through other trusted servers"), and recommended clear UI, pinning "using a hash or checksum" and cross-server boundaries [V 49]. The WhatsApp follow-up of 7 April 2025 used a sleeper "that only activates on the second launch of the MCP server, thereby circumventing the need to be re-approved" and exfiltrated chat history over WhatsApp itself [V 50]. The GitHub MCP finding of 26 May 2025 is the other class: a benign tool plus untrusted content, "not a flaw in the GitHub MCP server code itself", mitigated by "one repo per session" scoping [V 51].

The specification revision 2026-07-28 says: "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers"; "there **SHOULD** always be a human in the loop with the ability to deny tool invocations"; servers MUST "Sanitize tool outputs" and clients SHOULD "Show tool inputs to the user before calling the server" and "Log tool usage for audit purposes"; tool lists change through `notifications/tools/list_changed` and `tools/list` MUST NOT vary per connection [V 53]. The security best practices page covers confused deputy, token passthrough (MUST NOT accept tokens not issued to the server), SSRF (egress proxies such as Smokescreen for server-side clients), state-handle hijacking, local server compromise ("Show the exact command that will be executed, without truncation"), OAuth URL validation, mix-up attacks and scope minimisation; it has no section on description poisoning or rug pulls [V 54]. Claude Code's client behaviour on `list_changed` is to "automatically refresh the available capabilities from that server"; the page says nothing about surfacing a diff or re-prompting, and warns that in `claude -p`, SDK and cloud sessions project-scoped servers load "without asking" [V 12]. Managed Agents makes MCP toolsets default to `always_ask`, which "ensures that new tools added to an MCP server do not execute in your application without approval" [V 7]; that is a rug-pull mitigation by default policy rather than by hash [I].

The pattern across the record is that description poisoning is the demonstrated *class* and configuration-to-command injection is the *CVE volume* [I].

**A2A agent cards.** The card is "A self-describing manifest for an agent" with `description` on the card and "A detailed description of the skill" on each skill; `repeated AgentCardSignature signatures` carries `protected` ("The protected JWS header ... base64url-encoded JSON"), `signature` and an unprotected `header` [V 64]. Signing canonicalises with RFC 8785 JCS, uses RFC 7515 JWS, MUST include `alg`, MAY include `jku` for a JWKS, and "Clients verifying Agent Card signatures **SHOULD** verify at least one signature before trusting an Agent Card" [V 65]. The released version is 1.0.0 [V 63]. There is no MUST to verify and no statement that the description is model input; that the caller's model reads it is the design assumption of the registry in question and of every A2A client that routes by card [I]. kagent issue #2549 (2026-08-25, open, PR #2843 linked) reports that the pod's generated `/.well-known/agent-card.json` embedded "the entire system message" in the first skill's description while the controller's curated endpoint returned only approved metadata; the reporter's point is that "Anyone who can *list* the agent can read how it is instructed to behave, which is useful reconnaissance for prompt injection", and the workaround is to front agent endpoints with a gateway and serve the curated card only [V 66]. Anthropic's prompt-leak guidance is the same advice from the other side: do not put in the prompt what the task does not need [V 9]. Signed records outside A2A: AGNTCY's Agent Badge is "an enveloped VC, captured in the form of a JSON-LD object" over "an OASF definition or an A2A Agent Card schema", bound to an issuer and public key, with "different software versions and/or patched releases of an Agent" carrying different badges [V 67]; cosign signs OCI images by digest, stores signatures in the registry under the OCI 1.1 referrers model, and verifies with identity constraints [V 68].

### 5. Sandbox boundary precedents

**Conclusion.** In every surveyed product the LLM loop runs outside the thing that executes tools, and what crosses the boundary is a command or a file operation in one direction and stdout, exit code and files in the other. The products differ on three axes that matter for a gateway design: whether egress is default-deny, whether the working tree survives a pause, and whether a credential is ever inside the boundary. Three postures exist for credentials: plaintext in the environment (E2B, Modal; Codex filters names containing KEY, SECRET or TOKEN), a sentinel swapped at a proxy the sandbox cannot bypass (Managed Agents cloud vaults, Daytona, Claude Code `mask`), and a workload identity that fetches short-lived tokens (Foundry, per the 2026-09-21 research). The sentinel pattern only works for outbound HTTP the proxy can see; it fails for local signing and for a token the tool receives back. Extends *scaling §4*, which covered isolation and cost; this section covers the boundary contract.

**What the boundary means for a tool that needs a credential.** Three consequences follow. First, a sentinel scheme needs the proxy to terminate TLS and to know the destination host, so it covers "HTTP to an allow-listed API" and nothing else; Claude Code documents both requirements and the failure mode when TLS is not terminated ("the sentinel reaches the server unchanged and authentication fails") [V 13], and Managed Agents documents that exchanged tokens come back in the clear [V 75]. Second, an unrestricted-egress default plus plaintext credentials (E2B, Modal, Managed Agents' API default) makes any allowed host an exfiltration path, which Managed Agents states in its own docs [V 72]. Third, the split that *scaling §4* recommended, the loop outside and the sandbox as a callee, is what every product does, and it is what lets the credential live in the gateway rather than in the sandbox: the sandbox calls out through the proxy with a sentinel, the proxy injects, and the loop never hands a secret across the boundary [I]. For a credential a tool must hold (local git signing, a CLI that reads a token file), the choice is Daytona and Claude Code's answer (mask what you can, deny the rest) or Foundry's (vend a short-lived identity token into the sandbox and accept that it is inside) [I].

### 6. Approval gates in shipped products

**Conclusion.** Shipped products gate the same short list and differ mainly in *who* approves: a human at a prompt (Claude Code, Codex, Cursor, Devin), a client callback (Agent SDK), a typed event on the transcript that a webhook announces (Managed Agents), a repository control (GitHub), a per-tool toggle that is off by default (Copilot Studio), or a classifier model standing in for the human (Claude Code auto mode, Cursor Auto-review, Managed Agents `auto`). The two records worth copying are Managed Agents' `evaluated_permission` plus `evaluation` on every tool event, and GitHub's rule that the agent can never be the approver of its own work. The direction of travel is toward classifiers as the default, so a design that needs a human on a given action has to name that action explicitly.

### 7. A threat list for a registry-and-gateway design

Threats are those a registry of owner-published cards, a credential-holding egress gateway, a Postgres transcript store and a separate tool sandbox introduce or inherit. "Unmitigated in the field" means no surveyed product ships a control for it; the earlier research files are cited where they already hold the fact.
