# Egress gateway, per-agent identity, and locally derived tokens

Date: 2026-09-27. Research brief for the retarget conversation (no issue yet). Extends `2026-09-21-harness-container-gaps.md` §3 (cited as *gaps §3*) and the gap register in `02-harness.md` (rows G3, G7, G14, G15, G21). It answers only what those leave open: what agentgateway is and does, which credential kinds a gateway can keep out of the container, how a container proves which agent it is, what the fallbacks are, and who owns an egress allowlist. Written from pages fetched this session, documentation and repository reading only; nothing was installed or run. `[V]` means verified from a fetched primary page or source file listed in Sources. `[S]` means taken from a search summary or a page the tool could not fetch in full. `[I]` means inferred. Pages that failed are named at the top of Sources.

**Summary.** agentgateway is a Rust data plane with a Go controller, Apache 2.0, donated by Solo.io to the Linux Foundation on 2025-08-25 and under the Agentic AI Foundation since 2026-06. It ships v1.5.0 (2026-08-27) with a stable release roughly monthly and prereleases weekly. It fronts MCP (including several servers multiplexed into one), A2A, seven first-class LLM providers plus any OpenAI-compatible endpoint, and plain HTTP, and it installs standalone or on Kubernetes through its own Helm charts and the Gateway API without kgateway. Its `backendAuth` has nine kinds in code: passthrough, static key, AWS SigV4, GCP, Azure, GitHub Copilot, per-request signed JWT, RFC 8693 token exchange, and Cross App Access.

Two of the six credential kinds this brief asked about fall outside plain injection everywhere: an OAuth refresh token and a GitHub App installation token. No gateway surveyed mints a GitHub installation token; every shipped design that keeps the private key out of the container puts a vending step in front of the gateway (GitHub Actions, the community Vault plugin, AgentCore's vault). SigV4 is the exception that gateways do handle: agentgateway, Envoy's `aws_request_signing` filter, Secretless, and Claude Code's sandbox proxy all sign or re-sign at egress.

For per-agent identity, Kubernetes bound service-account tokens are a JWT the gateway can validate today; SPIFFE is the standard the hosted platforms converge on (Google's Agent Identity is SPIFFE-based; agentgateway exposes `source.spiffeId` to CEL). A shared runtime that serves several agents has one standards-shaped option, a runtime-minted JWT with the agent as subject and the runtime as actor, which is what Transaction Tokens and the Substrate actor JWT already do. On allowlists, Managed Agents and Claude Code both run two lists and intersect them; the gateway's route table is the natural single owner once all egress is forced through it.

### `backendAuth` kinds

The docs list seven methods; the code enum `BackendAuthKind` has nine variants [V]. The table joins the two, with what each kind does at request time and what it cannot do.

| Code variant | Docs name | Secret the gateway holds | Call at request time | Cache | Cannot do |
| --- | --- | --- | --- | --- | --- |
| `Passthrough` | Passthrough | None; forwards the client's credential, or the validated JWT when client auth stripped it | None | None | Give the backend a gateway-held credential; the backend sees the agent's own token |
| `Key` | Static key | Inline, `{file: <path>}`, `key`, or `secretRef`; files reload on change since 1.5 | None | None | Rotate or refresh on its own |
| `Aws` | Cloud provider credentials | The gateway's IAM identity from the default chain, explicit keys, or `AssumeRole` with `external_id` | STS when assuming; SigV4 computed locally over a buffered body | Source credentials cached; assumed-role cache of 8192 entries, 60 s refresh buffer | Sign a request a later policy mutates; sign bodies over the buffer limit |
| `Gcp` | Cloud provider credentials | The gateway's workload identity; `accessToken` or `idToken` | Token fetch (`gcp::insert_token`) | Not read | Per-agent identity |
| `Azure` | Cloud provider credentials | `implicit`, `explicitConfig`, or `developerImplicit` (standalone only) | Token fetch (`azure::get_token`) | Not read | Per-agent identity |
| `Copilot` | Cloud provider credentials | The gateway's Copilot login | Header insertion | Not read | Run on Kubernetes ("standalone binary only") |
| `JwtSign` | Signed JWT | A PEM private key (`signingKey` file or `signingKeyRef` Secret) | None; signs locally | None, "every request is signed afresh" | Exchange the JWT for anything; set `iat`, `exp`, `nbf` |
| `OAuthTokenExchange` | OAuth token exchange | A client credential (`ClientSecretBasic`, `ClientSecretPost`, `PrivateKeyJwt`) | POST to the token endpoint as RFC 8693 or RFC 7523 `JwtBearer` | In-memory, 8192 entries | Run without a subject token (400); request a custom `requestedTokenType` |
| `CrossAppAccess` | Cross App Access | Client registrations at two authorisation servers | Two POSTs | Same cache | Replace a single-leg exchange ("use OAuth token exchange instead") |
| `credentials` list | Extra credentials | As `Key`, one per location | None | None | Replace a primary method; it is additive |

A separate `credentials` list injects extra values to further locations [V]. A policy "sets at most one" primary method, and "Backend authentication decides what credential the gateway sends. It does not decide who is allowed through" [V]. Sources for a static key: inline or `{file: <path>}` standalone, `key` or `secretRef` on Kubernetes; secret files reload on change since 1.5 [V].

The AWS kind signs "each request that the gateway forwards with AWS Signature Version 4" for "any AWS SigV4 signing name", using the `aws-sigv4` crate with a signed (buffered) payload, credentials from explicit keys, the default chain (IRSA or Pod Identity on EKS), or `AssumeRole` with `external_id`, cached with a 60-second refresh buffer; a policy that changes the request after signing breaks the signature [V code and docs].

`JwtSign` mints an RS256 (default) JWT per request with `iat` backdated 10 s, `exp` = now + `ttl` (default 300 s), static `iss`, `sub`, `aud`, and custom claims; "nothing is cached"; no exchange step exists in `jwt_sign.rs` [V]. `OAuthTokenExchange` posts the inbound token as `subject_token` (RFC 8693) or as `assertion` (RFC 7523 `JwtBearer`), with `ClientSecretBasic`, `ClientSecretPost` or `PrivateKeyJwt` client auth, `audiences`, `scopes`, `resources`, an optional actor token, and an in-memory cache of 8192 entries; a missing subject token fails with 400, so it "cannot function as a pure client-credentials grant" [V]. Entra OBO is `JwtBearer` plus `requested_token_use=on_behalf_of` in `additionalParams` [V]. A "Substrate" credential provider (gRPC lookup, actor-scoped, header injection) merged on 2026-09-14 and is not in 1.5.0 [V PR #3411].

SPIFFE appears in two places [V]: the gateway can source "its mTLS identity and trust bundle directly from the SPIFFE Workload API" (1.5 release notes) and a backend TLS policy can set `certificateSource: SPIFFE` with `verifySubjectAltNames`. Both concern the gateway's own identity toward backends, not the calling agent's identity.

## 2. Locally exchanged or derived tokens

**Conclusion.** Header substitution covers static keys and any token someone else keeps fresh. SigV4 is a solved case at the gateway because the signing input is the request itself. The two cases that break are the ones where the secret is used once to obtain a second secret: an OAuth refresh and a GitHub App exchange. No gateway surveyed performs either; the shipped answer everywhere is a vending step that holds the long-lived secret and hands the gateway or the agent only the short-lived result. Managed Agents says this outright: "perform the exchange yourself and store the resulting token in the vault instead" [V].

### The six kinds, one by one

(a) Static bearer or API key. Every component surveyed injects it. The design question is where the gateway reads the value: agentgateway from a Secret or a file that reloads, Envoy Gateway from a Secret's `credential` key, Envoy from SDS, Managed Agents from its vault with `injection_location` set to header or body [V]. The failure mode is the injector pattern, which puts the value inside the boundary: Vault Agent renders to `/vault/secrets`, and Foundry resolves `${{connections.<name>.credentials.<field>}}` to "a plain environment variable" at sandbox start [V].

(b) OAuth access token with refresh. The refresh token is the long-lived secret. Two shapes keep it out of the container. A vault that refreshes: Managed Agents `mcp_oauth` with a `refresh` block, emitting `vault_credential.refresh_failed` when the grant is gone; AgentCore's three-legged flow, where "agents never have direct access to long-term secrets or refresh tokens" [V]. Or a gateway exchange that starts from the caller's token rather than a stored refresh token: agentgateway RFC 8693 and Cross App Access, AgentCore on-behalf-of [V]. agentgateway stores no refresh tokens, and the Envoy credential injector's OAuth2 support is the client-credentials grant, which needs none [V]. When an upstream offers only refresh-token flows, the refresher is a separate process that writes the access token where the gateway reads keys [I].

(c) GitHub App installation token. An exchange no surveyed gateway performs; the paragraph beginning "The GitHub App flow" has the mechanics and the vending precedents.

(d) AWS SigV4. The one derived credential gateways do handle, because the signing input is the request in front of them; the paragraph beginning "SigV4 needs the secret access key" lists the four components that sign or re-sign.

(e) mTLS client certificate. A client certificate is a signing key, so the SigV4 logic applies: whoever terminates the outbound TLS must hold it. In every surveyed design that party is the gateway, with the certificate from a Secret or the SPIFFE Workload API (agentgateway), from SPIRE over SDS (Envoy), or by TLS origination (Istio) [V]. No surveyed gateway presents a per-agent client certificate upstream; the upstream sees the gateway, and the agent travels, if at all, in a header or an exchanged token [I].

(f) Short-lived token per workload identity. This is the kind the hosted platforms are built around: AgentCore's workload access token, Entra's blueprint-minted tokens, Google's certificate-bound access tokens [V]. agentgateway offers two paths. Its cloud kinds (`aws`, `gcp`, `azure`) use the gateway's own identity, so they are per-gateway. RFC 8693 exchange of the agent's inbound JWT is per-agent, because the authorisation server sees the agent as `subject_token` and can narrow the result by `audiences` and `scopes` [V]. Short of one static key per agent, that exchange is the only per-agent credential path in 1.5.0 [I].

### The vending step, when one is needed

Three shipped shapes exist. (1) The platform mints the token and pushes it into the container at start: GitHub Actions' `GITHUB_TOKEN`; AgentCore's workload access token "as payload headers" [V]. (2) The container asks a broker at run time with its workload identity and receives only the short-lived value: AgentCore `GetResourceOauth2Token`; Vault `/github/token` after Kubernetes auth; the Entra Auth SDK sidecar [V]. (3) A refresher writes the token where the gateway reads keys and the container never sees it: agentgateway `Key {file}` with reload; the Substrate credential provider does the same over gRPC [V]. Only shape 3 keeps the derived token out of the container as well as the long-lived secret; shapes 1 and 2 hand the container a one-hour token. CB4A calls shape 2 "Model B" and shape 3 "Model A" [V].

The GitHub App flow, from GitHub's page [V]: sign a JWT with the app's private key, `POST /app/installations/INSTALLATION_ID/access_tokens` with `Authorization: Bearer <JWT>`, receive a token that "will expire after 1 hour", optionally narrowed with `repositories`, `repository_ids` and `permissions`; a stateless `ghs_APPID_JWT` format rolls out from 2026-04-27. agentgateway's `JwtSign` produces exactly the first artefact and nothing consumes the second [V]; the agentgateway blog concedes GitHub tokens "can't" be minted by exchange, "You have to go get it once, and then hold onto it" [V]. GitHub Actions is the reference vending design: `GITHUB_TOKEN` "is a GitHub App installation access token", limited to the repository, refreshable for up to 24 hours on self-hosted runners [V]. The community Vault plugin does the same for any caller: it holds the private key and serves `/github/token` with `installation_id` or `org_name`, `repositories`, `permissions`, one-hour tokens; its last public demo was 2021, so maintenance is uncertain [V].

SigV4 needs the secret access key to derive the signing key (`HMAC("AWS4"+secret, date)` and onward) and covers the canonical request including body hash [V]. Four egress components re-sign or sign: agentgateway `aws` (§1), Envoy's `aws_request_signing` filter (SigV4 and SigV4A, per-route, credential chain including web identity and EKS Pod Identity) [V], Secretless's AWS connector, which reads the placeholder-signed request's date, region and service and re-signs with the broker's credentials, leaving unsigned requests unsigned [V code], and Claude Code's sandbox proxy, which "detects a SigV4 request by the access key's sentinel and re-signs it" from an `awsPairs` entry, with a `sigv4` setting for the three forms it cannot recompute [V]. AgentCore Gateway signs with its service role or, for Runtime targets, with "the caller's IAM credentials" through FAS [V].

## 3. Per-agent identity toward the gateway

**Conclusion.** Kubernetes already issues a per-pod JWT the gateway can validate with no extra component. SPIFFE is where the hosted platforms are heading. A shared runtime serving several agents has to mint something itself, and the only standards-shaped precedent for that is a JWT with the agent as `sub` and the runtime as `act`.

| Mechanism | What the container holds | How the gateway checks it | Source |
| --- | --- | --- | --- |
| Kubernetes bound service-account token | A projected JWT with `iss`, `sub`, `aud`, `exp`, `kubernetes.io/namespace`, `serviceaccount/name`, `pod-name`, `pod-uid`, `node-name`; default 3600 s, minimum 600 s; kubelet rotates at 80 % of TTL or 24 h; invalid once the pod is deleted | `TokenReview`, or OIDC discovery at `/.well-known/openid-configuration` and `/openid/v1/jwks` (`ServiceAccountIssuerDiscovery`). agentgateway's JWT policy with a remote JWKS fits if the API server's JWKS is reachable to the gateway [I]; claims arrive as `jwt.*` in CEL [V] | [V] |
| SPIFFE SVID | X.509 or JWT SVID from the Workload API socket, attested per pod | Frontend mTLS `AllowValidOnly`, then `source.spiffeId` or `source.subjectAltNames` in CEL [V]. Google's Agent Identity is "based on the SPIFFE standard", `spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH`, 24-hour certificates, access tokens "cryptographically bound to the agent's unique X.509 certificates" [V] | [V] |
| mTLS with a platform CA | A client certificate | Same CEL fields; Istio names the same thing `source.principals` as `<TRUST_DOMAIN>/ns/<NAMESPACE>/sa/<SERVICE_ACCOUNT>` [V] | [V] |

Entra: agent identities "don't have credentials of their own", the blueprint mints tokens, optionally through the "Auth SDK (sidecar)" container. Two vendor documents disagree on a word. Foundry's deploy page says the agent identity "is a service principal that your running container uses"; Entra's concepts page lists "Traditional service principal (not recommended for AI agents)" and defines agent identities as a distinct construct [V both]. Treat "service principal" in Foundry as loose wording until a spike checks the token.

### A shared runtime serving several agents

One pod that runs several agents has one workload identity and must say per request which agent is calling. Three shapes exist.

| Shape | What the runtime does | What the gateway checks | Weakness | Precedent |
| --- | --- | --- | --- | --- |
| (i) Runtime-minted JWT | Signs a short-lived JWT per request with `sub` = agent and `act` = runtime, audience = gateway | The runtime's key via JWKS; policies read `jwt.sub` and `jwt.act` [V CEL] | The runtime can name any agent; the gateway trusts the runtime's honesty, not an attestation of the agent [I] | RFC 8693 `act`; Transaction Tokens; Substrate actor JWT [V][S] |
| (ii) Trusted header from an identified peer | Sets `x-agent-id` on a connection the gateway identifies by mTLS or a bound token | `source.spiffeId` or `jwt.sub` identifies the runtime; `request.headers['x-agent-id']` names the agent [V CEL] | Same trust as (i) without a signature; any hop that can add headers can impersonate [I] | `ext_authz` header rewriting [V] |
| (iii) One ServiceAccount per agent | Calls the TokenRequest API for the agent's own account and uses that token for the agent's calls | The cluster's JWKS; `jwt.sub` is `system:serviceaccount:<ns>:<agent>` [V] | Needs RBAC on `serviceaccounts/token`; turns "which agent" into a Kubernetes object per agent; the runtime can still request any account it is allowed [I] | `kubectl create token` [V] |

RFC 8693 defines `act` for shape (i) and rules that "Prior actors identified by any nested `act` claims are informational only" [V]. Transaction Tokens (draft-ietf-oauth-transaction-tokens-11, 2026-07-30, OAuth WG, standards track) are "short-lived, signed JWTs" that "propagate user identity, workload identity, and authorization context throughout service call chains within trusted domains" and do not mention agents [V]. The agent profile (draft-araut-oauth-transaction-tokens-for-agents-02, 2026-05-22, individual, expires 2026-11-23) adds `agentic_ctx` with `current_actor` and `originator` [V]. Substrate's actor JWT is the shipped instance [S]. Whichever shape is chosen, the gateway cannot distinguish "agent A" from "the runtime claiming to be agent A"; per-agent identity in a shared runtime is per-runtime attestation plus a claim [I].

Standards status on 2026-09-27 [V unless marked]: RFC 8693 (2020) is the only RFC. Active WG drafts: `draft-ietf-oauth-transaction-tokens-11`; `draft-ietf-oauth-identity-assertion-authz-grant-04` (2026-05-21, the "Cross-App Access" pattern agentgateway implements); WIMSE architecture -08, workload identifier -03, workload credentials -02, proof token -02, mTLS -02, HTTP signatures -07, and `draft-ietf-wimse-aims-00` "AI Identity Management System" (2026-09-15, authors from Defakto, AWS, Zscaler, Ping, OpenAI, Okta), which replaced the individual `draft-klrc-aiagent-auth`. Expired or individual: `draft-oauth-ai-agents-on-behalf-of-user-02` (`requested_actor`, `actor_token`; expired 2026-02, never adopted); `draft-hartman-credential-broker-4-agents-00` (CB4A, SANS, 2026-03-29, expires 2026-09-30) with its Model A proxy gateway, Model B short-lived minting, Model C wrap-and-revoke.

## 4. Fallbacks and alternatives to agentgateway

Reading across the rows: only agentgateway and Kong understand all three traffic kinds; only agentgateway and LiteLLM sign SigV4 for arbitrary MCP targets; nobody handles the GitHub App exchange.

The Envoy-based fallback, composed [I]: Envoy Gateway for routing and static credential injection; Envoy's `aws_request_signing` filter added per route through Envoy Gateway's patch or extension policies for SigV4; `ext_authz` to a small vending service that returns the upstream header for the exchange cases; JWT validation of bound service-account tokens or SPIRE-issued mTLS for the caller. That covers the same credential kinds as agentgateway with three moving parts instead of one, and without MCP tool-level rules, LLM token accounting, or MCP multiplexing. LiteLLM is the pragmatic LLM-only fallback and already has an MCP gateway; it does not identify the calling agent beyond a virtual key, and its Python footprint is the reason agentgateway benchmarks against it [V vendor].

## 5. Allowlist ownership

**Conclusion.** Both hosted precedents with two lists intersect them, and both make the credential's list the narrower one. A gateway that all egress passes through can collapse the two into one table.

| System | Reachability list | Credential list | Rule when both exist |
| --- | --- | --- | --- |
| Managed Agents [V] | Environment `networking`: `unrestricted` (default) or `limited` with `allowed_hosts` (bare hosts, `*.example.com`), `allow_mcp_servers`, `allow_package_managers` | Credential `networking.allowed_hosts` ("limited" or "unrestricted") plus `injection_location` header or body | "`networking.allowed_hosts` on a vault credential controls which requests use the secret, not which requests are allowed ... Both levels must include the domain" |
| Claude Code sandbox [V] | `network.allowedDomains` plus `WebFetch(domain:...)` allow rules, merged across settings scopes; `deniedDomains` "Blocks specific domains even when a broader `allowedDomains` wildcard would otherwise permit them"; `strictAllowlist` and `allowManagedDomainsOnly` honoured only from user, managed, or CLI settings | `mask` entries with `injectHosts`; honoured only from user, managed, or CLI settings, never from a repository's `.claude/settings.json` | "each `injectHosts` destination must also be reachable through `network.allowedDomains`"; "When the same variable is listed with `deny` in any scope, `deny` takes precedence" |
| agentgateway [V][I] | The route and backend table; a request reaches only a configured backend unless dynamic forward proxy is on; CEL authorisation can also match `destination.hostname` (SNI) and `request.host` | `backendAuth` attached to a backend or route | Implicit: a credential is scoped to the backend it is attached to, so it cannot be injected toward a host that has no backend [I] |
| CB4A draft [V] | Policy Decision Point | Credential Delivery Point | Separated by design; Model A is "proxying the call and injecting the credential on the way out" |

Proposal from the precedents [I]. Put the single source of truth in the gateway's backend table: one backend per external host or MCP server, the credential attached to that backend, and per-agent scope as an authorisation rule keyed on the agent's identity (`jwt.sub` or `source.spiffeId`) against `backend.name`. The environment then needs one network rule, "egress only to the gateway", which is what Substrate does ("All network traffic goes through agentgateway") [S] and what Google's Agent Gateway does for end-user credentials ("decrypted at the gateway, ensuring that the agent can never access the raw credential") [V]. Keep two semantics from Claude Code: any deny wins over any allow, and a credential's host list may only narrow the reachability list, never widen it. Managed Agents' two-list design exists because the sandbox and the vault are separate products; a self-hosted design does not have to inherit that split.

## Where this leaves the gap register

| Row | What the register says (`02-harness.md`) | What this brief adds |
| --- | --- | --- |
| G3 | An egress gateway in the agentgateway shape, holding credentials and injecting by backend; SPIRE deferred | Confirmed for static keys, SigV4 and cloud identities. Not confirmed for OAuth refresh or GitHub App tokens: those need a vending step in front of the gateway (§2). agentgateway is one Deployment plus a Go controller; the Rust binary asset is 88 MB, RSS 22 to 29 MB in the vendor's load test (§1) |
| G7 | The gateway identifies the calling agent by its own credential; SPIRE later | Kubernetes bound tokens are a per-pod JWT the gateway validates today with no new component; `source.spiffeId` is already in CEL for the SPIRE step (§3). A shared runtime cannot give the gateway more than a runtime-attested claim (§3) |
| G14 | Where exchanged or derived tokens live | Outside the container and outside the gateway: a refresher or broker that holds the long-lived secret and writes the short-lived result where the gateway reads keys (§2, vending step shape 3). Managed Agents, GitHub Actions, Vault and AgentCore all draw the line there |
| G15 | Who owns the per-agent egress allowlist when a credential and an environment each carry one | Both shipped precedents intersect the two lists and make the credential's list the narrower one; a gateway that all egress passes through can hold a single table with credentials attached to backends and per-agent scope as authorisation rules (§5) |
| G21 | Binding a conversation to an end user for credential vending | AgentCore's `GetWorkloadAccessTokenForUserId` treats the id as "an opaque string" the platform "cannot verify"; the JWT variant is the recommended path. The same split applies to shape (i) in §3: a runtime-minted claim is a statement, not an attestation |

## What a hands-on spike would have to confirm

1. GitHub App: `jwtSign` produces a JWT GitHub accepts at `/app/installations/{id}/access_tokens`; a sidecar or CronJob that mints the installation token to a file, with `Key {file}` reloading on change, and the measured window between expiry and reload.
2. AWS: `aws` backendAuth against a non-Bedrock service (`execute-api` or `s3`) with IRSA and with `assumeRole` plus `externalId`; confirm the body buffer limit and that no later policy mutates the signed request.
3. Kubernetes tokens as the agent credential: JWT policy with the API server's `/openid/v1/jwks` as remote JWKS (anonymous discovery or a token for the gateway), `aud` set to the gateway, and `jwt.sub` appearing in CEL.
4. mTLS identity: frontend `AllowValidOnly` with a private CA, and `source.spiffeId` or `source.subjectAltNames` populated in an authorisation rule; the mTLS page is silent on this.
5. Virtual MCP with per-target `backendAuth` and tool-level `Deny` rules; whether denied tools are hidden from `tools/list` or only refused on `tools/call`.
6. A2A: a signed agent card through the gateway (issue #2701 says rewriting invalidates signatures) and `AgentgatewayBackend` type `a2a` against a v1.0 server.
7. RFC 8693 exchange with a self-hosted authorisation server (Keycloak) using the pod's bound token as subject token; measure the 8192-entry cache behaviour on expiry.
8. Footprint at idle and with a few dozen agents: RSS of the proxy and the controller; the only figures are vendor benchmarks under load.
9. Helm install with Gateway API 1.6.0 standard channel alone, without kgateway; the CRDs that actually land.
10. Kong: whether `ai-proxy` and the MCP features run on the free tier of a self-hosted Kong Gateway.
11. The Substrate credential provider (PR #3411): whether it is usable without Substrate, since it is the only per-agent, actor-scoped credential path in the code.
