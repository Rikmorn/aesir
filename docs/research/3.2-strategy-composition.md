# Milestone v3.2: Strategy Composition

**Status:** Vision
**Scope:** Identify platform seams where the "right behavior" depends on the agent's domain, build abstraction surfaces for each, and implement one concrete strategy per seam for the current use case (software development workflows). The platform provides composable primitives; agent definitions declare which strategy fits.

**Predecessor:** v3.1 (Human Collaboration) — agents are competent domain professionals collaborating with humans
**Successor:** TBD

---

## Philosophy

v2.2 through v2.9 built the infrastructure. v3.0 built the actors. v3.1 connected them to humans. v3.2 makes the platform's internal behaviors as pluggable as the agents themselves.

Today, agents are declarative — a YAML definition + prompt.md produces a working agent without framework code changes. But the platform behaviors *underneath* those agents are hardcoded: one retrieval strategy, one compaction approach, one delegation protocol, one budget model. Every agent gets the same pipeline regardless of what it's doing.

This worked while Aesir had one use case. As the platform expands to new domains (customer support, incident response, data pipelines, content workflows), different agents will need fundamentally different platform behaviors:

- A long-running orchestrator managing a week-long feature lifecycle needs aggressive knowledge persistence before compaction. A short-lived coder sub-agent that runs for 30 seconds doesn't.
- A product agent triaging feature requests needs semantic-heavy retrieval with temporal decay — old discussions should fade as priorities shift. A dev agent debugging a crash needs keyword-heavy retrieval — exact error codes and function names matter more than paraphrases.
- A QA agent validating a change needs high-diversity retrieval results — it needs to find all the different failure modes, not five results about the same bug.

The principle: **the same pattern that made agents pluggable (declarative definitions) should make platform strategies pluggable.** The definition declares the strategy. The platform provides the primitives. New use cases don't require new platform code — they require a new definition with different strategy parameters.

### What this is NOT

This milestone is NOT about predicting or building strategies for hypothetical future use cases. It's about:

1. Identifying the **seams** — places where one hardcoded behavior currently exists but the right answer depends on the agent's domain
2. Building the **abstraction surface** — interfaces and definition-level configuration for each seam
3. Implementing **one concrete strategy per seam** — the one that fits software development workflows (our current use case)

The abstraction is the investment. The first strategy is the default. Future strategies are cheap to add — just as adding a new agent is cheap once the definition format exists.

## Identified Seams

### Seam 1: Knowledge Retrieval

**Current behavior:** Pure vector search via pgvector cosine similarity with a hard threshold (0.3). Single retrieval signal.

**Why it's a seam:** Different agents searching for different things need different retrieval characteristics:
- Semantic-heavy (paraphrase matching) for natural language queries about concepts
- Keyword-heavy (exact token matching) for error codes, function names, identifiers
- Blended (hybrid) for general-purpose retrieval
- Diversity-optimized for agents that need coverage over depth (finding all failure modes, not the five most similar results)

**Strategies (implement first, others are future):**

| Strategy | Description | Fits |
|----------|-------------|------|
| `vector` | Pure cosine similarity (current behavior) | General-purpose, default |
| `hybrid` | Weighted vector + BM25 keyword search | Agents working with technical content |
| `keyword` | BM25-dominant with vector tiebreaking | Agents searching for exact tokens |

**Abstraction surface:**

```yaml
# In agent definition YAML
knowledge:
  retrieval:
    strategy: vector | hybrid | keyword
    vector_weight: 0.7          # hybrid only
    keyword_weight: 0.3         # hybrid only
    min_score: 0.3
    max_results: 10
    diversity:
      enabled: false
      lambda: 0.7              # relevance vs diversity balance
```

**Platform primitives needed:**
- PostgreSQL `tsvector`/`tsquery` with GIN index on knowledge entries (BM25 equivalent)
- Score fusion function (weighted combination of vector + keyword scores)
- MMR re-ranking function (Jaccard similarity on tokenized content)
- Strategy resolver that reads definition config and wires up the right pipeline

### Seam 2: Knowledge Recency

**Current behavior:** Hard expiry per knowledge type (discoveries: 24h, constraints: 30d, architecture decisions: 7d). Binary — the entry exists or it doesn't.

**Why it's a seam:** Hard expiry is the right model for some agents (short-lived task executors where stale knowledge is worse than no knowledge). Temporal decay is the right model for others (long-running orchestrators where old-but-relevant knowledge should fade but not vanish).

**Strategies:**

| Strategy | Description | Fits |
|----------|-------------|------|
| `expiry` | Hard TTL per type (current behavior) | Short-lived agents, task executors |
| `decay` | Exponential decay scoring with configurable half-life | Long-running orchestrators, product agents |

**Abstraction surface:**

```yaml
knowledge:
  recency:
    strategy: expiry | decay
    # expiry strategy (current)
    ttl:
      discovery: 24h
      constraint: 30d
    # decay strategy
    half_life_hours: 168
    decay_weight: 0.15
    pinned_types: [constraint, architecture_decision]
```

### Seam 3: Pre-Compaction Behavior

**Current behavior:** HistoryManager compacts via Haiku summarization. No agent involvement — the conversation loses detail silently.

**Why it's a seam:** Long-running agents accumulate important context that may not survive summarization. Short-lived agents never hit compaction thresholds. The right pre-compaction behavior depends on conversation lifetime and knowledge importance.

**Strategies:**

| Strategy | Description | Fits |
|----------|-------------|------|
| `none` | No pre-compaction action (current behavior) | Short-lived sub-agents |
| `flush` | Prompt agent to persist knowledge via `store_knowledge` before compaction | Long-running orchestrators |

**Abstraction surface:**

```yaml
history:
  pre_compaction:
    strategy: none | flush
    # flush strategy
    system_prompt: "Your conversation is about to be summarized. Use store_knowledge now for any discoveries, constraints, or decisions worth preserving across conversations."
```

**Implementation notes:**
- The flush inserts a synthetic turn into the agent loop before compaction runs
- Agent uses existing `knowledge:store_knowledge` tool (auto-deduplicates via supersede)
- Unlike OpenClaw's file-write approach, this routes through the structured knowledge system — no risk of file overwrites or unstructured persistence
- Track flush count per conversation to prevent double-flushing

### Seam 4: Delegation Handshake

**Current behavior:** Accept-or-reject. The delegated agent either takes the task or rejects it. No negotiation.

**Why it's a seam:** Simple accept/reject works for well-specified tasks delegated to known agents. But richer negotiation patterns emerge as agents work across domains:
- Counter-proposals ("I can do X but not Y, or I can do all of it if you extend the budget")
- Capability queries ("Can you handle TypeScript? What about database migrations?")
- Conditional acceptance ("I'll take this but I need access to tool Z")

**Strategies:**

| Strategy | Description | Fits |
|----------|-------------|------|
| `accept_reject` | Binary acceptance (current behavior) | Well-specified tasks, known agents |
| `negotiate` | Multi-turn handshake with counter-proposals | Cross-domain delegation, human-like collaboration |

**Abstraction surface:**

```yaml
delegation:
  handshake:
    strategy: accept_reject | negotiate
    max_rounds: 3              # negotiate only
    timeout_per_round: 30s     # negotiate only
```

**Deferred until a real use case needs it.** The abstraction surface should be designed now but the `negotiate` strategy should only be built when a concrete scenario requires it. Accept/reject is the correct default.

### Seam 5: Budget Allocation

**Current behavior:** Parent shares remaining token budget with child. Single policy: the child gets whatever the parent has left.

**Why it's a seam:** Different delegation patterns need different budget models:
- A parent spawning one critical child should share most of its budget
- A parent spawning five parallel sub-agents should divide the budget
- A QA agent that mostly delegates should reserve budget for its own verification pass after children complete

**Strategies:**

| Strategy | Description | Fits |
|----------|-------------|------|
| `share_remaining` | Child gets parent's remaining budget (current behavior) | Single-child delegation |
| `fixed_allocation` | Child gets a fixed token amount from parent | Multi-child parallel delegation |
| `proportional` | Budget divided among children based on estimated complexity | Orchestrators with many sub-agents |

**Abstraction surface:**

```yaml
delegation:
  budget:
    strategy: share_remaining | fixed_allocation | proportional
    fixed_amount: 50000         # fixed_allocation only
    reserve_for_parent: 10000   # tokens parent keeps for post-delegation work
```

## Approach

### Phase 1: Seam Identification & Abstraction Design

Validate the seams identified above against real agent behavior. For each seam:
- Confirm the current hardcoded behavior
- Design the abstraction surface (definition YAML schema)
- Define the strategy interface (TypeScript types)
- Ensure the default strategy produces identical behavior to today (zero regression)

### Phase 2: Retrieval Primitives

Build the platform primitives that strategies compose from:
- Add PostgreSQL full-text search (`tsvector`/`tsquery` with GIN index) alongside pgvector
- Build score fusion functions (weighted vector + keyword combination)
- Build BM25 rank-to-score normalization
- Build MMR re-ranking with Jaccard similarity
- Build temporal decay scoring function
- Wire primitives into KnowledgeService behind strategy interface

### Phase 3: Pre-Compaction Flush

Implement the flush strategy in HistoryManager:
- Insert synthetic turn before compaction when strategy = `flush`
- Agent uses existing `store_knowledge` tool
- Track flush count per conversation (prevent double-flush)
- Graceful degradation: if flush fails or agent produces nothing, compaction proceeds normally

### Phase 4: Strategy Resolution

Build the strategy resolution layer:
- AgentRegistry reads strategy config from definition YAML
- Strategy resolver creates the right service configuration per agent
- ConversationExecutor passes strategy config to KnowledgeService, HistoryManager, etc.
- Default strategies match current behavior exactly (backward compatible)

### Phase 5: Budget & Delegation Strategies

Extend delegation with configurable budget allocation:
- Extract budget calculation from executor into strategy function
- Implement `fixed_allocation` and `proportional` strategies
- Design (but defer implementation of) `negotiate` handshake strategy

## What Success Looks Like

1. **A new agent definition can change retrieval behavior without platform code changes.** Setting `knowledge.retrieval.strategy: hybrid` in the YAML gives that agent hybrid search. No framework PRs needed.

2. **Current agents behave identically.** Every existing definition without strategy config gets today's exact behavior. Zero regression.

3. **The seams are explicit.** A developer looking at the definition schema can see exactly where platform behavior is configurable. The extension points are documented, not accidental.

4. **Adding a new strategy is a bounded task.** Implementing a new retrieval strategy means: write a function matching the strategy interface, register it, done. Same pattern as adding a new tool or a new agent.

---

## Validation

- **Regression**: All existing agent integration tests pass with unchanged definitions
- **Strategy switching**: Create test agent definitions with non-default strategies and verify behavior changes
- **Hybrid retrieval**: Queries for exact error codes return better results with `hybrid` vs `vector`
- **Pre-compaction flush**: Long-running test conversation persists knowledge entries before compaction
- **Budget allocation**: Multi-child delegation with `fixed_allocation` distributes budget correctly

## Relationship to Competition

This milestone was informed by analysis of OpenClaw's memory system (see `socials/competition/openclaw.md` section 9). OpenClaw built a sophisticated retrieval pipeline (hybrid vector+BM25, temporal decay, MMR re-ranking, pre-compaction flush) but hardcoded it for one use case — a personal assistant accumulating markdown notes.

Aesir's approach inverts this: instead of building one sophisticated pipeline, build composable primitives and let agent definitions declare the strategy. The result is a platform that can support OpenClaw-style retrieval for agents that need it, simple vector search for agents that don't, and strategies that haven't been invented yet for use cases that haven't arrived.

The competitive insight isn't "copy their features." It's "their features are strategies, and strategies should be configuration."
