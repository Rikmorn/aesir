# Milestone v3.1: Human Collaboration

**Status:** Vision
**Scope:** Formal protocols for agent-to-human delegation, human response handling, and mixed human-agent workflows. Agents and humans as peers in the entity directory with appropriate collaboration patterns for each. Deliberately sequenced after domain modeling — humans should interact with competent agents, not half-baked ones.

**Predecessor:** v3.0 (Domain Modeling) — agents must be competent professionals before humans collaborate with them
**Successor:** TBD

---

## Philosophy

The current semi-automatic workflow works well: humans create or tweak tickets, assign to agents, agents execute. This is effective because it plays to current strengths — humans make judgment calls, agents execute tasks.

v3.1 formalizes bidirectional collaboration: agents can create work for humans, humans can respond through natural channels (Slack, Linear), and the system handles the protocol translation between human communication patterns and agent signal processing.

The key insight: human collaboration isn't just "agent sends Slack message and waits." It's a protocol design problem with fundamentally different characteristics from agent-to-agent work:

- **Time scale** — humans respond in minutes to hours, not seconds. Context goes stale. History compaction runs. The agent's understanding of why it delegated may be lost by the time the human responds.
- **Unstructured responses** — humans say "yeah looks good but also check X" when the protocol expects accept/reject. Parsing intent from natural language is an LLM classification problem that will sometimes be wrong.
- **No-response** — humans forget, get busy, go on holiday. An agent waiting forever on a human is worse than a timeout — it's invisible wasted capacity.
- **Channel richness** — Slack has threading, reactions, edits, deletes. Linear has comments, status changes, assignee changes. Which interactions count as "responses"? Which are noise?
- **Expectations** — humans have higher expectations for interaction quality. A clunky bot message that an agent would accept is annoying to a human. Tone, formatting, context, and timing all matter.

## Phase 1: Human Directory Entries

**Goal**: Humans appear in the entity directory alongside agents, with capabilities, roles, and reachability information. Agents can discover humans via capability queries.

**Depends on**: v3.0 complete

### Requirements

| ID | Requirement |
|---|---|
| HDE-01 | Human entry schema — name, role, capabilities (natural language), reachVia (JSONB array of `{ channel, target }` objects), availability preferences (timezone, working hours), status |
| HDE-02 | Seed configuration — humans configured via seed file (YAML/JSON), seeded alongside agent directory entries via `pnpm seed:directory` |
| HDE-03 | Mixed directory queries — `directory:find` returns both agents and humans ranked by capability match. Results include entity type so agents can adjust their approach |
| HDE-04 | ReachVia extensibility — supports multiple channel types per human (Slack primary, Linear secondary, email future). Agent or infrastructure selects best channel based on availability and urgency |
| HDE-05 | Availability awareness — directory queries can filter by availability (timezone-aware working hours). Agents should not delegate to humans outside their working hours unless urgent |

### Success Criteria

1. `directory:find("approve architecture decisions")` returns both agents and humans, ranked by capability
2. Human entries include reachability information that the materialization layer can dispatch to
3. Seed script is idempotent — re-running updates existing entries without duplicates

## Phase 2: Delegation Materialization

**Goal**: When an agent delegates to a human, the task materializes as a message in the human's preferred channel with full context and response affordances.

**Depends on**: Phase 1

### Requirements

| ID | Requirement |
|---|---|
| DM-01 | Slack materialization — delegated task creates a Slack message in the human's channel with task description, context, expectations, and response buttons (Accept / Reject / Need More Info) |
| DM-02 | Linear materialization — delegated task optionally creates a Linear issue assigned to the human with task details and a link to the internal task |
| DM-03 | Channel selection — materialization target determined by human's `reachVia` in directory, with preference ordering. Agent can suggest a channel; infrastructure respects human's preferences |
| DM-04 | Context rendering — task description, expectations, relevant knowledge entries, and delegation chain context rendered in channel-appropriate format (Slack mrkdwn, Linear markdown) |
| DM-05 | Response affordances — structured response options (buttons, menus) for common actions. Free-text input for detailed responses |
| DM-06 | Delivery confirmation — system confirms the message was delivered to the human's channel. If delivery fails (channel not found, permissions error), agent is notified |

### Success Criteria

1. An agent delegates "review this architecture proposal" to a human, and the human receives a Slack message with context and Accept/Reject buttons
2. If the human's Slack channel is unavailable, the system falls back to their secondary channel (Linear issue creation)
3. The materialized message includes enough context for the human to understand what's needed without asking follow-up questions

## Phase 3: Async Handshake Protocol

**Goal**: The negotiation handshake works across human time scales (minutes to hours) without context degradation or invisible hangs.

**Depends on**: Phase 2

### Requirements

| ID | Requirement |
|---|---|
| AHP-01 | Long-wait context preservation — delegation context survives hours/days of waiting. Identity documents (v2.9) provide persistent agent understanding; `active_delegations` JSONB preserves task-specific context. Combined, the agent can resume coherently after a long wait |
| AHP-02 | Configurable reminders — if human hasn't responded, send follow-ups on a configurable schedule. Default: gentle reminder after 4 hours, informative reminder after 24 hours, escalation after 48 hours |
| AHP-03 | Reminder content — each reminder level has appropriate tone and additional context: first is a gentle nudge, second explains what's blocked, third offers to re-route |
| AHP-04 | Escalation path — if human doesn't respond within escalation window, agent is notified and can: re-delegate to another entity, complete the work itself, or pause and report the blocker |
| AHP-05 | Availability-aware timing — reminders respect human's timezone and working hours. Don't send reminders at midnight. Pause reminder timers during non-working hours |
| AHP-06 | Human-initiated cancellation — humans can cancel a delegation they've received (via Slack button or by closing a Linear issue). Agent receives a cancellation signal |

### Success Criteria

1. A delegation to a human who doesn't respond for 4 hours triggers a reminder in their Slack channel
2. After 48 hours without response, the agent receives an escalation signal and re-delegates to someone else
3. Reminders pause during non-working hours and resume when the human is likely available
4. A human cancels a delegation via Slack button and the agent resumes with a cancellation signal

## Phase 4: Response Parsing & Signal Handling

**Goal**: Human responses through natural channels are parsed into protocol-compatible signals — bridging the gap between unstructured human communication and structured agent protocols.

**Depends on**: Phase 3

### Requirements

| ID | Requirement |
|---|---|
| RSP-01 | Structured response mapping — Slack button clicks (Accept / Reject / Need More Info) map directly to handshake signals with zero ambiguity |
| RSP-02 | Free-text classification — natural language responses classified into protocol actions via LLM. "Looks good, go ahead" → accept. "I have concerns about the auth approach" → reject with reason. "Can you show me the API design first?" → counter-propose |
| RSP-03 | Confidence-gated actions — high-confidence classifications act immediately. Low-confidence classifications trigger a confirmation: "I understood that as approval — is that right?" |
| RSP-04 | Multi-part responses — humans often combine protocol action with additional context: "Yes, approved, but make sure to add error handling." Parse both the action (accept) and the supplementary context (additional requirement) |
| RSP-05 | Channel interaction semantics — define which Slack interactions are protocol-relevant: messages in thread (yes), reactions (configurable — thumbs-up could mean accept), edits (update previous response), deletes (ignore). Document the mapping clearly |
| RSP-06 | Conversation threading — human responses in a Slack thread stay associated with the original delegation. Multiple delegations to the same human in the same channel don't cross-contaminate |

### Success Criteria

1. A human clicks "Accept" in Slack and the agent immediately resumes with an acceptance signal
2. A human replies "yeah that looks fine, ship it" and the system classifies this as acceptance with high confidence
3. A human replies "I'm not sure, can you explain the tradeoffs?" and the system classifies this as a clarification request, prompting the agent to provide more context
4. Ambiguous responses ("maybe") trigger a confirmation rather than guessing

### Open Design Questions

1. **Reaction semantics** — Should Slack reactions count as responses? Thumbs-up as accept is intuitive but error-prone (people react casually). Probably configurable per-team: off by default, opt-in.
2. **Edit handling** — If a human says "approved" then edits to "actually wait, not approved" — does the agent see the edit? Probably not in v1 — edits are hard to track reliably. Document this limitation.
3. **Multi-delegation disambiguation** — If an agent has 3 outstanding delegations to the same human, and the human says "approved" in a Slack DM (not a thread), which delegation does it apply to? Probably: force threading so every delegation has its own thread. Unthreaded responses trigger "which task are you responding to?"

## Phase 5: Mid-Work Signals

**Goal**: Both humans and agents can send signals that change the trajectory of in-progress delegated work — cancellation, requirement changes, re-delegation, and priority shifts.

**Depends on**: Phase 4

### Requirements

| ID | Requirement |
|---|---|
| MWS-01 | Task cancellation signal — human or agent can cancel an in-progress delegated task. Worker receives cancellation signal with reason and decides how to wind down gracefully |
| MWS-02 | Requirement change signal — new information arrives mid-task that changes what's needed. Signal includes the change description. Worker decides: adapt in-flight, restart, or signal back that the change is too large |
| MWS-03 | Re-delegation — human partially completes work and hands back to agent (or agent partially completes and hands to human). Handoff includes what was done and what remains |
| MWS-04 | Priority change signal — urgency shifts mid-task. Worker adjusts effort allocation accordingly (deprioritize = background, escalate = immediate focus) |
| MWS-05 | Signal acknowledgment — worker confirms receipt of mid-work signals before acting on them. Prevents "I cancelled but the agent already merged" race conditions |
| MWS-06 | Signal rendering — mid-work signals from agents to humans are rendered in the human's channel with appropriate context. "The requirements for this task have changed: [description]. Please review the updated scope." |

### Success Criteria

1. A human cancels a delegation mid-work and the agent stops, cleans up, and reports what was completed
2. An agent sends a requirement change to a human mid-work and the human acknowledges via Slack
3. A human partially completes work and re-delegates back to the agent with context about what's done
4. Signal acknowledgment prevents race conditions between cancellation and completion

## Design Considerations

### The Unstructured Response Problem

Humans say "yeah looks good but can you also check X" when the protocol expects accept/reject. The response parsing layer (Phase 4) is the critical design challenge. Options:

- **Conservative**: Only act on structured inputs (button clicks). All free-text goes through LLM classification with confirmation. Safe but slow — humans find confirmation dialogs annoying.
- **Aggressive**: LLM classifies everything, acts on high-confidence classifications immediately. Fast but risky — wrong classifications damage trust.
- **Hybrid (recommended)**: Structured inputs for critical actions (accept/reject). LLM for supplementary context (additional requirements, clarifications). Confirmation only on low-confidence or high-stakes classifications.

The right approach probably varies by team and by action severity. Accepting a task is lower-stakes than approving a production deployment. Make the confidence threshold configurable.

### The No-Response Problem

Humans forget. The reminder/escalation system (Phase 3) needs to be respectful but effective:

- **First reminder** (4h): Gentle — "just checking if you've had a chance to look at this"
- **Second reminder** (24h): Informative — "this task is blocking [X], which is due by [Y]"
- **Escalation** (48h): Action-oriented — "no response after 48h, I'm going to [re-delegate to Z / do this myself / park this]"

All timing configurable per-team and per-person. Some people respond in minutes; some need a day. The system should learn preferences over time (cross-session learning from v3.0).

### The Context Staleness Problem

A conversation waiting 8 hours for a human response has stale context. History compaction might have run. The mitigations:

1. **Identity documents** (v2.9) — the agent's persistent understanding survives any wait
2. **`active_delegations` JSONB** (v2.7) — delegation-specific context preserved on the conversation
3. **Self-contained signal payloads** (v2.7) — the human's response includes enough context to resume
4. **Delegation context block** (v2.7) — injected on resume so the agent has immediate situational awareness

Combined, these should be sufficient. But validate with real scenarios — an 8-hour wait followed by a two-word human response ("looks good") is the acid test.

### The Trust Problem

Humans need to trust that the agent will handle their response correctly. Every misclassified response erodes trust. Every ignored cancellation erodes trust. Every unnecessary confirmation dialog erodes patience. The balance between safety and usability is the core design tension.

Start conservative (more confirmations, structured inputs preferred), measure misclassification rate, and relax toward aggressive as confidence grows. This is a knob, not a switch.
