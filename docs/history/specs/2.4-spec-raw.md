# v2.4 Spec: Operations Dashboard

## Goal

Real-time visibility into agent execution through a developer-focused web dashboard. See what agents are doing, inspect tool calls, view agent and tool configurations, and monitor conversation lifecycle -- all backed by the existing Postgres data from v2.3's unified event log. Built with defensive architecture that makes future auth, multi-tenancy, and external API layers trivial to add.

## Why This Matters

v2.3 shipped a unified agent framework with rich observability data -- `agent_events` records every tool call, LLM response, and lifecycle event with gapless per-conversation sequences. `agent_sessions` provides a reactive projection of conversation state and artifacts. But all this data is only accessible via direct database queries or log tailing.

As agents grow more capable and handle more workflows, the feedback loop for improving them becomes the bottleneck:

1. **Debugging agent decisions requires SQL.** To understand why an agent made a specific tool call or stalled, you query `agent_events` with filters, join to conversations, and mentally reconstruct the timeline. This is slow and error-prone.

2. **Tool failures are invisible.** A tool returning `isError: true` is recorded in the event log but never surfaced. You discover failures retroactively when an agent produces bad output -- not when the failure happens.

3. **Configuration is scattered.** Agent definitions live in YAML files, tool registrations in code, MCP permissions in three separate database tables, and integration endpoints in environment variables. Understanding "what can this agent do?" requires reading 4+ sources.

4. **No real-time awareness.** When an agent is running, you can't see what it's doing without tailing logs. There's no way to watch a conversation unfold, see tool calls as they happen, or know when something goes wrong.

5. **Iteration speed compounds.** Every agent improvement (better prompts, new tools, sub-agent tuning) requires a feedback cycle: make a change, trigger the agent, observe the result, adjust. Without visibility, each cycle is slower than it needs to be. Over weeks and months, this compounds significantly.

The dashboard doesn't compete with agent improvements -- it's the force multiplier for all future agent work.

## Architecture Overview

```
Browser (Next.js App Router)
    |
    | HTTP/SSE
    v
Dashboard Service (port 3005)
    |
    +---> Postgres (read-only)          # Conversations, events, sessions, permissions
    |       agents.conversations
    |       agents.agent_events
    |       agents.agent_sessions
    |       {linear,github,slack}.mcp_tool_permissions
    |
    +---> Agent Service API (port 3004) # Tool registry, worker state, integration health
            GET /api/tools/registry
            GET /api/tools/health
            GET /api/worker/status
```

### Key Architectural Decisions

**Separate service, not embedded.** The dashboard runs as its own Next.js service (`packages/dashboard/`), not embedded in the agent service. Reasons:
- Different deployment lifecycle -- dashboard changes shouldn't require agent service restarts
- Different resource profile -- SSR and static assets vs. background agent loops
- Clean dependency boundary -- the dashboard reads from Postgres and the agent service API, nothing more
- Follows the existing pattern of independent services in the monorepo

**Read-only Postgres access.** The dashboard connects to the existing Postgres instance and reads from `agents.*`, `linear.*`, `github.*`, and `slack.*` schemas. No write operations. No new tables for v2.4 (dashboard-specific data like saved views would go in a `dashboard.*` schema when needed).

**Agent service API for runtime state.** Some data doesn't live in the database -- the loaded tool registry, worker loop status, and integration health are runtime state. The agent service exposes a small read-only API surface that the dashboard consumes. This is also the seed of a future management API.

**Server-Sent Events for real-time.** The dashboard uses SSE to stream conversation and event updates to the browser. SSE is unidirectional (server → client), works through proxies/load balancers without special config, and is sufficient for "watch what's happening." The agent service can emit SSE events by bridging from the existing `EventLog.subscribe()` mechanism.

**Auth-ready middleware pipeline.** Next.js middleware.ts currently passes through every request. When auth is needed, a single file change wires in Auth.js. All data access goes through a service layer that accepts a context parameter (currently empty, later carries the authenticated user). API route handlers are structured to receive context. None of this adds meaningful complexity now.

## What Changes vs. v2.3

| Component | v2.3 (Current) | v2.4 (Target) |
|-----------|----------------|---------------|
| Visibility into agent execution | Direct SQL queries against agent_events | Dashboard with conversation timeline, event stream, tool inspector |
| Tool configuration visibility | Read YAML files + code + 3 database tables | Unified tool dashboard with registry view, permission matrix, performance metrics |
| Agent definition inspection | Read YAML + prompt.md files on disk | Agent definitions viewer showing config, tools, triggers, sub-agent mappings |
| Real-time monitoring | Tail service logs | Live conversation updates via SSE |

## What Stays the Same

- **Agent runtime** -- ConversationExecutor, worker loop, event log, all unchanged
- **Agent definitions** -- YAML + prompt.md, managed via files (no editing UI)
- **Integration packages** -- Linear, GitHub, Slack unchanged
- **MCP layer** -- All tool communication unchanged
- **Docker Compose topology** -- Existing services unchanged, dashboard added alongside

```
      components/              # Shared UI components

      services/                # Data access layer

        worker.ts              # Worker status queries
      lib/                     # Utilities
        db.ts                  # Drizzle client (read-only)

      middleware.ts             # Auth-ready passthrough
    next.config.ts
    tailwind.config.ts
    tsconfig.json
    package.json
    Dockerfile
```

**Technology choices:**

| Technology | Purpose | Rationale |
|------------|---------|-----------|
| Next.js 15 App Router | Framework | Server components for data-heavy pages, middleware for future auth, API routes for SSE endpoints, established ecosystem |
| Tailwind CSS 4 | Styling | Utility-first, works with shadcn/ui, no runtime overhead |
| shadcn/ui | Component library | Copy-paste components (owned code, not a dependency), Radix primitives for accessibility, Table/Dialog/Command/Sheet for dashboard patterns |
| Drizzle ORM | Database access | Already used in the project, shared schema definitions, type-safe queries |
| Server-Sent Events | Real-time updates | Unidirectional, proxy-friendly, sufficient for monitoring, bridges from existing EventLog.subscribe() |

**Design decisions:**

- **Server components by default.** Dashboard pages are read-heavy. Server components fetch data at render time with no client-side JS overhead. Client components are used only where interactivity is required (filters, expandable panels, real-time updates).

- **Service layer abstraction.** All database queries go through `src/services/`. No raw Drizzle calls in page components. Each service module exports typed functions that accept query parameters and return shaped data. This is the future API boundary -- when an API layer is added, services become the implementation behind route handlers.

- **Shared Drizzle schema.** The dashboard imports table definitions from existing packages (`@aesir/agents` schema). No schema duplication. The dashboard's Drizzle client is configured read-only (connection string can use a read replica in production).

- **No dashboard-specific database tables in v2.4.** All data comes from existing schemas. When dashboard-specific data is needed (saved views, user preferences), it goes in a `dashboard.*` schema via its own migration.

### 2. Conversations View

The primary pain point: seeing what agents are doing.

**Conversations list page (`/conversations`):**

Displays all conversations with filterable, sortable columns:
- Agent name (from `agent_definition_id`)
- Status badge (queued, running, waiting, completed, failed, cancelled)
- Trigger event type (from first `agent.started` event payload)
- Duration (created_at to updated_at, or "running" indicator)
- Token usage (sum of `token_count_input` + `token_count_output` from `agent_events` where type = 'llm.response')
- Last activity (from `agent_sessions.last_event_at`)
- Error indicator (if status = failed, show `error_message` excerpt)

Filters:
- Status (multi-select: queued, running, waiting, completed, failed)
- Agent type (multi-select from distinct `agent_definition_id` values)
- Time range (last hour, last 24h, last 7d, custom)
- Has errors (boolean)

Auto-refresh via SSE: when a conversation's status changes, the row updates without full page reload.

**Conversation detail page (`/conversations/[id]`):**

The core debugging view. Three panels:

**Panel 1: Event Timeline**
Chronological stream of `agent_events` for this conversation, rendered as a visual timeline:
- `agent.started` -- conversation began, shows agent name and trigger
- `tool.called` -- tool invocation, shows tool name and input parameters (expandable)
- `tool.succeeded` -- tool result (expandable, with syntax highlighting for code/JSON)
- `tool.failed` -- error with full error payload, visually distinct (red)
- `llm.response` -- LLM turn, shows token counts and latency
- `agent.paused` -- waiting for signal, shows wait type and reason
- `signal.received` -- signal arrived, shows type and source
- `agent.resumed` -- conversation resumed
- `agent.completed` -- conversation finished

Sub-agent events (where `parent_instance_id` is set) are rendered as nested/indented sections within the parent timeline.

Each event row shows:
- Timestamp (relative and absolute)
- Duration (for tool calls and LLM responses)
- Token count (for LLM responses)
- Expandable payload (JSON viewer)

**Panel 2: Conversation Messages**
The LLM message history from `conversations.messages` rendered as a chat view:
- System prompt (collapsible, shown as first message)
- User messages (including signal-injected messages)
- Assistant messages with reasoning
- Tool use blocks with input
- Tool result blocks with output (collapsible for large results)

**Panel 3: Conversation Metadata**
Sidebar showing:
- Conversation ID
- Agent definition + version
- Status with state transitions timeline
- Pending wait (if waiting): type, reason, metadata
- Queued signals (if any)
- Retry count / max retries
- Parent conversation (if sub-agent, link to parent)
- Child conversations (if has sub-agents, links to children)
- Session artifacts (from `agent_sessions.artifacts`)
- Created at / Updated at

**Data sources:**
- Conversation metadata: `agents.conversations` table
- Event timeline: `agents.agent_events` table (ordered by sequence)
- Session artifacts: `agents.agent_sessions` table
- Sub-agent hierarchy: `conversations.parent_conversation_id` + `agent_events.parent_instance_id`

### 3. Agent Definitions View

Visibility into what agents exist and how they're configured.

**Agent list page (`/agents`):**

Cards or table showing all loaded agent definitions:
- Agent name and ID
- Description
- Model and temperature
- Tool count (number of tools in the definition)
- Sub-agents (if any, with links)
- Trigger events (what starts this agent)
- Version
- Recent activity (last N conversations for this agent type, from `agent_sessions`)

**Agent detail page (`/agents/[id]`):**

Full definition view:
- **Configuration:** model, temperature, maxIterations, tokenBudget, history settings (pruneThreshold, protectedMessages, summaryThreshold, summaryModel)
- **System prompt:** Full prompt.md content rendered with Markdown formatting (collapsible, since prompts are long)
- **Tools:** List of all tools this agent can use, with namespace grouping. Each tool links to the tool detail view.
- **Sub-agents:** Visual mapping of role → agent definition, with links to the sub-agent's detail page
- **Triggers:** Event types that start this agent
- **Recent conversations:** Last 10 conversations for this agent, with status and duration

**Data source:** Agent-service API endpoint (`GET /api/agents/registry`), NOT direct file reads. The dashboard should not read YAML files from disk -- it queries the agent service's loaded registry state. This ensures the dashboard shows what's actually loaded and running, not what's on disk (which might differ if files were changed but the service wasn't restarted).

### 4. Tool Dashboard

The tool visibility layer discussed in our conversation. Two concerns: tool observability (what tools are doing) and tool configuration (what tools exist and who can use them).

**Tool dashboard page (`/tools`):**

**Section 1: Tool Registry**
All registered tools from the agent service's ToolRegistry, organized by namespace:
- `codebase:` -- read_file, write_file, search_codebase, list_directory, run_command
- `coordination:` -- spawn_agent, wait_for, request_human_input
- `linear:` -- get_issue, create_issue, update_issue_status, list_teams, list_labels, search_issues, create_comment
- `github:` -- get_repository, create_branch, create_commit, create_pull_request, get_pull_request, list_pull_requests, merge_pull_request, get_file_contents, list_files
- `slack:` -- send_message, send_approval_request, get_message, reply_to_thread, list_channels

Each tool shows:
- Full name (namespace:tool_name)
- Description (from the tool definition)
- Which agents have access (cross-referenced with agent definitions)
- Recent call volume (from `agent_events` where type = 'tool.called')
- Failure rate (tool.failed / total calls)
- Average latency (from `duration_ms`)

Data source: Agent-service API (`GET /api/tools/registry`) for tool definitions, Postgres for metrics.

**Section 2: Permission Matrix**
Cross-reference view: agents (rows) x tools (columns), showing which agent can call which tool. Data from two sources:
- Agent definitions (what the YAML says the agent can use)
- MCP permissions (`{linear,github,slack}.mcp_tool_permissions` tables -- what the integration actually allows)

Highlight mismatches: if an agent definition references a tool but the MCP permission table doesn't grant access, that's a configuration error worth surfacing.

**Section 3: Tool Performance**
Aggregated metrics from `agent_events`:
- Call volume over time (bar chart, per tool or per namespace)
- Failure rate over time (line chart)
- Latency distribution (p50, p95, p99 from `duration_ms`)
- Top errors (most common `tool.failed` payload patterns)
- Slowest tools (ranked by average latency)

Filters: time range, namespace, agent type.

**Section 4: Recent Failures**
Filterable list of `tool.failed` events showing:
- Timestamp
- Tool name
- Agent that called it
- Conversation ID (link to conversation detail)
- Error payload (expandable)
- Duration

**Section 5: Integration Health**
Status of each MCP integration endpoint:
- Linear (http://linear-integration:3001): last successful call, current error state, latency
- GitHub (http://github-integration:3002): last successful call, current error state, latency
- Slack (http://slack-integration:3003): last successful call, current error state, latency

Data source: Agent-service API (`GET /api/tools/health`) which pings integration health endpoints and reports status.

### 5. System Overview

The landing page (`/`). A quick pulse check on the system.

**Conversation Status Summary**
Counts by status: running, waiting, queued, completed (last 24h), failed (last 24h). Visual indicators (colored badges or small sparkline).

**Active Conversations**
List of currently running/waiting conversations with agent name, duration, last event, and a link to detail.

Last 10 failed conversations or tool failures, with links to conversation detail.

Aggregate token consumption over the last 24h, broken down by agent type. From `agent_events` where type = 'llm.response'.

### 6. Real-Time Updates (SSE)

Live updates so the dashboard reflects current state without manual refresh.

**Architecture:**

```
EventLog.subscribe()            # In-memory, existing mechanism
    |
    v
SSE Bridge (agent-service)      # New: /api/sse/events endpoint
    |
    | Server-Sent Events
    v
Dashboard SSE Client            # New: React hook that connects to SSE
    |
    v
Component State Updates         # React state update triggers re-render
```

**Agent-service SSE endpoint (`GET /api/sse/events`):**

New endpoint on the agent service that:
1. Accepts an SSE connection
2. Subscribes to the EventLog's in-memory subscriber mechanism
3. Streams events to the client as they happen
4. Supports query parameter filters: `?conversationId=xxx` for single-conversation streams, `?types=tool.called,tool.failed` for specific event types

**Dashboard SSE client:**

React hook `useEventStream(options)` that:
1. Connects to the agent-service SSE endpoint
2. Parses incoming events
3. Updates component state (conversation list refreshes, timeline appends new events)
4. Handles reconnection with exponential backoff
5. Cleans up on component unmount

**What gets real-time updates:**
- Conversations list: status changes, new conversations appearing
- Conversation detail: new events appending to timeline as they happen
- System overview: conversation counts, active conversations

**What doesn't need real-time (static data):**
- Agent definitions (change only on service restart)
- Tool registry (change only on service restart)
- MCP permissions (change only via database seed)

### 7. Agent Service API Extensions

Small, focused additions to the existing agent service to expose runtime state that doesn't live in the database.

**New endpoints on agent-service (port 3004):**

```
GET /api/tools/registry
  Response: Array of { name, namespace, description, inputSchema }
  Source: ToolRegistry.list() -- new method

GET /api/tools/health
  Response: { linear: { status, lastSuccess, latency }, github: { ... }, slack: { ... } }
  Source: Ping integration /health endpoints, cache for 30s

GET /api/agents/registry
  Response: Array of full AgentDefinition objects (minus system prompt content, which can be large)
  Source: AgentRegistry.list()

GET /api/agents/registry/:id
  Response: Full AgentDefinition including system prompt content
  Source: AgentRegistry.get(id)

GET /api/worker/status
  Response: { activeClaims, maxConcurrent, pollIntervalMs, lastPollAt, uptimeMs }
  Source: WorkerLoop internal state

GET /api/sse/events
  Response: SSE stream of agent events
  Source: EventLog.subscribe() bridged to SSE
  Query params: conversationId, types (comma-separated)
```

**Design decisions:**

- **Separate `/api/` prefix.** These are dashboard/management endpoints, distinct from the existing operational endpoints (`/events`, `/conversations/:id`). The prefix makes it easy to apply different middleware (e.g., auth for management endpoints only).

- **System prompt excluded from list endpoint.** Prompts can be very large. The list endpoint returns metadata only. The detail endpoint includes the full prompt. This keeps list responses fast.

- **Health check caching.** Integration health pings are cached for 30 seconds. The dashboard polls this endpoint, not the integrations directly. Prevents the dashboard from overwhelming integrations with health checks.

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Next.js adds significant build complexity to the monorepo | Slower CI, more dependencies, potential TypeScript config conflicts | Isolate Next.js config to `packages/dashboard/`. Use standalone output mode for Docker. Keep Next.js dependencies confined to the dashboard package. |
| Token usage aggregation queries become slow at scale | Dashboard pages load slowly when querying millions of agent_events | Use `agent_sessions` for summary data (it's a projection). Aggregate queries use time-bounded windows (last 24h default). Add materialized views or summary tables if needed later. |
| SSE connections overwhelm the agent service | Too many dashboard tabs = too many event subscribers | Rate limit SSE connections. Use a single multiplexed stream per client with client-side filtering. Limit to 10 concurrent SSE connections. |
| Shared Drizzle schema imports create tight coupling | Dashboard changes could require agent package changes | Schema imports are read-only type references. The dashboard never modifies schemas. Schema changes in the agent package are always additive (new columns don't break reads). |
| Agent-service API endpoints add surface area | More code to maintain, potential security exposure | Endpoints are read-only, on a separate `/api/` prefix, behind the same network boundary. Auth middleware will apply to these first when added. |
| Dashboard becomes a distraction from agent improvements | Time spent on UI polish instead of agent capabilities | Scope is fixed: 5 views, no editing, no analytics. Ship functional over polished. Iteration on the dashboard is future work. |

## Out of Scope for v2.4

- **Agent definition editing** -- Definitions are managed via YAML files. No create/edit/delete UI.
- **Historical analytics / trends** -- No time-series charts, no trend analysis. Raw data and recent aggregates only.
- **Alerting / notifications** -- No email, Slack, or push notifications for failures. Dashboard is pull-based (you look at it).
- **Multi-user / authentication** -- Architecture supports it, but no auth is enforced in v2.4.
- **Mobile responsiveness** -- Desktop developer tool. No mobile optimization.
- **Tool configuration editing** -- Tool permissions, rate limits, and availability are read-only. Editing would require write paths to integration databases.
- **Conversation actions** -- No ability to cancel, retry, or signal conversations from the dashboard. Management endpoints exist on the agent service but the dashboard doesn't expose them as UI actions yet.
- **Log viewer** -- pino logs are separate from agent_events. No log aggregation in the dashboard.

## Appendix A: Design Rationale

### A.1 Why Next.js Over a Vite SPA

The primary alternatives considered:

**Vite + React SPA:**
- Pro: Simpler, faster builds, no SSR complexity
- Con: Needs a separate API server for data fetching. You'd end up building Express routes that duplicate what Next.js API routes give you for free. When auth is needed, you'd build middleware that Next.js already has.
- Con: Client-side data fetching means loading spinners everywhere. Server components render with data already present.

**Remix / React Router v7:**
- Pro: Excellent loader/action pattern for data-heavy apps
- Con: Smaller ecosystem, fewer compatible component libraries
- Con: Auth story is less mature than Next.js + Auth.js

**Astro:**
- Pro: Great for content-heavy sites, islands architecture
- Con: React integration adds complexity. Better suited for documentation sites than interactive dashboards.

**Decision: Next.js.** The things that make it "heavier" (middleware pipeline, server components, API routes) are exactly the foundations needed for future growth. A Vite SPA would need a separate backend eventually, and you'd rebuild half of what Next.js provides.

### A.2 Why SSE Over WebSockets

**WebSockets:**
- Pro: Bidirectional, lower overhead per message
- Con: Requires special proxy config (nginx `proxy_pass` with `Upgrade` headers), stateful connections, more complex server-side management
- Con: The dashboard doesn't need to send data to the server -- it only receives updates

**Server-Sent Events:**
- Pro: Unidirectional (server → client), works through standard HTTP proxies without config changes
- Pro: Auto-reconnection built into the browser API (`EventSource`)
- Pro: Simple server implementation (write to response stream)
- Con: Unidirectional only (but that's all we need)

**Decision: SSE.** The dashboard is a monitoring tool -- data flows one direction (server → browser). SSE is simpler, proxy-friendly, and sufficient. If bidirectional communication is needed later (e.g., sending commands from the dashboard), individual endpoints can be upgraded to WebSockets without changing the SSE infrastructure.

### A.3 Why a Service Layer Instead of Direct Queries in Components

Server components can query the database directly -- Next.js makes this easy. Why add a service layer?

1. **Future API boundary.** When a REST/GraphQL API is added, service functions become the implementation behind route handlers. Components import from the same service module and don't change.

2. **Query logic isolation.** Dashboard queries involve joins (conversations + events for token usage), aggregations (failure rates), and time-bounded windows. These are complex enough to deserve their own test suite, separate from component rendering.

3. **Type shaping.** Database rows and dashboard view models are different shapes. The service layer transforms rows into exactly what components need. Components don't handle null columns, JSONB parsing, or aggregation math.

4. **Multi-source data.** Some data comes from Postgres, some from the agent-service API. The service layer unifies these sources. Components don't know or care where data comes from.

### A.4 Why Read-Only and No Editing in v2.4

The instinct to add agent editing, tool management, and conversation actions is strong -- "we're building a dashboard, we should be able to do things." Resisting this for v2.4:

1. **Write paths are harder than read paths.** Adding editing means: validation, optimistic updates, error handling, conflict resolution, undo. Each one is a meaningful design decision.

2. **YAML is working.** Agent definitions as files, version-controlled in git, is a good pattern for a single-developer workflow. The dashboard validates that what's loaded matches expectations -- that's the 80% value.

3. **Write paths require an API.** You can't have the dashboard write to YAML files on the agent service's filesystem. You'd need an API, which means designing the management API properly. That's a v2.5 concern.

4. **Read-only is still transformative.** Going from "grep through logs and query Postgres manually" to "see everything in a browser with real-time updates" is a massive improvement. That's the v2.4 value.

### A.5 Agent Service API as the Seed of a Management API

The new `/api/` endpoints on the agent service are deliberately designed as the first iteration of a management API:

- **Separate prefix.** `/api/` is distinct from `/events` and `/conversations/:id` (operational endpoints). This allows different auth policies: operational endpoints might use service-to-service tokens, management endpoints might use user sessions.

- **Read-only for now.** But the pattern (`GET /api/tools/registry`, `GET /api/agents/registry`) naturally extends to `POST /api/agents/registry` (create), `PUT /api/agents/registry/:id` (update), `DELETE /api/agents/registry/:id` (archive).

- **Typed responses.** Each endpoint returns a well-defined JSON shape. These become the contract for external consumers (dashboard, CLI tools, future mobile app).

## Appendix B: Data Access Patterns

Concrete query patterns the dashboard will use. These inform service layer implementation and index requirements.

### B.1 Conversations List

```sql
-- Main query: conversations with token usage
SELECT
  c.id,
  c.agent_definition_id,
  c.status,
  c.error_message,
  c.created_at,
  c.updated_at,
  s.last_event_at,
  s.artifacts,
  COALESCE(token_agg.total_input, 0) as token_input,
  COALESCE(token_agg.total_output, 0) as token_output
FROM agents.conversations c
LEFT JOIN agents.agent_sessions s ON s.conversation_id = c.id
LEFT JOIN LATERAL (
  SELECT
    SUM(token_count_input) as total_input,
    SUM(token_count_output) as total_output
  FROM agents.agent_events
  WHERE conversation_id = c.id AND type = 'llm.response'
) token_agg ON true
WHERE c.status = ANY($1)  -- status filter
  AND c.agent_definition_id = ANY($2)  -- agent filter
  AND c.created_at >= $3  -- time range
ORDER BY c.created_at DESC
LIMIT $4 OFFSET $5;
```

**Existing indexes that support this:**
- `idx_conversations_status` on (status)
- `idx_conversations_definition` on (agent_definition_id)
- `idx_agent_events_conversation` on (conversation_id, sequence)

### B.2 Conversation Event Timeline

```sql
-- Events for a single conversation, ordered
SELECT *
FROM agents.agent_events
WHERE conversation_id = $1
ORDER BY sequence ASC;
```

**Existing index:** `idx_agent_events_conversation` on (conversation_id, sequence) -- perfect for this query.

### B.3 Tool Performance Metrics

```sql
-- Tool call stats over a time window
SELECT
  payload->>'tool_name' as tool_name,
  COUNT(*) FILTER (WHERE type = 'tool.called') as total_calls,
  COUNT(*) FILTER (WHERE type = 'tool.failed') as failures,
  AVG(duration_ms) FILTER (WHERE type IN ('tool.succeeded', 'tool.failed')) as avg_latency_ms,
  PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY duration_ms)
    FILTER (WHERE type IN ('tool.succeeded', 'tool.failed')) as p95_latency_ms
FROM agents.agent_events
WHERE type IN ('tool.called', 'tool.succeeded', 'tool.failed')
  AND timestamp >= NOW() - INTERVAL '24 hours'
GROUP BY payload->>'tool_name'
ORDER BY total_calls DESC;
```

**Potential index need:** A partial index on `type` + `timestamp` for tool events would improve this query at scale:

```sql
CREATE INDEX idx_agent_events_tool_perf
  ON agents.agent_events (timestamp, (payload->>'tool_name'))
  WHERE type IN ('tool.called', 'tool.succeeded', 'tool.failed');
```

This index is not needed immediately but should be added if the tool performance page becomes slow.

### B.4 Permission Matrix

```sql
-- MCP permissions across all integrations
SELECT agent_id, tool_name, allowed, 'linear' as integration
FROM linear.mcp_tool_permissions
UNION ALL
SELECT agent_id, tool_name, allowed, 'github' as integration
FROM github.mcp_tool_permissions
UNION ALL
SELECT agent_id, tool_name, allowed, 'slack' as integration
FROM slack.mcp_tool_permissions
ORDER BY agent_id, integration, tool_name;
```

Small tables, no index concerns.

### B.5 Token Usage Aggregation

```sql
-- Token usage by agent over last 24h
SELECT
  agent_definition_id,
  COUNT(*) as llm_calls,
  SUM(token_count_input) as total_input_tokens,
  SUM(token_count_output) as total_output_tokens
FROM agents.agent_events
WHERE type = 'llm.response'
  AND timestamp >= NOW() - INTERVAL '24 hours'
GROUP BY agent_definition_id;
```

**Existing index:** `idx_agent_events_type` on (type) helps filter to llm.response events.
