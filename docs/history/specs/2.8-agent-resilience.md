# Milestone v2.8: Agent Resilience & Observability

**Status:** Planning
**Scope:** Stabilize the platform before domain modeling begins. Close gaps discovered during v2.7 live testing — runtime resilience, echo elimination, dashboard observability, work correlation. The system records failures but doesn't act on them; the dashboard shows data but not the full story. When v2.8 ships, every failure is visible and notified, the dashboard tells the complete story, and agents know what work exists before starting their own.

## Phase 2: Echo Elimination

**Depends on**: Phase 1 (quick fixes clear noise before infrastructure work)

**Goal**: The platform suppresses duplicate and self-caused events at the infrastructure level, before they reach the router or agents. Two layers: webhook delivery dedup (at-least-once protection) and actor-based echo suppression (agent's own side effects).

| Issue | What |
|-------|------|
| ISS-005 | Agent actions trigger webhooks that loop back as input. v2.7's Agent SDK migration solved activity/comment echo. The remaining echo is agent session events (`agent_session.prompted`) and the general pattern of agent-caused webhooks across all integrations. |

### Layer 1: Event ID Dedup

Webhook providers (Linear, GitHub, Slack) use at-least-once delivery — the same event can arrive multiple times due to timeouts or retries. Each delivery carries an event ID.

- **Seen-events table** — `processed_webhook_events (event_id TEXT PRIMARY KEY, received_at TIMESTAMPTZ)` with periodic cleanup (TTL-based, e.g., 24h)
- **Check at adapter/dispatcher level** — before any event processing, reject if `event_id` already exists. INSERT with ON CONFLICT DO NOTHING + check affected rows.
- All three integrations (Linear, GitHub, Slack) include event/delivery IDs in their webhook payloads

### Layer 2: Actor-Based Echo Suppression

When an agent calls an MCP tool (e.g., `linear:update_issue`), the integration performs the action, and the platform may receive a webhook about that action. The agent should never see its own side effects as new input.

- **Shared interface** — `isAgentOriginated(event): boolean` check in the adapter base or dispatcher, called after Layer 1 dedup passes
- **Per-integration actor extraction:**
  - Linear: `actor.type === 'application'` or `actor.id` matches the bot's identity
  - GitHub: `sender.type === 'Bot'` or `sender.login` matches the app's installation user
  - Slack: `bot_id` presence or `app_id` matches the installed app
- **Suppressed events** are logged (for debugging) but not forwarded to the router

### Relationship to Phase 5 (Work Correlation)

Layers 1 and 2 are stateless filters — they don't need to know about active work. Layer 3 (semantic dedup: "is this work already in progress?") requires work correlation state and is addressed by Phase 5's disposition model. The boundary is clear: if the event is a technical duplicate or agent-caused, suppress here. If it's a legitimate event about an entity with active work, Phase 5's disposition vocabulary handles it.

## Phase 3: Runtime Resilience

**Goal**: The framework closes the loop between failure observation and recovery action. When something goes wrong, the system notifies, classifies, and adapts — not just records. When notification itself fails, the dashboard is the backstop.

**Depends on**: Phase 2 (echo elimination must be in place before failure notifications generate events that could echo back)

| Issue | What |
|-------|------|
| ISS-001 | Failure notification gaps — infrastructure partially notifies on failure but only for Linear agent sessions and only for non-retryable errors. See design below. |
| ISS-006 | Stale heartbeat re-enqueue causes repeated re-exploration. Root cause: the event log records everything (sub-agent completions, tool results, signals) but nobody reads it on resume. Messages are only persisted at loop iteration boundaries and `wait_for` pauses — work done in the crashed iteration is lost from messages but exists in the event log. Fix: read the event log on resume and inject a `<recovery_context>` block (same pattern as `<task_context>` and `<active_delegations>`). See detailed design below. |
| ISS-009 | MCP error classification and agent-first error handling. See design below. |

**Key deliverables:**
- Failure notification for all channels and all failure paths (see ISS-001 design below)
- MCP error classification with agent-first error flow (see ISS-009 design below)
- Recovery context injection on resume (see ISS-006 design below)

### ISS-001 Design: Failure Notification

**What already exists:**

The infrastructure is partially built. `reply_context` (JSONB) is stored on every conversation row — populated by adapters on `start()`, updated when signals arrive. It's a discriminated union on `channel` with variants for Slack (`teamId`, `channelId`, `threadTs`), Linear (`issueId`, `agentSessionId`), and GitHub (`owner`, `repo`, `prNumber`).

`emitErrorActivity()` in `worker-loop.ts` already reads `reply_context` and calls Linear MCP directly on non-retryable failures (TokenBudgetExhausted, AgentAborted). The denormalizer in `shared/communication/denormalizer.ts` supports routing to all three channels.

**What's missing (the delta):**

1. **Channel coverage** — `emitErrorActivity()` hardcodes Linear agent sessions: `if channel !== "linear" || !agentSessionId return`. Slack and GitHub conversations that fail get no notification. Fix: route through the denormalizer instead of the Linear-specific path, so all channels are covered by the same codepath.

2. **Failure path coverage** — current code only notifies on non-retryable errors. When a conversation reaches `failed` after exhausting retries (the common case), no notification is sent. Fix: notify on all terminal `failed` status transitions, not just specific error types.

3. **`notification.failed` event** — current code is fire-and-forget with logging. If the notification MCP call itself fails (integration down, channel deleted), there's no visibility. Fix: emit a `notification.failed` event that the dashboard surfaces (Phase 4). The dashboard is the ultimate backstop — if the notification can't be sent, the failure still shows up somewhere.

**Design:**

```
Conversation reaches `failed` status (any path)
    ↓
Read conversation.reply_context
    ↓
Route through denormalizer with failure message
(includes: what the agent was working on, failure reason, retry count)
    ↓
Success → done (notification delivered)
Failure → emit `notification.failed` event + log (dashboard is backstop)
```

No secondary channel fallback. If the primary channel is unreachable, the failure appears on the dashboard. Revisit if/when workspace-level channel configuration exists (v2.9 or later).

**Dropped from original scope:**
- ~~Communication fallback (alternative channel when primary MCP is down)~~ — requires secondary channel infrastructure that doesn't exist. Dashboard is the backstop. Revisit if/when workspace-level channel configuration exists (v2.9 or later).

### ISS-009 Design: MCP Error Classification

**Two principles:**

1. **Infrastructure handles transient failures transparently.** The MCP client retries 5xx and 429 errors with backoff — this is standard resilient software design. The agent never sees a transient error that resolved on retry. A successful retry is invisible to the agent; it just gets its tool result slightly later.

2. **Unresolved errors are agent context, not infrastructure decisions.** When retries are exhausted or the error is permanent (4xx), the error flows back to the agent as a tool result with full context — status code, error message, what was attempted. The agent decides what to do. The infrastructure never swallows errors or makes recovery decisions on the agent's behalf.

**Classification (MCP client level):**

| Status | Classification | Infrastructure Behavior | Agent Sees |
|---|---|---|---|
| 2xx | Success | Return result | Tool result |
| 400, 401, 403, 404, 422 | Permanent | No retry — return immediately | Tool error with status, message, and context (e.g., "Linear issue LIN-456 not found (404)") |
| 429 | Transient (rate limit) | Retry with backoff, respect `Retry-After` header | Tool error only if retries exhausted — includes retry count and total wait time |
| 5xx | Transient (server error) | Retry with exponential backoff | Tool error only if retries exhausted — includes retry count and error details |
| Network error | Transient | Current behavior (fail immediately) | Tool error with connectivity context |

**What the agent does with errors is the agent's decision:**
- A 404 on `linear:get_issue` might mean the issue was deleted — the agent can skip it, report back, or try an alternative approach
- A 403 might mean missing permissions — the agent can flag this to the user rather than silently failing
- Exhausted retries on a 5xx might mean the integration is down — the agent can pause that line of work and continue with other tasks, or notify the user
- The agent may decide an error is fatal to its task and call `complete_task` with a failure status — that's the agent's call, not the infrastructure's

**When infrastructure DOES fail the conversation:**
Only when the error is completely outside agent control and unrecoverable at the conversation level — e.g., the Anthropic API itself is down (the agent can't reason if it can't think), or the agent has exceeded its max iterations. These are executor-domain concerns per the Agent-First Decision Checklist.

**Event emission:**
- `mcp.error` event for permanent errors (4xx) — includes tool name, status, error message
- `mcp.rate_limited` event for rate limits (429) — includes endpoint, backoff duration, retry count
- `mcp.retries_exhausted` event when transient retries are exhausted — includes tool name, total attempts, final error
- All events are for observability (Phase 4 dashboard). They do NOT change the error flow to the agent.

### ISS-006 Design: Recovery Context Injection

**The problem in detail:**

Messages are persisted at two points: (1) when the agent loop iteration completes, and (2) when `wait_for` pauses the conversation. Work done between persistence points — tool calls, sub-agent completions, reasoning — is lost from the message history if the conversation crashes. But the event log records all of it (tool.called, tool.succeeded, agent.started, agent.completed with `parent_instance_id`).

| What happened | In message history after crash? | In event log? |
|---------------|-------------------------------|---------------|
| Full loop iteration completed | Yes | Yes |
| `wait_for` pause | Yes | Yes |
| Sub-agent spawned and completed, parent crashed before iteration end | **No** | **Yes** |
| Tool calls made, parent crashed before iteration end | **No** | **Yes** |

The agent resumes with "Continue from where you left off" but doesn't know what was lost. It re-spawns sub-agents, re-reads files, re-explores — wasting tokens on work already done.

**The fix:**

On resume (when `isResumed = true`), read the event log for events that occurred after the last persisted message state. Build a `<recovery_context>` block and inject it before the resume message. This follows the existing pattern used by `<task_context>` and `<active_delegations>`.

**Implementation:**

1. **Determine the recovery boundary** — the event log sequence number corresponding to the last persisted state. On `wait_for` pause, the executor already emits `agent.paused` — its sequence number marks the boundary. On crash, use the highest sequence number from the last successful persistence (track this as `last_persisted_sequence` on the conversation row, or infer from the `agent.paused`/`agent.resumed` events).

2. **Query recovery events** — `SELECT * FROM agent_events WHERE conversation_id = ? AND sequence > ? ORDER BY sequence`. Filter for actionable event types:
   - `agent.completed` with `parent_instance_id` (sub-agent completions) — include agent type and output preview from payload
   - `tool.succeeded` (successful tool calls) — include tool name and output summary
   - `signal.received` (signals that arrived) — include signal type and data
   - Skip: `tool.called` (redundant with succeeded), `llm.response` (internal), `agent.started` for sub-agents (redundant with completed)

3. **Format as `<recovery_context>`** — structured text block:
   ```xml
   <recovery_context>
   This conversation was interrupted (retry #1 of 2) and is being resumed.

   The following work completed since your last checkpoint but is not in
   your message history. You do not need to repeat it:

   - Sub-agent "researcher" completed successfully:
     "Found auth middleware at src/middleware/auth.ts, uses JWT with RS256..."
   - Tool "github:get_pull_request" succeeded:
     PR #42, status: open, 3 files changed
   - Signal received: task_completion from dev-agent
     Task "implement auth endpoint" completed successfully

   Continue from where you left off, accounting for the above.
   </recovery_context>
   ```

4. **Inject into resume flow** — in `executeConversation()` where `isResumed = true` (around line 760 in worker-loop.ts), after the `agent.resumed` event emission. The recovery context becomes part of the user message that triggers the resumed agent loop, alongside task context and active delegations.

5. **Retry awareness** — include the retry count and the fact that this is a recovery in the context block. The agent can reason about whether to try a different approach ("last time I crashed while calling the GitHub API, maybe I should check connectivity first").

**What this does NOT change:**
- Message persistence frequency stays the same (at loop iteration boundaries and `wait_for`). More frequent persistence is orthogonal and can be considered separately if work loss remains a problem after recovery context is in place.
- The event log remains append-only and write-only during normal execution. Recovery context reads are only triggered on resume.
- No changes to history compaction. The `<recovery_context>` block is injected fresh on each resume, not persisted as part of the message history.

## Phase 4: Dashboard Observability

**Depends on**: Phase 3 (new event types from runtime resilience must exist before the dashboard can render them)

**Goal**: The dashboard tells the full story of what happened during a conversation. Anything important that currently lives only in logs should be emitted as a proper event and rendered in the timeline. The dashboard is the visibility tool — use it.

This phase has two layers: (1) **emit** events that currently only live in logs, and (2) **render** all events with proper grouping and attribution.

### Layer 1: Event Emission (framework)

Several important lifecycle moments are logged but not emitted as `agent_events`. Some are addressed by Phase 3 work; the remainder are Phase 4 deliverables.

| Event | Current State | Owned By |
|-------|--------------|----------|
| `agent.started`, `.resumed`, `.paused`, `.completed`, `.reopened` | Already emitted | Render only (Layer 2) |
| Sub-agent spawn/completion | Already emitted (`agent.started`/`.completed` with `parent_instance_id`) | Render only (Layer 2) |
| `mcp.error`, `mcp.rate_limited`, `mcp.retries_exhausted` | **Not tracked** | **Phase 3** (ISS-009 MCP error classification) |
| `notification.failed` | **Not tracked** | **Phase 3** (ISS-001 failure notification pipeline) |
| Stale heartbeat re-enqueue | **Logged only** (`worker-loop.ts` warnings) | **Phase 4** — emit `agent.stale_recovered` with `workerId`, `staleDuration`, `retryCount` |
| Retry attempts | **Partial** — `agent.completed` with `retrying: true` payload | **Phase 4** — emit dedicated `agent.retry_scheduled` with error context and retry count |

### Layer 2: Dashboard Rendering

| Issue | What |
|-------|------|
| ISS-008 | Render all lifecycle events in the timeline with distinct visual treatment — icons and color differentiation from tool events. Lifecycle events (started, paused, resumed, reopened, stale recovery, retry) should be visually distinct from tool call events. |
| ISS-012 | Tool call/result grouping — `tool.called` + `tool.succeeded`/`tool.failed` as single expandable card by `toolCallId`. Shows: tool name, duration, input (collapsed), output (collapsed). |
| ISS-013 | Sub-agent attribution — the schema already has `agent_definition_id`, `agent_instance_id`, and `parent_instance_id` on every event. Use these to visually separate orchestrator work from sub-agent work: agent name labels, indented/nested blocks, or color-coded lanes. |

**Key deliverables:**
- New event types emitted (Phase 4 owned): `agent.stale_recovered`, `agent.retry_scheduled`
- Dashboard renders ALL event types — including Phase 3's `mcp.*` and `notification.failed` events
- Lifecycle event rendering with distinct visual treatment (icon/color differentiation)
- Tool call grouping by `toolCallId` — single card with expandable details
- Sub-agent attribution — visual nesting or labeling using existing `parent_instance_id` relationship

## Phase 5: Work Correlation

**Depends on**: Phase 1 (quick fixes clear noise). Independent of Phases 3/4 — can run in parallel.

**Goal**: The platform has a formal concept of **work correlation** — the ability to answer "what work exists for entity X, and what state is it in?" This enables unified task trees, event-to-work matching, and a disposition vocabulary that the router and agents can use. ISS-016 (duplicate task trees) is the immediate symptom; work correlation is the underlying capability.

**Note**: This is a feature phase, not a bug fix. It establishes infrastructure and vocabulary that v3.0 agents will build intelligence on top of.

| Issue | What |
|-------|------|
| ISS-016 | Task tree should unify across trigger paths. Currently product-agent and dev-agent create independent root tasks for the same work when triggered via different paths (e.g., product-agent creates a task from Slack, dev-agent creates an independent task from the same Linear issue's webhook). |

### Concept Model

Work correlation has three parts:

**1. Registration** — when a conversation starts working on an external entity (Linear issue, GitHub PR, Slack thread), it registers that correlation. This is self-assignment formalized as a platform concept: the agent calls a tool, and the platform records `(entity_type, entity_id) → (conversation_id, agent_id, status)`.

**2. Query** — anything in the system can ask "what work exists for LIN-456?" and get back: conversation ID, agent, status (active/waiting/completed/failed), task tree, when it started. The router uses this to disposition incoming events. Agents use this to check before starting work. The dashboard uses this for entity-centric views.

**3. Disposition** — when a new event arrives about an entity with existing work, the system has formal vocabulary for what to do:

| Disposition | Meaning | When |
|---|---|---|
| `new` | No existing work — start fresh | No correlation found |
| `signal` | Deliver to active work | Correlation exists, conversation active/waiting |
| `retry` | Reopen failed work | Correlation exists, conversation failed |
| `supersede` | New work replaces old | Explicit re-assignment or scope change |
| `duplicate` | Suppress entirely | Same event ID (Layer 1) or agent echo (Layer 2) — handled by Phase 2 |

### Entity Reference on IncomingEvent

Adapters produce a standardized entity reference on every `IncomingEvent`: `{ entity_type, entity_id }`. Each integration decides how to build these from its events — Linear: `('linear_issue', issueId)`, GitHub: `('github_pr', '${owner}/${repo}#${prNumber}')`, Slack: `('slack_thread', '${channelId}:${threadTs}')`. This makes correlation lookups uniform across all integrations.

### Router Integration

Correlation augments the existing routing pipeline — it doesn't replace any part of it. The existing trigger matching (fast path) handles common cases. Correlation adds a fallback for events that don't match any trigger but ARE about an entity with active work:

```
Event arrives
    ↓
Phase 2 filters (event ID dedup, actor echo)
    ↓
Existing trigger matching (unchanged)
    ↓
No trigger match?
    ↓
Extract entity reference → correlation lookup
    ↓
Active work found → signal that conversation
No active work → slow_path or ignore (as today)
```

For ambiguous cases (failed or completed correlation), the event goes to the slow-path LLM with correlation data **pre-enriched in the context** — no new router tools needed. The LLM sees "Event: comment on LIN-456. Existing work: dev-agent conversation C-789, status: failed, started 2h ago" and decides between `retry`, `new`, or `ignore`.

### Multiple Active Correlations

When multiple conversations are correlated with the same entity (common in delegation chains — product-agent delegates to dev-agent, both relate to LIN-456):

**v2.8 approach: signal all active/waiting conversations.** Each agent receives the signal and decides relevance. This is agent-first — the platform doesn't guess which agent cares. In practice, most entities have one active conversation at the leaf; the orchestrator is typically `waiting`.

Some events carry their own routing hints independent of correlation state — e.g., comments with @mentions have a target recipient in the payload. These natural signals can refine routing in v3.0 when agents are smarter about declaring what they care about. For v2.8, broadcast to all correlated conversations and let agents reason about relevance.

### Infrastructure: Correlation Registry

A lightweight table linking external entities to active work:

```
work_correlations (
  entity_type    TEXT,       -- 'linear_issue', 'github_pr', 'slack_thread'
  entity_id      TEXT,       -- 'LIN-456', 'PR-42', 'T-abc123'
  conversation_id UUID,
  agent_id       TEXT,
  status         TEXT,       -- mirrors conversation status
  created_at     TIMESTAMPTZ,
  PRIMARY KEY (entity_type, entity_id, conversation_id)
)
```

Updated when conversations start (via self-assignment tool) and when conversation status changes (via executor lifecycle hooks). Query is a simple lookup — no vector search needed for "is anyone working on LIN-456?"

### Infrastructure: Dual-Mode Knowledge Query

The correlation registry handles entity-to-work lookups. The knowledge system needs a complementary upgrade for broader structured queries — "what do we know about the auth module?" with metadata filters.

**What exists:**
- Semantic search via pgvector embeddings
- Type filter (exact match on knowledge type)
- Topic filter (exact case-insensitive match)

**What's needed:**
- Metadata JSONB field on knowledge entries for structured data (issue IDs, PR numbers, branch names)
- Exact match queries on metadata fields (`WHERE metadata->>'issueId' = 'LIN-123'`)
- Query mode parameter: `semantic` (default, current behavior) vs `exact` (metadata WHERE clause)
- Combined mode: filter by metadata, then rank by semantic similarity within matches

### Agent Tools

- **`work:register`** — agent registers that it's working on an external entity. Writes to correlation registry. Called early in the conversation, after the agent identifies what it's working on. Agents need prompt guidance to use this tool consistently.
- **`work:query`** — agent checks if work exists for an entity. Returns correlation data. Used before starting new work ("is anyone already on this?"). The router uses the same underlying query internally (pre-enrichment) but does not expose it as a router tool.
- **Knowledge query extensions** — existing `knowledge:query` tool gains metadata filter and exact mode.

### What v3.0 Builds On Top

The work correlation infrastructure is deliberately minimal — registry, query, disposition vocabulary. v3.0 adds the agent intelligence:

- **Reconnaissance patterns** — agents proactively checking correlations before committing to action
- **Disposition judgment** — agents reasoning about when to signal vs supersede vs start fresh (beyond what the router handles)
- **Learning from outcomes** — adjusting behavior based on past correlation decisions

The platform provides the mechanisms and language. The agents provide the intelligence.

## Design Constraints

- All changes must be backward compatible — existing agent definitions and conversations continue working
- Resilience mechanisms are infrastructure, not agent behavior (per Agent-First Decision Checklist)
- Dashboard changes follow the design system in `.interface-design/system.md`
- Echo filtering (Layers 1-2) belongs at the adapter/dispatcher layer. Semantic dedup (Layer 3) uses work correlation — the router and agents reason about it, not deterministic filters
- Work correlation is platform infrastructure with minimal agent tooling — v3.0 adds the intelligence layer
- Do not deepen per-agent external identities — no new per-agent bot users, no agent-specific integration configurations. Unified external identity is a v3.0 target (see design vision)
