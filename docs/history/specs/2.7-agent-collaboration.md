## Phase 70: Linear Agent SDK Migration

**Goal**: The Linear integration uses Linear's native Agent SDK — agent activities replace comments, `actor=app` gives the agent its own identity, and the echo problem is eliminated by design.

**Depends on**: v2.6 complete

**Context**: Currently the agent communicates via `create_comment` using the installing user's OAuth token. This means agent comments appear as the user, echo filtering relies on `LINEAR_BOT_USER_ID` matching (brittle), and we miss Linear's first-class agent UX (activity types, session state, mention/assignment support). Linear's Agent SDK solves all three.

**References**:
- [Getting Started – Linear Agents](https://linear.app/developers/agents)
- [Agent Interaction – Linear Developers](https://linear.app/developers/agent-interaction)
- [OAuth Actor Authorization](https://linear.app/developers/oauth-actor-authorization)

### Requirements

| ID | Requirement |
|---|---|
| LSDK-01 | OAuth re-authorization with `actor=app` — agent gets its own workspace identity (name, icon), not the installing user's |
| LSDK-02 | New scopes `app:assignable` + `app:mentionable` — agent can be delegated issues and @mentioned |
| LSDK-03 | Agent activity MCP tools replace `create_comment` — `create_agent_activity` with typed content (`thought`, `response`, `elicitation`, `action`, `error`) |
| LSDK-04 | `agentSessionId` tracked from `agent_session.created` webhook through replyContext — denormalizer uses session ID for outbound activities |
| LSDK-05 | Communication tool to activity type mapping: `reply` → `response`, `ask` → `elicitation`, `notify(reasoning)` → `thought`, `notify(action)` → `action` |
| LSDK-06 | Inbound `agent_session.prompted` events replace `comment.created` for user follow-ups during active agent sessions |
| LSDK-07 | Echo filter (`LINEAR_BOT_USER_ID`) removed — agent activities and user prompts are different types, no filtering needed |

### Success Criteria

1. The agent appears in Linear's mention menu and can be assigned issues directly, with its own name and avatar (not the installing user's)
2. When the dev-agent replies via `communication:reply` with a Linear replyContext, the denormalizer calls `createAgentActivity` with type `response` (not `create_comment`)
3. When a user sends a follow-up message on an agent session, it arrives as `agent_session.prompted` — adapter extracts the prompt, router signals the active conversation
4. Agent session state is visible in Linear UI (active/complete/error) based on agent activity emissions
5. No echo filtering code exists for Linear — agent activities and user prompts are structurally distinct

### Open Design Questions

1. **ReplyContext shape** — `agentSessionId` needs to be in replyContext alongside `issueId`. The session ID comes from the `created` webhook but the agent needs it for every outbound message. Store in replyContext or conversation row?
   - **Resolution:** Store in replyContext. Session ID flows from webhook → adapter → replyContext JSONB → denormalizer. Already persisted in the `reply_context` column on conversations. No new table needed.

2. **Activity type classification** — `reply→response`, `ask→elicitation` is clean. Should `thought` activities be automatic (from `<reasoning>` blocks) or explicit (agent tool call)? Linear shows thoughts as ephemeral status updates.
   - **Resolution:** Explicit via tool mapping. The denormalizer maps communication intents to activity types. `<reasoning>` blocks can be emitted as thoughts automatically by the agent loop if configured, but the primary path is through communication tools.

3. **Product-agent** — Triggered from Slack, creates issues. No agent session. Still needs `create_comment` for issue comments, or just doesn't communicate via Linear?
   - **Resolution:** Product-agent continues using `create_comment` for issue comments (no agent session context). The denormalizer checks `replyContext.agentSessionId`: present → activity tools, absent → comment tools. Both paths coexist.

4. **Backward compatibility** — Support both `create_comment` and `createAgentActivity` during migration, or cut over?
   - **Resolution:** Hard cutover, not gradual. Atomic deployment: switch to `actor=app` + activity tools + remove echo filter in one release. Avoids MODERATE-2 (echo storm during migration period).

5. **Session lifecycle** — Agent should update session state (active → complete/error). Map to conversation lifecycle events?
   - **Resolution:** Map conversation lifecycle to Linear session states: `queued`→`pending`, `running`→`active`, `waiting`→`awaitingInput`, `completed`→`complete`, `failed`→`error`. Session state updated via `agentSessionUpdate` mutation.

6. **Error activity emission** — When a conversation fails (token budget exhausted, unrecoverable error), who emits the `error` activity type listed in LSDK-03?
   - **Resolution:** The conversation executor emits `error` activity before updating session state to `error`. This is infrastructure — the agent is already dead when these errors occur. Brief message (e.g., "Token budget exhausted"). Same pattern as the 10s acknowledgment thought: lifecycle events owned by infrastructure, not agent behavior.

## Phase 71: Shared Memory

**Goal**: Agents can store, classify, and query knowledge that persists across conversations — reducing redundant exploration and enabling context accumulation across the swarm.

**Depends on**: v2.6 complete

**Context**: Each agent conversation is isolated. When an agent discovers something (codebase structure, architecture decisions, constraints), that knowledge dies with the conversation. Task handoffs carry some context, but there's no persistent, queryable knowledge store. This means agents in a delegation chain repeatedly re-discover the same things, wasting token budget on redundant exploration. Shared memory provides the institutional knowledge that human teams build naturally through docs, wikis, and conversation history.

### Requirements

| ID | Requirement |
|---|---|
| MEM-01 | Knowledge classification system — entries are typed (e.g., `discovery`, `architecture_decision`, `constraint`, `thought`) with metadata (expiry, author agent, scope). Confidence scoring deferred — agents are poor at self-calibrating confidence for v1. |
| MEM-02 | Private agent memory (notepad) — working memory that persists across an agent's conversation turns but is not shared with other agents |
| MEM-03 | Shared knowledge store — classified entries accessible by all agents, queryable by topic/type/relevance |
| MEM-04 | MCP tools for memory operations — `knowledge:store`, `knowledge:query`, `knowledge:update` exposed as standard agent tools |
| MEM-05 | Scope and permissions — sensible defaults: shared (discovery, constraint, architecture_decision, preference, test_result) and private (thought). Hardcoded for v1 — YAML-based scope overrides deferred until real override needs emerge. Not a policy engine. |
| MEM-06 | Storage abstraction — pgvector in PostgreSQL for semantic search + structured metadata queries. Single table, dual-indexed. No separate vector DB. Provider-agnostic embedding interface (`EMBEDDING_PROVIDER=ollama|voyage`) with configurable dimensions. |
| MEM-07 | Knowledge lifecycle — entries have mandatory expiry by category (discoveries 24h, architecture_decisions 7d, constraints 30d, thoughts 24h, preferences 30d). Entries can be superseded or explicitly invalidated. |

### Additional Requirements (from research)

| ID | Requirement | Source |
|---|---|---|
| MEM-08 | Knowledge deduplication — before storing, query existing entries on same topic and supersede rather than duplicate. Prevents knowledge store becoming a token sink. | HIGH-6 |
| MEM-09 | Graceful degradation — `knowledge:query` returns empty results on connection failure, never crashes agent loop. `knowledge:store` failures are non-fatal. | Design constraint |
| MEM-10 | Classification taxonomy: fixed set of 6 types (discovery, constraint, architecture_decision, thought, preference, test_result). Expand based on usage data, not speculation. | MODERATE-6 |

### Success Criteria

1. An agent stores a discovery ("auth middleware uses JWT, located at src/middleware/auth.ts") and a subsequent agent in a different conversation queries "what do we know about auth?" and retrieves it
2. Private notepad entries are only visible to the authoring agent's conversations — other agents cannot query them
3. Knowledge entries carry classification metadata (type, expiry, author) that scope defaults can act on. Confidence deferred.
4. ~~User can configure scope policies (e.g., "all discoveries are shared", "thoughts stay private") without code changes~~ *(deferred — hardcoded defaults sufficient for v1, YAML overrides added when real override needs emerge)*
5. Expired or invalidated knowledge is excluded from query results

### Open Design Questions

1. **Storage backends** — Vector DB (pgvector? dedicated service?) for semantic queries, Postgres for structured facts, or a unified store with multiple indexes? Start with one and expand, or design multi-backend from day one?
   - **Resolution:** pgvector in existing PostgreSQL. Single table (`agents.knowledge_entries`) dual-indexed: structured metadata columns (type, scope, author, expiry) + HNSW index on vector embeddings for semantic search. No separate vector DB — operational simplicity for moderate volume (hundreds to low thousands of entries). Docker image swap from `postgres:15-alpine` to `pgvector/pgvector:pg15`.

2. **Knowledge granularity** — Per-workspace? Per-project? Per-agent-type? A discovery about "the auth system" might be relevant to dev-agent but noise for product-agent.
   - **Resolution:** Per-workspace for v1. Project and agent-type scoping deferred. The type and topic fields enable filtering at query time without schema complexity.

3. **Conflict resolution** — Two agents store contradictory facts about the same topic. Last-write-wins? Confidence-based? Flag for human review?
   - **Resolution:** Deduplication + supersession (MEM-08). Before storing, query existing entries on same topic and supersede. No voting or confidence-based conflict resolution for v1. Contradictions surface naturally through expiry — stale entries die, fresh entries survive.

4. **Curation mechanism** — Beyond expiry, should there be active curation (agent or human reviews and prunes)? Or is passive decay sufficient for v1?
   - **Resolution:** Passive decay via mandatory expiry (MEM-07) for v1. Active curation deferred. Log entries that hit expiry without supersession to inform whether active curation is needed.

5. **Classification taxonomy** — Fixed set of types or extensible? Too few types and everything is a `discovery`; too many and agents miscategorize.
   - **Resolution:** Fixed set of 6 types: discovery, constraint, architecture_decision, thought, preference, test_result. Each type has clear examples in agent prompts. Expand based on usage data (log unclassified entries) not speculation.

6. **Embedding provider** — Voyage AI was the initial choice (Anthropic alignment, 1024 dims). Should the embedding layer be provider-specific or swappable?
   - **Resolution:** Provider-agnostic interface with explicit switching via `EMBEDDING_PROVIDER=ollama|voyage` env var. Ollama (local Docker service) for development, Voyage AI for production. Validated at startup: `ollama` requires `OLLAMA_URL`, `voyage` requires `VOYAGE_API_KEY`. Vector dimension configurable via `EMBEDDING_DIMENSIONS` (e.g., 768 for Ollama, 1024 for Voyage AI). No auto-detection — explicit provider selection prevents silent fallback.

| Plan | Scope |
|---|---|
| 71-01 | Knowledge schema design + classification taxonomy + storage layer (Postgres + pgvector, Docker image swap) |
| 71-02 | MCP tools (`knowledge:store`, `knowledge:query`, `knowledge:update`) + deduplication logic |
| 71-03 | Private notepad (agent-scoped memory) + scope/permission defaults (hardcoded) |
| 71-04 | Agent prompt updates — teach agents when and how to store/query knowledge |

## Phase 72: Entity Directory

**Goal**: Agents can discover other agents by capability — enabling informed delegation decisions based on who exists in the system and what they can do.

**Depends on**: Phase 70 (Linear Agent SDK — agent identity must be resolved before directory exposes agents)

**Context**: For agents to delegate work, they need to know who can help. Currently, agent definitions exist as YAML files on disk. There's no queryable registry that an agent can search to answer "who can implement code changes?" The directory provides service discovery for the agent swarm.

### Requirements

| ID | Requirement |
|---|---|
| DIR-01 | Entity table in database — stores agents with type, capabilities, status, and metadata. Schema supports `type='human'` and `reach_via` JSONB for future human entries. |
| DIR-02 | Agent seeding from YAML — `pnpm seed:directory` reads agent definitions, extracts `id`, `name`, `description`, and new `capabilities` field, seeds to directory table. Only agents with a `capabilities` field are seeded — sub-agents (coder, researcher, tester) are excluded as they are spawned internally, not delegated to. |
| DIR-03 | Human entries — manually configured (seed script or admin UI). Includes name, role, capabilities, and reachVia (channel type + target, e.g., `{ channel: "slack", target: "#aesir-dev" }`) |
| DIR-04 | Capability-based query tool — `directory:find` accepts a capability description ("implement code changes", "approve architecture decisions") and returns matching entities ranked by relevance |
| DIR-05 | Entity detail tool — `directory:get` returns full profile for a specific entity (capabilities, reachability, type) |
| DIR-06 | Capabilities declared in definition.yaml — new `capabilities` field (list of natural language strings) describing what the agent can do at an intent level, not tool level |

### Additional Requirements (from research)

| ID | Requirement | Source |
|---|---|---|
| DIR-07 | Semantic capability matching via pgvector — reuse Phase 71's embedding pipeline (Voyage AI, 1024 dimensions). Embed combined capabilities text at seed time. | ARCHITECTURE |
| DIR-08 | Idempotent seed script — `ON CONFLICT DO UPDATE` with `last_seeded_at` timestamp. Agents removed from YAML are marked `status='inactive'` (scoped to `type='agent'`, won't affect future human entries). Safe for concurrent deployments. | MINOR-3 |
| DIR-09 | Graceful degradation — `directory:find` returns empty results on failure, agents fall back to self-execution. | Design constraint |

### Scope Reductions

| Original | Decision | Rationale |
|---|---|---|
| DIR-03: Human entries | **Deferred** | Human entries add cascading complexity to delegation (Slack dispatch, async handshake, human response parsing). Schema is human-ready (`type='human'`, `reach_via` JSONB) but human seeding and human-targeted delegation deferred to future milestone. |
| Success criteria 2, 4, 5 (human-related) | **Deferred** | Success criteria referencing human entries do not apply for v2.7. Agent-only validation. |

### Success Criteria

1. An agent calls `directory:find` with "implement code changes and open pull requests" and receives dev-agent as the top result
2. ~~An agent calls `directory:find` with "approve design decisions" and receives human entries with appropriate Slack reachability~~ *(deferred — human entries)*
3. Agent definitions include a `capabilities` field that is seeded to the directory table via `pnpm seed:directory`
4. ~~Human entries exist in the directory with reachVia pointing to Slack channels~~ *(deferred — human entries)*
5. ~~Directory queries return both agents and humans — the delegating agent chooses based on capability match, not entity type~~ *(deferred — agent-only for v2.7)*

### Open Design Questions

1. **Capability matching** — Exact text match, keyword search, or semantic similarity (vector search)? Semantic is more flexible but adds complexity. Keyword + description search may be sufficient for v1.
   - **Resolution:** Semantic similarity via pgvector. Phase 71 introduces pgvector and the Voyage AI embedding pipeline. Reuse for directory capabilities — marginal incremental cost. Embed combined capabilities text at seed time, query with cosine similarity. One matching approach across knowledge + directory.

2. **Availability/capacity** — Should the directory reflect whether an agent is currently busy? Or assume all agents are always available? For v1, always-available is simpler.
   - **Resolution:** Assume always-available for v1. Agents are services, not employees. The conversation executor handles concurrency. Add availability tracking when directory grows past ~20 entities.

3. **Human reachVia extensibility** — Start with Slack only (user's constraint), but the schema should accommodate Linear, email, etc. later. `reachVia` as a typed JSON field?
   - **Resolution:** `reach_via` JSONB in schema, supporting multiple channel types. Human entries deferred but schema is ready. When humans are added, reachVia drives materialization dispatch.

4. **Directory staleness** — Agents change over time (new capabilities, deprecated ones). Re-seed on deploy? Or watch for YAML changes?
   - **Resolution:** Re-seed on every deploy. Idempotent seed script (`ON CONFLICT DO UPDATE`) with `last_seeded_at` timestamp. Negotiation handshake (Phase 73) validates directory claims at runtime — stale capabilities caught by rejection.

## Phase 73: Task Delegation

**Goal**: Agents can delegate work to other agents through tasks, with a negotiation handshake that gives the delegator agency over whether to wait, pivot, or escalate.

**Depends on**: Phase 72 (Entity Directory — agents need to discover who to delegate to)

**Context**: Currently, work flows through external systems: product-agent creates a Linear ticket, a human assigns it, dev-agent picks it up via webhook. This works but requires human intervention at every handoff. Task delegation generalizes this — an agent can send a task to another agent from the directory, the task materializes as a new conversation, and a negotiation handshake ensures the delegator maintains agency over the work.

The delegation mechanism extracts the protocol that tickets already encode (deadline, priority, assignee, status, back-and-forth) and makes it medium-agnostic.

### Requirements

| ID | Requirement |
|---|---|
| DEL-01 | `task:delegate` tool — creates a task targeting an entity from the directory, with description, expectations (priority, estimated effort), and context from shared memory |
| DEL-02 | Task tree structure — delegated tasks carry `parentTaskId`, forming a tree from root task through all subtasks. Enables tracing the full delegation chain |
| DEL-03 | Negotiation handshake — target entity responds to delegation with accept (+ estimate), reject (+ reason), or counter-propose. Delegator decides: proceed, cancel, or try someone else |
| DEL-04 | Handshake abstraction — the negotiation protocol is a strategy that can be swapped. v1: simple accept/reject with estimate. Interface supports richer strategies later (counter-propose, redirect, partial accept) |
| DEL-05 | Materialization layer — task delivery adapts to recipient type. Agent → internal conversation start/signal. Human → Slack message (v1), with schema supporting Linear ticket, email, etc. later |
| DEL-06 | Materialization as policy — whether delegation creates an external artifact (Linear ticket) or stays internal is a prompt-level decision, not hardcoded. Teams configure their preferred transparency |
| DEL-07 | Delegation judgment guidance — agent prompts include criteria for when delegation is worth the overhead vs. doing the work directly. Prevents over-delegation / management-layer anti-pattern. Key distinction: **sub-agent spawn** (work is part of your capability, sub-agent defined in your YAML, shared budget, same conversation) vs **task delegation** (work requires a different agent's capability, discovered via directory, separate conversation and budget). If it's in your `subAgents` list, spawn. If you need `directory:find`, delegate. |

### Additional Requirements (from research)

| ID | Requirement | Source |
|---|---|---|
| DEL-08 | Handshake timeout (30s default, configurable) separate from task timeout. Timeout treated as rejection — delegator pivots to next entity. | MODERATE-1 |
| DEL-09 | Maximum task delegation depth reduced to 3 for v1 (orchestrator → orchestrator → sub-agent). Increase only with evidence. | CRITICAL-2 |
| DEL-10 | Focused brief — delegated tasks carry task description + expectations + knowledge references, not full message history. Target queries shared memory independently. | Anti-pattern |

### Scope Reductions

| Original | Decision | Rationale |
|---|---|---|
| DEL-03: Counter-propose in handshake | **Deferred** | Accept/reject covers 90% of delegation scenarios. Counter-propose adds protocol complexity for edge cases. Strategy abstraction interface enables future addition without refactoring. |
| DEL-05: Human materialization (Slack) | **Deferred** | Human entries deferred from directory (Phase 72). Without human targets, materialization is agent-only: single path via `executor.start()`. |
| DEL-06: Materialization as policy | **Deferred** | With only agent targets and only internal materialization, there's no policy choice to make. Keep the abstraction boundary (extensible interface) so adding transparent mode later is a new implementation, not a refactor. |
| Success criteria 2 (human delegation) | **Deferred** | Human-targeted delegation depends on human directory entries. |
| Success criteria 5 (materialization modes) | **Deferred** | Only one materialization path in v2.7 (internal). |

### Success Criteria

1. Product-agent discovers dev-agent via directory, delegates a task ("implement this feature"), dev-agent accepts with an estimate, and work begins in a new conversation linked as a subtask
2. ~~An agent delegates to a human — the task materializes as a Slack message in the human's channel with context and expectations~~ *(deferred — human delegation)*
3. A delegated-to agent rejects a task with a reason ("this requires database access, I don't have that capability") and the delegator pivots to another entity
4. Task tree is queryable — given a root task, all subtasks and their conversations are retrievable
5. ~~The same delegation flow works with materialization as a Linear ticket (prompt-configured) or as an internal handoff — no code change required~~ *(deferred — single materialization path)*

### Open Design Questions

1. **Internal materialization mechanics** — Agent-to-agent delegation without external artifacts. Does the delegating agent call `start()` directly (via a tool), or does the system handle it? The tool creates the task, the materialization layer calls `start()` with the task as context?
   - **Resolution:** `task:delegate` creates the task, thin materialization layer calls `executor.start()` with taskId. v1 implementation is a single-method interface with one path. Extensible for future materialization targets (Slack, Linear) without refactoring the delegation tool.

2. **Context passing** — The task description is the brief. Should it also include a reference to relevant shared memory entries, or does the target agent query memory independently?
   - **Resolution:** Task description is the brief + optional knowledge references. Target agent queries shared memory independently for additional context. No full message history on handoff — self-service context retrieval.

3. **Parallel delegation** — Can an agent delegate to multiple entities simultaneously (fan-out)? If so, how does it handle partial completions?
   - **Resolution:** Sequential only for v1. Parallel delegation adds partial-completion ambiguity (HIGH-1). Task groups with completion policies (all_required, any_sufficient, majority) deferred to future milestone (ASIG-02).

4. **Delegation depth limits** — For v1, scope rules (product-agent → dev-agent, not reverse). But the system should track depth for future cycle detection.
   - **Resolution:** Max depth 3 for v1 (orchestrator → orchestrator → sub-agent is natural maximum). Existing `MAX_TASK_DEPTH` reduced from 5. Track depth on task table. Increase only with evidence of legitimate deeper chains.

5. **Human response format** — When a human receives a delegated task via Slack, how do they accept/reject? Slack buttons (like existing approval flow)? Free-text reply?
   - **Resolution:** Deferred. Human entries not in v2.7 directory. When added, likely Slack buttons (existing approval pattern) for accept/reject + free-text for counter-propose.

6. **Delegation tool blocking behavior** — Should `task:delegate` block until the handshake completes, or return immediately?
   - **Resolution:** Async — `task:delegate` returns immediately with the task ID after creating the task and starting the target conversation. The delegating agent then calls `wait_for` separately to pause for the handshake signal. The target agent's `task:respond` (accept/reject) fires a signal back to the delegator. This composes with existing `wait_for` + signal infrastructure rather than introducing a new blocking mechanism. DEL-08's 30s handshake timeout maps to the `wait_for` timeout. Future-proofs for human delegation where handshake response times are minutes/hours, not seconds.

|---|---|

| 73-02 | `task:delegate` tool + materialization layer (agent-only, single path via `executor.start()`) |

## Phase 74: Completion Signaling

**Goal**: When a delegated task completes (or fails), the delegating agent is notified and can resume work — closing the collaboration loop.

**Depends on**: Phase 73 (Task Delegation — signals need tasks to signal about)

**Context**: This is the hardest part of the collaboration system. The delegator pauses via `wait_for` while the target works. When the target finishes, a signal must route back to the delegator's waiting conversation with results. Multiple completion sources exist (agent reports done, PR merged, timeout exceeded) and edge cases are numerous (partial completion, target needs clarification, delegator's conversation expired). The existing signal infrastructure (`wait_for`, `signal()`, domain-typed signals) provides the foundation, but task-lifecycle-driven signaling is new.

### Requirements

| ID | Requirement |
|---|---|
| SIG-01 | Task completion signal — when a delegated task is marked complete, the system fires a signal to the delegating conversation with task results and completion summary |
| SIG-02 | Task failure signal — when a delegated task fails, the delegating agent receives a failure signal with reason, enabling retry with a different entity or escalation |
| SIG-03 | Callback routing — delegated tasks carry `callbackConversationId` so the system knows which conversation to signal on completion |
| SIG-04 | Multiple completion sources — completion can be triggered by: agent marking task done, external event (PR merged), or timeout. All route through the same signal mechanism |
| SIG-05 | Clarification signal — target agent can signal back to the delegator requesting more information. Delegator wakes, responds, pauses again. Bidirectional conversation mediated by tasks |
| SIG-06 | Expectation-based timeout — delegator sets expectations during handshake ("need this in 10 minutes"). If the estimate passes without completion, delegator receives a timeout signal and decides: keep waiting, cancel, or escalate |
| SIG-07 | Orphan handling — if the delegating conversation is no longer active (errored, garbage-collected), completion signals are logged but not lost. Dashboard shows orphaned completions |

### Additional Requirements (from research)

| ID | Requirement | Source |
|---|---|---|
| SIG-08 | Multi-type `wait_for` — `pending_wait.types` accepts array of signal types. Signal matching checks membership. Prevents CRITICAL-3 deadlock where delegator is deaf to unexpected signal types. | CRITICAL-3 |
| SIG-09 | `wait_for_task` variant — auto-registers for all task-lifecycle signal types (completion, failure, timeout) so agents cannot forget to listen for failure/timeout. | CRITICAL-3 |
| SIG-10 | Callback routing through tasks — resolve latest active conversation for parent task, not static conversation IDs. Survives conversation re-trigger (HIGH-3). | HIGH-3 |
| SIG-11 | Orphan-safe result storage — `completion_result` JSONB column on tasks stores results regardless of callback conversation state. Work product never lost. | CRITICAL-1 |
| SIG-12 | Delegation context preservation — `active_delegations` JSONB column on conversations survives history compaction. Self-contained signal payloads include original task description and results. Delegation context block injected on resume. | HIGH-4 |

### Scope Reductions

| Original | Decision | Rationale |
|---|---|---|
| SIG-05: Bidirectional clarification signal | **Deferred** | Highest complexity piece. With humans deferred, the primary clarification scenario (agent asks human) doesn't exist. Agent-to-agent delegation should include sufficient context in the brief. Multi-type `wait_for` (SIG-08) ships the infrastructure needed — adding clarification flow later is a new signal type + tool, not a refactor. Deferred as ASIG-01. |
| Success criteria 3 (clarification) | **Deferred** | Depends on bidirectional clarification signal. |

### Success Criteria

1. Dev-agent completes a delegated task → product-agent's waiting conversation resumes with the completion results
2. Dev-agent fails → product-agent receives a failure signal, queries directory for alternatives, and re-delegates
3. ~~Dev-agent needs clarification → signals back to product-agent, which wakes, answers via the task, and pauses again~~ *(deferred — bidirectional clarification)*
4. A delegated task exceeds its estimated time → delegator receives a timeout signal and decides to keep waiting or cancel
5. Completion signals for conversations that no longer exist are logged in agent_events and visible in the dashboard

### Open Design Questions

1. **Signal payload shape** — What does a completion signal carry? Just "done + summary" or structured results (artifacts produced, files changed, PR URL)?
   - **Resolution:** Self-contained structured payload: original task description, expected outcomes, results, and artifacts (PR URL, branch name, files changed). Agent should be able to resume from signal payload alone without relying on conversation history. This addresses HIGH-4 (history compaction destroys delegation context).

2. **Partial completion** — Target agent made progress but can't finish. Cancel and return partial results? Or hand off to someone else with accumulated context?
   - **Resolution:** For v1, sequential delegation only avoids partial-completion ambiguity. Failed tasks carry partial results in the failure signal payload. Delegator decides: retry with different entity, escalate, or accept partial. Task groups with completion policies deferred (ASIG-02).

3. **Cascading failures** — A → B → C delegation chain. C fails. B handles it (retries with D). Does A know about C's failure, or only B's eventual resolution? Probably only B's — each level manages its own subtree.
   - **Resolution:** Confirmed — each level manages its own subtree. A sees only B's final result (success or failure), not C's intermediate failures. This keeps the signal model simple and prevents noise propagation up the tree.

4. **Resume context** — When the delegator wakes up after a long wait, how much context does it need to re-establish? History manager may have compacted. Shared memory helps, but the signal payload should be self-contained enough to resume.
   - **Resolution:** Three mechanisms: (1) self-contained signal payloads with original task + results, (2) `active_delegations` JSONB column on conversations survives compaction, (3) delegation context block injected on resume (analogous to `<task_context>`). Agent resumes from signal + context block, not from compacted history.

5. **Expectation-based timeout mechanism** — SIG-06 says "handshake estimate feeds pg-boss delayed signal." Should the system automatically parse the estimate and schedule a timeout, or should the agent set the timeout?
   - **Resolution:** Agent-driven. The handshake estimate is free-text context ("~15 minutes", "2 tool calls"), not a machine-parseable duration. The delegating agent interprets the estimate, applies its own judgment about appropriate patience (buffer, urgency, task complexity), and sets the `wait_for` timeout accordingly. That timeout feeds pg-boss via the existing timeout scheduler. No estimate-parsing infrastructure in the framework — this is semantic reasoning that belongs to the agent (agent-first principle).

## Phase 76: QA Agent + Validation Workflow

**Goal**: A lightweight QA orchestrator agent exercises the full collaboration system end-to-end — proving directory discovery, task delegation, negotiation handshake, completion signaling, shared memory, and delegation graph observability work together in a real multi-agent workflow.

**Depends on**: Phase 75 (Delegation Graph Observability — all collaboration infrastructure must be in place)

**Context**: The collaboration infrastructure (Phases 71–75) is general-purpose, but validating it with only the existing product-agent → dev-agent pipeline tests a two-node linear flow. The interesting failure modes — feedback loops, competing subtasks, delegation depth, shared memory across unrelated conversations — only emerge with three or more participants. The QA agent is not a production-grade test system — it's a validation vehicle that creates a triangular workflow exercising every collaboration primitive.

### The Validation Workflow

```
Product-agent ──delegates──→ Dev-agent ──delegates──→ QA-agent
                                 ↑                        │
                                 └──delegates fix back────┘
```

1. Product-agent receives a feature request, delegates implementation to dev-agent (directory query, handshake, materialization)
2. Dev-agent implements and delegates verification to QA-agent (second-level delegation, task tree grows)
3. QA-agent runs tests, checks PR against requirements
4. **Pass**: QA-agent signals completion → dev-agent resumes → signals completion → product-agent resumes
5. **Fail**: QA-agent delegates a fix back to dev-agent (feedback loop, third-level delegation) → dev-agent fixes → re-delegates to QA → pass → completion chain unwinds

This single workflow exercises: directory queries (3 lookups), delegation handshake (3+ negotiations), materialization (internal), completion signaling (success + failure + re-delegation), shared memory (QA stores test results, dev queries known failures), and a task tree 3 levels deep.

### Requirements

| ID | Requirement |
|---|---|
| QA-01 | QA agent definition — orchestrator-level agent with `capabilities` declared in definition.yaml, registered in entity directory |
| QA-02 | Core tools — thin wrappers for running tests (sandbox) and reviewing PR diffs (GitHub MCP). Not production-grade test analysis. |
| QA-03 | Collaboration tools — `directory:find`, `directory:get`, `task:delegate`, `knowledge:store`, `knowledge:query`, plus standard communication tools (reply/ask/notify) |
| QA-04 | Delegation acceptance — QA agent participates in negotiation handshake (accepts verification tasks with time estimates, rejects tasks outside its capability) |
| QA-05 | Feedback loop — when tests fail, QA agent delegates a fix task back to dev-agent with failure details, test output, and relevant knowledge entries. Waits for completion signal |
| QA-06 | Knowledge contribution — QA agent stores test results, discovered regressions, and known-failure patterns in shared memory for future QA runs and dev-agent reference |
| QA-07 | Validation test suite — integration tests that run the full triangular workflow end-to-end, asserting: task tree structure, signal delivery, knowledge entries, delegation graph |

### Scope Reductions

| Original | Decision | Rationale |
|---|---|---|
| QA-07: Comprehensive test suite | **Reduced** | One happy-path live validation run (not automated Vitest). Deploy all agents, trigger a controlled feature request, observe the triangular workflow completes via dashboard + database inspection. Real agents with real LLM reasoning against real infrastructure — no mock choreography. Documented validation procedure, not a test file. Comprehensive multi-agent test harness deferred (PQA-03). |
| QA-02: Production QA tools | **Reduced** | Thin wrappers only: run test command, read PR diff. Sophisticated test analysis, coverage reporting, regression detection deferred to production QA milestone (PQA-01, PQA-02). |

### Success Criteria

1. The full product → dev → QA → (fix) → QA → complete workflow runs end-to-end with correct task tree structure
2. QA agent appears in directory and is discoverable by dev-agent via capability query ("verify code changes and run tests")
3. QA agent negotiates handshake — accepts with estimate when given a PR to review, rejects when given tasks outside its capability
4. Failed tests trigger a delegation back to dev-agent — the feedback loop completes and the task tree shows the re-delegation
5. Knowledge entries from QA runs are queryable by subsequent agents ("what test failures have we seen in the auth module?")
6. The delegation graph in the dashboard renders the full 3-level tree with all signals visible

### Open Design Questions

1. **Test execution environment** — Does QA agent run tests in the same dev container as dev-agent, or does it need its own sandbox? Shared container is simpler for v1, separate container is more realistic.
   - **Resolution:** Shared sandbox. QA runs tests in the same container dev-agent used — the branch, code, and dependencies are already there. QA's tool call is `codebase:run_command` targeting the same workspace. No second container, no re-clone, no re-install. QA is read-only (run tests, read diff) — no risk of corrupting the workspace. Isolated environments for reproducibility are production QA territory (v2.8+).
2. **Requirements source** — QA agent checks "against requirements." Where do these come from? The delegated task description? Shared memory? The original Linear ticket? All three?
   - **Resolution:** Two thin checks. (1) Run the test command — binary pass/fail from exit code, no output parsing or coverage analysis. (2) Diff sanity check — read PR diff via GitHub MCP, LLM-judge whether the diff plausibly addresses the delegation brief. Requirements source is the delegation brief (task description + expectations from `task:delegate`), not the original Linear ticket. QA agent can query shared memory for supplementary context but the brief is the contract. No structured rubrics, coverage thresholds, or regression detection (PQA-01/02 territory).
3. **Retry limits** — How many fail → fix → retest cycles before QA agent escalates to a human? Prompt-guided judgment or hard limit?
   - **Resolution:** Hard limit of 2 fix cycles, enforced by delegation depth (DEL-09 max depth 3), not a separate retry counter. In the triangular workflow: product(1)→dev(2)→QA(3)→dev-fix(4) is the first attempt. A second fix would be depth 5, blocked by the framework. When QA cannot delegate another fix, it signals failure back to dev-agent with accumulated context (what was tried, remaining failures). Each level manages its own subtree. Sufficient for a validation vehicle — increase depth limit when production QA needs more cycles.
4. **Scope for v2.8** — This agent is a validation vehicle. What does a production QA agent look like? Continuous test monitoring, regression detection, test coverage analysis? Document the expansion path.

## Design Constraints

These apply across all phases:

**Graceful degradation** — Collaboration enhances, isolation still works. If the directory is unreachable, agents continue solo. If completion signaling fails, delegators eventually timeout rather than hang forever. If the knowledge store is down, agents work without shared context (higher token cost, not a hard failure). Each collaboration primitive is best-effort — agents should catalog failures in knowledge for future reference and fail cleanly when collaboration is truly impossible.
