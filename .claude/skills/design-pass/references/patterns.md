# Pattern index

Problem shapes that recur in a platform like aesir, the patterns worth weighing for each, the question that decides between them, and what each costs. An index, not a menu: the pattern card in the note still has to say why the pattern applies here and where it already appears. "No pattern" is a row because most problems are local.

| Problem shape | Candidates | The deciding question | Cost, and when not |
|---|---|---|---|
| A switch or if-chain selects among slightly different implementations by a discriminator (`provider`, `channel`, `type`) | **Strategy** (one interface, one object per variant); **registry + factory** (variants registered by key, chosen by data); **table-driven dispatch** (a map of key to function); **discriminated union with an exhaustive switch** when the variants are data and the set is closed (`sk-typescript.md`) | Is the set of variants open, added by config or a new package (registry), or closed and known at compile time (union)? Do variants carry state or lifecycle (strategy object) or are they one function each (table)? | A registration step and a "not found" path; one more file per variant. Not for two variants with no third in sight: the third occurrence is when the abstraction becomes mandatory. |
| A second source or target of a kind that already exists (tracker, channel, embedding provider) | **Adapter** (normalise in, denormalise out, one per vendor); **port and adapter** (the core speaks domain vocabulary, vendors live at the edges) | Does the core already speak the vendor's names? If yes, the port is the finding, and the second vendor is when you name the domain events. | A translation layer to keep in sync; a legacy variant while stored data migrates. In aesir: `packages/agents/src/adapters/`, the signal type map, `ReplyContext` as an opaque address. |
| Multi-step work across services or tables that must not half-complete (create the task, notify the tracker, start the conversation) | **Saga**, orchestrated (one coordinator holds the steps and their compensations) or choreographed (each participant reacts to events and compensates itself); **transactional outbox** (write the event with the state change in one transaction, a relay publishes it); **idempotency keys** (the second delivery is a no-op); **two-phase commit** only inside one database | Can every step be compensated, or must the whole thing be atomic (then keep it inside one database transaction)? Who needs to see a half-done state, and where: an orchestrator gives one place to look, choreography gives none. | Compensation logic per step; eventual consistency visible to readers; the outbox needs a relay and a dedupe on the consumer. In aesir: the event log as ground truth, `start()` idempotent on `correlationKey`, pg-boss delayed signals, `SKIP LOCKED` claims with heartbeats. |
| A record with a lifecycle: statuses mutated ad hoc from several places | **Explicit state machine** (states, transitions, guards, one place that applies them); **event-sourced projection** (the log is the truth, the status table is derived and rebuildable) | Who writes each field, and can the state be rebuilt from events? If two lifecycles share one record, split the record before adding states. | A transition table to maintain; projections lag and need a catch-up path. In aesir: `SessionProjection` over the event log; conversation `queued / running / waiting / completed`. |
| The same external call may run twice (retry after success, duplicate webhook) | **Idempotency key** or **natural key + upsert**; at-least-once delivery with a dedupe on the consumer | Is there a natural key (issue id, delivery id, correlation key)? If not, mint one before the first call and store it with the intent. | A key store and its retention. Never "exactly once" across a network; design for the duplicate. In aesir: webhook dedupe namespaced by source; `{agent}-{correlationKey}` conversation ids. |
| A cross-cutting concern creeping into every function (logging, timing, retries, auth, budget checks) | **Decorator / middleware / interceptor** at one boundary (the tool-call path, the HTTP layer, the LLM call) | Does the concern need per-call configuration, or is it uniform? Uniform goes in one wrapper; per-call goes in the options of the thing being wrapped. | Hidden control flow: a reader has to know the wrapper exists. Name it where the wrapped call is made. |
| A component with several collaborators, some optional | **Factory function with an options object, fail fast on the required ones** (aesir's DI convention, `AGENTS.md` §Dependency Injection); never a service locator or a module-level global | Is the collaborator required for the instance to be valid? Then it is a constructor argument, not a setter, and its absence is an error at construction. | An options type to keep honest. Not a framework: the factory is a function, the interface is exported next to it. |
| A function steered by booleans or a long parameter list | **Parameter object**; **discriminated options** (`{ mode: "a", ... } | { mode: "b", ... }`); **separate functions** when the flags never combine | Do the flags combine independently (options object) or select one of a few shapes (discriminated options) or never combine (two functions)? | A type to keep in sync with the call sites. Not for a single boolean with one call site. |
| An expensive, rate-limited, or flaky external dependency (the LLM API, a tracker, Docker) | **Backoff with jitter** and a **status classification** (retry 5xx and 429, fail fast on 4xx); **circuit breaker** (stop calling while it is down); **bulkhead** (a bounded pool so one dependency cannot exhaust the workers); **cache with explicit invalidation** | What should the caller experience while it is down: wait, fail fast, or degrade? Decide that first; the pattern follows. | State to hold (breaker state, pool size), and a way to see it. In aesir: the custom retry loop in the MCP client, chosen over a library because status classification mattered. |
| Code that must accept future kinds without edits (a new agent, tool, adapter, trigger) | **Registration + declarative configuration** (the open/closed principle done as data: a registry the new kind adds itself to, a YAML file the registry discovers); a **plugin seam** when the kinds arrive from outside the repo | Is the variation data (a definition file) or code (a new implementation)? Data goes in config discovered by a registry; code goes behind an interface the registry loads. | A discovery step and a validation schema at load. Not when the set is closed and small: an exhaustive union is cheaper and the compiler checks it. In aesir: `AgentRegistry`, `ToolRegistry`, `definitions/*/definition.yaml`. |
| Data read or written across a package or service boundary (the dashboard reads agents' tables; an integration posts events) | **Schema at the boundary** (Zod, parse don't validate); **versioned or additive contracts** (add a field, never change its meaning); **one owner per schema** | Who owns the schema, and can the other side deploy independently? If yes, every change is additive first and the old shape keeps parsing for one release. | A second copy of the type on the reading side (the dashboard's local schema is deliberate). Never share a package to avoid the copy if it drags the dependency tree along. |
| Two implementations, a local problem, or a change inside one module | **No pattern**: a plain function, a lookup table, a well-named module | Would a reader need a second file to understand this? If not, a pattern adds a second file for nothing. | The cost of every pattern is the reader's second file. Take the seam (an interface with one trivial implementation) only where change is known to come. |
