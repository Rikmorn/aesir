```sql
ALTER TABLE agents.conversations ADD COLUMN IF NOT EXISTS retry_count integer NOT NULL DEFAULT 0;
ALTER TABLE agents.conversations ADD COLUMN IF NOT EXISTS max_retries integer NOT NULL DEFAULT 2;
ALTER TABLE agents.conversations ADD COLUMN IF NOT EXISTS error_message text;

CREATE INDEX IF NOT EXISTS idx_conversations_parent ON agents.conversations (parent_conversation_id) WHERE parent_conversation_id IS NOT NULL;

-- Enable LZ4 compression on messages JSONB column (PostgreSQL 14+)
-- Only affects new writes; existing data keeps original compression.
-- Since the table is new (Phase 37), all data will use LZ4.
ALTER TABLE agents.conversations ALTER COLUMN messages SET COMPRESSION lz4;
```

Use the same idempotent pattern as migrations 0000 and 0001 (IF NOT EXISTS for ADD COLUMN where possible, IF NOT EXISTS for CREATE INDEX).

Create `packages/agents/src/framework/wait-for-tool.ts`:

Implement `createWaitForTool(waitForState: WaitForState): ToolDefinition` factory.

The function accepts a mutable `WaitForState` object (created by the executor before each agent loop run). When the tool's `execute` is called:
1. Parse input using a Zod schema with fields: `type` (string, required), `reason` (string, required), `timeout` (string, optional, format: `<number><unit>` where unit is h/d), `metadata` (record, optional)
2. Set `waitForState.triggered = true` and populate the other fields from the parsed input
3. Return a confirmation message: `"Conversation paused. Waiting for: ${type}. Reason: ${reason}."` (append timeout if present)
4. Do NOT throw -- the confirmation message is fed back to the LLM so it can generate an end_turn response

The tool name MUST be `wait_for` (matching the placeholder in tool-factories.ts).

The tool description should guide the agent on when to use it:
```
"Pause this conversation and wait for an external signal before continuing. Use when you need: human approval for a plan, user reply in a conversation, PR review feedback, CI results, or any external input. The conversation will resume automatically when the signal arrives or the timeout expires."
```

Input schema fields:
- `type`: string -- "What to wait for. Must match the signal type that will wake this conversation. Common types: 'approval', 'user_reply', 'pr_review', 'pr_merged', 'escalation_resolved'."
- `reason`: string -- "Why you are pausing. Logged for observability and included in timeout notifications."
- `timeout`: string, optional -- "Max time to wait. Format: '<number><unit>' where unit is h (hours) or d (days). E.g., '72h', '7d'."
- `metadata`: record of unknown, optional -- "Additional context stored with the pause."

Also export a helper: `createDefaultWaitForState(): WaitForState` that returns `{ triggered: false, waitType: null, reason: null, timeout: null, metadata: null }`.

Create `packages/agents/src/framework/wait-for-tool.test.ts`:

Test cases (aim for ~10-12 tests):

5. Execute with valid input populates reason from input.reason
6. Execute with timeout populates waitForState.timeout

8. Execute returns confirmation message (not isError)
9. Confirmation message includes type and reason
10. Confirmation message includes timeout when present
11. Execute without optional fields leaves them null on state
12. createDefaultWaitForState returns untriggered state

Use vitest (describe/it/expect). Follow existing test patterns in the framework directory.
