**Implementation -- poll cycle:**

The `start()` method begins the polling loop using setTimeout (NOT setInterval -- each poll schedules the next after completion to prevent overlap).

Each `poll()` iteration:
1. If draining, skip
2. Call `recoverStaleConversations()` -- find conversations with status='running' and last_heartbeat_at older than staleThresholdMs. For each: if retry_count < max_retries, set status='queued', clear claimed_by/claimed_at/last_heartbeat_at, increment retry_count. If retry_count >= max_retries, set status='failed', set error_message="Stale heartbeat: exceeded max retries".
3. Calculate capacity: `concurrencyLimit - running.size`
4. If capacity > 0, claim conversations using an atomic CTE query:

```sql
WITH claimable AS (
  SELECT id FROM agents.conversations
  WHERE status = 'queued'
  ORDER BY created_at ASC
  FOR UPDATE SKIP LOCKED
  LIMIT $capacity
)
UPDATE agents.conversations
SET status = 'running',
    claimed_by = $workerId,
    claimed_at = NOW(),
    last_heartbeat_at = NOW(),
    updated_at = NOW()
FROM claimable
WHERE agents.conversations.id = claimable.id
RETURNING agents.conversations.*
```

Use `db.execute(sql`...`)` for this raw SQL query since the CTE pattern does not compose well with Drizzle's query builder.

5. For each claimed conversation, fire-and-forget `executeConversation()`:
   ```typescript
   const controller = new AbortController();
   running.set(conv.id, controller);
   void executeConversation(conv, controller.signal)
     .finally(() => running.delete(conv.id));
   ```

6. Schedule next poll via `setTimeout(poll, pollIntervalMs)`

**Implementation -- drain() and close():**

`drain()`:
1. Set draining = true
2. Clear the poll timer
3. Return a Promise that resolves when running.size === 0 (poll every 500ms, or use a simple interval check)
4. Do NOT abort running conversations -- let them finish naturally

`close()`:
1. Call drain()
2. After drain completes, flush eventLog
3. Clean up any remaining state

Fill in the full `executeConversation(conv, abortSignal)` implementation in worker-loop.ts. This is the core execution path for a single conversation.

**Steps:**

1. **Load agent definition:** `agentRegistry.get(conv.agent_definition_id, conv.agent_definition_version)`. If not found, mark failed and return.

2. **Initialize eventLog sequence:** `eventLog.initSequence(conv.id)`

3. **Append lifecycle event:** `agent.started` event (or `agent.resumed` if conversation has existing messages beyond the initial message).

4. **Resolve tools:** `toolRegistry.resolve(definition.tools, toolContext)` where toolContext = `{ agentId: conv.agent_definition_id, correlationId: conv.id, logger: childLogger }`

5. **Wire wait_for interception:** Create a fresh WaitForState via `createDefaultWaitForState()`. Find the `wait_for` tool in the resolved tools array. If found, replace its `execute` function with a wrapper that calls `createWaitForTool(waitForState).execute(input)` -- this ensures the mutable state object is captured. If not found, that's fine (not all agents use wait_for).

6. **Check queued signals before running:** Read `conv.queued_signals` (JSONB array). For each queued signal, check if it matches a `pending_wait.type` from a previous pause (stored on the conversation row). If a match is found:
   - Append the matching signal as a user message to the messages array: `{ role: "user", content: signal.message ?? "Signal received: ${signal.type}. Data: ${JSON.stringify(signal.data)}" }`
   - Clear `pending_wait` to null
   - Remove the consumed signal from `queued_signals`
   - Persist these changes to the database row immediately (UPDATE within the executeConversation scope)
   - Log: "Consumed queued signal {type} for conversation {id} -- skipping pause"
   If no match is found, leave queued_signals as-is and proceed normally.

7. **Apply history compaction:** If conversation has messages, create a HistoryManager from the agent definition's history config and call `compact(messages, sessionProjection.getSession(conv.id))`. Use the compacted messages for the agent loop.

8. **Build AgentLoopOptions and call runAgentLoop:**

   The `runAgentLoop()` function always starts with a fresh internal `conversationMessages` array and adds `initialMessage` (with optional `context` prepended) as the first user message. It does NOT accept pre-existing messages.

   **Approach for Phase 40 (context-serialization):**
   - **New conversations** (no prior messages beyond the initial): Use `initialMessage` from the conversation's first message content, and `context` from the agent definition. Call `runAgentLoop()` normally.
   - **Resumed conversations** (have prior messages from a previous run): Serialize the prior messages array as a JSON string. Pass this serialized history as the `context` parameter. Set `initialMessage` to `"Continue the conversation from where you left off."`. The LLM will receive: `[serialized prior messages]\n\nContinue the conversation from where you left off.` as the first user message, giving it full history context.

   This approach works because:
   - `runAgentLoop()` prepends `context` to `initialMessage` (see `buildInitialMessage()` in run-agent-loop.ts)
   - The LLM receives the full conversation history in a single user message
   - No modifications to runAgentLoop's signature are needed
   - Future optimization: modify runAgentLoop to accept a `messages` parameter for native multi-turn, but that's outside Phase 40 scope

   Other AgentLoopOptions fields:
   - `systemPrompt`: from agent definition
   - `tools`: resolved tools (with wait_for wrapper)
   - `model`: from agent definition
   - `maxIterations`: from agent definition
   - `onHeartbeat`: heartbeat callback (see below)
   - `abortSignal`: from parameter
   - `logger`: child logger with conversationId

9. **Heartbeat callback:** Create a closure that tracks `lastBeatTime = Date.now()`. On each `onHeartbeat()` call (fired after every LLM response by runAgentLoop), check if `heartbeatIntervalMs` has elapsed since lastBeatTime. If so, update lastBeatTime and fire-and-forget an UPDATE: `SET last_heartbeat_at = NOW() WHERE id = conv.id AND claimed_by = workerId`. Log errors but don't throw.

10. **Run agent loop:** `const result = await runAgentLoop(loopOptions)`

11. **Post-loop: verify ownership** before persisting. Query `WHERE id = conv.id AND claimed_by = workerId`. If ownership changed (stale detection kicked in), log warning and discard results -- do NOT persist.

12. **Post-loop: handle result based on waitForState and loop status:**

    a. If `waitForState.triggered`:
       - Persist messages (full array replacement via UPDATE SET messages = $fullArray)
       - Set status='waiting', pending_wait={ type: waitForState.waitType, reason: waitForState.reason, timeout: waitForState.timeout, metadata: waitForState.metadata }
       - Clear claimed_by, claimed_at, last_heartbeat_at
       - Append `agent.paused` event
       - Flush eventLog

    b. If `result.status === 'completed'`:
       - Persist messages
       - Set status='completed'
       - Clear claimed_by, claimed_at, last_heartbeat_at
       - Append `agent.completed` event
       - Flush eventLog

    c. If `result.status === 'error'` or `result.status === 'max_tokens'` or `result.status === 'max_iterations'`:
       - Check if error is non-retryable (inspect result.output for "Token budget exhausted" or "Agent aborted" patterns, or check if retry_count >= max_retries)
       - If retryable: persist messages, set status='queued', increment retry_count, clear claimed_by/claimed_at/last_heartbeat_at, set error_message
       - If non-retryable: persist messages, set status='failed', set error_message, clear claimed_by/claimed_at/last_heartbeat_at
       - Append `agent.completed` event with error payload
       - Flush eventLog

    d. If `result.status === 'aborted'`:
       - Persist messages at current point
       - Set status='queued' (will be re-claimed), clear claimed_by/claimed_at/last_heartbeat_at
       - Append `agent.paused` event (graceful shutdown)
       - Flush eventLog
