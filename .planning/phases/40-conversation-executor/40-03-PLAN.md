Create `packages/agents/src/framework/worker-loop.ts` implementing `createWorkerLoop(options: WorkerLoopOptions): WorkerLoop`.

**WorkerLoopOptions type** (define in this file or in types.ts if cleaner):
```typescript
interface WorkerLoopOptions {
  db: NodePgDatabase<typeof agentsSchemaModule>;
  eventLog: EventLog;
  sessionProjection: SessionProjection;
  agentRegistry: AgentRegistry;
  toolRegistry: ToolRegistry;
  logger: PinoLogger;
  pollIntervalMs?: number;       // default: 5000
  concurrencyLimit?: number;     // default: 3
  heartbeatIntervalMs?: number;  // default: 30000
  staleThresholdMs?: number;     // default: 300000 (5 min)
  workerId?: string;             // default: generated wrkr_<nanoid>
}
```

**WorkerLoop interface:**
```typescript
interface WorkerLoop {
  start(): void;
  drain(): Promise<void>;
  close(): Promise<void>;
  isRunning(): boolean;
  getRunningCount(): number;
}
```

**Implementation -- poll cycle:**

The `start()` method begins the polling loop using setTimeout (NOT setInterval -- each poll schedules the next after completion to prevent overlap).

Each `poll()` iteration:
1. If draining, skip
2. Call `recoverStaleConversations()` -- find conversations with status='running' and last_heartbeat_at older than staleThresholdMs. For each: if retry_count < max_retries, set status='queued', clear claimed_by/claimed_at/last_heartbeat_at, increment retry_count. If retry_count >= max_retries, set status='failed', set error_message="Stale heartbeat: exceeded max retries".
3. Calculate capacity: `concurrencyLimit - running.size`
4. If capacity > 0, claim conversations using an atomic CTE query:

```sql
WITH claimable AS (
  SELECT id FROM agents.conversations
  WHERE status = 'queued'
  ORDER BY created_at ASC
  FOR UPDATE SKIP LOCKED
  LIMIT $capacity
)
UPDATE agents.conversations
SET status = 'running',
    claimed_by = $workerId,
    claimed_at = NOW(),
    last_heartbeat_at = NOW(),
    updated_at = NOW()
FROM claimable
WHERE agents.conversations.id = claimable.id
RETURNING agents.conversations.*
```

Use `db.execute(sql`...`)` for this raw SQL query since the CTE pattern does not compose well with Drizzle's query builder.

5. For each claimed conversation, fire-and-forget `executeConversation()`:
   ```typescript
   const controller = new AbortController();
   running.set(conv.id, controller);
   void executeConversation(conv, controller.signal)
     .finally(() => running.delete(conv.id));
   ```

6. Schedule next poll via `setTimeout(poll, pollIntervalMs)`

**Implementation -- executeConversation(conv, abortSignal):**

This is the core execution path for a single conversation:

1. Load agent definition: `agentRegistry.get(conv.agent_definition_id, conv.agent_definition_version)`. If not found, mark failed and return.

2. Initialize eventLog sequence: `eventLog.initSequence(conv.id)`

3. Append `agent.started` event (or `agent.resumed` if conversation has existing messages)

4. Resolve tools: `toolRegistry.resolve(definition.tools, toolContext)` where toolContext = `{ agentId: conv.agent_definition_id, correlationId: conv.id, logger: childLogger }`

5. **Wire wait_for interception:** Create a fresh WaitForState via `createDefaultWaitForState()`. Find the `wait_for` tool in the resolved tools array. If found, replace its `execute` function with a wrapper that calls `createWaitForTool(waitForState).execute(input)` -- this ensures the mutable state object is captured. If not found, that's fine (not all agents use wait_for).

6. **Check queued signals before running:** Read `conv.queued_signals`. If any signals match a pending_wait type (from a previous pause), consume the first matching signal immediately -- append it as a user message, clear pending_wait, clear the consumed signal from queued_signals. The conversation does NOT actually pause.

7. **Apply history compaction:** If conversation has messages, create a HistoryManager from the agent definition's history config and call `compact(messages, sessionProjection.getSession(conv.id))`. Use the compacted messages for the agent loop.

8. **Build AgentLoopOptions:**
   - `systemPrompt`: from agent definition
   - `tools`: resolved tools (with wait_for wrapper)
   - `initialMessage`: empty string (messages already contain the conversation history)
   - `model`: from agent definition
   - `maxIterations`: from agent definition
   - `onHeartbeat`: heartbeat callback (see below)
   - `abortSignal`: from parameter
   - `logger`: child logger with conversationId

   IMPORTANT: The runAgentLoop() function builds the initial user message and expects `initialMessage` + existing `conversationMessages` internally. Since we are RESUMING a conversation with existing messages, we need to pass the existing messages array. However, `runAgentLoop()` always starts with a fresh `conversationMessages` array and adds an initial user message.

   **Resolution:** The executor needs to either:
   (a) Modify the messages array to extract the last user message as `initialMessage` and somehow pass prior messages, OR
   (b) Accept that runAgentLoop() manages its own internal message array, and the executor passes the FULL conversation as context.

   The cleanest approach for Phase 40: Pass the conversation messages as the `context` parameter (serialized), with a short `initialMessage` like "Continue the conversation." for resumed conversations, or the actual initial message for new ones. The system prompt already contains behavioral instructions. The context parameter is prepended to the initial message.

   ACTUALLY -- re-read runAgentLoop(): it puts `initialMessage` (with optional context prepended) as the first user message. For NEW conversations, this is the initial task. For RESUMED conversations, the prior messages need to be in the conversation. Since runAgentLoop() manages its own `conversationMessages` array internally, the executor should reconstruct the Anthropic message format from the stored messages.

   **Final approach:** For resumed conversations, rather than using runAgentLoop's initialMessage, pass the stored messages directly. This requires that the executor constructs the `AgentLoopOptions` with the stored messages. Since runAgentLoop currently does not accept pre-existing messages, the executor should:
   - For NEW conversations: use `initialMessage` and `context` as normal
   - For RESUMED conversations: the stored messages ARE the conversation. Set `initialMessage` to a brief resume instruction like "Continue from where you left off." and pass the serialized prior messages as `context`. The LLM will see the full history.

   Note: This is a simplification for Phase 40. A future optimization could modify runAgentLoop to accept a messages parameter, but that's outside this phase's scope.

9. **Heartbeat callback:** Create a closure that tracks `lastBeatTime`. On each `onHeartbeat()` call (fired after every LLM response by runAgentLoop), check if `heartbeatIntervalMs` has elapsed since lastBeatTime. If so, fire-and-forget an UPDATE: `SET last_heartbeat_at = NOW() WHERE id = conv.id AND claimed_by = workerId`. Log errors but don't throw.

10. **Run agent loop:** `const result = await runAgentLoop(loopOptions)`

11. **Post-loop: verify ownership** before persisting. Query `WHERE id = conv.id AND claimed_by = workerId`. If ownership changed (stale detection kicked in), log warning and discard results -- do NOT persist.

12. **Post-loop: handle result based on waitForState and loop status:**

    a. If `waitForState.triggered`:
       - Persist messages (full array replacement)
       - Set status='waiting', pending_wait={ type: waitForState.waitType, reason: waitForState.reason, timeout: waitForState.timeout, metadata: waitForState.metadata }
       - Clear claimed_by, claimed_at, last_heartbeat_at
       - Append `agent.paused` event
       - Flush eventLog

    b. If `result.status === 'completed'`:
       - Persist messages
       - Set status='completed'
       - Clear claimed_by, claimed_at, last_heartbeat_at
       - Append `agent.completed` event
       - Flush eventLog

    c. If `result.status === 'error'` or `result.status === 'max_tokens'` or `result.status === 'max_iterations'`:
       - Check if error is non-retryable (inspect result.output for "Token budget exhausted" or "Agent aborted" patterns, or check if retry_count >= max_retries)
       - If retryable: persist messages, set status='queued', increment retry_count, clear claimed_by/claimed_at/last_heartbeat_at, set error_message
       - If non-retryable: persist messages, set status='failed', set error_message, clear claimed_by/claimed_at/last_heartbeat_at
       - Append `agent.completed` event with error payload
       - Flush eventLog

    d. If `result.status === 'aborted'`:
       - Persist messages at current point
       - Set status='queued' (will be re-claimed), clear claimed_by/claimed_at/last_heartbeat_at
       - Append `agent.paused` event (graceful shutdown)
       - Flush eventLog

13. **Error handling:** Wrap the entire executeConversation in try/catch. On unexpected error:
    - Attempt to persist current state and mark as failed (or queued if retryable)
    - Log error with full context
    - Ensure the conversation is removed from the running map (via finally block)

**Implementation -- drain() and close():**

`drain()`:
1. Set draining = true
2. Clear the poll timer
3. Return a Promise that resolves when running.size === 0 (poll every 500ms, or use a simple interval check)
4. Do NOT abort running conversations -- let them finish naturally

`close()`:
1. Call drain()
2. After drain completes, flush eventLog
3. Clean up any remaining state

Also update `conversation-executor.ts` to accept and expose the worker loop. Add a `startWorker()` and `stopWorker()` method to the ConversationExecutor, or alternatively export the worker loop separately. The cleanest approach: the ConversationExecutor factory internally creates and manages the worker loop. Add two methods to the ConversationExecutor interface:
- `startWorker(): void` -- starts the polling loop
- `stopWorker(): Promise<void>` -- graceful shutdown (drain + close)

Update the ConversationExecutor interface in types.ts to include these methods. Update conversation-executor.ts to wire them.

Export `createWorkerLoop` from framework/index.ts (even though it's used internally, exporting enables testing and future composition).
