    **What to change:** Replace the current "Working with Humans" section with an expanded version that includes judgment criteria for ask vs reply and channel-aware communication guidance. Also update the "Communication on Linear" section (lines 115-122) to align with the channel-aware principles.

    **Locked decisions to honor (exact principles, wording is Claude's discretion):**

    1. **Default mode: state assumptions and go.** The agent communicates what it's doing and starts working ("I'm implementing X with approach Y"). No blocking, no waiting for permission. User can course-correct.

    2. **Delegation context = low interactivity.** Tasks from product-agent already have clarified requirements. Only ask if something is genuinely contradictory or technically impossible.

    3. **Direct trigger = medium interactivity.** Requirements may be sparse. A one-liner like "add logout button" doesn't need clarification. A vague "improve auth security" probably does.

    4. **Block only on genuine ambiguity.** Things the agent truly can't infer from context or the codebase. "The issue says 'fix auth' but there are 3 auth systems" is blocking. "Should I use the existing test pattern?" is not.

    5. **Bundle all unknowns into one ask + wait_for.** Every pause is a context switch for the user and idle time for the agent. Gather all questions, present in one message, wait once.

    6. **ask is for questions, reply is for statements.** Don't overcorrect completion behavior -- `reply` + `complete_task` for completion stays as-is.

    7. **Channel-aware progress communication:**
       - Linear (ticket context): Update freely -- research findings, approach decisions, sub-agent delegations, PR links, blockers
       - Slack/reply (direct to requester): Outcomes and blockers only
       - notify (channel broadcast): Channel-relevant outcomes only

    8. **Principle:** Communication cost should match the channel's attention cost.

    **Prompt guide rules to follow:**
    - Give judgment criteria, NOT a state machine. No `IF delegation THEN skip questions; IF direct THEN classify as simple/complex`.
    - Use "prefer", "tend toward" instead of MUST/ALWAYS for behavioral guidance (reserve strong directives for safety).
    - Trust the model -- the agent can reason about when requirements are clear vs ambiguous.
    - Keep the section concise. Don't repeat what the tools section already says about how reply/ask/notify work mechanically.

    **What NOT to change:**
    - The `<identity>` section -- unchanged
    - The `<constraints>` section -- unchanged
    - The `<examples>` section -- unchanged (examples already show good judgment)
    - The `<tools>` section -- unchanged
    - The mechanical description of how reply/ask/notify work (replyContext handling, etc.) -- keep this
    - The task delegation and sub-agent sections -- unchanged
    - The independent verification section -- unchanged

    **Scope check:** The diff should be confined to the "Working with Humans" and "Communication on Linear" sections within `<domain_knowledge>`. If you find yourself editing examples, constraints, or other sections, you've exceeded scope.
