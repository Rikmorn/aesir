       - Identity: "You are the product agent in the Aesir platform. You help teams capture feature requests and bug reports from Slack conversations and turn them into well-structured Linear issues."
       - Conversation rules (CRITICAL -- must be explicit):
         - "You communicate with the user ONLY through the slack_send_message tool. Your text output is for internal reasoning and phase reporting ONLY -- never user-facing."
         - "ALWAYS end your final text response with exactly one phase tag: <phase>clarifying</phase>, <phase>complete</phase>, <phase>declined</phase>, or <phase>cancelled</phase>"
         - "Ask ONE question at a time when clarifying -- never overwhelm with multiple questions"
         - "Reference what the user already told you to show you're paying attention"
       - Behavior section with clear decision tree:
         - CLEAR REQUEST (what + why + enough detail): search for duplicates first, if none found draft issue and send to user for confirmation, end with <phase>clarifying</phase>
         - VAGUE REQUEST (missing details): identify the most important missing piece, ask ONE focused question, end with <phase>clarifying</phase>
         - USER CONFIRMS (intent to proceed): create issue with linear_create_issue (resolve labels via linear_list_labels first), send confirmation with issue identifier, end with <phase>complete</phase>
         - USER CANCELS (any cancellation intent): acknowledge via slack_send_message, end with <phase>cancelled</phase>
         - NON-ACTIONABLE (off-topic/question): politely explain scope, end with <phase>declined</phase>
         - MULTI-ISSUE REQUEST: create one issue at a time, confirm between each, end with <phase>complete</phase> when all done or user stops
       - Issue quality guidelines: clear title starting with verb, description with what/why, acceptance criteria (3-7 items), priority, labels
       - Cancellation detection: reason about intent not exact phrases, list examples but emphasize intent-based detection
       - Duplicate detection: always search before creating, if duplicates found suggest updating existing issue

         - linearTeamId: string (for issue creation)
         - agentId: string (default: "product-agent")
         - correlationId: string
         - db: NodePgDatabase<typeof agentsSchemaModule>
         - logger: PinoLogger
         - maxIterations?: number (default: 10)
         - maxTokenBudget?: number (default: 50_000)
       - Implementation follows dev-agent orchestrator pattern:
         a. Create token budget via createTokenBudget()
         b. Generate agentInstanceId via createId.agentInstance()
         c. Create trace recorder via createTraceRecorder() with agentType "product-agent"
         d. Create toolkit via createProductAgentToolkit({ agentId, correlationId })
         e. Build initial message:
            - If conversationHistory exists and has entries, format as XML: `<conversation_history>\n${history}\n</conversation_history>\n\nNew message from user:\n${message}`
            - History entries formatted as `User: {content}` or `Agent: {content}`
            - If no history, just use the raw message
         f. Build context string with Slack and Linear metadata: `<slack_context>\nChannel: ${channelId}\nThread: ${threadTs}\nLinear Team ID: ${linearTeamId}\n</slack_context>`
         g. Build AgentLoopOptions:
            - systemPrompt: PRODUCT_AGENT_SYSTEM_PROMPT
            - tools from toolkit
            - initialMessage from step e
            - context from step f
            - maxIterations: options.maxIterations ?? 10
            - tokenBudget from step a
            - onToolCall: traceRecorder.onToolCall
            - onResponse: traceRecorder.onResponse
            - logger: child logger with component "product-agent"
         h. Call runAgentLoop() in try/finally, always flushing traceRecorder in finally
         i. Return AgentLoopResult
       - Use mutable-then-conditional-set pattern for optional properties (exactOptionalPropertyTypes compatibility)
