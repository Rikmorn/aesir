## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Signal delivery semantics
- Preserve original domain-specific signal types (pr_review, approval, etc.) -- task routing changes the destination, not the event identity
- Signal payload is identical to non-task-routed signals -- no task metadata enrichment. The `<task_context>` block injected by the worker loop at run start is the canonical task context source
- All three active statuses (running, waiting, queued) are "active" from routing perspective -- event goes as signal to the existing conversation
- Use `queued_signals` for async delivery to running conversations -- advisory lock is for the routing decision only, not signal delivery itself

#### New conversation bootstrapping
- Agent definition derived from `task.assignee_id` (which is an agent definition ID when `assignee_type = "agent"`)
- If `assignee_type !== "agent"` (human assignee or missing): fall through to EventRouter -- no agent to route to, not a judgment call
- Initial message constructed from event payload only (same as non-task routing) -- task context comes from worker loop's `<task_context>` injection
- Context enrichment (workspace_context, slack_context) stays in the router where it already lives -- extract the enrichment logic into a shared helper so both existing start path and task-routing start path reuse it (DRY, no architectural change)
- CorrelationKey: `${taskId}:${event.deduplicationId || event.type}` -- event.type fallback per spec, sufficient for real webhook events which always have deduplicationId
- `executor.start()` sets `task_id` directly on INSERT -- no separate `linkConversation()` call needed (that's for after-the-fact linking in create_task tool)

#### Conflict & edge cases
- Do NOT check task status in the router -- terminal tasks (completed/cancelled) still receive routed events. The agent sees task status via `<task_context>` and decides how to respond. Router's job is "which task?" not "should this task receive events?"
- Advisory lock contention (normal): wait for lock (`pg_advisory_xact_lock`) -- serialization is the entire point, transactions are short (milliseconds)
- Advisory lock failure (DB error): fall through to EventRouter, log warning -- event isn't lost, just loses task affinity for this delivery
- Canonical lock order: task advisory lock first, then conversation SKIP LOCKED -- prevents deadlock between the two locking mechanisms

#### Backward compatibility & fallthrough
- When task lookup fails (deleted task, DB error): strip taskId from event before falling through to EventRouter -- orphaned taskId is misleading downstream
- All events with a taskId go through task routing regardless of origin (webhooks, manual POST /events, etc.) -- routing branch checks `incomingEvent.taskId` existence, not source
- Regression testing: verify existing routing scenarios (fast-path start, signal, ignore, slow-path) with `taskId: undefined` produce identical behavior -- confirms task routing is a clean early-exit
- High-value test cases unique to 58.4: task routing with active conversation (signal), no active conversation (new conversation), advisory lock serialization under concurrency, fall-through cases (human assignee, missing task, lock failure)

## Summary

This phase adds a task-routing branch to `routeEvent()` in `packages/agents/src/router/router.ts`. When an `IncomingEvent` has a `taskId` (injected by Phase 58.3's integration correlation pipeline), the event bypasses the existing `EventRouter.handle()` and routes directly to the task's active conversation (as a signal) or creates a new conversation within the task. PostgreSQL advisory locks (`pg_advisory_xact_lock(hashtext(task_id))`) serialize concurrent events for the same task, preventing duplicate conversation creation.

The implementation touches four layers: (1) `routeEvent()` gains an early-exit task branch, (2) `ConversationExecutor` gains `findActiveForTask()` method and `taskId` support in `StartConversationParams`, (3) context enrichment logic is extracted from the router's `case "start"` into a shared helper reused by both paths, and (4) comprehensive tests cover task routing, signal delivery, advisory lock serialization, and backward compatibility.

The existing event routing pipeline (adapter -> EventRouter -> executor) is unchanged for events without `taskId`. This is verified by running existing tests with `taskId: undefined`.

**Primary recommendation:** Insert the task-routing branch between the adapter pipeline and `EventRouter.handle()` in `routeEvent()`, using a short database transaction that acquires an advisory lock, looks up the task and active conversation, then either signals or starts. All decision-making is within the transaction; actual executor calls happen after.

### Pattern 1: Task-Routing Early Exit in routeEvent()

**What:** Insert a check for `incomingEvent.taskId` between the adapter pipeline and `EventRouter.handle()`. If present, route via task path. If absent, existing routing continues unchanged.

**When to use:** Every event routed through `routeEvent()`.

**Implementation flow:**
```typescript
// In routeEvent(), after adapter pipeline (step 1), before EventRouter (step 2):

// 1.5. Task routing branch (early exit)
if (incomingEvent.taskId && deps.taskService && deps.db) {
  try {
    const taskResult = await routeViaTask(incomingEvent, deps, eventLogger);
    if (taskResult !== null) {
      return taskResult; // Task routing succeeded
    }
    // taskResult === null means fall through to EventRouter
  } catch (error) {
    // Advisory lock failure or DB error: fall through, strip taskId
    eventLogger.warn({ err: error, taskId: incomingEvent.taskId },
      "Task routing failed, falling through to EventRouter");
    incomingEvent = { ...incomingEvent, taskId: undefined };
  }
}

// 2. EventRouter: deterministic routing decision (existing code)
const routeDecision = deps.eventRouter.handle(incomingEvent);
```

### Pattern 2: Advisory Lock Transaction

**What:** Short transaction that serializes routing decisions for the same task. Advisory lock prevents two concurrent events from both creating new conversations.

**Key insight:** The transaction scope is narrow -- just the routing decision. The actual `executor.start()` or `executor.signal()` calls happen AFTER the transaction commits. The advisory lock prevents the race between "no active conversation found" and "create new conversation."

```typescript
async function routeViaTask(
  event: IncomingEvent,
  deps: RouteEventDeps,
  logger: PinoLogger,
): Promise<RouteEventResult | null> {
  const taskId = event.taskId!;

  return await deps.db.transaction(async (tx) => {
    // 1. Acquire advisory lock (waits if another event is routing for same task)
    await tx.execute(sql`SELECT pg_advisory_xact_lock(hashtext(${taskId}))`);

    // 2. Look up task
    const task = await deps.taskService!.get(taskId);
    if (!task) {
      // Task not found: strip taskId, fall through
      logger.warn({ taskId }, "Task not found, falling through to EventRouter");
      return null; // Signals caller to strip taskId and fall through
    }

    // 3. Check assignee is an agent
    if (task.assignee_type !== "agent") {
      logger.info({ taskId, assigneeType: task.assignee_type },
        "Task assignee is not an agent, falling through to EventRouter");
      return null;
    }

    // 4. Find active conversation for this task
    const activeConv = await deps.executor.findActiveForTask(taskId);

    if (activeConv) {
      // 5a. Signal existing conversation
      // (signal delivery happens within this transaction context,
      //  but uses queued_signals for running/queued conversations)
      const signal = {
        type: event.type,
        data: event.data,
        message: event.message,
        source: event.source,
        deduplicationId: event.deduplicationId,
      };
      const signalResult = await deps.executor.signal(activeConv.id, signal);
      return { received: true, action: signalResult.action, conversationId: activeConv.id };
    }

    // 5b. No active conversation: create new one
    const agentDefinitionId = task.assignee_id;
    const correlationKey = `${taskId}:${event.deduplicationId || event.type}`;
    const initialMessage = enrichInitialMessage(event, deps);

    const conversationId = await deps.executor.start({
      agentDefinitionId,
      correlationKey,
      initialMessage,
      taskId,  // Sets task_id on INSERT
    });

    return { received: true, action: "started", conversationId };
  });
}
```

### Pattern 3: Context Enrichment Helper

**What:** Extract the workspace_context and slack_context enrichment from the existing `case "start"` block into a reusable function. Both the existing fast-path start and the new task-routing start path call this helper.

```typescript
// router/enrichment.ts
export function enrichInitialMessage(
  event: IncomingEvent,
  deps: Pick<RouteEventDeps, 'githubOwner' | 'githubRepo' | 'githubBaseBranch' | 'linearTeamId'>,
  message?: string,
): string {
  let initialMessage = message ?? event.message ?? JSON.stringify(event.data);

  // Workspace context
  const workspaceLines: string[] = [];
  if (deps.githubOwner) workspaceLines.push(`GitHub Owner: ${deps.githubOwner}`);
  if (deps.githubRepo) workspaceLines.push(`GitHub Repo: ${deps.githubRepo}`);
  if (deps.githubBaseBranch) workspaceLines.push(`GitHub Base Branch: ${deps.githubBaseBranch}`);
  if (deps.linearTeamId) workspaceLines.push(`Linear Team ID: ${deps.linearTeamId}`);

  if (workspaceLines.length > 0) {
    const block = ["<workspace_context>", ...workspaceLines, "</workspace_context>"].join("\n");
    initialMessage = `${block}\n\n${initialMessage}`;
  }

  // Slack context (for Slack-originated events)
  const eventData = event.data as Record<string, unknown>;
  if (event.source === "slack:webhook" && eventData?.channelId) {
    const contextBlock = [
      "<slack_context>",
      `Channel: ${eventData.channelId}`,
      `Thread: ${eventData.threadTs ?? ""}`,
      "</slack_context>",
    ].join("\n");
    initialMessage = `${contextBlock}\n\n${initialMessage}`;
  }

  return initialMessage;
}
```

### Pattern 4: findActiveForTask Query

```typescript
// In ConversationExecutor
async findActiveForTask(taskId: string): Promise<ConversationInfo | null> {
  const rows = await db
    .select({
      id: conversations.id,
      agent_definition_id: conversations.agent_definition_id,
      agent_definition_version: conversations.agent_definition_version,
      status: conversations.status,
      created_at: conversations.created_at,
      updated_at: conversations.updated_at,

    .from(conversations)
    .where(
      and(
        eq(conversations.task_id, taskId),
        sql`${conversations.status} IN ('running', 'waiting', 'queued')`,
      ),
    )
    .orderBy(desc(conversations.created_at))
    .limit(1);

  if (rows.length === 0 || !rows[0]) return null;
  return toConversationInfo(rows[0]);
}
```

### Anti-Patterns to Avoid

- **Checking task status in the router:** The CONTEXT.md explicitly forbids this. Terminal tasks still receive routed events. The agent decides how to handle a follow-up on a completed task via `<task_context>`.

- **Enriching signal payload with task metadata:** Signals are identical regardless of routing path. Task context comes from the worker loop's `<task_context>` injection, not the signal payload.

- **Holding the advisory lock during executor.start()/signal():** The lock serializes the routing decision, not the execution. Keep the transaction short. The executor has its own locking (FOR UPDATE) for conversation creation.

- **Using FOR UPDATE on task row instead of advisory lock:** Advisory locks are in a separate lock space from row locks and cannot deadlock with the SKIP LOCKED mechanism used by the worker loop. Row-level locks on tasks would create a deadlock risk.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| String-to-integer hash | Custom hash function | `hashtext()` (PG built-in) | Built-in, deterministic, collision-safe for advisory locks |
| Advisory lock acquisition | Application-level mutex | `pg_advisory_xact_lock()` | Transaction-scoped, automatic release, DB-native |
| Active conversation lookup | Manual SQL | `findActiveForTask()` on executor | Reuses existing `idx_conversations_task` index, consistent pattern |
| Context enrichment | Copy-paste from existing case | Extract to `enrichment.ts` helper | DRY, both paths stay in sync |

**Key insight:** The advisory lock and hashtext combination is a well-established PostgreSQL pattern for serializing access to logical resources identified by string keys. No application-level locking or external libraries needed.

## Common Pitfalls

### Pitfall 1: Deadlock Between Advisory Lock and Conversation FOR UPDATE
**What goes wrong:** If the advisory lock transaction also tries to acquire row-level locks on conversations (via executor.start()'s FOR UPDATE), and a concurrent worker loop holds the conversation lock while trying the advisory lock, deadlock occurs.
**Why it happens:** Inconsistent lock ordering between two locking mechanisms.
**How to avoid:** Keep the advisory lock transaction narrow -- the decision transaction acquires the advisory lock and does the lookup/decision. The actual executor.start() or executor.signal() happens outside or uses its own separate transaction with FOR UPDATE. Since `executor.start()` and `executor.signal()` manage their own transactions internally, call them after the routing-decision transaction commits. Alternatively, the routing transaction can include the executor operations (start/signal) within it, which is safe because advisory lock is always acquired first.
**Warning signs:** "deadlock detected" errors in PostgreSQL logs during concurrent event routing.

### Pitfall 2: Fall-Through with Stale taskId
**What goes wrong:** An event with taskId pointing to a deleted task falls through to EventRouter, which doesn't understand taskId and routes incorrectly based on correlationKey alone.
**Why it happens:** taskId not stripped before fall-through.
**How to avoid:** Per CONTEXT.md decision: strip taskId from event before falling through. Create a new IncomingEvent object with `taskId: undefined`.
**Warning signs:** Events with orphaned taskIds appearing in slow-path routing logs.

### Pitfall 3: RouteEventDeps Not Updated in main.ts
**What goes wrong:** `taskService` and `db` are not wired into `routeEventDeps` in `main.ts`, causing the task routing branch to silently skip (the `if` guard checks for their existence).
**Why it happens:** Adding fields to the interface without updating the bootstrap wiring.
**How to avoid:** Explicitly wire `taskService` and `db` into `routeEventDeps` in `service/main.ts`. The TypeScript compiler will catch the missing field if the interface requires it (not optional).
**Warning signs:** Task routing never fires despite events having taskId -- check logs for "Task routing" log entries.

### Pitfall 4: Signal Type Mismatch with wait_for
**What goes wrong:** Task routing delivers a signal with the original event type (e.g., "pr_review"), but the waiting conversation's `pending_wait.type` expects something different.
**Why it happens:** This is actually working correctly -- the decision to preserve original signal types is by design. The adapter produces the domain-language type, and the agent's wait_for specifies matching types.
**How to avoid:** No action needed. This is a non-pitfall that looks like one. The signal type from the adapter (e.g., "approval", "pr_review") matches what agents use in wait_for.
**Warning signs:** N/A -- this works correctly by design.

### Pitfall 5: Concurrency Test Flakiness
**What goes wrong:** Tests that verify advisory lock serialization are inherently timing-dependent and flaky in CI.
**Why it happens:** True concurrency tests require multiple database connections racing to acquire locks.
**How to avoid:** Use integration tests with testcontainers for real concurrency verification. For unit tests, verify the SQL generation (that `pg_advisory_xact_lock` is called with the right key). Keep concurrency tests in a separate test file tagged for integration-only runs.
**Warning signs:** Intermittent test failures in CI that pass locally.

### Pitfall 6: hashtext() Collision Risk
**What goes wrong:** Two different task_id values hash to the same integer, causing unnecessary serialization.
**Why it happens:** `hashtext()` returns 32-bit integer; collision probability is non-zero with large task sets.
**How to avoid:** For this use case, collision only means unnecessary serialization (one event waits for another to complete routing), not data corruption. The routing transaction is milliseconds. This is acceptable. If proven problematic, switch to the two-integer variant: `pg_advisory_xact_lock(hashtext('task:'), hashtext(task_id))` for a wider key space.
**Warning signs:** Unusual advisory lock wait times on tasks with different IDs (detectable via `pg_stat_activity`).

### Complete routeViaTask Implementation

```typescript
// Source: Synthesized from spec (2.5-agentic-conversations.md:257-273) and codebase patterns

import type { IncomingEvent } from "../adapters/types.js";
import type { PinoLogger } from "@aesir/platform";
import { sql } from "drizzle-orm";
import type { RouteEventDeps, RouteEventResult } from "./types.js";

/**
 * Route an event through the task-aware path.
 *
 * Returns RouteEventResult on success, or null to signal fall-through
 * to EventRouter. Throws on advisory lock / DB failure (caller catches
 * and falls through).
 */
async function routeViaTask(
  event: IncomingEvent,
  deps: RouteEventDeps,
  logger: PinoLogger,
): Promise<RouteEventResult | null> {
  const taskId = event.taskId!;

  // Use db.transaction for advisory lock scope
  return await deps.db.transaction(async (tx) => {
    // 1. Advisory lock: serialize events for same task
    await tx.execute(sql`SELECT pg_advisory_xact_lock(hashtext(${taskId}))`);

    // 2. Look up task
    const task = await deps.taskService!.get(taskId);
    if (!task) {
      logger.warn({ taskId }, "Task not found during task routing");
      return null; // Fall through, caller strips taskId
    }

    // 3. Guard: agent assignee only
    if (task.assignee_type !== "agent") {
      logger.info(
        { taskId, assigneeType: task.assignee_type },
        "Task has non-agent assignee, falling through",
      );
      return null;
    }

    // 4. Find active conversation
    const activeConv = await deps.executor.findActiveForTask(taskId);

    if (activeConv) {
      // 5a. Deliver as signal to existing conversation
      const signal = {
        type: event.type,
        data: event.data,
        message: event.message,
        source: event.source,
        deduplicationId: event.deduplicationId,
      };

      logger.info(
        { taskId, conversationId: activeConv.id, signalType: signal.type },
        "Task routing: signaling active conversation",
      );

      const signalResult = await deps.executor.signal(activeConv.id, signal);
      return {
        received: true,
        action: signalResult.action,
        conversationId: activeConv.id,
      };
    }

    // 5b. No active conversation: create new one
    const agentDefinitionId = task.assignee_id;
    const correlationKey = `${taskId}:${event.deduplicationId || event.type}`;
    const initialMessage = enrichInitialMessage(event, deps);

    logger.info(
      { taskId, agentDefinitionId, correlationKey },
      "Task routing: creating new conversation",
    );

    const conversationId = await deps.executor.start({
      agentDefinitionId,
      correlationKey,
      initialMessage,
      taskId,
    });

    return { received: true, action: "started", conversationId };
  });
}
```

## Open Questions

1. **Transaction scope for executor.start()/signal() calls**
   - What we know: The advisory lock transaction must include the routing decision. The spec says "actual conversation creation/signal delivery happens outside the transaction."
   - What's unclear: Whether `executor.start()` and `executor.signal()` should be called inside or outside the advisory lock transaction. Calling inside is simpler (one transaction) but holds the lock longer. Calling outside requires a TOCTOU guard.
   - Recommendation: Call inside the transaction. The lock is held for the duration of `executor.start()`/`executor.signal()`, which are both short operations (single INSERT or UPDATE). The total lock hold time is a few milliseconds. This eliminates the TOCTOU race completely. The advisory lock is separate from SKIP LOCKED (different lock space), so no deadlock risk.

2. **RouteEventDeps.db type**
   - What we know: The router currently has no direct DB access -- it goes through `deps.executor` and `deps.eventRouter`.
   - What's unclear: Whether to pass the full typed `AgentsDb` or use a raw `Pool` for the advisory lock call.
   - Recommendation: Pass the typed Drizzle `db` (same instance as in main.ts). The `sql` template tag for advisory lock works with Drizzle's `db.transaction()`. This is consistent with how worker-loop.ts uses `db.execute(sql\`...\`)`.

3. **Optional vs required taskService/db in RouteEventDeps**
   - What we know: Making them optional with `?` means the task routing branch silently skips if not wired.
   - What's unclear: Whether to make them required (breaking change to interface) or optional (silent failure if misconfigured).
   - Recommendation: Make them optional with the `?` operator. The guard `if (incomingEvent.taskId && deps.taskService && deps.db)` is explicit. This maintains backward compatibility for any test fixtures or alternative callers. The main.ts bootstrap explicitly wires them.
