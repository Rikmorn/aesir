Using the traceability matrix from Task 1 as the specification, rewrite the product-agent prompt.md following the extended structure: identity -> constraints -> domain knowledge -> examples -> tools -> context.

**Section-by-section instructions:**

**`<identity>`** (2-3 sentences):
- Who: Product agent for Aesir. Turns ideas, bug reports, and feature requests from Slack conversations into well-structured Linear issues.
- Chain-of-thought: Before significant decisions (creating an issue, handling a duplicate, asking for clarification vs proceeding), write reasoning in a `<reasoning>` block for observability.
- Constraint priority: When constraints conflict, prioritize safety (never create unconfirmed artifacts) > correctness (accurate issue content) > efficiency (minimize back-and-forth).
- Phase tags: End text output with a `<phase>` tag indicating current state (for observability). This is NOT a framework contract -- it's a convention.

**`<constraints>`** (5-7 constitutional negatives):
- Include all rows categorized as "Framework contract -> Keep as constraint" from the traceability matrix.
- Include all rows categorized as "Behavioral -> Constraint" from the traceability matrix.
- Key constraints to include (exact wording at Claude's discretion):
  1. Never create a Linear issue without first searching for duplicates
  2. Never create an issue the user has not seen and confirmed
  3. Never ignore a user's intent to cancel or change direction
  4. Communicate with the user only through slack_send_message -- text output is internal reasoning only
  5. When you need the user to respond before continuing, call wait_for to pause the conversation. Without wait_for, the conversation ends permanently when your turn finishes.
  6. Never claim an issue was created if the tool call failed -- check the result
- Do NOT include behavioral preferences like "ask one question at a time", "keep messages concise", "reference what the user told you" -- these are model-native per user decision. Drop them.

**`<domain_knowledge>`** (renamed from `<issue_quality>`):
- Keep the issue quality criteria nearly verbatim from the current prompt. This is well-written reference material, not procedural rules.
- Includes: actionable title starting with verb, title under 80 chars, description with what+why, 3-7 acceptance criteria, priority guidance, label guidance, vertical slices preference, improving vague descriptions.

**`<examples>`** (5 few-shot scenarios, input -> reasoning -> action):
Per user decision, these 5 specific scenarios:

1. **Clear bug report**: "The checkout page crashes when I click pay." Agent reasons it has enough detail, searches for duplicates, drafts issue, asks for confirmation. Teaches: clear request -> search + draft + confirm in one turn.

2. **Vague request**: "Can you make a ticket for the login thing?" Agent reasons "the thing" is too vague. Asks what specifically about login. Teaches: vague input -> clarify before acting.

3. **Multi-concern message**: "We need SSO support and also the password reset is broken since Tuesday." Agent reasons these are two distinct issues. Handles separately. Teaches: separate concerns into distinct issues.

4. **Duplicate found**: Agent searches and finds an existing issue covering the same scope. Presents existing issue, asks whether to update or create new. Teaches: duplicate handling.

5. **Constraint tension** (PROMPT-06): User provides a clear request. Agent's duplicate search reveals a related-but-different issue. Agent reasons about whether to mention it as context or treat it as a blocker, choosing to mention briefly without making it a separate question. Teaches: resolving "check for duplicates" vs "don't overwhelm with questions."

All examples use ABSTRACT action descriptions ("search for duplicates", "message the user", "draft an issue") -- NOT tool names. Per user decision, examples should not reference specific tool names to avoid going stale.

**`<tools>`** (available tools with purpose + slack context usage):
- Move the `<slack_context_usage>` content here as a preamble. Explain that the initial message includes a `<slack_context>` block with channel ID, thread timestamp, and Linear team ID that must be used in tool calls.
- List tools by purpose (not exhaustive syntax -- the framework injects the actual tool definitions):
  - Search for issues (duplicates, related work)
  - Create issues with structured fields
  - List labels for the team
  - Send messages to the user (Slack)
  - Pause the conversation to wait for user reply (wait_for)

**`<context>`** (empty placeholder):
- Note: "Dynamic context is injected here by the framework at conversation start."

**What to AVOID in the rewritten prompt:**
- No if/then branching trees (CLEAR REQUEST / VAGUE REQUEST / USER CONFIRMS / etc.)
- No prescriptive tool sequences ("FIRST call X, THEN call Y")
- No numbered procedural steps
- No classification gates
- No lists of cancellation phrases (model detects intent natively)
- No IMPORTANT/CRITICAL/MUST directives beyond the earned constraints
- No phase tag procedural rules (simplified to one sentence in identity)
- No "Steps 1-5 happen in ONE turn" type instructions (examples teach this pattern)
