    **1. Create `packages/dashboard/src/lib/agent-service.ts`:**

    Server-side HTTP client for the agent-service registry API. This module is only used in server components / API routes (never shipped to the client).

    Define TypeScript interfaces that mirror the agent-service API response types (from `packages/agents/src/service/api/types.ts`). Do NOT import from @aesir/agents -- define locally to maintain dashboard independence, consistent with how `lib/schema.ts` mirrors the DB schema.

    Local interfaces needed:
    ```typescript
    // Matches AgentRegistrySummary from agent-service API
    interface AgentSummary {
      id: string;
      name: string;
      description: string;
      version: string;
      model: string;
      temperature?: number;
      tools: string[];
      subAgents?: Record<string, string>;
      maxIterations: number;
      tokenBudget: number;
      history: {
        pruneThreshold: number;
        protectedMessages: number;
        summaryThreshold: number;
        summaryModel: string;
      };
      triggers?: Array<{ event: string }>;
    }

    // Matches AgentRegistryDetail from agent-service API
    interface AgentDetail extends AgentSummary {
      systemPrompt: string;
    }
    ```

    Implement two exported functions:

    - `fetchAgentList(): Promise<AgentSummary[]>` -- calls `GET /api/agents/registry`, returns the array. Returns empty array on error (log the error).
    - `fetchAgentDetail(id: string): Promise<AgentDetail | null>` -- calls `GET /api/agents/registry/:id`, returns the detail object. Returns null on 404 or error.

    Use `process.env.AGENT_SERVICE_URL ?? "http://localhost:3004"` as the base URL.

    For fetch options:
    - `AbortSignal.timeout(5000)` for timeout (not setTimeout + AbortController -- simpler)
    - `next: { revalidate: 60 }` for Next.js fetch caching (refresh agent definitions every 60s)
    - `headers: { Accept: "application/json" }`
    - Handle non-ok responses: log error with status code, return fallback (empty array or null)
    - Handle network errors (agent-service unreachable): log error, return fallback

    Export the interfaces as well (consumed by services/agents.ts and components).

    **2. Create `packages/dashboard/src/services/agents.ts`:**

    Service layer that combines agent-service HTTP API data with database queries. Follow the same pattern as `services/conversations.ts` -- typed functions, camelCase interfaces, server-side only.

    Functions:

    - `getAgentList(): Promise<AgentSummary[]>` -- delegates to `fetchAgentList()` from agent-service client. Simple passthrough for now, but the service layer abstraction lets us add caching or enrichment later.

    - `getAgentDetail(id: string): Promise<AgentDetail | null>` -- delegates to `fetchAgentDetail(id)`.

    - `getRecentConversationsByAgent(agentDefinitionId: string, limit?: number): Promise<RecentConversation[]>` -- Drizzle query against `agents.conversations` table filtered by `agent_definition_id`, ordered by `created_at DESC`, limited to `limit` (default 10). Join with `agent_sessions` for `last_event_at`. Return type:

    ```typescript
    interface RecentConversation {
      id: string;
      status: string;
      createdAt: Date;
      updatedAt: Date;
      lastActivity: Date | null;
      tokenInput: number;
      tokenOutput: number;
    }
    ```

    For token aggregation in `getRecentConversationsByAgent`, use the same subquery join pattern as `listConversations` in `services/conversations.ts` (join with `agentEvents` aggregation subquery for token counts).

    Export all interfaces and functions.

    **3. Update `docker-compose.yml`:**

    Add `AGENT_SERVICE_URL=http://agent-service:3004` to the dashboard service's environment section. This uses the Docker network hostname (not localhost). Place it after the database env vars, with a comment like `# Agent service API (Docker network)`.

    Also add `agent-service` to the dashboard's `depends_on` section with `condition: service_healthy` -- the dashboard needs the agent-service to be running to fetch registry data. This is a soft dependency (pages show error states when unavailable), but having it in depends_on ensures correct startup order in Docker Compose.
