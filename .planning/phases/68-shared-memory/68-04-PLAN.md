**update.ts** -- Create `createKnowledgeUpdateTool(knowledgeService, ctx)`:

Zod input schema with discriminated union on `action`:
```typescript
const KnowledgeUpdateInputSchema = z.object({
  id: z.string().describe("ID of the knowledge entry to update"),
  action: z.enum(["supersede", "invalidate"]).describe("Update action"),
  // Supersede fields
  content: z.string().min(1).optional().describe("New content (required for supersede)"),
  type: z.enum(KNOWLEDGE_TYPES).optional().describe("Override type (supersede only)"),
  topic: z.string().optional().describe("Override topic (supersede only)"),
  // Invalidate fields
  reason: z.string().optional().describe("Reason for invalidation"),
});
```

Tool definition:
- name: `"knowledge_update"`
- description: "Update an existing knowledge entry. Use 'supersede' to replace with updated content (creates a new entry, marks old as replaced). Use 'invalidate' to mark an entry as no longer valid. Superseded/invalidated entries are excluded from future queries."
- execute logic:
  1. Parse and validate input
  2. If `action === "supersede"`:
     - Require `content` field (return error if missing: "content is required for supersede action")
     - Call `knowledgeService.supersede(id, { content, type, topic })`
     - Return `{ content: "Superseded: ${result.id} [${result.type}] ${result.topic} (replaces ${id})" }`
  3. If `action === "invalidate"`:
     - Call `knowledgeService.invalidate(id, reason)`
     - Return `{ content: "Invalidated: ${id}${reason ? " — " + reason : ""}" }`
  4. On error, return `{ content: "Failed to update knowledge: ${message}", isError: true }`

Wire up a pg-boss cron job for knowledge entry cleanup in `main.ts`.

Follow the pattern from timeout-scheduler.ts (which also uses pg-boss). The TimeoutScheduler is already created in main.ts and exposes the pg-boss instance, OR the cron schedule can be registered directly using the pool.

After the executor is created (step 8) but before the Express app setup (step 10), add the knowledge cleanup cron:

```typescript
// 8b. Knowledge cleanup -- hourly hard-delete of entries expired 24h+ ago
// Uses pg-boss schedule() for exactly-once cron execution (survives restarts, no double-cleanup)
const pgBoss = timeoutScheduler.getBoss(); // If TimeoutScheduler exposes pg-boss, use it
// OR import PgBoss and create independently if not exposed:
// This depends on whether TimeoutScheduler exposes its pg-boss instance.
```

Check how TimeoutScheduler is structured. If it exposes the pg-boss instance, use it directly. If not, the cleanup can be registered as part of the TimeoutScheduler's initialization (which runs boss.start()). The cleanest approach is to:

1. Check if `timeoutScheduler` has a method to register additional jobs, or if it exposes the boss instance.
2. If the boss instance is accessible (e.g., `timeoutScheduler.boss` or a `getBoss()` method), register directly:
```typescript
const boss = timeoutScheduler.getBoss();
await boss.schedule("knowledge-cleanup", "0 * * * *", {}); // Every hour
await boss.work("knowledge-cleanup", async () => {
  const deleted = await knowledgeService.cleanupExpired();
  if (deleted > 0) {
    logger.info({ deletedCount: deleted }, "Knowledge cleanup completed");
  }
});
```
3. If the boss instance is NOT accessible, add a `registerCleanupJob` method to the TimeoutScheduler interface and implement it there. OR, create a separate pg-boss instance for knowledge cleanup (not ideal but functional).
4. If neither approach is clean, use a simpler approach: register the cleanup as a periodic task in the worker loop or as a setInterval in main.ts. The pg-boss approach is preferred but not worth a major refactor.

**Practical recommendation:** Look at timeout-scheduler.ts. If it exports/exposes the boss, use it. If not, the simplest approach that works is a setInterval with the cleanup call, since the agent service is a single-process deployment:

```typescript
// Fallback: simple interval-based cleanup (runs every hour)
const CLEANUP_INTERVAL_MS = 60 * 60 * 1000; // 1 hour
const cleanupTimer = setInterval(async () => {
  try {
    const deleted = await knowledgeService.cleanupExpired();
    if (deleted > 0) {
      logger.info({ deletedCount: deleted }, "Knowledge cleanup completed");
    }
  } catch (err) {
    logger.error({ err }, "Knowledge cleanup failed");
  }
}, CLEANUP_INTERVAL_MS);
cleanupTimer.unref(); // Don't prevent process exit
```

Add cleanup timer clearing to the graceful shutdown sequence:
```typescript
clearInterval(cleanupTimer);
```

The preference order is: (1) pg-boss cron via existing boss instance > (2) setInterval. Use whichever is achievable without modifying timeout-scheduler.ts significantly.

Also verify that the `cleanupExpired()` method in KnowledgeService (from Plan 68-03) uses:
```sql
DELETE FROM agents.knowledge_entries WHERE expires_at < NOW() - INTERVAL '24 hours'
```
This ensures entries are invisible after their expiry (query-time filter) but linger 24h extra in the DB for debugging before hard deletion.
