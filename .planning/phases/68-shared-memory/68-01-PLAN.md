Create hand-written SQL migration `0007_add_knowledge_entries.sql` (following the project convention of hand-written migrations with `--> statement-breakpoint` separators):

1. `CREATE EXTENSION IF NOT EXISTS vector;` -- enables pgvector
2. Create `agents.knowledge_entries` table:
   - `id` TEXT PRIMARY KEY
   - `type` TEXT NOT NULL with CHECK constraint for 6 types: discovery, constraint, architecture_decision, thought, preference, test_result
   - `topic` TEXT NOT NULL (dedup key, stored normalized)
   - `content` TEXT NOT NULL (max 2000 chars enforced at app level, not DB)
   - `author` TEXT NOT NULL (agentId)
   - `scope` TEXT NOT NULL with CHECK constraint: shared, private
   - `tags` JSONB DEFAULT '[]'
   - `embedding` vector (unconstrained dimension -- no fixed size, allows 768 dev / 1024 prod)
   - `superseded_by` TEXT REFERENCES agents.knowledge_entries(id)
   - `invalidated` BOOLEAN NOT NULL DEFAULT false
   - `invalidation_reason` TEXT
   - `expires_at` TIMESTAMPTZ NOT NULL
   - `created_at` TIMESTAMPTZ NOT NULL DEFAULT now()
3. Create indexes:
   - `idx_knowledge_type_topic` on (type, LOWER(TRIM(topic))) -- for dedup matching
   - `idx_knowledge_scope_author` on (scope, author) -- for visibility filtering
   - `idx_knowledge_expires` on (expires_at) WHERE expires_at > NOW() -- partial index for query-time filter
   - `idx_knowledge_not_superseded` on (id) WHERE superseded_by IS NULL AND invalidated = false -- for active entries
   - `idx_knowledge_embedding_cosine` HNSW index on (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)

Add Drizzle schema definition in `schema.ts`:
- Add `vector` import from `drizzle-orm/pg-core` (Drizzle v0.31+ native support)

- Use `text("scope", { enum: ["shared", "private"] })` for scope
- Use `vector("embedding")` without dimensions parameter (unconstrained to match migration)
- Define indexes matching the migration (B-tree indexes; HNSW index defined in migration only since Drizzle index syntax may not fully support HNSW WITH params)
- Export the table and infer `KnowledgeEntry` type via `typeof knowledgeEntries.$inferSelect`

Mirror the table definition in `schema.drizzle.ts` (for drizzle-kit migration tracking). If the `vector` import doesn't work in the drizzle-kit CJS context, use `text("embedding")` as a placeholder with a comment explaining why.

Extend the Zod schema in `config.ts` with embedding provider configuration. The embedding env vars must be optional with sensible defaults so existing tests and non-embedding workflows don't break:

```typescript
// Embedding provider (optional -- only required when knowledge tools are used)
EMBEDDING_PROVIDER: z.enum(["ollama", "voyage"]).default("ollama"),
EMBEDDING_DIMENSIONS: z.coerce.number().int().positive().default(768),
OLLAMA_URL: z.string().url().optional(),
OLLAMA_MODEL: z.string().default("nomic-embed-text"),
VOYAGE_API_KEY: z.string().optional(),
VOYAGE_MODEL: z.string().default("voyage-3.5"),
```

Add an `embedding` section to the `config` object:
```typescript
embedding: {
  provider: env.EMBEDDING_PROVIDER,
  dimensions: env.EMBEDDING_DIMENSIONS,
  ollama: {
    url: env.OLLAMA_URL || "http://ollama:11434",
    model: env.OLLAMA_MODEL,
  },
  voyage: {
    apiKey: env.VOYAGE_API_KEY,
    model: env.VOYAGE_MODEL,
  },
},
```

Note: Do NOT add conditional validation (e.g., requiring VOYAGE_API_KEY when provider=voyage) at the Zod schema level. The EmbeddingService factory (Plan 68-02) handles provider-specific validation at creation time.

In `docker-compose.yml`:
