# Phase 58.2: Agent Task Tools - Research

**Researched:** 2026-02-06
**Domain:** Agent tool implementation, task lifecycle management, context injection
**Confidence:** HIGH

## Summary

Phase 58.2 implements six task tools (`create_task`, `complete_task`, `pause_task`, `handoff_task`, `list_tasks`, `get_task_context`) registered under the `task:` namespace, adds them to orchestrator agent YAML definitions, and injects `<task_context>` blocks in the worker loop when conversations have a `task_id`. The Phase 58.1 foundation (TaskService, schema, ToolContext.taskId) is complete and provides all CRUD operations needed by the tool layer.

Research focused on: (1) the exact codebase patterns for tool factories, registration, and adapters, (2) what the TaskService already provides vs. what's missing, (3) how context injection works in the worker loop and router, and (4) the status transition logic that tools must enforce as business rules.

**Primary recommendation:** Follow the existing `codebaseAdapter`/`mcpAdapter` pattern in `tool-factories.ts` by creating a `taskAdapter` closure that captures TaskService and passes it alongside ToolContext to each tool factory. Tools live in a new `packages/agents/src/shared/tools/task/` directory matching the existing codebase/coordination/integration structure.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **Tool response format:** Write ops return minimal confirmation (task ID, new status, side-effect). Read ops return rich plain text (not JSON). list_tasks includes lastHandoffSummary capped at 200 chars. get_task_context uses flat chronological format.
- **Error behavior:** All errors use `isError: true` (not throw). Include current status + valid transitions for self-correction.
- **create_task when conversation already has task_id:** Create always succeeds. Linking conditional on ctx.taskId being undefined (first-time: link + mutate ctx; subsequent: create in DB, no link).
- **Hierarchy guardrails deferred to Phase 59:** Phase 58.2 accepts parentId and creates FK -- no depth/subtask/circular enforcement.
- **Atomic status+handoff:** complete_task and pause_task atomically transition status AND record handoff in one call.
- **Context injection:** Always inject when task_id exists. Two modes: metadata-only (no handoffs) or metadata + latest handoff (truncated 4000 chars). Conditional get_task_context pointer only when truncated or multiple handoffs.
- **Two injection points:** New conversations: prepend to initial user message after workspace_context. Reopened conversations: inject alongside world_state at reopen boundary.
- **Always fresh fetch:** Worker loop fetches latest handoff at run start.

### Pattern 1: Task Adapter in tool-factories.ts

**What:** A `taskAdapter` closure that captures TaskService and passes it to individual tool factories via ToolContext, following the established adapter pattern.

**When to use:** Registration of all 6 task tools in `registerAllTools()`.

**Example (based on existing codebaseAdapter):**
```typescript
// In tool-factories.ts

import { TaskService } from "../shared/services/task-service.js";
import { createCreateTaskTool, createCompleteTaskTool, ... } from "../shared/tools/task/index.js";

export interface RegisterAllToolsOptions {
  registry: ToolRegistry;
  agentRegistry: AgentRegistry;
  taskService?: TaskService;  // Optional for backward compatibility
  logger: PinoLogger;
}

function taskAdapter(
  createFn: (taskService: TaskService, ctx: ToolContext) => ToolDefinition,
  taskService: TaskService,
): (ctx: ToolContext) => ToolDefinition {
  return (ctx: ToolContext) => createFn(taskService, ctx);
}

// Registration (inside registerAllTools):
if (options.taskService) {
  registry.register("task:create_task", taskAdapter(createCreateTaskTool, options.taskService));
  registry.register("task:complete_task", taskAdapter(createCompleteTaskTool, options.taskService));
  // ... etc
}
```

**Confidence: HIGH** -- pattern directly observed in `codebaseAdapter` and `mcpAdapter` in `tool-factories.ts` (lines 65-105).

### Pattern 4: Context Injection in Worker Loop

**What:** The worker loop in `worker-loop.ts` builds the ToolContext and runs the agent loop. Context blocks are injected via the `routeEvent()` pipeline (for new conversations) or via the `reopen()` method (for reopened conversations).

**Current injection flow for new conversations (router.ts lines 76-120):**
1. Build workspace_context block from config values
2. Prepend to initialMessage: `<workspace_context>...\n\n` + event content
3. Optionally prepend slack_context for Slack-originated events
4. Pass enriched initialMessage to executor.start()

**Current injection flow for reopened conversations (conversation-executor.ts lines 583-590):**
1. Build `<world_state>` block with reason
2. Append as user message to existing messages array
3. Transition to queued

**Task context injection must happen in TWO places:**
1. **Router/start path (new conversations):** After workspace_context, before event content. Requires fetching latest handoff in the router or start() method.
2. **Worker loop (all conversations):** At run start, fetch latest handoff and either modify the first message (new) or append alongside world_state (reopened). The spec says "always fresh at run start" so the worker loop is the correct place.

**CRITICAL FINDING:** The cleanest injection point is the worker loop's `executeConversation()` function (line 347+), between loading the conversation and building the agent loop options. This is where the conversation is already loaded, task_id is available from `conv.task_id`, and the TaskService can fetch the latest handoff. For new conversations, the task_context block can be prepended to the first message content. For resumed/reopened conversations (detected by `isResumed = existingMessages.length > 1`), inject as a fresh user message at the end alongside any world_state.

**Confidence: HIGH** -- directly read worker-loop.ts, conversation-executor.ts, and router.ts.

### Pattern 5: Mutable ToolContext for create_task Linking

**What:** `create_task` needs to mutate `ctx.taskId` after creating the first task (so subsequent MCP calls include the task ID via header). This follows the mutable state pattern used by `wait_for` tool.

**How wait_for does it:** The `WaitForState` object is mutable -- the tool sets `waitForState.triggered = true` and the executor reads it after the loop exits. Similarly, `create_task` mutates `ctx.taskId` and subsequent tools see the change because ToolContext is passed by reference.

**Important nuance:** ToolContext is constructed once in `executeConversation()` (worker-loop.ts line 461) and the same object is used for all tool resolutions. Since tools capture `ctx` in their closure at resolve time, mutations to `ctx.taskId` by `create_task` ARE visible to tools resolved from the same context object. This works naturally.

**Confidence: HIGH** -- verified by reading worker-loop.ts lines 461-486 where ToolContext is constructed once and passed to all tool resolutions.

### Anti-Patterns to Avoid

- **Throwing errors from tool execute():** Always return `isError: true`, never throw. The agent loop expects ToolResult, not exceptions.
- **JSON tool responses:** The spec explicitly says plain text, not JSON. The LLM is the only consumer, and JSON adds ~30% token overhead.
- **Business logic in TaskService:** Status transitions are enforced in the tool layer, not the service. The service does shape validation only (SERVICE-SHAPE-ONLY decision).
- **Registering task tools unconditionally:** They should only register if `taskService` is provided (backward compat).

## Common Pitfalls

### Pitfall 1: Missing TaskService Methods

**What goes wrong:** The TaskService from Phase 58.1 is missing `listByParent()` and `linkConversation()` methods that are required by the spec for this phase.

**Why it happens:** Phase 58.1-02 SUMMARY shows only these methods were implemented: `create`, `get`, `update`, `addHandoff`, `getHandoffs`, `getLatestHandoff`, `listByAssignee`. The spec calls for `listByParent` (for `list_tasks` with parentId) and `linkConversation` (for `create_task` to link conversations).

**How to avoid:** Phase 58.2 must add these two methods to TaskService before implementing the tools that depend on them:
- `listByParent(parentId, filters?)` -- query tasks WHERE parent_id = ? with optional status/limit
- `linkConversation(taskId, conversationId)` -- UPDATE conversations SET task_id = ? WHERE id = ?

**Warning signs:** `list_tasks` tool can't query subtasks; `create_task` can't link the conversation.

**Confidence: HIGH** -- verified by reading task-service.ts and grep for listByParent/linkConversation returning no matches.

### Pitfall 2: Context Injection Placement Complexity

**What goes wrong:** Task context injection must work in two distinct code paths (new conversations and reopened conversations) with different message structures.

**Why it happens:** New conversations have a single initial user message where context blocks are prepended. Reopened conversations have a full message history with a world_state message appended at the end.

**How to avoid:** Build a single `buildTaskContextBlock(task, handoff, handoffCount)` helper that generates the XML string. Then inject it at the correct location in each path:
- New conversations: In the worker loop, modify the first message content to insert `<task_context>` between `<workspace_context>` and the event content.
- Reopened conversations: In the worker loop, when the conversation is resumed and has a task_id, append a user message with `<task_context>` alongside or after the `<world_state>` message.

**Warning signs:** Task context appearing in wrong order or being duplicated.

### Pitfall 3: Ordering of getHandoffs Results

**What goes wrong:** The TaskService `getHandoffs()` method orders by `created_at DESC` (newest first), but `get_task_context` needs chronological order (oldest first) for narrative flow.

**Why it happens:** The service was designed for `getLatestHandoff()` use case where DESC is correct.

**How to avoid:** Either reverse the results in the tool, or pass an `order` parameter. The simplest approach is to reverse in the tool: `handoffs.reverse()` since the list is typically small.

**Confidence: HIGH** -- verified by reading task-service.ts line 281: `.orderBy(desc(taskHandoffs.created_at))`.

### Pitfall 4: create_task Linking Race with ctx.taskId

**What goes wrong:** The `create_task` tool must both create the task in the DB and link the conversation via `linkConversation()`. If the task creation succeeds but linking fails, the system is in an inconsistent state.

**Why it happens:** Two separate DB operations (INSERT task, UPDATE conversation) without a transaction.

**How to avoid:** Use TaskService.linkConversation() which is a simple UPDATE. If it fails, log the error and return the task ID anyway with a note that linking failed. The task still exists and can be linked manually. Alternatively, wrap both in a transaction at the service level -- but the spec says "SERVICE-SHAPE-ONLY" so the tool should handle this.

**Warning signs:** Conversation without task_id after create_task succeeds.

### Pitfall 5: Task Adapter Missing When TaskService Not Provided

**What goes wrong:** If `registerAllTools()` is called without a `taskService` (e.g., in tests), and an agent definition references `task:create_task`, the tool registry will throw "Unknown tool reference."

**Why it happens:** TaskService is optional for backward compatibility.

**How to avoid:** Either:
1. Make taskService required in RegisterAllToolsOptions and update all callers.
2. Register task tools with a guard that returns a helpful error if taskService is missing (similar to spawn_agent when spawnDeps is absent).

The cleaner approach is option 1 since TaskService should always be available after Phase 58.1. Option 2 adds unnecessary complexity.

### Pitfall 6: Status Transition Map

**What goes wrong:** Tools enforce different transition rules inconsistently.

**Why it happens:** Each tool implements its own status checks without a shared transition map.

**How to avoid:** Define a single `VALID_TRANSITIONS` map in `shared/tools/task/types.ts`:
```typescript
const VALID_TRANSITIONS: Record<string, string[]> = {
  created: ["active"],
  active: ["paused", "completed", "cancelled"],
  paused: ["active", "cancelled"],
  completed: [],
  cancelled: [],
};
```
Every status-changing tool checks against this map before calling TaskService.update().

## Code Examples

### Task Tool Factory Pattern

```typescript
// Source: Based on packages/agents/src/shared/tools/coordination/spawn-agent.ts
export function createCompleteTaskTool(
  taskService: TaskService,
  ctx: ToolContext,
): ToolDefinition {
  return {
    name: "complete_task",
    description: "Mark a task as completed with a structured completion handoff...",
    inputSchema: CompleteTaskInputSchema,
    async execute(input: unknown): Promise<ToolResult> {
      const parsed = CompleteTaskInputSchema.safeParse(input);
      if (!parsed.success) {
        return {
          content: `Invalid input: ${parsed.error.issues.map(i => i.message).join(", ")}`,
          isError: true,
        };
      }

      const taskId = parsed.data.taskId ?? ctx.taskId;
      if (!taskId) {
        return {
          content: "No task ID provided and no task associated with this conversation.",
          isError: true,
        };
      }

      // Fetch current task to validate transition
      const task = await taskService.get(taskId);
      if (!task) {
        return { content: `Task not found: ${taskId}`, isError: true };
      }

      // Validate status transition
      const validTransitions = VALID_TRANSITIONS[task.status] ?? [];
      if (!validTransitions.includes("completed")) {
        return {
          content: `Cannot complete ${taskId}: status is "${task.status}".\nValid transitions from ${task.status}: ${validTransitions.join(", ") || "none (terminal state)"}`,
          isError: true,
        };
      }

      // Atomic: update status + record handoff
      await taskService.update(taskId, { status: "completed" });
      await taskService.addHandoff({
        taskId,
        conversationId: ctx.correlationId,
        handoffType: "completion",
        context: {
          summary: parsed.data.summary,
          key_decisions: parsed.data.key_decisions,
          artifacts: parsed.data.artifacts,
          next_steps: parsed.data.next_steps,
        },
        authorType: "agent",
        authorId: ctx.agentId,
      });

      return {
        content: `Task completed: ${taskId}\nStatus: completed`,
      };
    },
  };
}
```

### Task Context Block Generation

```typescript
// Source: Based on conversation-executor.ts world_state pattern (lines 583-590)
function buildTaskContextBlock(
  task: Task,
  latestHandoff: TaskHandoff | null,
  handoffCount: number,
): string {
  const lines: string[] = ["<task_context>"];

  // Metadata block (always present)
  lines.push(`Task: ${task.id}`);
  lines.push(`Title: ${task.title}`);
  if (task.objective) lines.push(`Objective: ${task.objective}`);
  lines.push(`Status: ${task.status}`);
  lines.push(`Assignee: ${task.assignee_type}:${task.assignee_id}`);

  if (latestHandoff) {
    lines.push("");
    lines.push("--- Latest Handoff ---");
    const ctx = latestHandoff.context as Record<string, unknown>;
    let handoffText = formatHandoffContext(latestHandoff, ctx);

    const fullBlock = [...lines, handoffText, "</task_context>"].join("\n");
    const wasTruncated = fullBlock.length > 4000;

    if (wasTruncated) {
      handoffText = handoffText.slice(0, 4000 - lines.join("\n").length - 100);
      handoffText += "\n[Truncated -- call get_task_context for full history]";
    } else if (handoffCount > 1) {
      handoffText += `\n\n${handoffCount} total handoffs. Call get_task_context for full history.`;
    }

    lines.push(handoffText);
  }

  lines.push("</task_context>");
  return lines.join("\n");
}
```

// 3b. Inject task context if conversation has a task
if (conv.task_id) {
  const task = await taskService.get(conv.task_id);
  if (task) {
    const latestHandoff = await taskService.getLatestHandoff(conv.task_id);
    const handoffs = await taskService.getHandoffs(conv.task_id, { limit: 1 });
    const handoffCount = handoffs.length; // Actually need a count query

    if (!isResumed && existingMessages.length > 0) {

      // Reopened/resumed: append as user message
      currentMessages.push({
        role: "user",
        content: taskContextBlock,
      });
    }
  }

## Open Questions

1. **Handoff count for get_task_context pointer logic**
   - What we know: The conditional pointer ("call get_task_context for full history") should only appear when truncated OR multiple handoffs exist.
   - What's unclear: TaskService doesn't have a `countHandoffs(taskId)` method. We need either a count query or to fetch all handoffs and check length.
   - Recommendation: Use `getHandoffs(taskId)` which already exists and check `.length`. The list is typically small (<20 handoffs per task). If performance becomes an issue, add a count method later.

2. **Atomicity of status update + handoff creation in complete_task/pause_task**
   - What we know: The spec says "atomically transition status AND record handoff." TaskService has separate `update()` and `addHandoff()` methods.
   - What's unclear: Whether to wrap both calls in a DB transaction at the tool level, or rely on the fact that the service layer handles each independently and any partial failure is recoverable.
   - Recommendation: Keep them as two sequential calls. If `addHandoff()` fails after `update()` succeeds, the task status is correct but the handoff is missing -- the agent can retry. Wrapping in a transaction would require passing a transaction object through TaskService, which changes its interface. The failure mode is rare and the recovery is simple.

3. **TaskService bootstrap in main.ts**
   - What we know: TaskService needs to be created in `bootstrap()` and passed to `registerAllTools()` and the worker loop.
   - What's unclear: Whether TaskService should also be passed to ConversationExecutor options or just to the worker loop.
   - Recommendation: Pass to `registerAllTools()` (for tool registration) and to `createWorkerLoop()` or `createConversationExecutor()` (for context injection in the worker loop). The worker loop options need a `taskService` field.
