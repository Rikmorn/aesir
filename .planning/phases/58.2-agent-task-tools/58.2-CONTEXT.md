# Phase 58.2: Agent Task Tools - Context

**Gathered:** 2026-02-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Six task tools (`create_task`, `complete_task`, `pause_task`, `handoff_task`, `list_tasks`, `get_task_context`) registered under `task:` namespace, added to orchestrator agent YAML files, with automatic `<task_context>` injection when a conversation has a `task_id`. Tool schemas, registration strategy, adapter pattern, and status transitions are locked by the spec (`2.5-agentic-conversations.md`). This phase is tool mechanics only -- hierarchy guardrails (depth, subtask cap, circular delegation) are deferred to Phase 59.

</domain>

<decisions>
## Implementation Decisions

### Tool response format
- **Write ops (create, complete, pause, handoff)**: Minimal confirmation -- task ID, new status, side-effect confirmation. The LLM already knows the input params; only echo server-assigned values and state changes.
  - Example: `Task created: task_abc123\nStatus: active\nConversation linked to this task.`
- **Read ops (list_tasks, get_task_context)**: Rich plain text, not JSON. LLMs reason better on natural text; JSON braces/quotes add ~30% token overhead with zero benefit since the only consumer is the LLM.
- **list_tasks**: Summary rows per task: id, title, status, assignee, created_at + `lastHandoffSummary` capped at 200 chars. Enough to triage similar tasks without a follow-up `get_task_context` call.
- **get_task_context**: Flat chronological format. Task metadata block (title, status, assignee, created_at), then all handoffs as a numbered list ordered by date. Each handoff shows: timestamp, type, author, summary, and all structured fields (key_decisions, artifacts, open_questions, next_steps). Chronological tells the task narrative; grouping by type breaks the story.
- **All error responses**: Use `isError: true` (not throw). Include current status + valid transitions so the LLM can self-correct. Consistent with spawn_agent pattern.
  - Example: `Cannot complete task_abc123: status is "paused".\nValid transitions from paused: active, cancelled.`

### Error behavior and edge cases
- **Invalid status transitions**: Return `isError: true` with current status and valid transitions. Applies to complete_task, pause_task, and any guard failures.
- **create_task when conversation already has task_id**: Create always succeeds. Linking is conditional:
  - `ctx.taskId` is undefined: create task, link conversation, mutate `ctx.taskId` (first-time setup)
  - `ctx.taskId` already set: create task in database, return ID, no link, no `ctx` mutation (creating subtasks or tasks for other agents)
  - This supports the orchestrator flow: first create_task links the conversation, subsequent create_task calls create subtasks without disrupting the parent association.
- **Hierarchy guardrails**: Deferred entirely to Phase 59. Phase 58.2's create_task accepts `parentId` and creates the FK -- that's it. All enforcement (depth limit, subtask cap, circular delegation) ships together in 59 where they share ancestry-walking logic.
- **Atomic status+handoff**: complete_task and pause_task atomically transition status AND record handoff in one call. No way to change status without providing context. The composable path exists via handoff_task (handoff without status change) for "handoff then pause" sequences.

### Context injection placement
- **Always inject when task_id exists** -- no skip-when-no-handoffs logic. Simplifies the code path.
- **Two injection modes based on handoff existence:**
  - No handoffs yet: inject metadata-only block (task ID, title, objective, status, assignee)
  - Handoffs exist: inject metadata + full latest handoff (summary, key_decisions, artifacts, open_questions, next_steps), truncated at 4000 chars
- **Conditional get_task_context pointer**: Only include "Call get_task_context for full history" when the handoff was truncated OR there are multiple handoffs. If the full latest handoff fits and it's the only one, the agent already has everything.
- **Two injection points depending on conversation state:**
  - New conversations: prepend to initial user message in order: `<workspace_context>` (broad) -> `<task_context>` (specific) -> event content
  - Reopened conversations: inject alongside `<world_state>` at the reopen boundary (both are "here's what's new since last run")
- **Always fresh**: Worker loop fetches latest handoff at run start. For reopened conversations, task context may have evolved while the conversation was terminal -- fresh fetch captures handoffs from other conversations on the same task.

### Claude's Discretion
- Exact plain text formatting of tool responses (spacing, separators, label style)
- Whether to include task objective in create_task confirmation
- How to format the truncation indicator when handoff exceeds 4000 chars

</decisions>

<specifics>
## Specific Ideas

- Write ops should feel like git CLI confirmations -- terse, informative, zero noise
- get_task_context tells a narrative: "created -> worked on -> paused -> delegated -> completed" -- the chronological order IS the value
- list_tasks with 200-char handoff previews solves the "three paused subtasks with similar titles" disambiguation problem
- The two-injection-point model (initial message vs reopen boundary) mirrors the natural question: "What context do I need right now?"

</specifics>
