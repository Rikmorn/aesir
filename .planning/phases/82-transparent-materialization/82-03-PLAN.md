  <name>Task 1: Implement LinearMaterializationAdapter</name>
  <files>
    packages/agents/src/shared/services/materialization/linear-adapter.ts
  </files>
  <action>
    Create `linear-adapter.ts` with a `createLinearMaterializationAdapter` factory function.

    **Dependencies (options object):**
    - `db`: NodePgDatabase (for materialization_records queries)
    - `logger`: PinoLogger
    - `linearTeamId`: string (from config -- default team ID fallback)
    - `dashboardBaseUrl`: string (for dashboard links in issue descriptions)
    - `correlationService`: CorrelationService (from `../correlation-service.js` -- for registering work correlations on materialized issues)

    **Initialization:**
    - On first `create()` call, resolve the `agent-work` label ID by calling `callMcpTool({ integration: "linear", tool: "list_labels", params: { teamId: linearTeamId }, agentId: "system", correlationId: "materialization-init" })` and finding the label named "agent-work". Cache the label ID. If label not found, log a warning and proceed without the label (graceful degradation).

    **create() implementation:**
    1. Build issue description from params:
       - First line: task description (the delegation brief)
       - Blank line
       - Attribution: "Delegated by {agentId}"
       - Dashboard link: `[View in Dashboard](${dashboardBaseUrl}/conversations/${conversationId})`
       - Keep it clean -- no internal IDs, no negotiation history (per CONTEXT.md locked decisions)

    2. Map priority string to Linear priority number: urgent=1, high=2, medium=3, low=4, none=0. Default to 0 (no priority) if omitted.

    3. Build labelIds array: always include `agent-work` label (if resolved). Add any additional labels from params.properties.labels (these would be label IDs, not names).

    4. Resolve teamId: params.properties?.teamId (explicit) > attempt to get parent issue team if parentIssueId provided (call get_issue MCP tool, extract team.id) > linearTeamId fallback. Log which resolution path was used.

    5. Call `callMcpTool({ integration: "linear", tool: "create_issue", params: { teamId, title: description.slice(0, 100), description: builtDescription, priority: mappedPriority, labelIds, ...(params.parentIssueId && { parentId: params.parentIssueId }) }, agentId: params.agentId, correlationId: params.correlationId })`.

    6. Parse MCP result (JSON string). Extract id, identifier, url from structuredContent.

    7. Insert materialization_records row: `{ task_id: params.taskId, target: "linear", external_id: issueId, external_url: issueUrl, conversation_id: params.conversationId, agent_id: params.agentId, config: params (full config snapshot), sync_status: "active" }`.

    7b. Register work correlation for the materialized issue. This is CRITICAL for comment routing -- without this, `linear.comment.created` events on the materialized issue will not find an active correlation and will fall through to slow_path (and then fail to route):
       ```typescript
       await correlationService.register({
         entityType: "linear_issue",
         entityId: issueId,
         conversationId: params.conversationId,
         agentId: params.agentId,
       });
       ```
       This uses the existing CorrelationService.register() which does an upsert (ON CONFLICT → reactivate). The correlation enables:
       - Comment routing: `linear.comment.created` events → router slow_path → correlation_fallback → signal to conversation
       - Parent issue resolution: `resolveParentLinearIssueId` in delegate_task (Plan 04) queries work_correlations

    8. Return `{ externalId: issueId, externalUrl: issueUrl }`.

    9. Wrap ENTIRE create() in try/catch. On any error, log with full context and return null (graceful degradation per locked decision).

    **syncStatus() implementation:**
    1. Map internal status to Linear state type: `active` -> "started", `completed` -> "completed", `cancelled` -> "canceled". Return early if status doesn't map.
    2. Call `callMcpTool({ integration: "linear", tool: "update_issue_status", params: { issueId: params.externalId, stateType: mappedStateType }, agentId: "system", correlationId: `mat-sync-${params.taskId}` })`.
    3. Update materialization_records.sync_status to "completed" when task is completed/cancelled, keep "active" otherwise.
    4. Update materialization_records.updated_at.
    5. Wrap in try/catch, log errors, never throw (fire-and-forget per locked decision).

    **handleWebhook() implementation:**
    1. Look up materialization_records by target="linear" and external_id=params.externalId.
    2. If no record found, return null (not a materialized issue).
    3. Parse eventData for status changes, assignee changes, and comments.
    4. For status changes: check if new state type is "canceled" -> return `{ signalType: "task_cancelled", signalData: { reason: "Cancelled in Linear by human", taskId: record.task_id }, conversationId: record.conversation_id, deduplicationId: "mat-cancel-{externalId}" }`.
    5. For status "completed" -> return `{ signalType: "materialization_status_update", signalData: { status: "completed", reason: "Marked done in Linear by human", taskId: record.task_id }, conversationId: record.conversation_id, deduplicationId: "mat-done-{externalId}" }`. This is informational -- agent decides what to do.
    6. For assignee changes where new assignee is a human (not the bot) -> return `{ signalType: "task_cancelled", signalData: { reason: "Reassigned to {assignee name} in Linear", taskId: record.task_id }, conversationId: record.conversation_id, deduplicationId: "mat-reassign-{externalId}" }`.
    7. For other changes -> return null (informational only, logged but no signal).

    **Pattern notes:**
    - Use `callMcpTool` from `../../mcp/index.js` for ALL Linear API calls (architecture boundary)
    - Use `createPinoLogger` child logger: `logger.child({ component: "linear-materialization-adapter" })`
    - Follow existing fire-and-forget pattern from task-signal-dispatcher.ts for non-blocking operations
