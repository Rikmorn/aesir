<research_summary>
## Summary

Phase 9.1 addresses infrastructure gaps discovered during milestone verification. The required technologies (OAuth2, Docker Compose) are well-established with clear patterns. This research documents the specific integration requirements for Linear OAuth and Temporal docker-compose.

Key finding: The existing Linear client (`src/integrations/linear/client.ts`) already implements token refresh logic. What's missing is the **initial authorization flow** (code exchange) and **token persistence**. The OAuth authorization URL must include `actor=app` to ensure agent actions appear as the app identity rather than the authorizing user.

**Primary recommendation:** Implement OAuth authorization flow as a standalone script that persists tokens to JSON file (or SQLite). Docker Compose should use Temporal's official `docker-compose.yml` with PostgreSQL backend. Linear Agent SDK is already well-implemented in the codebase; only minor gaps exist (external URLs, action results).

</research_summary>

## Linear Agent Interaction SDK

The project already implements agent activities in `src/integrations/linear/activities.ts`. This section documents the full Linear Agent SDK for reference and any gaps.

### Agent Sessions

Agent sessions represent the lifecycle of an agent's work on an issue. Sessions are created automatically when:
- Agent is mentioned in an issue/comment
- Agent is delegated (assigned) an issue

**Session States:**
| State | Description | Triggered By |
|-------|-------------|--------------|
| `pending` | Session created, agent not yet responded | Initial creation |
| `active` | Agent is working | `thought` or `action` activity |
| `awaitingInput` | Agent needs user input | `elicitation` activity |
| `error` | Agent encountered failure | `error` activity |
| `complete` | Agent finished work | `response` activity |

**Important:** Linear tracks session state automatically based on last emitted activity. No manual state management needed.

### Activity Types

Five semantic activity types for communicating progress:

```typescript
// Already implemented in src/integrations/linear/activities.ts

// 1. Thought - internal reasoning visible to user
{ type: "thought", body: "Analyzing the requirements..." }

// 2. Action - tool invocation (in-progress)
{ type: "action", action: "Reading", parameter: "repository code" }

// 3. Action - tool invocation (completed with result)
{ type: "action", action: "Read", parameter: "repository code", result: "Found 15 files" }

// 4. Response - final completion message
{ type: "response", body: "Created PR #123 with the implementation." }

// 5. Error - failure message
{ type: "error", body: "Failed to access repository. Check permissions." }

// 6. Elicitation - request user input
{ type: "elicitation", body: "Which authentication method should I use?" }
```

### Response Time Requirements

- **Webhook response:** Must return HTTP response within 5 seconds
- **Initial activity:** Emit `thought` activity within 10 seconds of `created` event
- **Failure to respond:** Session may be marked as unresponsive

### OAuth Scopes for Agents

Required scopes for full agent functionality:
| Scope | Purpose |
|-------|---------|
| `read` | Read issues, comments, users |
| `write` | Update issues, create comments |
| `issues:create` | Create new issues |
| `comments:create` | Create comments on issues |
| `app:assignable` | Allow delegation to agent |
| `app:mentionable` | Allow @mentions of agent |

**Note:** Apps using `actor=app` cannot request `admin` scope.

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Missing `actor=app` Parameter
**What goes wrong:** Agent actions appear as the authorizing user instead of the app
**Why it happens:** Default OAuth flow uses `actor=user`
**How to avoid:** Always include `actor=app` in authorization URL
**Warning signs:** Actions in Linear show user avatar instead of app avatar

### Pitfall 2: Forgetting to Refresh Tokens
**What goes wrong:** Agent stops working after 24 hours when token expires
**Why it happens:** Access tokens have 24-hour lifespan (was 10 years for legacy)
**How to avoid:** Already handled in `client.ts` - ensure `onTokenRefresh` callback persists new tokens
**Warning signs:** "Unauthorized" errors appearing after running for a day

### Pitfall 3: Docker Compose Port Conflicts
**What goes wrong:** Services fail to start due to port conflicts
**Why it happens:** Local services already using 7233, 8080, etc.
**How to avoid:** Document required ports; provide alternative port mappings
**Warning signs:** "port already in use" errors on `docker-compose up`

### Pitfall 4: State Parameter Mismatch
**What goes wrong:** OAuth callback rejected with CSRF error
**Why it happens:** State parameter not verified between request and callback
**How to avoid:** Generate random state, store it, verify on callback
**Warning signs:** "Invalid state" error after authorization

### Pitfall 5: Temporal Worker Not Connected
**What goes wrong:** Workflows start but tasks never execute
**Why it happens:** Worker running before Temporal server is ready
**How to avoid:** Add health check / retry logic; or use `depends_on` with health condition
**Warning signs:** Workflow shows "pending" tasks indefinitely

</common_pitfalls>

## Code Examples

### OAuth Authorization Script Structure
```typescript
// src/scripts/linear-oauth.ts
// Source: Based on Linear OAuth docs

import http from "node:http";
import open from "open";  // Or just console.log URL for manual opening

const CLIENT_ID = process.env.LINEAR_CLIENT_ID!;
const REDIRECT_URI = "http://localhost:3000/oauth/callback";
const STATE = crypto.randomUUID();

// 1. Build authorization URL
const authUrl = new URL("https://linear.app/oauth/authorize");
authUrl.searchParams.set("client_id", CLIENT_ID);
authUrl.searchParams.set("redirect_uri", REDIRECT_URI);
authUrl.searchParams.set("response_type", "code");
authUrl.searchParams.set("state", STATE);
authUrl.searchParams.set("scope", "read,write,issues:create,comments:create");
authUrl.searchParams.set("actor", "app");  // CRITICAL for app identity

// 2. Start local server to receive callback
const server = http.createServer(async (req, res) => {
  const url = new URL(req.url!, `http://localhost:3000`);

  if (url.pathname === "/oauth/callback") {
    const code = url.searchParams.get("code");
    const returnedState = url.searchParams.get("state");

    // Verify state
    if (returnedState !== STATE) {
      res.writeHead(400);
      res.end("Invalid state parameter");
      return;
    }

    // Exchange code for tokens
    const tokens = await exchangeCodeForTokens(code!);

    // Save tokens
    await saveTokens(tokens);

    res.writeHead(200);
    res.end("Authorization successful! You can close this window.");
    server.close();
  }
});

server.listen(3000, () => {
  console.log("Open this URL in your browser:");
  console.log(authUrl.toString());
  // Optionally: open(authUrl.toString());
});
```

<open_questions>
## Open Questions

1. **Should OAuth tokens be encrypted at rest?**
   - What we know: JSON file is simple; encryption adds complexity
   - What's unclear: User's security requirements for local dev
   - Recommendation: Use restrictive file permissions (0600) for MVP; add encryption later if needed

2. **Docker Compose: Full stack vs Temporal only?**
   - What we know: User wants "docker-compose up starts everything"
   - What's unclear: Whether agents should run in containers or on host
   - Recommendation: Start with Temporal-only compose; agents on host for easier debugging. Add agent containers as optional profiles.

3. **E2E test scope?**
   - What we know: Success criteria includes "Full E2E test passes on real repository"
   - What's unclear: What constitutes the E2E test - just Product Agent? Full workflow?
   - Recommendation: Clarify during planning; likely Product Agent → Linear task creation is sufficient for v1.0
