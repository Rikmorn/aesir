Create `packages/agents/src/router/types.ts` with:

1. Import `NormalizedEvent` from `@aesir/types`, `PinoLogger` from `@aesir/platform`, `Client` from `@temporalio/client`.

2. Define `RouterDeps` interface:
   - `workflowClient: Client` (Temporal client for starting/signaling workflows)
   - `logger: PinoLogger`
   - `alertsChannel?: string` (Slack channel for ROUT-06 fallback alerts)

3. Define `FastPathAction` discriminated union type with variants:
   - `{ type: "signal"; workflowId: string; signal: string; payload: Record<string, unknown> }` -- for signaling existing workflows
   - `{ type: "start"; workflowName: string; taskQueue: string; workflowId: string; args: unknown[]; needsEnrichment?: boolean; enrichmentContext?: Record<string, unknown> }` -- for starting new workflows
   - `{ type: "ignore"; reason: string }` -- for acknowledged but not-actionable events (e.g., linear.issue.created/updated)

4. Define `RouteResult` type:
   - `status: "routed" | "ignored" | "failed"`
   - `action?: string` (what was done, for logging)
   - `workflowId?: string`
   - `error?: string`

5. Define `RoutingRule` interface:
   - `name: string` (human-readable rule name for logging)
   - `match: (event: NormalizedEvent) => boolean`
   - `action: (event: NormalizedEvent) => FastPathAction`

Create `packages/agents/src/router/fast-path.ts` with:

1. Import types from `./types.js`, `NormalizedEvent` from `@aesir/types`.
2. Import `callMcpTool` from `../../shared/mcp/index.js` (needed by executeFastPath for agent_session enrichment).
3. Import signal definitions from `../../shared/temporal/signals.js`: `planApprovalSignal`, `prCompletionSignal`, `escalationResolvedSignal`.

4. Define `DETERMINISTIC_RULES: RoutingRule[]` array covering ALL 7 fast-path events plus 2 ignore events:

   a. `slack-approval-button`: Match `slack.block_actions.approved`. Action: signal `planApproval` to `dev-agent-{payload.taskIdentifier}` with `{ approved: true, source: "slack" }`.

   b. `slack-rejection-button`: Match `slack.block_actions.rejected`. Action: signal `planApproval` to `dev-agent-{payload.taskIdentifier}` with `{ approved: false, feedback: "Rejected via Slack button", source: "slack" }`.

   c. `slack-escalation-retry`: Match `slack.block_actions.escalation_retry`. Action: signal `escalationResolved` to `dev-agent-{payload.taskIdentifier}` with `{ action: "retry" }`.

   d. `slack-escalation-abort`: Match `slack.block_actions.escalation_abort`. Action: signal `escalationResolved` to `dev-agent-{payload.taskIdentifier}` with `{ action: "abort" }`.

   e. `github-pr-merged`: Match `github.pull_request.merged`. Action: Extract task ID from `payload.branchName` using regex `/feature\/([A-Z]+-\d+)/i` (same pattern as signal-handler.ts line 174). Signal `prCompletion` to `dev-agent-{taskId}` with `{ merged: true, prNumber: payload.prNumber }`. If regex doesn't match, return `ignore` action with reason.

   f. `github-pr-closed`: Match `github.pull_request.closed`. Same extraction logic as (e) but with `{ merged: false, prNumber: payload.prNumber }`.

   g. `linear-agent-session-created`: Match `linear.agent_session.created`. Action: `start` with workflowName `"devAgentWorkflow"`, taskQueue `"dev-agent"`, workflowId `dev-agent-{payload.issueId}`, `needsEnrichment: true`, `enrichmentContext: { issueId: payload.issueId }`. The args array should be empty -- executeFastPath will populate it after enrichment.

   h. `linear-issue-created`: Match `linear.issue.created`. Action: `ignore` with reason "Issue events acknowledged but not actionable".

   i. `linear-issue-updated`: Match `linear.issue.updated`. Action: `ignore` with reason "Issue events acknowledged but not actionable".

5. Cast payload to typed interfaces. Use inline interface definitions matching the payload shapes from events.ts (SlackBlockActionsPayload, GitHubPRClosedPayload, etc.) or use `Record<string, unknown>` with type narrowing.

6. Define `matchFastPath(event: NormalizedEvent): FastPathAction | null`:
   - Iterate through DETERMINISTIC_RULES
   - Return first match's action result
   - Return null if no match (event goes to slow path)

7. Define `executeFastPath(action: FastPathAction, deps: RouterDeps): Promise<RouteResult>`:
   - For "signal": Get workflow handle via `deps.workflowClient.workflow.getHandle(action.workflowId)`, look up the signal definition object from the imported signal definitions using a map from signal name string to signal definition (e.g., `{ planApproval: planApprovalSignal, prCompletion: prCompletionSignal, escalationResolved: escalationResolvedSignal }`), then call `handle.signal(signalDef, action.payload)`. Handle WorkflowNotFoundError gracefully (log warn, return `{ status: "failed", error: "Workflow not found" }`).
   - For "start" WITHOUT `needsEnrichment`: Start workflow directly with `deps.workflowClient.workflow.start(action.workflowName, { taskQueue: action.taskQueue, workflowId: action.workflowId, args: action.args })`. Handle WorkflowExecutionAlreadyStartedError gracefully (log info, return `{ status: "routed", action: "workflow already exists" }`).
   - For "start" WITH `needsEnrichment` (agent_session events): Use `callMcpTool` to fetch issue details from Linear (`integration: "linear"`, `tool: "get_issue"`, `params: { issueId: action.enrichmentContext.issueId }`, `agentId: "router"`). Build `DevAgentWorkflowInput` from the issue details (title, description, identifier, etc.). Then start the workflow with the built input as args. If MCP call fails, log error and return `{ status: "failed", error: "Failed to fetch issue details for enrichment" }`.
   - For "ignore": Return `{ status: "ignored", action: reason }`.

IMPORTANT: Use the same workflow ID derivation formulas as the existing code:
- Dev agent: `dev-agent-{Linear UUID or identifier}`
- Product agent: `product-agent-{threadTs}`

Follow codebase patterns:
- Import PinoLogger from @aesir/platform
- Use exactOptionalPropertyTypes-compatible spread patterns for optional fields
- Use Biome type import ordering (type imports before value imports in combined imports)

Create `packages/agents/src/router/system-prompt.ts` with a comprehensive system prompt for the router's LLM path.

The prompt MUST absorb the approval classification guidance from `dev-agent/classification/approval.ts` (APPROVAL_CLASSIFICATION_PROMPT). The router replaces the dedicated classifier.

Export `ROUTER_SYSTEM_PROMPT` as a const string using template literal for readability.

Structure the prompt with XML sections (established pattern from Phase 31/33):

```
<identity>
You are a routing agent for the Aesir development platform. Your job is to classify incoming events and route them to the correct agent workflow by calling the appropriate tool.

You receive a single event and must decide: which workflow to start, signal, or ignore.
</identity>

<available_agents>
- **Dev Agent** (task queue: "dev-agent"): Handles Linear issue implementation. Workflow ID format: dev-agent-{issueId}
  - Signals: planApproval, prFeedback, escalationResolved, prCompletion
- **Product Agent** (task queue: "product-agent"): Handles Slack conversations for requirement gathering. Workflow ID format: product-agent-{threadTs}
  - Signals: userReply, cancelConversation
</available_agents>

<routing_rules>
1. **Slack @mention (not in thread)**: Start a product-agent workflow. Use the message timestamp as threadTs.
2. **Slack thread reply**: Signal the existing product-agent workflow with userReply. Workflow ID: product-agent-{threadTs}.
3. **Linear comment on issue with running workflow**: Classify the comment intent and signal accordingly:
   - approve/reject -> signal planApproval with approved=true/false
   - guidance -> signal escalationResolved with action="retry" and guidance text
   - abort -> signal escalationResolved with action="abort"
   - question/unclear -> send a clarifying message via Slack, do NOT signal the workflow
4. **GitHub PR review**: Signal the dev-agent workflow with prFeedback containing the review body. Extract task ID from the branch name pattern feature/{IDENTIFIER}.
5. **Unknown events**: If you cannot determine the correct action, log the event as unroutable.
</routing_rules>

<intent_classification>
[Port the FULL intent classification guidance from APPROVAL_CLASSIFICATION_PROMPT here, including all intent types with examples: approve, reject, question, unclear, guidance, abort]
</intent_classification>

<constraints>
- Route events, do NOT process them. Your job is classification and routing, not content analysis.
- Do NOT interpret cancellation intent in thread messages. Route ALL thread replies to existing workflows; the agent decides if it's a cancellation.
- Make ONE routing decision per event. Do not call multiple tools.
- If you cannot find a running workflow for a signal, log the event as unroutable.
- Prefer query_running_workflows before signaling if you're unsure a workflow exists.
</constraints>

<tools>
- query_running_workflows: List active workflows, optionally filtered by taskId. Use to check if a workflow exists before signaling.
- start_workflow: Start a new Temporal workflow on the correct task queue.
- signal_workflow: Send a signal to an existing workflow.
- send_message: Send a Slack message (for clarification or error reporting).
</tools>
```

Key requirements:
- Port ALL intent examples from APPROVAL_CLASSIFICATION_PROMPT (approve, reject, question, unclear, guidance, abort) with their example phrases
- Include workflow ID derivation rules explicitly
- Include signal names and their payload shapes
- Keep the prompt focused on ROUTING, not content processing
