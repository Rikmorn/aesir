# Phase 58.3: Integration Correlation - Research

**Researched:** 2026-02-07
**Domain:** MCP header propagation, database correlation tables, webhook correlation lookup
**Confidence:** HIGH

## Summary

This phase adds bidirectional correlation between the v2.5 task primitive and external artifacts (Linear issues, GitHub PRs, Slack threads). Outgoing MCP calls from agents record correlations when creating artifacts, and incoming webhooks look up correlations to attach task IDs to events before forwarding.

The codebase is well-structured for this change. The MCP HTTP layer already passes `X-Agent-ID` and `X-Correlation-ID` headers from the agent-side `callMcpTool()` client through to integration handlers. Adding `X-Task-ID` follows the exact same pattern. Each integration package is independent with its own DB schema, migration directory, and HTTP routes -- the correlation table and recording/lookup logic stays fully within each package boundary.

The webhook handlers already parse payloads and extract entity references (issueId, PR number, channelId:threadTs) before normalizing events. The correlation lookup is a simple `SELECT task_id FROM {schema}.task_correlations WHERE external_type = $1 AND external_ref = $2` query, called from the existing webhook handler after payload parsing.

**Primary recommendation:** Follow the existing MCP header pattern exactly. Add `taskId?: string` to `McpCallOptions` and `McpToolDeps`. Extract from `X-Task-ID` header in integration MCP routes. Record correlation as fire-and-forget INSERT after API success. Look up in webhook handlers before normalizing events. Add `taskId?: string` to `IncomingEventSchema`.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **Anchor-entity pattern**: Incoming lookup uses anchor entity only (Linear: issue, GitHub: pull_request, Slack: thread + approval). Sub-artifacts (comments, branches, commits) are write-only for correlation.
- **Lookup in webhook handler**: Not middleware. One shared helper per integration: `lookupTaskCorrelation(db, type, ref) -> taskId | undefined`.
- **Recording after API success**: Fire-and-forget INSERT after integration API returns. `INSERT ... ON CONFLICT (external_type, external_ref) DO NOTHING`. First wins.
- **Shared utility per integration**: `recordTaskCorrelation(db, taskId: string | undefined, type, ref)` -- guards itself when taskId is undefined, handlers call unconditionally.
- **One migration per integration**: Each package gets its own migration in `src/db/migrations/`. No index on task_id.
- **Type changes are not migrations**: Adding `taskId?: string` to `IncomingEvent` is a TypeScript change, not a DB migration.

### Pattern 1: X-Task-ID Header Propagation

**What:** Flow task ID from conversation through MCP call to integration handler.
**When to use:** Every outgoing MCP call from an agent.

The chain is:
1. `ToolContext.taskId` (set by worker-loop from `conv.task_id`) already exists at line 613 of worker-loop.ts
2. `mcpAdapter` in tool-factories.ts extracts it into `McpToolDeps`
3. `createMcpToolWrapper` passes it through `McpCallOptions` to `callMcpTool`
4. `callMcpTool` adds `X-Task-ID` header when present
5. Integration MCP route extracts header and passes to tool handler or records correlation directly

**Example (agent-side MCP client):**
```typescript
// packages/agents/src/shared/mcp/types.ts
export interface McpCallOptions {
  integration: McpIntegration;
  tool: string;
  params: Record<string, unknown>;
  agentId: string;
  correlationId: string;
  taskId?: string;  // NEW
}

// packages/agents/src/shared/mcp/client.ts
const headers: Record<string, string> = {
  "Content-Type": "application/json",
  "X-Agent-ID": agentId,
  "X-Correlation-ID": correlationId,
};
if (options.taskId) {
  headers["X-Task-ID"] = options.taskId;
}
```

**Example (integration-side extraction):**
```typescript
// In any integration's api/mcp.ts POST /tools/:name handler
const taskId = req.headers["x-task-id"] as string | undefined;
// After successful tool execution:
if (taskId && isCorrelatableOperation(name)) {
  await recordTaskCorrelation(db, taskId, externalType, externalRef);
}
```

### Pattern 2: Correlation Recording (Fire-and-Forget)

**What:** After a tool handler successfully creates an artifact, record the correlation.
**When to use:** On correlatable MCP tool calls (create_issue, create_pull_request, send_message, etc.).

**Example:**
```typescript
// packages/integrations/linear/src/db/task-correlations.ts
export async function recordTaskCorrelation(
  db: NodePgDatabase,
  taskId: string | undefined,
  externalType: string,
  externalRef: string,
): Promise<void> {
  if (!taskId) return;  // No-op guard

  try {
    await db.execute(sql`
      INSERT INTO linear.task_correlations (external_type, external_ref, task_id)
      VALUES (${externalType}, ${externalRef}, ${taskId})
      ON CONFLICT (external_type, external_ref) DO NOTHING
    `);
  } catch (err) {
    // Fire-and-forget: log and continue
    // The existing MCP error handling will not be affected
  }
}
```

### Pattern 3: Correlation Lookup (Webhook Handler)

**What:** Before forwarding a webhook event to the router, look up whether the artifact has a task correlation.
**When to use:** In webhook handlers for anchor entities only.

**Example:**
```typescript
// packages/integrations/linear/src/db/task-correlations.ts
export async function lookupTaskCorrelation(
  db: NodePgDatabase,
  externalType: string,
  externalRef: string,
): Promise<string | undefined> {
  const rows = await db.execute(sql`
    SELECT task_id FROM linear.task_correlations
    WHERE external_type = ${externalType} AND external_ref = ${externalRef}
    LIMIT 1
  `);
  return rows[0]?.task_id as string | undefined;
}
```

### Pattern 4: NormalizedEvent taskId Attachment

**What:** The webhook handler attaches taskId to the NormalizedEvent payload, the adapter extracts it into IncomingEvent.taskId.
**When to use:** When correlation lookup returns a result.

Two options for how to carry taskId through the event pipeline:

**Option A (Recommended): Add taskId to IncomingEvent only.** The adapter does the lookup. NormalizedEvent stays unchanged. Simpler, fewer cross-package changes. But this means the lookup happens in the agent-service adapters, not in the integration webhook handlers.

**Option B: Carry through NormalizedEvent payload.** The integration webhook handler puts taskId in the NormalizedEvent payload. The adapter extracts it. This matches the CONTEXT.md decision ("in the existing webhook handler").

Given CONTEXT.md explicitly says lookup happens in the webhook handler (not adapter), **Option B is correct**:
```typescript
// In webhook handler, after payload parsing:
const taskId = await lookupTaskCorrelation(db, "issue", issueId);

// Include in NormalizedEvent payload
const normalizedEvent = normalizeCommentCreatedEvent(commentPayload, deliveryId);
// Add taskId to payload before dispatch
if (taskId) {
  (normalizedEvent.payload as Record<string, unknown>).taskId = taskId;
}
dispatcher.dispatch(normalizedEvent);
```

Then in the adapter:
```typescript
// Extract taskId from payload if present
const taskId = payload.taskId as string | undefined;
return {
  type: "issue_comment",
  data: { ... },
  source: "linear:webhook",
  correlationKey: issueId,
  taskId,  // NEW optional field on IncomingEvent
};
```

### Anti-Patterns to Avoid
- **Middleware for lookup**: The decision explicitly says "not middleware" -- the handler already has the parsed payload and knows the entity type.
- **Reverse index on task_id**: No queries go from task_id to external_ref in this phase. Index earns its place when the first reverse query ships.
- **Many-to-many correlations**: First-write wins via ON CONFLICT DO NOTHING. Many-to-many is explicitly deferred.
- **Application-level duplicate checking**: Let Postgres handle duplicates via the PK constraint. No `SELECT` before `INSERT`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Duplicate correlation handling | Application-level duplicate detection | `ON CONFLICT DO NOTHING` PK constraint | Atomic, race-condition-free, zero extra queries |
| Task ID propagation | Custom middleware or interceptor | HTTP header (`X-Task-ID`) following existing `X-Agent-ID` pattern | Consistent with established codebase pattern |
| Migration schema | Drizzle-kit generated migration | Hand-written SQL migration file | Existing pattern in all three integration packages |

## Common Pitfalls

### Pitfall 1: Forgetting to Pass taskId Through McpToolDeps

**What goes wrong:** The mcpAdapter in tool-factories.ts constructs McpToolDeps from ToolContext. If it doesn't extract `taskId`, the MCP client never sends the header.
**Why it happens:** McpToolDeps currently only has `agentId` and `correlationId`.
**How to avoid:** Update `McpToolDeps` interface, update `mcpAdapter` to extract `ctx.taskId`, update `createMcpToolWrapper` to pass it to `callMcpTool`.
**Warning signs:** MCP calls succeed but no correlations are recorded in the DB.

### Pitfall 2: Recording Correlation on Read-Only Operations

**What goes wrong:** `get_issue`, `search_issues`, `get_pull_request` etc. are read-only -- they don't create artifacts. Recording correlations for these would create spurious entries.
**Why it happens:** The X-Task-ID header is sent on all MCP calls.
**How to avoid:** Only record correlation on specific correlatable operations. The recording call is per-tool, not automatic.
**Warning signs:** Thousands of correlation rows for get_issue calls.

### Pitfall 3: Blocking MCP Response on Correlation Failure

**What goes wrong:** If the correlation INSERT fails (e.g., DB connection issue), the MCP tool invocation also fails.
**Why it happens:** Not wrapping the correlation INSERT in try/catch.
**How to avoid:** Fire-and-forget pattern: try/catch around INSERT, log error, return the original tool result regardless.
**Warning signs:** MCP tools intermittently failing when the correlation table is inaccessible.

### Pitfall 4: Slack Thread Reference Format

**What goes wrong:** Slack threads are identified by `channelId:threadTs`, not threadTs alone. Same threadTs in different channels refers to different threads.
**Why it happens:** Developer records only threadTs, ignoring channel scoping.
**How to avoid:** Always compose the external_ref as `${channelId}:${threadTs}` for Slack thread correlations.
**Warning signs:** Cross-channel correlation confusion.

### Pitfall 5: GitHub PR Number vs Owner/Repo Scoping

**What goes wrong:** PR number 42 exists in many repos. Recording just "42" as the external_ref creates cross-repo conflicts.
**Why it happens:** PR numbers are not globally unique.
**How to avoid:** Compose external_ref as `${owner}/${repo}#${prNumber}` for GitHub PR correlations.
**Warning signs:** Webhook from repo-A's PR routes to repo-B's task.

### Pitfall 6: Linear Issue Identifier Formats

**What goes wrong:** Linear issues have both UUIDs (`id`) and human identifiers (`identifier`, e.g., "ABC-123"). The webhook and the MCP tool may use different formats.
**Why it happens:** The `create_issue` tool returns both `id` (UUID) and `identifier`. The webhook payload includes `data.issueId` which is the UUID.
**How to avoid:** Use the Linear issue UUID (`id`) as the external_ref consistently. Both the MCP tool result and the webhook payload provide this.
**Warning signs:** Correlation lookup fails because the recording used identifier but the webhook uses UUID.

### Pitfall 7: Drizzle Schema Files Must Be Updated in Both Places

**What goes wrong:** The application code uses `schema.ts` (imports `@aesir/types`), but migration generation uses `schema.drizzle.ts` (standalone, no external deps). If only one is updated, either the app or migrations are out of sync.
**Why it happens:** Two schema files exist per integration (see Gotchas in CLAUDE.md).
**How to avoid:** Update both `schema.ts` and `schema.drizzle.ts` when adding the task_correlations table.
**Warning signs:** Drizzle-kit generates an unexpected migration or the application can't query the table.

### Migration SQL (Linear Example)

```sql
-- Task correlations table
-- Maps external Linear artifacts to internal task IDs.
-- PK on (external_type, external_ref) ensures one task per artifact.
-- ON CONFLICT DO NOTHING provides first-write-wins semantics.
CREATE TABLE IF NOT EXISTS "linear"."task_correlations" (
  "external_type" text NOT NULL,
  "external_ref" text NOT NULL,
  "task_id" text NOT NULL,
  "created_at" timestamp with time zone DEFAULT now() NOT NULL,
  PRIMARY KEY ("external_type", "external_ref")
);
```

## Open Questions

1. **MCPToolContext vs separate parameter**
   - What we know: The integration MCP handlers receive `MCPToolContext` with `agentId`, `correlationId`, `logger`, `startTime`. Task ID needs to reach the handler.
   - What's unclear: Should `taskId` be added to `MCPToolContext` (types package change), or extracted separately in the HTTP handler?
   - Recommendation: Add `taskId?: string` to `MCPToolContext` for consistency. It's a backward-compatible optional addition. The HTTP handler creates this context from headers anyway.

2. **Composite PK in Drizzle**
   - What we know: Drizzle supports composite PKs but the syntax depends on version.
   - What's unclear: Exact Drizzle syntax for composite primary key in the table definition.
   - Recommendation: Use raw SQL migration for the PK (consistent with existing hand-written migrations like `0000_create_linear_schema.sql`), and approximate it in Drizzle schema. Or use `primaryKey()` in the table's constraint array -- verify at implementation time.

3. **Slack send_message thread detection**
   - What we know: `send_message` can create new threads (first message in channel) or send within existing threads (when `threadTs` is provided). The response always includes `ts` (the new message's timestamp).
   - What's unclear: For a new message that starts a thread, `ts` IS the `threadTs` for future replies. For a reply, `threadTs` was provided by the caller.
   - Recommendation: Record correlation as `("thread", "{channel}:{ts}")` where `ts` is the response timestamp. This works for both cases since the first message's `ts` becomes the thread's identifier.
