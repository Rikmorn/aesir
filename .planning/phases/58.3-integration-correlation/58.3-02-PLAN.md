    Create NEW file `packages/integrations/linear/src/db/task-correlations.ts` with two exported functions:

    **recordTaskCorrelation:**
    ```typescript
    export async function recordTaskCorrelation(
      db: NodePgDatabase,
      taskId: string | undefined,
      externalType: string,
      externalRef: string,
      logger: MCPLogger,
    ): Promise<void>
    ```
    - Guard: if taskId is undefined, return immediately (no-op). This lets callers call unconditionally.
    - Execute: `INSERT INTO linear.task_correlations (external_type, external_ref, task_id) VALUES ($1, $2, $3) ON CONFLICT (external_type, external_ref) DO NOTHING`
    - Use raw SQL via `db.execute(sql`...`)` from drizzle-orm (simpler than query builder for an upsert with DO NOTHING on composite PK).
    - Wrap in try/catch. On error, log at error level with context `{ taskId, externalType, externalRef }` and the message "Failed to record task correlation (non-fatal)". Do NOT rethrow -- this is fire-and-forget per user decision.

    **lookupTaskCorrelation:**
    ```typescript
    export async function lookupTaskCorrelation(
      db: NodePgDatabase,
      externalType: string,
      externalRef: string,
      logger: MCPLogger,
    ): Promise<string | undefined>
    ```
    - Execute: `SELECT task_id FROM linear.task_correlations WHERE external_type = $1 AND external_ref = $2 LIMIT 1`
    - Return the task_id string or undefined if no row found.
    - Wrap in try/catch. On error, log at error level with context `{ externalType, externalRef }` and return undefined (non-fatal).

    Import `sql` from `drizzle-orm` for raw queries. Import `NodePgDatabase` from `drizzle-orm/node-postgres`. Import `MCPLogger` from `@aesir/types`.

    **MCP handler (mcp.ts) -- outgoing recording:**

    1. Extract `X-Task-ID` header at the top of the POST /tools/:name handler, alongside existing header extraction:
       ```typescript
       const taskId = req.headers["x-task-id"] as string | undefined;
       ```
       Add taskId to the requestLogger child bindings for tracing.

    2. After each correlatable tool handler returns successfully (no isError), call recordTaskCorrelation. The correlatable tools and their external_type/external_ref are:

       - `create_issue`: After `handleCreateIssue` returns result, extract the issue UUID from `result.structuredContent.id` (the CreateIssueOutput has an `id` field). Record as `("issue", issueId)`.
       - `create_comment`: After `handleCreateComment` returns result, extract the comment ID from `result.structuredContent.id`. Record as `("comment", commentId)`.

       Pattern for each correlatable case in the switch:
       ```typescript
       case "create_issue":
         result = await handleCreateIssue(context, args, issueToolDeps);
         if (!result.isError) {
           const data = result.structuredContent as { id: string } | undefined;
           if (data?.id) {
             recordTaskCorrelation(db, taskId, "issue", data.id, requestLogger)
               .catch(() => {}); // Already logged inside
           }
         }
         break;
       ```

       Note: `recordTaskCorrelation` guards on undefined taskId internally, so no conditional needed around the call. The `.catch(() => {})` suppresses unhandled promise rejection since the function already logs errors internally.

    3. Do NOT record correlations for read-only operations (get_issue, list_teams, list_labels, search_issues, update_issue_status).

    4. Also pass `taskId` into MCPToolContext so tool handlers have it available:
       ```typescript
       const context: MCPToolContext = {
         logger: requestLogger,
         correlationId,
         agentId,
         startTime,
         taskId, // v2.5 task correlation
       };
       ```

    5. Import `recordTaskCorrelation` from `../db/task-correlations.js`.

    **Webhook handler (webhooks.ts) -- incoming lookup:**

    1. Import `lookupTaskCorrelation` from `../db/task-correlations.js`.

    2. The webhook router needs a `db` dependency. Add `db: NodePgDatabase` to the `WebhookRouterDeps` interface. (This is a backward-compatible addition -- the caller in main.ts already has the db available and can pass it through.)

    3. For **Comment events** (type === "Comment", action === "create"):
       - After parsing `commentPayload`, before normalizing the event:
       - Look up correlation using the anchor entity: `lookupTaskCorrelation(db, "issue", commentPayload.data.issueId, childLogger)`
       - If taskId found, add it to the normalizedEvent payload: `normalizedEvent.payload.taskId = taskId`
       - The NormalizedEvent.payload is typed as `z.unknown()` so this works with a cast to `Record<string, unknown>`.

    4. For **AgentSession events** (type === "AgentSessionEvent"):
       - After parsing `payload`, before normalizing the event:
       - Look up correlation: `lookupTaskCorrelation(db, "issue", payload.agentSession.issueId, childLogger)`
       - If taskId found, add it to the normalizedEvent payload similarly.

    5. The adapter layer (packages/agents/src/adapters/linear.ts) will need to extract taskId from the payload and map it to IncomingEvent.taskId, but that change is part of the adapter work. For now, just ensure the taskId is present in the NormalizedEvent payload so the adapter can find it. This wiring pattern is: webhook handler puts taskId in NormalizedEvent.payload -> adapter extracts to IncomingEvent.taskId.

    6. Update the Linear adapter in `packages/agents/src/adapters/linear.ts`: In each case that produces an IncomingEvent, extract `taskId` from the payload if present and include it in the returned IncomingEvent:
       ```typescript
       const taskId = payload.taskId as string | undefined;
       return {
         type: "...",
         data: { ... },
         source: "linear:webhook",
         ...(taskId && { taskId }),
         // ... other fields
       };
       ```
       Apply this to: `linear.comment.created` and `linear.agent_session.prompted` cases (these are the ones that have anchor entity lookups). Also apply to `linear.agent_session.created` since that event uses issueId too.
