# Phase 58.3: Integration Correlation - Context

**Gathered:** 2026-02-07
**Status:** Ready for planning

<domain>
## Phase Boundary

External artifacts (Linear issues, GitHub PRs, Slack threads) get automatically correlated to tasks. Outgoing MCP calls record the correlation when agents create artifacts. Incoming webhooks look up correlations and attach the task reference to events before forwarding to the agent service. This enables Phase 58.4 (task-aware event routing) to route events to the correct task's conversation.

</domain>

<decisions>
## Implementation Decisions

### Anchor-entity pattern for incoming lookup

Incoming webhook lookup uses the **anchor entity** for each integration, not every correlated type:

| Integration | Outgoing (record) | Incoming (lookup) |
|-------------|-------------------|-------------------|
| Linear | issue, comment | **issue only** |
| GitHub | pull_request, branch, commit | **pull_request only** |
| Slack | thread, approval | **thread + approval** |

**Rationale:** Comment, branch, and commit correlations are write-only in practice. Incoming webhooks for these types always include the parent entity ID in the payload (issueId in comment webhooks, PR number in push/check webhooks). Route via the anchor entity, not the sub-artifact. Outgoing recording of all types still happens for observability/audit.

**Slack specifics:**
- Thread replies: look up `("thread", "channelId:threadTs")` — direct responses to agent messages
- Approval button clicks (block_actions): look up `("approval", "channelId:messageTs")` — structured approval flow
- Reactions: NOT looked up — too noisy, no reliable way to distinguish meaningful acknowledgment from casual emoji

### Lookup location

Correlation lookup happens **in the existing webhook handler**, not in a middleware layer. The handler already parses the payload and knows the entity type. One shared helper function per integration:

```
lookupTaskCorrelation(db, type, ref) → taskId | undefined
```

Called from the webhook handler after payload parsing, before constructing the NormalizedEvent. Sets `taskId` on the event if found, leaves it undefined if not.

### Correlation recording mechanics

**Timing:** After the integration API call succeeds. No artifact ID exists until the API returns — nothing to correlate before that. Flow: MCP handler receives request with X-Task-ID header → call integration API → API returns entity ID → INSERT correlation (fire-and-forget) → return MCP response.

**SQL strategy:** `INSERT ... ON CONFLICT (external_type, external_ref) DO NOTHING`. No application-level error handling for duplicates — a duplicate key is a normal condition (same artifact re-correlated within the same task). Unexpected failures (connection error, schema issue) are handled by the existing MCP handler error handling.

**First wins:** ON CONFLICT DO NOTHING means the first task that creates an artifact owns the correlation. If a different task references the same artifact, the original correlation is preserved. The "many-to-many artifact correlation" scope item (deferred) is the proper fix for edge cases where this matters.

**Shared utility per integration:**
```
recordTaskCorrelation(db, taskId: string | undefined, type, ref)
```
- Utility guards itself — returns early if `taskId` is undefined. Handlers call unconditionally after API success.
- One utility per integration package (each writes to its own `{integration}.task_correlations` table)
- Not abstracted across integrations — they're independent packages with no shared dependency

### Migration and schema

- **One migration per integration package** — Linear, GitHub, Slack each get their own migration file in their `src/db/migrations/` directory. Follows existing independent package pattern.
- **No index on task_id** — The only query path in 58.3 and 58.4 is `(external_type, external_ref) → task_id`, which the PK covers. Reverse lookup index earns its place when the first reverse-lookup query ships (dashboard artifacts view, task cleanup, etc.), not before.
- **Type changes are not migrations** — `NormalizedEvent` (in @aesir/types) and `IncomingEvent` (in adapters/types.ts) are TypeScript types, not database tables. Adding `taskId?: string` is a backward-compatible interface addition, bundled in the same phase work.

### Claude's Discretion

- Exact helper function signatures and error logging patterns
- How to extract artifact references from webhook payloads (integration-specific payload parsing)
- MCP header propagation mechanics (X-Task-ID through McpCallOptions, McpToolDeps, MCPToolContext)
- Plan decomposition and ordering of work units

</decisions>

<specifics>
## Specific Ideas

- The `recordTaskCorrelation` utility should be a no-op when `taskId` is undefined — handlers call it unconditionally, less code per handler, one less thing to forget when adding new correlatable operations
- Linear comment webhooks route via issueId (always in the webhook payload), not by looking up the comment correlation. Same pattern: GitHub PR comment webhooks route via PR number
- GitHub push events to a PR branch fire a `pull_request` webhook with action `synchronize` that includes the PR number — route via PR, not branch. Check suites/runs include a `pull_requests` array — route via PR again.

</specifics>
