# Phase 47.1: Sub Agent Spawn - Research

**Researched:** 2026-02-03
**Domain:** Agent framework internal wiring (in-process nested agent loops)
**Confidence:** HIGH

## Summary

This phase wires the placeholder `spawn_agent` tool to the ConversationExecutor so the dev-agent can delegate work to sub-agents (researcher, coder, tester) that run as nested in-process agent loops. The research focused on understanding the current codebase state -- what exists, what needs to change, and how the pieces fit together.

The implementation is well-scoped: all infrastructure already exists (agent definitions, tool registry, agent loop, token budget, sandbox wiring). The work is primarily integration -- creating `spawn-agent.ts`, extending `ToolContext` with `spawnDeps`, replacing the placeholder in `tool-factories.ts`, and passing dependencies from the worker loop. No new libraries, no schema changes, no new patterns needed.

The key technical challenges are: (1) extending `ToolContext` cleanly without polluting it for non-spawning agents, (2) ensuring the tool registry's resolve flow works with spawn deps that only exist at conversation execution time, and (3) proper event tracking with `parent_instance_id` using existing event types.

**Primary recommendation:** Follow the wait_for tool pattern for executor integration, extend ToolContext with optional `spawnDeps`, and create `spawn-agent.ts` as a pure tool factory in `shared/tools/coordination/`.

### Pattern 1: ToolContext Extension with Optional Dependencies
**What:** Extend the existing `ToolContext` interface with an optional `spawnDeps` field that carries the spawn-specific dependencies.
**When to use:** When a tool factory needs dependencies that only exist at conversation execution time (not at registration time).
**Why this pattern:** CONTEXT.md locks this as the chosen approach (over closure capture). The worker loop populates `spawnDeps` conditionally when the agent has `coordination:spawn_agent` in its tool list.

```typescript
// In types.ts - ToolContext extension
export interface SpawnAgentDeps {
  agentRegistry: AgentRegistry;
  toolRegistry: ToolRegistry;
  tokenBudget: TokenBudget;
  eventLog: EventLog;
  parentDefinition: AgentDefinition;
  parentInstanceId: string;
  abortSignal?: AbortSignal;
  currentDepth: number;     // Spawn depth tracking
  maxSpawnDepth: number;    // Default: 3
}

export interface ToolContext {
  agentId: string;
  correlationId: string;
  containerManager?: DevContainerManager | undefined;
  taskId?: string | undefined;
  logger: PinoLogger;
  spawnDeps?: SpawnAgentDeps | undefined;  // NEW
}
```

### Pattern 2: Tool Factory with Context-Injected Dependencies
**What:** The `coordination:spawn_agent` factory in `tool-factories.ts` reads `ctx.spawnDeps` at resolution time and creates a tool that calls `runAgentLoop()` directly.
**When to use:** For tools that need framework-level dependencies not available at factory registration time.

```typescript
// In tool-factories.ts - replace placeholder
```

### Pattern 3: Worker Loop Dependency Injection
**What:** The worker loop checks if the agent definition has `coordination:spawn_agent` in its tool list and populates `toolContext.spawnDeps` before calling `toolRegistry.resolve()`.
**When to use:** At conversation execution time in `executeConversation()`.

```typescript
// In worker-loop.ts, inside executeConversation(), before tool resolution
const toolContext: ToolContext = {
  agentId: conv.agent_definition_id,
  correlationId: conv.id,
  logger: childLogger,
  ...(needsSandbox && sandboxManager && {
    containerManager: sandboxManager,
    taskId: conv.id,
  }),
};

// Populate spawn deps if agent can spawn sub-agents
const hasSpawnAgent = definition.tools.includes("coordination:spawn_agent");
if (hasSpawnAgent) {
  toolContext.spawnDeps = {
    agentRegistry,
    toolRegistry,
    tokenBudget: createTokenBudget(definition.tokenBudget), // shared budget
    eventLog,
    parentDefinition: definition,
    parentInstanceId: instanceId,
    abortSignal,
    currentDepth: 0,
    maxSpawnDepth: 3,
  };
}
```

### Pattern 4: Wait-For Tool Reference for Executor Integration
**What:** The wait_for tool uses a mutable state flag pattern where the tool mutates shared state, and the executor checks after the loop exits. The spawn_agent tool is SIMPLER -- it's synchronous from the tool's perspective (blocks until sub-agent completes) and returns the result directly. No mutable state needed.
**When to use:** As a pattern reference for how tool-factories.ts replaces resolved tools at execution time.

**Key difference from wait_for:** The wait_for tool requires post-loop interception by the executor (the executor replaces the tool's execute function with one bound to a per-conversation WaitForState). The spawn_agent tool does NOT need this -- it gets all dependencies via `ctx.spawnDeps` at resolve time and executes the sub-agent loop inline during tool execution. This is simpler.

### Anti-Patterns to Avoid
- **Sub-agent persistence as separate conversations:** Don't create conversation rows for sub-agents. They run in-process, don't pause/resume, and don't need the ConversationExecutor lifecycle. Events-only tracking is sufficient.
- **Closure capture in tool-factories.ts:** The CONTEXT.md locks the approach as ToolContext extension, not closure capture. Don't try to capture spawn deps at registration time.
- **Token budget creation per sub-agent:** Don't create a new TokenBudget for each sub-agent. Pass the parent's TokenBudget by reference. The sub-agent's YAML `tokenBudget` value is ignored.
- **Running sub-agent history through parent's config:** Sub-agents get fresh history. Don't apply parent's `pruneThreshold`/`summaryThreshold` to sub-agents.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Agent loop execution | Custom LLM call loop for sub-agents | `runAgentLoop()` from `shared/agent-loop/` | Already handles rate limiting, token budget, abort signals, tracing |
| Tool resolution for sub-agents | Manual tool construction | `toolRegistry.resolve(definition.tools, subToolContext)` | Registry already handles all 28 tools correctly |
| Instance ID generation | Custom UUID/timestamp | `nanoid(12)` with `inst_` prefix | Matches existing worker-loop pattern |
| Token budget sharing | Custom counter or copy | Pass parent's `TokenBudget` object by reference | Mutable object design was built for this exact use case |
| Sub-agent history management | Manual message truncation | Sub-agent's own YAML history config via `runAgentLoop()` | Loop already supports history config internally |

**Key insight:** The entire sub-agent execution is literally "resolve tools, then call runAgentLoop()". The complexity is in wiring the dependencies, not in the execution itself.

## Common Pitfalls

### Pitfall 1: Token Budget Not Being Created for Parent
**What goes wrong:** The worker loop currently does NOT create a `TokenBudget` object from `definition.tokenBudget`. Looking at the current `executeConversation()` in `worker-loop.ts`, there is no `tokenBudget` being created or passed to `runAgentLoop()`. The `loopOptions` object on line 516-525 has no `tokenBudget` field.
**Why it happens:** The token budget feature exists in the agent loop (run-agent-loop.ts lines 235-312) but was never wired in the worker loop because there were no sub-agents to share it with.
**How to avoid:** The worker loop must `createTokenBudget(definition.tokenBudget)` for every agent that has spawn_agent, and pass it to both the parent's `runAgentLoop()` call AND to `spawnDeps.tokenBudget`. This is new code, not a modification.
**Warning signs:** If the parent runs without a token budget, sub-agents won't share one either. Look for `tokenBudget` in the `loopOptions` construction.

### Pitfall 2: Sub-Agent ToolContext Missing Sandbox Fields
**What goes wrong:** Sub-agent's codebase tools fail because containerManager or taskId is undefined in their ToolContext.
**Why it happens:** The sub-agent's ToolContext must inherit the parent's containerManager and taskId. If you construct a fresh ToolContext for the sub-agent without copying these, codebase tools will fail.
**How to avoid:** When building the sub-agent's ToolContext, explicitly copy `containerManager` and `taskId` from the parent's context.
**Warning signs:** Sub-agent coder/researcher/tester fails with "Cannot read properties of undefined" from codebase tools.

### Pitfall 3: Event Log Sequence Not Initialized for Sub-Agent Events
**What goes wrong:** `eventLog.append()` throws or produces incorrect sequences for sub-agent events.
**Why it happens:** `eventLog.initSequence()` MUST be called before the first `append()` for a conversation. Sub-agent events are appended to the PARENT conversation (same `conversationId`), so the sequence should already be initialized. But if you use a different conversationId, you need to initialize it.
**How to avoid:** Use the parent's `conversationId` (which is `conv.id`) for sub-agent events. The parent already calls `initSequence(conv.id)`, so sub-agent events can use the same sequence.
**Warning signs:** "Sequence not initialized" errors during sub-agent execution.

### Pitfall 4: ToolRegistry `resolve()` Called with Sub-Agent's ToolContext that has spawnDeps
**What goes wrong:** When resolving tools for a sub-agent, the sub-agent's ToolContext might incorrectly include `spawnDeps`, which would allow recursive spawning.
**Why it happens:** If you copy the parent's full ToolContext including spawnDeps to the sub-agent.
**How to avoid:** Build a fresh ToolContext for the sub-agent WITHOUT spawnDeps (unless the sub-agent itself has `coordination:spawn_agent` in its tools AND the depth limit allows it). Current sub-agents (researcher, coder, tester) don't have spawn_agent, so this is safe today. Depth tracking prevents future issues.
**Warning signs:** Sub-agents attempting to spawn their own sub-agents recursively.

### Pitfall 5: Event Type Enum Constraint
**What goes wrong:** Using non-existent event types like "sub_agent.started" causes database constraint violations.
**Why it happens:** The `agentEventTypeValues` enum is fixed at 9 values: `tool.called`, `tool.succeeded`, `tool.failed`, `llm.response`, `agent.started`, `agent.completed`, `agent.paused`, `agent.resumed`, `signal.received`.
**How to avoid:** Use `agent.started` and `agent.completed` for sub-agent lifecycle events. Differentiate from parent events via the `parent_instance_id` field and the `payload` content.
**Warning signs:** Postgres enum constraint errors on event insert.

### Pitfall 6: Definition Validation Timing
**What goes wrong:** If a sub-agent definition referenced in `subAgents` mapping doesn't exist in the registry, the error only surfaces when spawn_agent is called (potentially after significant token spend).
**Why it happens:** Tool resolution happens at conversation start, but sub-agent definition loading is deferred to spawn time.
**How to avoid:** Validate all `subAgents` references exist in the registry at conversation start (before the agent loop runs). Do this in the worker loop right after loading the parent definition.
**Warning signs:** Late "Agent definition not found" errors during spawn.

### Pitfall 7: Test Mock Architecture
**What goes wrong:** Tests become brittle because they mock too many layers.
**Why it happens:** `createSpawnAgentTool` depends on `runAgentLoop` and `ToolRegistry` and `AgentRegistry`.
**How to avoid:** Mock `runAgentLoop` at the module level (like worker-loop.test.ts does with `vi.mock("../shared/agent-loop/run-agent-loop.js")`). Mock `AgentRegistry.get()` to return test definitions. Mock `ToolRegistry.resolve()` to return dummy tools. Keep the spawn-agent.ts unit test focused on the wiring, not on testing runAgentLoop itself.
**Warning signs:** Tests that fail due to missing Anthropic API keys or network calls.

## Code Examples

### spawn-agent.ts Core Structure
```typescript
// Source: Codebase analysis - existing patterns from wait-for-tool.ts, request-human-input.ts

import { nanoid } from "nanoid";
import { z } from "zod";
import type { ToolDefinition, ToolResult } from "../../agent-loop/types.js";
import { runAgentLoop } from "../../agent-loop/run-agent-loop.js";
import type { SpawnAgentDeps, ToolContext } from "../../../framework/types.js";

const SpawnAgentInputSchema = z.object({
  agentType: z.enum(["researcher", "coder", "tester"])
    .describe("Type of sub-agent to spawn"),
  task: z.string()
    .describe("Task description for the sub-agent to execute"),
  context: z.string().optional()
    .describe("Additional context to prepend to the task"),
});

export function createSpawnAgentTool(ctx: ToolContext): ToolDefinition {
  return {
    name: "spawn_agent",
    description: "...",  // Same description as current placeholder
    inputSchema: SpawnAgentInputSchema,
    async execute(input: unknown): Promise<ToolResult> {
      const parsed = SpawnAgentInputSchema.parse(input);
      const deps = ctx.spawnDeps;

      // Guard: deps must exist
      if (!deps) {
        return {
          content: "spawn_agent is not available in this context.",
          isError: true,
        };
      }

      // Guard: depth limit
      if (deps.currentDepth >= deps.maxSpawnDepth) {
        return {
          content: `Maximum spawn depth (${deps.maxSpawnDepth}) exceeded.`,
          isError: true,
        };
      }

      // 1. Resolve agentType -> definition ID
      const agentId = deps.parentDefinition.subAgents?.[parsed.agentType];
      if (!agentId) {
        return {
          content: `Unknown agent type: ${parsed.agentType}. Available: ${Object.keys(deps.parentDefinition.subAgents ?? {}).join(", ")}`,
          isError: true,
        };
      }

      // 2. Load sub-agent definition
      const definition = await deps.agentRegistry.get(agentId);
      if (!definition) {
        return {
          content: `Agent definition not found: ${agentId}`,
          isError: true,
        };
      }

      // 3. Build sub-agent ToolContext (shared sandbox, NO spawnDeps)
      const subToolContext: ToolContext = {
        agentId: definition.id,
        correlationId: ctx.correlationId,
        logger: ctx.logger.child({ subAgent: definition.id }),
        containerManager: ctx.containerManager,
        taskId: ctx.taskId,
        // spawnDeps omitted unless sub-agent itself can spawn
      };

      // 4. Resolve sub-agent tools
      const tools = deps.toolRegistry.resolve(definition.tools, subToolContext);

      // 5. Build initial message
      const initialMessage = parsed.context
        ? `${parsed.context}\n\n${parsed.task}`
        : parsed.task;

      // 6. Record agent.started event
      const subInstanceId = `inst_${nanoid(12)}`;
      const startTime = Date.now();
      deps.eventLog.append({
        conversationId: ctx.correlationId,  // parent's conv ID
        agentDefinitionId: definition.id,
        agentDefinitionVersion: definition.version,
        agentInstanceId: subInstanceId,
        parentInstanceId: deps.parentInstanceId,
        type: "agent.started",
        payload: {
          agentType: parsed.agentType,
          task: parsed.task.slice(0, 200),
          spawnDepth: deps.currentDepth + 1,
        },
      });

      // 7. Run sub-agent loop
      const result = await runAgentLoop({
        systemPrompt: definition.systemPrompt,
        tools,
        initialMessage,
        model: definition.model,
        maxIterations: definition.maxIterations,
        tokenBudget: deps.tokenBudget,  // SHARED reference
        abortSignal: deps.abortSignal,
        logger: subToolContext.logger,
      });

      const durationMs = Date.now() - startTime;

      // 8. Record agent.completed event
      deps.eventLog.append({
        conversationId: ctx.correlationId,
        agentDefinitionId: definition.id,
        agentDefinitionVersion: definition.version,
        agentInstanceId: subInstanceId,
        parentInstanceId: deps.parentInstanceId,
        type: "agent.completed",
        payload: {
          status: result.status,
          tokenCount: result.tokenCount,
          toolCallCount: result.toolCallCount,
          outputPreview: result.output.slice(0, 300),
        },
        tokenCountInput: result.tokenCount.input,
        tokenCountOutput: result.tokenCount.output,
        durationMs,
      });

      // 9. Return result to parent
      if (result.status === "error" || result.status === "aborted") {
        return {
          content: `Sub-agent ${parsed.agentType} failed (${result.status}): ${result.output}`,
          isError: true,
        };
      }

      if (result.status === "max_iterations" || result.status === "max_tokens") {
        return {
          content: `Sub-agent ${parsed.agentType} stopped (${result.status}): ${result.output}`,
          isError: false,  // Partial work is still useful
        };
      }

      return {
        content: result.output,
        isError: false,
      };
    },
  };
}
```

## Open Questions

1. **TokenBudget for non-spawning agents**
   - What we know: Currently the worker loop does NOT create a TokenBudget for any agent. This phase adds one for spawning agents.
   - What's unclear: Should non-spawning agents also get a TokenBudget to enforce their YAML `tokenBudget` limit? Currently `runAgentLoop` runs without budget enforcement for top-level conversations.
   - Recommendation: Only create TokenBudget when agent has spawn_agent (matches CONTEXT.md scope). Enforcing budget for all agents is a separate concern.

2. **History management during long sub-agent runs**
   - What we know: Sub-agent YAML defines `history.pruneThreshold` (e.g., coder: 40000). The `runAgentLoop()` currently does NOT apply history compaction -- that's done by the worker loop's `historyManager.compact()` call.
   - What's unclear: Since sub-agents run via `runAgentLoop()` directly (not through the worker loop), history compaction won't happen during sub-agent execution. For short sub-agent tasks (< 40 iterations) this is fine. For long ones, messages could exceed context windows.
   - Recommendation: Accept this limitation for now. Sub-agents have low maxIterations (20-40) and use Haiku (200K context). If it becomes an issue, history compaction can be added to the spawn_agent tool wrapper.

3. **EventLog flush timing during sub-agent execution**
   - What we know: `eventLog.append()` is synchronous (buffered). `flush()` forces persistence. The worker loop flushes at lifecycle boundaries.
   - What's unclear: Should spawn_agent flush after each sub-agent completes, or let the parent's flush handle it?
   - Recommendation: Do NOT flush inside spawn_agent. The parent's lifecycle flush will capture all events. Flushing inside spawn_agent would add latency for no benefit since sub-agent events don't need to be visible to external systems in real-time.
