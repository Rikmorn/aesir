# Phase 47.1: Sub Agent Spawn - Context

**Gathered:** 2026-02-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire the placeholder `spawn_agent` tool to the ConversationExecutor so the dev-agent can delegate work to sub-agents (researcher, coder, tester) that run as nested in-process agent loops with shared token budgets and sandbox access. Sub-agents run to completion and return their output as the tool result.

Reference spec: `.planning/specs/2.3-spec-phase-48-raw.md` (written as Phase 48, implementing as Phase 47.1)

</domain>

<decisions>
## Implementation Decisions

### Execution model
- In-process nested `runAgentLoop()` call within the parent's worker loop execution
- NOT a separate conversation claimed by the worker pool
- Sub-agents are synchronous from the parent's perspective -- parent blocks until sub-agent finishes
- Sub-agents don't need persistence (they don't pause, resume, or receive signals)
- Sequential execution only -- no parallel sub-agent spawning

### Dependency injection
- Extend `ToolContext` with optional `spawnDeps?: SpawnAgentDeps` field
- Worker loop populates `spawnDeps` when the agent has `coordination:spawn_agent` in its tool list
- `SpawnAgentDeps` includes: agentRegistry, toolRegistry, tokenBudget, eventLog, parentDefinition, parentInstanceId, abortSignal

### Token budget
- Shared by reference -- parent's `TokenBudget` object passed directly to sub-agent loop
- Sub-agent YAML `tokenBudget` is ignored when spawned by a parent
- Sub-agent `maxIterations` from YAML IS respected (prevents runaway sub-agents)

### Result passing
- Sub-agent's final text output (`result.output`) returned as the spawn_agent tool result string
- No structured artifact passing -- parent sees text and decides what to do with it
- Failed sub-agents return error result with diagnostic information

### Sandbox sharing
- Sub-agent's `ToolContext` uses the SAME `containerManager` and `taskId` as the parent
- Codebase tools in the sub-agent operate on the same container and filesystem
- No additional container spawn needed

### Message persistence
- Events only (agent.started + agent.completed with parent_instance_id)
- Sub-agent messages discarded after tool result returned to parent
- If debugging proves insufficient, persistence can be added later

### maxIterations control
- Always use sub-agent's YAML definition value (coder=40, researcher=30, tester=20)
- Parent controls scope via the task brief, not iteration limits
- No override parameter on spawn_agent input

### Spawn depth tracking
- Track current spawn depth in SpawnAgentDeps
- Reject spawns beyond maxSpawnDepth (default: 3)
- Current sub-agents don't have spawn_agent in their tools, but depth tracking prevents future runaway recursion

### History management
- Sub-agents get their own fresh message history (system prompt + task brief as first user message)
- Parent's history config does NOT apply to sub-agents
- Sub-agent's own YAML history config IS applied if conversation grows long enough

### Abort signal propagation
- Parent's abort signal (from graceful shutdown) passed to sub-agent loop
- If service is shutting down, both parent and child exit cleanly

### Definition validation
- If parent's definition specifies `subAgents` mapping, all referenced agent IDs must exist in the registry
- Fail fast at conversation start (not at spawn time) if a referenced sub-agent definition is missing

### Claude's Discretion
- Exact error message formatting for sub-agent failures
- Event payload structure for agent.started/agent.completed events
- Whether to use nanoid or another ID generation for sub-agent instance IDs
- Test structure and organization

</decisions>

<specifics>
## Specific Ideas

- The implementation sketch in the Phase 48 spec (`.planning/specs/2.3-spec-phase-48-raw.md`) is the reference design -- `createSpawnAgentTool()` with `SpawnAgentDeps`
- Follow the `wait_for` tool as the integration pattern reference -- mutable state flag intercepted by executor is proven, though spawn_agent is simpler (synchronous, no state mutation needed)
- File structure: `spawn-agent.ts` in `packages/agents/src/shared/tools/coordination/` alongside existing `request-human-input.ts`
- The tool factory in `tool-factories.ts` replaces the current placeholder that returns "spawn_agent via ToolRegistry is not yet wired to the executor"

</specifics>

<deferred>
## Deferred Ideas

- Parallel sub-agent execution -- sequential only for now (spec decision)
- Sub-agent message persistence (child conversation rows) -- events only for now
- Agent-managed memory (Phase 3 history management) -- future evolution
- Cross-agent collaboration (agents signaling each other via executor) -- out of v2.3 scope
- Parent override of sub-agent maxIterations -- YAGNI for current agents

</deferred>
