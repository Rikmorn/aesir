<objective>
Add hierarchy guardrails to the create_task tool: max depth of 5 levels, max 10 subtasks per parent, and circular delegation prevention (non-consecutive same-assignee detection).

Purpose: Without guardrails, agents could create unbounded task hierarchies, overload parents with subtasks, or create A->B->A delegation cycles. These safety limits protect system integrity while allowing valid self-decomposition (A->A->A).

Output: Updated create-task.ts with pre-validation checks, constants in types.ts, comprehensive unit tests in create-task.test.ts.
</objective>

  **Step 1: Add constants to types.ts**

  Add two exported constants after the existing `VALID_TRANSITIONS` and utility functions:

  /** Maximum depth of parent_id chains (system-wide safety limit). */

  /** Maximum subtasks per parent task (system-wide safety limit). */

  **Step 2: Add guardrail validation to create-task.ts**

  Import the new constants from types.ts. Add three async validation functions INSIDE the factory function (private to the closure) or as module-level helper functions. Then call them in the `execute()` method BEFORE `taskService.create()`, only when `parentId` is provided.

  **Validation 1: Depth check**

  Walk the parent chain from `parentId` upward via repeated `taskService.get()` calls. Count the depth. If adding a new child would exceed `MAX_TASK_DEPTH`, return an error.

  Logic:
  - Start at `parentId`, depth = 1 (the parent is level 1)
  - While currentId is not null:
    - Fetch task via `taskService.get(currentId)`
    - If task is null (broken chain), return `{ content: "Cannot create subtask: parent chain is broken at ${currentId}. Verify the parent task exists.", isError: true }`
    - Increment depth
    - If depth >= MAX_TASK_DEPTH, return `{ content: "Cannot create subtask: would exceed maximum nesting depth of ${MAX_TASK_DEPTH} levels. Current depth: ${depth}.", isError: true }`
    - Set currentId = task.parent_id ?? null
  - Return null (no error, depth is valid)

  The loop is bounded by MAX_TASK_DEPTH to prevent runaway queries even on corrupt data.

  **Validation 2: Subtask cap**

  Call `taskService.listByParent(parentId)` and check `.length`. If >= `MAX_SUBTASKS_PER_PARENT`, return an error.

  Error message: `"Cannot create subtask: parent ${parentId} already has ${count} subtasks (maximum ${MAX_SUBTASKS_PER_PARENT})."`

  **Validation 3: Circular delegation detection (refined rule from CONTEXT.md)**

  Walk the parent chain tracking whether a different assignee has been encountered. The rule:
  - Consecutive same-assignee (A->A->A) = self-decomposition, ALLOWED
  - Non-consecutive same-assignee (A->B->A) = circular delegation, BLOCKED

  Algorithm:
  ```
  let currentId = parentId
  let seenDifferentAssignee = false

  while (currentId != null):
    task = taskService.get(currentId)
    if task is null:
      return error "parent chain broken" (same as depth check -- can reuse)

    sameAssignee = (task.assignee_type === newAssigneeType && task.assignee_id === newAssigneeId)

    if sameAssignee AND seenDifferentAssignee:
      return error "Circular delegation detected: ${newAssigneeId} appears in the ancestor chain after a different assignee. This creates a delegation cycle (A delegates to B delegates back to A)."

    if NOT sameAssignee:
      seenDifferentAssignee = true

    currentId = task.parent_id ?? null
  ```

  Bound the loop at MAX_TASK_DEPTH iterations for safety.

  **Integration into execute():**

  After input parsing succeeds and before `taskService.create()`, add:

  ```typescript
  if (parentId) {
    // Run hierarchy guardrails
    const depthError = await checkDepth(taskService, parentId);
    if (depthError) return depthError;

    const capError = await checkSubtaskCap(taskService, parentId);
    if (capError) return capError;

    const circularError = await checkCircularDelegation(
      taskService, parentId, assigneeType, assigneeId
    );
    if (circularError) return circularError;
  }
  ```

  Each check function returns `ToolResult | null` -- null means pass, ToolResult means error (with `isError: true`).

  **Important implementation details:**
  - DB errors during chain walks should throw (caught by the outer try/catch), resulting in `"Failed to create task: ..."` -- fail safe, don't allow a task you can't validate.
  - The depth check and circular delegation check both walk the parent chain. You CAN combine them into a single walk for efficiency (one loop doing both checks), OR keep them separate for clarity. Either approach is fine -- the max iterations is 5, so the overhead of two walks is negligible.
  - All error returns use `{ content: "...", isError: true }` matching the existing pattern for input validation errors.
  - Do NOT add any prompt guidance about these limits (per locked decision: "Error messages are the recovery mechanism").
