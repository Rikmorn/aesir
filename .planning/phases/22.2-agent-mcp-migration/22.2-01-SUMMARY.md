# Phase 22.2 Plan 01: MCP Client Wrapper Summary

**One-liner:** HTTP client wrapper for agent-to-integration communication using fetch-retry-ts with exponential backoff and structured error handling for LLM consumption

---

## What Was Built

Created `packages/agents/src/mcp/` module providing a thin HTTP client layer for agents to call MCP tool endpoints. This replaces direct SDK client imports (LinearClient, Octokit, Slack Bolt) with standardized HTTP calls to MCP servers.

### Key Components

1. **Client-side MCP types** (`types.ts`):
   - `McpIntegration`: Type union for supported integrations ('linear' | 'github' | 'slack')
   - `McpCallOptions`: Interface for tool invocation parameters
   - `McpErrorResponse`: Error response wire format from MCP servers
   - `McpSuccessResponse<T>`: Success response wire format with generic typed data

2. **Error handling** (`errors.ts`):
   - `McpError` class extending Error with structured error data
   - `toToolResult()` method producing LLM-friendly error format
   - Getters for `type`, `code`, `correlationId`, `retryAfter` (rate limit handling)
   - Error message parsing for type classification (rate_limit, auth, validation, etc.)

3. **HTTP client wrapper** (`client.ts`):
   - `callMcpTool<T>()` function for making MCP HTTP requests
   - Retry logic: 3 retries with exponential backoff (1s, 2s, 4s, max 10s)
   - Retries on: 429 (rate limit), 500, 502, 503, 504 (server errors)
   - Headers: Content-Type, X-Agent-ID (permissions), X-Correlation-ID (tracing)
   - URL construction from `process.env` (works before/after config refactor in Plan 04)
   - Response unwrapping: `data || structuredContent || response`

4. **Barrel export** (`index.ts`):
   - Re-exports all types, errors, and client functions

### Architecture Decisions

**Why separate client-side and server-side types?**
- `@aesir/common/mcp`: Server-side types (`MCPToolContext`, `MCPToolResult`, `MCPToolMeta`) for building MCP handlers
- `@aesir/agents/mcp`: Client-side types (`McpCallOptions`, `McpErrorResponse`, `McpSuccessResponse`) for consuming HTTP responses
- Different purposes in request/response flow — servers *produce* `MCPToolResult`, clients *consume* wire format

**Why process.env instead of config object?**
- Works before and after config refactor (Plan 04)
- Simple, no circular dependencies
- Env vars: `LINEAR_MCP_URL`, `GITHUB_MCP_URL`, `SLACK_MCP_URL`
- Defaults to Docker service names: `http://linear-integration:3001`, etc.

**Why fetch-retry-ts?**
- Lightweight wrapper for native fetch (no axios/ky overhead)
- Exponential backoff built-in
- Battle-tested retry logic (handles edge cases like jitter, max backoff)
- Minimal dependencies (fetch is Node.js built-in since v18)

**Error handling strategy:**
- Throw `McpError` on HTTP error responses (4xx/5xx)
- LLM decides recovery strategy via `toToolResult()` structured format
- Network failures (ECONNREFUSED, DNS) fail immediately (no masking infrastructure issues)
- Rate limit errors include `retryAfter` for backoff guidance

---

## Decisions Made

| Decision | Rationale | Impact |
|----------|-----------|--------|
| Use fetch-retry-ts instead of axios/ky | Native fetch is built-in, fetch-retry-ts adds minimal wrapper for retry logic | Smaller bundle, fewer dependencies, standard web API |
| Separate client/server MCP types | Different purposes: servers produce results, clients consume wire format | Clear separation of concerns, no accidental coupling |
| Use process.env directly for MCP URLs | Works before and after config refactor, no circular dependencies | Simple, compatible with both current and future config patterns |
| Throw exceptions for errors | Matches current agent code patterns, simpler than ResultAsync initially | Can refactor to ResultAsync later if needed |
| Retry on 429, 5xx only | Fail fast on 4xx (client errors), retry transient server issues | Avoid infinite retries on unrecoverable errors |
| Exponential backoff (1s, 2s, 4s, max 10s) | Industry standard, prevents thundering herd | Graceful degradation under load |
| Extract data/structuredContent from response | MCP servers use different field names, normalize in client | Consistent API for agent code |

## Implementation Details

### Retry Configuration

```typescript
{
  retries: 3,
  retryDelay: (attempt: number) => Math.min(1000 * 2 ** attempt, 10000),
  retryOn: [429, 500, 502, 503, 504],
}
```

- Attempt 1: Wait 1s before retry (2^0 * 1000ms)
- Attempt 2: Wait 2s before retry (2^1 * 1000ms)
- Attempt 3: Wait 4s before retry (2^2 * 1000ms)
- Max backoff: 10s (prevents excessive delays)

### Error Response Format

MCP servers return this structure on errors:

```json
{
  "error": "rate_limit: Too many requests, retry after 60s",
  "isError": true,
  "meta": {
    "correlation_id": "req_abc123",
    "duration_ms": 42
  }
}
```

`McpError` parses this and exposes:
- `type`: "rate_limit" (extracted from prefix)
- `code`: undefined (or parsed from `[400]` pattern)
- `correlationId`: "req_abc123"
- `retryAfter`: 60 (extracted from message)
- `toToolResult()`: Converts to LLM-friendly format

### Success Response Format

MCP servers return this structure on success:

```json
{
  "data": { "title": "Fix authentication bug" },
  "meta": {
    "correlation_id": "req_abc123",
    "duration_ms": 150,
    "rate_limit_remaining": 98
  }
}
```

`callMcpTool()` unwraps: `data || structuredContent || response` — agents get the data directly.

## Lessons Learned

1. **fetch-retry-ts import gotcha**: Default export is `fetchBuilder`, not `fetchRetry` — initial import failed typechecking.

2. **TypeScript strictness with regex match**: `match[1]` can be undefined — need to use optional chaining `match?.[1]` or ternary with null check.

3. **Biome import sorting**: Barrel exports must be in specific order (client, errors, types) — auto-fixed by linter.

4. **Response type assertion**: `response.json()` returns `unknown` — need explicit type assertion for union types.
