# Phase 22.2: Agent MCP Migration - Research

**Researched:** 2026-01-25
**Domain:** HTTP client migration, agent architecture refactoring
**Confidence:** HIGH

## Summary

This phase migrates agents from direct integration client usage (LinearClient, Octokit, Slack Bolt) to MCP HTTP calls. The migration completes the circuit started in Phase 19 where MCP servers were created but not consumed by agents.

**Current state:** Agents import `@aesir/integration-linear`, `@aesir/integration-github`, and use direct SDK clients (LinearClient, Octokit). Direct client instances injected via factory pattern into LangGraph nodes. Integration tokens stored in agent configuration.

**Target state:** Agents make HTTP calls to MCP endpoints (POST /mcp/tools/:name). Thin MCP client wrapper in @aesir/agents. No integration tokens in agent config (only workspace IDs). Temporal activities keep direct clients (infrastructure, not LLM-driven).

**Primary recommendation:** Use native fetch with exponential backoff retry wrapper for MCP HTTP calls. Avoid heavy HTTP client libraries (axios, ky) since the MCP protocol is simple (JSON POST with headers). Implement structured error handling that propagates to LLM as tool results.

### Pattern 1: MCP Client Wrapper
**What:** Thin wrapper that encapsulates HTTP request boilerplate
**When to use:** Every MCP tool call from agents

**Example:**
```typescript
// packages/agents/src/mcp/client.ts
import fetchRetry from 'fetch-retry-ts';

const fetchWithRetry = fetchRetry(fetch);

export interface McpCallOptions {
  integration: 'linear' | 'github' | 'slack';
  tool: string;
  params: Record<string, unknown>;
  agentId: string;
  correlationId: string;
  baseUrl?: string;
}

export async function callMcpTool<T = unknown>(
  options: McpCallOptions
): Promise<T> {
  const { integration, tool, params, agentId, correlationId, baseUrl } = options;

  // Build URL from config
  const url = `${baseUrl || config.mcp[integration].url}/mcp/tools/${tool}`;

  const response = await fetchWithRetry(url, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-Agent-ID': agentId,
      'X-Correlation-ID': correlationId,
    },
    body: JSON.stringify(params),
    retries: 3,
    retryDelay: (attempt) => Math.min(1000 * 2 ** attempt, 10000), // Exponential backoff
    retryOn: [429, 500, 502, 503, 504], // Retry on rate limit and server errors
  });

  if (!response.ok) {
    const errorData = await response.json();
    throw new McpError(errorData);
  }

  const result = await response.json();

  // Return structured data if available, else parse content
  return result.data || result.structuredContent || result;
}
```

**Source:** [fetch-retry-ts npm](https://www.npmjs.com/package/fetch-retry-ts)

### Pattern 2: Node Migration Pattern
**What:** Replace direct client calls with MCP HTTP calls
**When to use:** All LangGraph nodes (not Temporal activities)

**Before:**
```typescript
// Direct client usage
export function createPickupTaskNode(linearClient: LinearClient) {
  return async function pickupTaskNode(state: DevWorkflowStateType) {
    const issue = await readIssue(linearClient, state.taskId);
    await updateIssueStatus(linearClient, state.taskId, "In Progress");
    return { taskDescription: issue.title };
  };
}
```

**After:**
```typescript
// MCP HTTP usage
const AGENT_ID = "dev-agent"; // Hardcoded agent identifier

export function createPickupTaskNode() {
  return async function pickupTaskNode(state: DevWorkflowStateType) {
    // Read issue via MCP
    const issue = await callMcpTool<{ title: string; description?: string }>({
      integration: 'linear',
      tool: 'get_issue',
      params: { issueId: state.taskId },
      agentId: AGENT_ID,
      correlationId: state.correlationId || generateCorrelationId(),
    });

    // Update status via MCP
    await callMcpTool({
      integration: 'linear',
      tool: 'update_issue_status',
      params: { issueId: state.taskId, statusName: 'In Progress' },
      agentId: AGENT_ID,
      correlationId: state.correlationId || generateCorrelationId(),
    });

    return { taskDescription: issue.title };
  };
}
```

### Pattern 3: Error Handling for LLM Consumption
**What:** Structured error responses that LLMs can interpret
**When to use:** All MCP tool calls

**Example:**
```typescript
export class McpError extends Error {
  constructor(
    public readonly errorData: {
      error: string;
      isError: true;
      meta: { correlation_id: string; duration_ms?: number };
    }
  ) {
    super(errorData.error);
    this.name = 'McpError';
  }

  toToolResult(): MCPToolResult {
    return {
      content: [{ type: 'text', text: this.errorData.error }],
      meta: this.errorData.meta,
      isError: true,
    };
  }
}

// Usage in nodes
try {
  const result = await callMcpTool(...);
  return { data: result };
} catch (error) {
  if (error instanceof McpError) {
    // Let LLM see the error and decide recovery
    return { error: error.toToolResult() };
  }
  throw error; // Network failures fail immediately
}
```

**Source:** Based on existing MCPToolResult interface in @aesir/common

### Anti-Patterns to Avoid
- **Direct SDK imports in new code:** Don't import LinearClient or Octokit in agent nodes after migration. Use MCP client only.
- **Client-side retries on network failures:** Fail immediately if MCP service unreachable (don't mask infrastructure problems).
- **Runtime Zod validation of responses:** Trust MCP server validation, avoid duplicate schema validation in client (performance overhead).
- **Global HTTP client instance:** Create new fetch call per request for clarity, fetch is lightweight.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP retries with backoff | Custom retry loop | fetch-retry-ts | Battle-tested, handles edge cases (jitter, max backoff, retry conditions) |
| Correlation ID propagation | Manual header passing | Bind correlationId in state | LangGraph state makes correlation ID available to all nodes |
| MCP URL construction | String concatenation | Config object with url property | Centralized config prevents typos, supports nginx proxy pattern |
| Error categorization | Error parsing logic | Use MCP server error format | Server already categorizes (rate_limit, auth, validation, etc.) |

**Key insight:** The MCP protocol is simple (JSON POST with headers), but production concerns (retries, observability, error handling) benefit from standard patterns. Don't reimplement retry logic or error categorization.

## Common Pitfalls

### Pitfall 1: Forgetting X-Agent-ID Header
**What goes wrong:** MCP endpoints return 400 "X-Agent-ID header is required"
**Why it happens:** Agent ID required for rate limiting and permission checks
**How to avoid:** Include agentId in all callMcpTool calls, enforce with TypeScript required parameter
**Warning signs:** 400 errors in logs with missing header message

### Pitfall 2: Not Removing Integration Tokens from Docker Compose
**What goes wrong:** Agents boot successfully but still have unnecessary credentials
**Why it happens:** docker-compose.yml has redundant env vars from pre-MCP era
**How to avoid:** Grep for LINEAR_ACCESS_TOKEN, GITHUB_TOKEN in docker-compose.yml, remove from agent service
**Warning signs:** Docker logs show warnings about unused env vars

### Pitfall 3: Migrating Temporal Activities
**What goes wrong:** Temporal activities fail or have unnecessary HTTP overhead
**Why it happens:** Activities are infrastructure code (not LLM-driven), don't need MCP protocol overhead
**How to avoid:** Only migrate LangGraph nodes, skip temporal/activities/ directory
**Warning signs:** Temporal activity errors, increased latency for simple operations

### Pitfall 4: Hardcoding MCP URLs
**What goes wrong:** Can't switch between localhost and nginx proxy, breaks in different environments
**Why it happens:** MCP URLs vary (localhost:3001 in dev, nginx:80 in Docker)
**How to avoid:** Store MCP base URLs in config, read from env vars
**Warning signs:** Connection errors when switching between local and containerized dev

### Pitfall 5: Swallowing Network Errors
**What goes wrong:** Agent appears stuck, no clear failure signal
**Why it happens:** Retry logic masks unreachable MCP services
**How to avoid:** Fail immediately on network errors (ECONNREFUSED, DNS failures), only retry 5xx/429
**Warning signs:** Long timeouts, silent failures without error logs

## Open Questions

Things that couldn't be fully resolved:

1. **Correlation ID propagation in LangGraph state**
   - What we know: LangGraph state is thread-local, correlation ID could be added to DevWorkflowState
   - What's unclear: Whether correlation ID should be in base state or passed as context
   - Recommendation: Add correlationId to DevWorkflowState, generated at workflow start

2. **MCP base URL configuration strategy**
   - What we know: URLs differ between local dev (localhost:3001) and Docker (nginx or service names)
   - What's unclear: Single base URL with path prefixes vs per-integration URLs
   - Recommendation: Per-integration URLs for flexibility (can point to different hosts if needed)

3. **Error handling: ResultAsync vs exceptions**
   - What we know: Current agent code uses exceptions, LLMs can handle both patterns
   - What's unclear: Whether to introduce ResultAsync pattern for MCP errors
   - Recommendation: Use exceptions initially (matches current code), refactor to ResultAsync later if needed
