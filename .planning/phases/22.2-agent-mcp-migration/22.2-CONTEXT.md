# Phase 22.2: Agent MCP Migration - Context

**Gathered:** 2026-01-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Migrate agents (dev-agent, product-agent) from direct integration client usage to MCP HTTP calls. Remove redundant integration tokens from agent configuration. Completes the circuit started in Phase 19 (MCP servers exist but agents don't use them).

</domain>

<decisions>
## Implementation Decisions

### MCP Client Pattern
- Thin wrapper helper in @aesir/agents package (not common)
- `callMcpTool(integration, tool, params)` pattern — handles URL, headers, response parsing
- Correlation ID propagation automatic on every call (X-Correlation-ID header)
- Returns `MCPResult<T>` — caller specifies expected type, no runtime Zod validation
- Built-in retries for transient failures (5xx, network errors)
- Error handling: Claude decides — ResultAsync vs throw based on agent code patterns

### Migration Scope
- Both agents in scope: dev-agent and product-agent
- All integration calls migrated at once — complete cutover
- Old direct client code deleted immediately after migration (no deprecation period)
- Tests updated to mock MCP calls instead of direct clients
- Tool names hardcoded in agent code — no dynamic /mcp/tools discovery
- No startup verification that MCP servers have expected tools
- Temporal activities keep using direct clients — MCP is for LangGraph agent layer only

### Credential Cleanup
- Remove all integration tokens from agent config: LINEAR_*, GITHUB_*, SLACK_*
- Keep workspace IDs in agent config — passed to MCP calls for multi-tenant readiness
- Agent ID hardcoded in agent code (e.g., `const AGENT_ID = "dev-agent"`)
- MCP URLs configurable via env (can use nginx base URL from Docker setup)
- docker-compose.yml cleaned up — remove redundant integration env vars from agent service
- Verification: grep for token patterns + Docker startup test without integration tokens

### Error Handling
- Errors propagated to LLM as tool result — LLM decides recovery strategy
- Structured JSON error format: `{ error: true, type: "...", code: "...", message: "..." }`
- Error types categorized: rate_limit, auth, not_found, validation, server
- Fail immediately on unreachable MCP service — no client-side retries for network failures
- retryAfter included in rate limit errors

### Claude's Discretion
- Exact retry strategy for transient errors (count, backoff)
- MCP base URL configuration pattern (single vs per-integration)
- ResultAsync vs exception pattern for MCP client internals
- Test mocking approach for MCP calls

</decisions>
