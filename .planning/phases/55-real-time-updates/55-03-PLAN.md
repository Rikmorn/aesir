  <name>Task 1: Create LiveDetailPanels client wrapper with SSE event accumulation</name>
  <files>

  <action>
    Create a "use client" component that wraps the entire conversation detail view and adds real-time updates via SSE.

    **Props (initial server-rendered data):**
    ```typescript
    interface LiveDetailPanelsProps {
      conversation: ConversationDetail;
      initialEvents: ConversationEvent[];
      initialMessages: unknown[];
      childConversations: ChildConversation[];
    }
    ```

    **SSE connection:**
    Use `useEventStream` with:
    - `url: "/dashboard/api/sse/events"`
    - `conversationId: conversation.id` (filter to this conversation's events only)
    - No `types` filter (receive all event types for the full timeline)
    - `enabled: conversation.status === "running" || conversation.status === "waiting"` -- only connect when conversation is active
    - `maxEvents: 1000` -- cap client-side buffer

    **State management:**

    1. **Events state**: `useState<ConversationEvent[]>(initialEvents)`
       - When SSE events arrive, convert each `SseEvent` to `ConversationEvent` format (the fields are the same but need Date objects for timestamps, and the SSE payload shape maps directly).
       - Append new events to the end of the array (timeline is chronological).
       - Cap at 1000 events: if `initialEvents.length + sseEvents.length > 1000`, keep only the latest 1000. Track whether events were truncated with a `truncatedCount` state.

    2. **Messages state**: `useState<unknown[]>(initialMessages)`
       - This is trickier. SSE `llm.response` events contain the messages in their payload. The messages array format is Anthropic's Messages API format. However, the SSE event payload only has the event metadata, not the full message history.
       - **Decision**: Do NOT attempt to reconstruct messages from SSE events. Instead, when the conversation completes (an `agent.completed` event arrives), do a `router.refresh()` to get the final messages from the server. During the conversation, the messages panel shows the initial server-rendered messages plus a "Messages update when conversation completes" note if SSE is active and new events are arriving.
       - Actually, reconsider: the conversation detail page's message panel shows the full messages array from `conversations.messages` JSONB column. This is only updated when the agent loop persists results. For running conversations, this would be stale. The better UX is: show initial messages, and when SSE events arrive that are `llm.response` or `tool.called`/`tool.succeeded`/`tool.failed`, these don't contain message content -- they contain event metadata. So messages panel stays static until a page refresh. Add a small note "Refresh to see latest messages" if the conversation is active and SSE events have arrived. When `agent.completed` arrives, trigger `router.refresh()`.

    3. **Conversation metadata state**: `useState<ConversationDetail>(conversation)`
       - When lifecycle SSE events arrive (`agent.completed`, `agent.paused`, `agent.resumed`), update the local conversation state:
         - `agent.completed`: Set status to "completed", update updatedAt
         - `agent.paused`: Set status to "waiting", update updatedAt
         - `agent.resumed`: Set status to "running", update updatedAt
       - Accumulate token totals from `llm.response` events: add `tokenCountInput` and `tokenCountOutput` to a running total state, then pass accumulated totals to the sidebar.

    **Smart auto-scroll:**
    Use a `useRef` for the timeline scroll container. Track whether user is "at bottom" (within 100px of scroll end) using a scroll event listener. When new events append and user is at bottom, call `scrollIntoView({ behavior: "smooth" })` on the last event. When user has scrolled up and new events arrive, show a small "N new events" pill at the bottom of the timeline that, when clicked, scrolls to the latest event.

    Implementation:
    - `useRef<HTMLDivElement>(null)` for the scroll container
    - `useRef<boolean>(true)` for `isAtBottom` -- initially true
    - `onScroll` handler checks `scrollTop + clientHeight >= scrollHeight - 100`
    - After state update with new events, if `isAtBottom`, scroll to bottom
    - If NOT at bottom and new events exist, show a floating pill ("N new events ↓") that calls `scrollToBottom()` on click

    **Event truncation indicator:**
    If `truncatedCount > 0`, show a small banner at the top of the timeline: "Showing latest 1000 of {totalCount} events. Earlier events are available on refresh."

    **Gap handling:**
    When `state.hasGap` is true (from EventStreamStore), call `router.refresh()` to re-fetch all data from the server.

    **Render structure:**
    Render the existing `DetailLayout` component, passing:
    - `timelinePanel`: Event timeline header + auto-scroll container + EventTimeline with combined events + new events pill
    - `messagesPanel`: Messages header + MessagePanel with messages + refresh note if active
    - `sidebarPanel`: MetadataSidebar with updated conversation metadata

    Also render `ConnectionStatusIndicator` in the header area (only visible when conversation is active).

  <action>
    Update the conversation detail page to use LiveDetailPanels instead of directly rendering DetailLayout with the three panels.

    **Changes:**

    1. Import `LiveDetailPanels` from `@/components/conversation-detail/live-detail-panels`
    2. Keep all server-side data fetching exactly as is (getConversationById, getConversationEvents, getConversationMessages, getChildConversations)
    3. Keep the notFound() check
    4. Keep the header section (back link, title, conversation ID)
    5. Replace the `<DetailLayout>` block with:
       ```tsx
       <LiveDetailPanels
         conversation={conversation}
         initialEvents={events}
         initialMessages={messages}
         childConversations={childConversations}
       />
       ```

    The LiveDetailPanels component handles the DetailLayout internally, including the sidebar toggle and three-panel grid.

    **Important:** The page remains a server component (async function). Only the LiveDetailPanels is a client component. The server component fetches initial data and passes it as props, following the established wrapper pattern.

    **Serialization note:** All props passed to the client component must be JSON-serializable. ConversationDetail has Date objects in `createdAt`, `updatedAt`, `lastEventAt`. ConversationEvent has Date objects in `timestamp`. These need to be serialized as ISO strings or the client component needs to handle string-to-Date conversion. Check if Next.js handles this automatically via RSC serialization (it does for server-to-client component prop passing with Dates in React 19). If not, convert Dates to ISO strings in the service layer or in the page before passing.

    Actually, Next.js RSC serialization does NOT automatically serialize Date objects across the server/client boundary. Dates will arrive as strings on the client. The LiveDetailPanels component should:
    - Accept dates as `string | Date` and normalize them on the client side
    - OR the page should pre-serialize dates before passing

    The cleaner approach: Update the service types to use `string` for date fields in the interfaces passed to client components, and convert in the page. But that changes existing interfaces. Instead, in LiveDetailPanels, convert date strings back to Date objects in an initialization effect. OR define separate "serializable" versions of the interfaces for the client props.

    **Recommended approach:** In the page.tsx, serialize the data before passing to the client component. Create a small serialization helper or just spread and override date fields:
    ```tsx
    <LiveDetailPanels
      conversation={{
        ...conversation,
        createdAt: conversation.createdAt.toISOString(),
        updatedAt: conversation.updatedAt.toISOString(),
        lastEventAt: conversation.lastEventAt?.toISOString() ?? null,
      }}
      initialEvents={events.map(e => ({
        ...e,
        timestamp: e.timestamp.toISOString(),
      }))}
      initialMessages={messages}
      childConversations={childConversations.map(c => ({
        ...c,
        createdAt: c.createdAt.toISOString(),
      }))}
    />
    ```

    Then in LiveDetailPanels, define the prop types with `string` for date fields (e.g., `SerializedConversationDetail` with `createdAt: string`), and the existing presentational components that need Dates can receive them after conversion via `new Date(dateString)`.

    This is the safest approach to avoid RSC serialization issues. Define the serialized types in the live-detail-panels.tsx file itself (they're local to the client boundary).
