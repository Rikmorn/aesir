This validates the system prompt instruction "Your first action should always be to read the issue details."

   - `it("skips researcher for simple task")` -- Mock sequence: (1) LLM calls `linear_get_issue` with a simple issue (e.g., "Fix typo in README"), (2) LLM calls `spawn_agent` with agentType "coder" directly (no researcher), (3) LLM returns text response. Assert: spawn_agent called with agentType "coder" but NOT with agentType "researcher". This validates DEVO-09.

   - `it("spawns researcher before coder for complex task")` -- Mock sequence: (1) LLM calls `linear_get_issue` with a complex issue (e.g., "Implement OAuth2 flow"), (2) LLM calls `spawn_agent` with agentType "researcher", (3) LLM calls `spawn_agent` with agentType "coder", (4) LLM calls `spawn_agent` with agentType "tester", (5) LLM returns text response. Assert: spawn_agent called 3 times, in order: researcher, coder, tester. This validates DEVO-02, DEVO-09.

3. `describe("error recovery")` -- Validates DEVO-11, DEVO-13:

   - `it("tries different approach after sub-agent failure")` -- Mock sequence: (1) LLM calls spawn_agent(coder, task_v1), (2) tool returns error, (3) LLM calls spawn_agent(coder, task_v2 -- different brief), (4) tool returns success, (5) LLM returns text. Assert: two spawn_agent calls with DIFFERENT task content. The test verifies the input.task values differ between the two calls. This validates DEVO-11.

   - `it("escalates after 3 distinct failed approaches")` -- Mock sequence: (1) LLM calls spawn_agent (attempt 1, fails), (2) LLM calls spawn_agent (attempt 2, different task, fails), (3) LLM calls spawn_agent (attempt 3, different task, fails), (4) LLM calls request_human_input. Assert: 3 spawn_agent calls with distinct tasks, followed by a request_human_input call. This validates DEVO-13.

4. `describe("trace recording")`:

   - `it("flushes trace recorder on error")` -- Mock an API error (mockCreate rejects). Verify flush is still called (in the catch path).

**Key implementation notes:**
- The mockCreate function needs to return different responses on successive calls. Use `mockCreate.mockResolvedValueOnce(...)` chaining for each step in a scenario.
- For tool_use responses, the mock needs to return messages with content blocks of type "tool_use" with id, name, and input.
- The loop processes tool calls and sends results back. For spawn_agent calls, the mock needs to handle the nested runAgentLoop call. Since runAgentLoop is called recursively for sub-agents, and we mock @anthropic-ai/sdk at the module level, the sub-agent's loop will also use mockCreate. Plan the mock response sequence to include responses for both the orchestrator and sub-agent loops.
- Alternative approach: Mock `runAgentLoop` itself (not the SDK) at a higher level to avoid the nested loop complexity. This is cleaner for behavioral tests. In this case, mock `../../shared/agent-loop/run-agent-loop.js` to capture calls and return controlled results. This lets you inspect exactly what systemPrompt and tools were passed without dealing with the SDK mock complexity.

**Recommended approach (cleaner):** Mock `runAgentLoop` directly rather than `@anthropic-ai/sdk`. This way:
- The first call to runAgentLoop is the orchestrator itself. Capture the tools and system prompt.
- To test behavioral assertions (which tools the LLM calls), inspect the `tools` array passed to runAgentLoop and verify the orchestrator toolkit composition.
- For actual tool call sequences, mock runAgentLoop to call specific tools from the toolkit and return results based on those calls.

However, the Phase 28 pattern mocks the SDK directly. **Choose whichever approach produces clearer, more maintainable tests.** The key requirement is that tests prove adaptive behavior: different issue types lead to different tool call patterns.

Use `beforeEach(() => { vi.clearAllMocks(); })` to reset mocks between tests.
