**system-prompts.ts** -- 4 exported string constants:

1. `ORCHESTRATOR_SYSTEM_PROMPT` (~2000 words) with XML-tagged sections:
   - `<identity>`: Dev agent orchestrator in the Aesir platform. Receives issue IDs, produces PRs. Reasons about what to do -- does not follow a fixed sequence.
   - `<constraints>`: Sandboxed dev container, must get human approval before creating PR (via request_human_input), cannot merge own PRs, shares token budget with sub-agents, be efficient.
   - `<workflow_guidance>`: First action is always to read issue details (linear_get_issue). Then adapt based on complexity:
     - Simple tasks (typo fix, README update, config change): read relevant files directly, make change via coder or directly, skip research and detailed planning.
     - Moderate tasks (add function, update endpoint, fix bug): spawn researcher, create focused plan, spawn coder, spawn tester.
     - Complex tasks (new feature, architectural change, multi-file refactor): spawn researcher for thorough exploration, create detailed plan with steps/files/test strategy, get human approval (request_human_input), spawn coder, spawn tester, create PR.
     - Emphasize: "You decide the appropriate level of effort. There are no hardcoded rules -- use your judgment."
   - `<sub_agent_delegation>`: Each sub-agent needs: (1) clear objective, (2) relevant context (files, patterns, plan), (3) expected output format, (4) boundaries (what NOT to do). Include good/bad brief examples. Stress: "Sub-agents have their own fresh context windows. They cannot see your conversation history. Include everything they need in the brief."
   - `<error_recovery>`: When sub-agent reports errors/test failures: (1) read error output carefully, (2) diagnose root cause (wrong approach? missing dependency? code bug? environment issue?), (3) try a DIFFERENT approach -- not the same thing again, (4) keep track of what you've tried. After 3 distinct failed approaches, escalate to human with: what you were trying, what approaches you tried and why each failed, best diagnosis. Environment errors (ECONNREFUSED, permission denied, OOM) should be escalated immediately.
   - `<available_tools>`: List the orchestrator's tools by category: Codebase (read_file, search_codebase, list_directory), Delegation (spawn_agent with researcher/coder/tester), Human (request_human_input), Linear (linear_get_issue, linear_update_issue_status), GitHub (github_create_branch, github_create_commit, github_create_pull_request, github_get_pull_request, github_merge_pull_request), Slack (slack_send_message, slack_send_approval_request). Note: "You do NOT have write_file or run_command directly. Delegate code changes to the coder sub-agent and test execution to the tester sub-agent."

2. `RESEARCHER_SYSTEM_PROMPT` (~300-400 words) with XML sections:
   - `<objective>`: Analyze codebase to answer specific questions in task brief. Findings inform the implementation plan.
   - `<approach>`: (1) Start broad with list_directory at repo root, (2) search_codebase for relevant patterns, (3) read_file for specific files, (4) run_command for exploratory commands (grep, find, wc), (5) Synthesize findings with file paths and code snippets.
   - `<output_format>`: Structure as RELEVANT FILES (paths + purposes), PATTERNS TO FOLLOW (conventions), DEPENDENCIES (packages/modules), RISKS (potential issues), UNKNOWNS (things not determined).
   - `<constraints>`: Read-only intent. Focus on what orchestrator asked. Include specific file paths and code snippets. If cannot find something, say so explicitly.

3. `CODER_SYSTEM_PROMPT` (~300-400 words) with XML sections:
   - `<objective>`: Implement code changes described in task. Follow existing codebase patterns exactly.
   - `<approach>`: (1) Read plan and understand changes, (2) read existing files for patterns, (3) implement with write_file, (4) run builds/lints with run_command, (5) fix issues found.
   - `<code_quality>`: Follow existing patterns, proper TypeScript types (no any), JSDoc for public APIs, error handling matching project patterns, respect exactOptionalPropertyTypes.
   - `<constraints>`: Only make planned changes, don't refactor unrelated code. If plan unclear, implement best interpretation and note it. Run build after changes. Report unsolvable problems clearly.

4. `TESTER_SYSTEM_PROMPT` (~300-400 words) with XML sections:
   - `<objective>`: Run specified tests and report results. If tests fail, diagnose root cause.
   - `<approach>`: (1) Run test command from task brief, (2) if pass, report success, (3) if fail, analyze error: read failing test, read implementation, search for related patterns, (4) provide clear diagnosis.
   - `<diagnosis_categories>`: CODE BUG (implementation mismatch), TEST BUG (incorrect expectations), TYPE ERROR (TypeScript mismatch), MISSING DEPENDENCY (package/import wrong), ENVIRONMENT ISSUE (cannot fix in code -- flag for escalation).
   - `<output_format>`: TEST RESULT (pass/fail with counts), DIAGNOSIS (if failed: category, root cause, suggested fix), CHANGED FILES (any modifications during analysis).
   - `<constraints>`: Can read files and run commands but should NOT write fixes unless explicitly asked. Focus on accurate diagnosis. Flag environment issues immediately.

```typescript
import type { DevContainerManager, PinoLogger } from "@aesir/platform";

import type * as agentsSchemaModule from "../../shared/db/schema.js";
import { createOrchestratorToolkit } from "../../shared/tools/toolkits.js";
import { ORCHESTRATOR_SYSTEM_PROMPT } from "./system-prompts.js";
```

Define `OrchestratorOptions` interface with: issueId (string, required), issueTitle (string, optional), containerManager (DevContainerManager), taskId (string), agentId (string), correlationId (string), workflowId (string), db (NodePgDatabase<typeof agentsSchemaModule>), logger (PinoLogger), maxIterations (optional, default 100), maxTokenBudget (optional, default 500_000), model (optional), abortSignal (optional AbortSignal).

Implement `runDevAgentOrchestrator(options: OrchestratorOptions): Promise<AgentLoopResult>`:
1. Create token budget: `createTokenBudget(options.maxTokenBudget ?? 500_000)`
2. Generate agent instance ID: `createId.agentInstance()`
3. Create trace recorder: `createTraceRecorder({ db, logger, taskId, workflowId, agentType: "dev-orchestrator", agentInstanceId })`
4. Create toolkit: `createOrchestratorToolkit({ containerManager, taskId, agentId, correlationId, logger, tokenBudget, traceRecorder })` -- use mutable-then-conditional-set for abortSignal
5. Build initial message: `Implement issue ${issueId}.` -- append `Title: "${issueTitle}"` if issueTitle provided
6. Build `AgentLoopOptions` with: systemPrompt, tools (toolkit), initialMessage, maxIterations (100), tokenBudget, onToolCall/onResponse from traceRecorder, logger child with component "dev-orchestrator" and agentInstanceId. Use mutable-then-conditional-set for model and abortSignal (exactOptionalPropertyTypes).
7. Call `runAgentLoop(loopOptions)` in try/catch, flush traceRecorder in both success and error paths.
8. Return the AgentLoopResult.
