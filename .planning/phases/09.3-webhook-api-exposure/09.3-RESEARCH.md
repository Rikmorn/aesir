# Phase 9.3: Webhook API Exposure - Research

**Researched:** 2026-01-19
**Domain:** Secure tunnel exposure for local webhook development (Cloudflare Tunnel)
**Confidence:** HIGH

## Summary

This phase addresses a critical integration gap: the webhook handlers created in Phase 9.2 exist but are unreachable from external services. Linear and GitHub servers cannot reach `localhost:3001` to deliver webhook events. Cloudflare Tunnel (cloudflared) is the recommended solution for exposing local development endpoints to the internet securely.

Cloudflare Tunnel establishes outbound-only connections to Cloudflare's global network, eliminating the need for port forwarding, firewall modifications, or public IP addresses. The `cloudflared` daemon runs as a Docker container alongside existing services, creating a persistent encrypted tunnel that routes external traffic to internal services.

**Primary recommendation:** Use Cloudflare Tunnel with a remotely-managed tunnel (token-based) configured via the Zero Trust dashboard, deployed as a Docker Compose service alongside dev-agent.

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Cloudflare Tunnel | ngrok | ngrok has better request inspection/replay UI for debugging, but slower (8.81 vs 46.30 Mbps), expensive at scale, and less secure by default |

| Token-based tunnel | Local credentials file | Credentials file is more complex to manage, token via environment is simpler for Docker Compose |

**Installation:**
No npm packages needed. cloudflared runs as a Docker container.

## Architecture Patterns

### Recommended Docker Compose Structure
```yaml
services:
  # Existing services...
  dev-agent:
    # ... existing configuration
    # NOTE: Removed 'ports: - "3001:3001"' - no longer needed
    # Traffic comes through cloudflared, not direct port mapping

  cloudflared:
    image: cloudflare/cloudflared:2025.2.0
    container_name: aesir-cloudflared
    restart: unless-stopped
    command: tunnel --no-autoupdate run --metrics=0.0.0.0:2000
    environment:
      - TUNNEL_TOKEN=${CLOUDFLARE_TUNNEL_TOKEN}
    networks:
      - aesir-network
    depends_on:
      dev-agent:
        condition: service_started

  # Optional: Health check sidecar for proper depends_on support
  cloudflared-health:
    image: quay.io/curl/curl:8.10.1
    init: true
    command: sleep infinity
    depends_on:
      - cloudflared
    healthcheck:
      test: ['CMD-SHELL', 'curl -fsS http://cloudflared:2000/ready']
      interval: 1s
      timeout: 2s
      retries: 60
    networks:
      - aesir-network
```

### Pattern 1: Token-Based Remote Tunnel
**What:** Tunnel configuration stored in Cloudflare dashboard, authenticated via token
**When to use:** Local development, Docker Compose deployments, team environments
**Example:**
```yaml
# Source: Cloudflare official documentation
# Token set via Zero Trust Dashboard -> Networks -> Tunnels
environment:
  - TUNNEL_TOKEN=${CLOUDFLARE_TUNNEL_TOKEN}
command: tunnel --no-autoupdate run
```

### Pattern 2: Public Hostname Routing
**What:** Map custom subdomains to internal Docker services
**When to use:** When tunnel is created, configure ingress in Zero Trust dashboard
**Configuration in dashboard:**
```
Subdomain: aesir-dev
Domain: your-domain.com
Service: http://dev-agent:3001
Path: /webhooks/*

Result: https://aesir-dev.your-domain.com/webhooks/linear -> http://dev-agent:3001/webhooks/linear
```

### Pattern 3: Quick Tunnel for Temporary Testing
**What:** No-account tunnel with random URL
**When to use:** Quick one-off testing, demos, initial setup verification
**Example:**
```bash
# NOT for production or persistent development
# Source: Cloudflare TryCloudflare documentation
docker run --rm --network aesir-network cloudflare/cloudflared:latest \
  tunnel --url http://dev-agent:3001
# Outputs: https://random-words.trycloudflare.com
```

### Anti-Patterns to Avoid
- **Exposing ports directly:** Don't use `ports: - "3001:3001"` when using cloudflared. External traffic should flow through the tunnel, not direct port mapping.
- **Committing tunnel tokens:** Never commit `CLOUDFLARE_TUNNEL_TOKEN` to version control. Use `.env` file excluded via `.gitignore`.
- **Using Quick Tunnels for persistent development:** URL changes on restart, breaking webhook configurations.
- **Skipping health checks:** Without health checks, dependent services may start before tunnel is ready.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Expose localhost to internet | Port forwarding, dynamic DNS | Cloudflare Tunnel | Handles NAT traversal, HTTPS, DDoS protection |
| SSL certificates for webhooks | Let's Encrypt, certbot | Cloudflare Tunnel | Automatic HTTPS, certificate management by Cloudflare |
| Stable URL for development | Dynamic DNS services | Cloudflare custom domain | Persistent URL tied to your domain |
| Tunnel health monitoring | Custom scripts | `--metrics` flag + `/ready` endpoint | Built-in, reliable |

**Key insight:** Webhook providers require HTTPS endpoints. Self-managing certificates for local development is complex and error-prone. Cloudflare Tunnel provides automatic HTTPS with zero configuration.

## Common Pitfalls

### Pitfall 1: Token Exposure in Command Line
**What goes wrong:** Using `--token <value>` exposes token in process list
**Why it happens:** Token passed directly in command instead of environment variable
**How to avoid:** Always use `TUNNEL_TOKEN` environment variable
**Warning signs:** Token visible in `docker ps` or `ps aux` output

### Pitfall 2: Docker Network Isolation
**What goes wrong:** cloudflared cannot reach dev-agent
**Why it happens:** Containers on different Docker networks or using default bridge
**How to avoid:** Ensure both services use the same named network (aesir-network)
**Warning signs:** Connection refused errors in cloudflared logs

### Pitfall 3: Race Condition on Startup
**What goes wrong:** External requests fail during container startup
**Why it happens:** cloudflared starts but tunnel not yet established when webhooks arrive
**How to avoid:** Use health check sidecar pattern with `depends_on: condition: service_healthy`
**Warning signs:** Intermittent 502/503 errors immediately after `docker compose up`

### Pitfall 4: Forgetting to Update Webhook URLs
**What goes wrong:** Webhooks still pointing to old ngrok/localhost URLs
**Why it happens:** Created tunnel but didn't update Linear/GitHub webhook configuration
**How to avoid:** Document webhook URL update as explicit setup step
**Warning signs:** No webhook events received after tunnel setup

### Pitfall 5: Quick Tunnel URL Instability
**What goes wrong:** Webhook configuration breaks after container restart
**Why it happens:** Quick tunnel URLs are randomly generated on each run
**How to avoid:** Use persistent tunnel with custom domain for development
**Warning signs:** URL like `random-words.trycloudflare.com` in configuration

## Code Examples

Verified patterns from official sources:

### Complete Docker Compose Service
```yaml
# Source: Cloudflare documentation + community best practices
cloudflared:
  image: cloudflare/cloudflared:2025.2.0
  container_name: aesir-cloudflared
  restart: unless-stopped
  # --no-autoupdate: prevents container from updating itself
  # --metrics=0.0.0.0:2000: exposes /ready endpoint for health checks
  command: tunnel --no-autoupdate run --metrics=0.0.0.0:2000
  environment:
    - TUNNEL_TOKEN=${CLOUDFLARE_TUNNEL_TOKEN}
  networks:
    - aesir-network
  depends_on:
    dev-agent:
      condition: service_started
```

```bash
# Add to .env.example

# ===================

# Tunnel token from Cloudflare Zero Trust dashboard

CLOUDFLARE_TUNNEL_TOKEN=your-tunnel-token-here
```

### Zero Trust Dashboard Configuration Steps
```
1. Go to dash.cloudflare.com -> Zero Trust
2. Navigate to: Networks -> Tunnels
3. Click "Create a tunnel"
4. Select "Cloudflared" as connector type
5. Name: "aesir-dev" (or similar)
6. Copy the tunnel token -> add to .env as CLOUDFLARE_TUNNEL_TOKEN
7. Add Public Hostname:
   - Subdomain: aesir-dev (or your choice)
   - Domain: your-cloudflare-domain.com
   - Path: (leave empty for all paths)
   - Service Type: HTTP
   - URL: dev-agent:3001
8. Save tunnel
9. Update Linear/GitHub webhooks to use:
   https://aesir-dev.your-cloudflare-domain.com/webhooks/linear
   https://aesir-dev.your-cloudflare-domain.com/webhooks/github
```

## Linear Webhook Requirements

From Linear official documentation:

| Requirement | Detail |
|-------------|--------|
| Protocol | HTTPS only (non-localhost) |
| Response | Must return HTTP 200 within 5 seconds |
| Retry policy | 3 retries with backoff: 1 min, 1 hour, 6 hours |
| Signature header | `Linear-Signature` (HMAC-SHA256) |
| Delivery ID header | `Linear-Delivery` (UUID) |
| Event type header | `Linear-Event` |

**Existing implementation in codebase:** `src/api/webhooks/linear-agent-session.ts` already handles signature verification using `verifyWebhookSignature` from `src/integrations/linear/webhooks.ts`.

## GitHub Webhook Requirements

From GitHub official documentation:

| Requirement | Detail |
|-------------|--------|
| Protocol | HTTPS recommended for production |
| Response | Must return 2xx status |
| Signature header | `X-Hub-Signature-256` (HMAC-SHA256) |
| Content-Type | application/json |

**Existing implementation in codebase:** `src/api/webhooks/github-pr-review.ts` already handles signature verification using timing-safe comparison.

## Setup Checklist

### Prerequisites
1. Cloudflare account (free tier is sufficient)
2. Domain added to Cloudflare (for custom subdomain)
3. Zero Trust enabled on account

### Tunnel Setup Steps
1. Create tunnel in Zero Trust dashboard
2. Copy tunnel token to `.env`
3. Add cloudflared service to `docker-compose.yml`
4. Configure public hostname in dashboard pointing to `dev-agent:3001`
5. Update Linear webhook URL in Linear settings
6. Update GitHub webhook URL in repository settings
7. Verify webhooks reach endpoint: `docker compose logs -f dev-agent`

### Verification Commands
```bash
# Start services
docker compose up -d

# Verify tunnel is healthy
docker compose exec cloudflared curl -fsS http://localhost:2000/ready

# Check tunnel logs
docker compose logs -f cloudflared

# Test webhook endpoint through tunnel
curl -X POST https://your-subdomain.your-domain.com/webhooks/linear
# Expected: 401 (no signature) - confirms endpoint is reachable
```

## Open Questions

Things that couldn't be fully resolved:

1. **Tunnel availability during Cloudflare outages**
   - What we know: Cloudflare has high uptime, but tunnels depend on their edge network
   - What's unclear: Impact on development workflow if Cloudflare has issues
   - Recommendation: Keep Quick Tunnel as fallback for emergencies (no account needed)

2. **Multiple developers sharing tunnel**
   - What we know: Each developer needs their own tunnel or shared staging environment
   - What's unclear: Best practice for team development workflows
   - Recommendation: Each developer creates personal tunnel; document in README
