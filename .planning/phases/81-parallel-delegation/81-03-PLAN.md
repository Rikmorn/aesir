<objective>
Extend the TaskSignalDispatcher with group policy evaluation and add groupId-scoped signal matching. This is the core infrastructure that makes parallel delegation work -- it determines when the delegator wakes up.

Purpose: Without this, group task completions would trigger individual per-task signals (wrong behavior). The dispatcher must aggregate terminal events, evaluate group policy, and only signal the delegator when the policy dictates.

Output: Extended dispatcher with group-aware signaling, signal matching with groupId support, new signal types.
</objective>

**Extend TaskSignalDispatcher (task-signal-dispatcher.ts):**

1. Add `GroupService` to `TaskSignalDispatcherOptions`:
   ```typescript
   export interface TaskSignalDispatcherOptions {
     executor: ConversationExecutor;
     taskService: TaskService;
     eventLog: EventLog;
     db: NodePgDatabase<typeof agentsSchemaModule>;
     logger: PinoLogger;
     /** GroupService for policy evaluation (Phase 81, optional for backward compat) */
     groupService?: GroupService;
   }
   ```

2. In `onTaskUpdate()`, after fetching the task (step 2), add a group-aware branch:

   ```
   // 3a. Group-aware signaling: if task has group_id, delegate to group evaluation
   if (task.group_id && groupService) {
     await handleGroupTaskUpdate(task, newStatus);
     return;
   }
   // 3b. Root task: no parent, nobody to signal
   if (!task.parent_id) return;
   // ... existing per-task signaling continues ...
   ```

3. Implement `handleGroupTaskUpdate(task, newStatus)` as an inner function:
   a. Lock the group row with `SELECT ... FOR UPDATE` to prevent race conditions (Pitfall 1 from research):
      ```sql
      SELECT * FROM agents.task_groups WHERE id = $groupId FOR UPDATE
      ```
   b. If group is already in terminal state (satisfied, unsatisfiable, cancelled), skip evaluation. But still check for `settled` transition.
   c. Get group state via `groupService.getGroupState(task.group_id)`.
   d. Call `evaluatePolicy(group.policy, state)` (imported from group-service.ts).
   e. **Wake-up decision tree:**
      - If `satisfied` and group.status was `active` -> update group to `satisfied`, send `group_policy_satisfied` signal
      - If `unsatisfiable` and group.status was `active` -> update group to `unsatisfiable`, send either `group_policy_unsatisfiable` (for any_sufficient/min_required) or `group_task_failed` (for all_required, to indicate the specific failure)
      - If neither -> no signal (more tasks still running)
   f. **Settled check:** After policy evaluation, check if all tasks are terminal (`state.running === 0 && state.pending === 0`). If so and group status is satisfied/unsatisfiable (not active), transition to `settled` and send `group_settled` signal.
   g. **Signal payload** for group signals (state + context, not suggested actions per user decision):
      ```typescript
      const signalData = {
        groupId: task.group_id,
        taskId: task.id,  // The triggering task
        policyType: group.policy.type,
        policySatisfied: result.satisfied,
        policyUnsatisfiable: result.unsatisfiable,
        groupState: {
          total: state.total,
          completed: state.completed,
          failed: state.failed,
          cancelled: state.cancelled,
          running: state.running,
        },
        // Include summaries for completed/failed tasks
        taskSummaries: state.tasks
          .filter(t => ["completed", "failed", "cancelled"].includes(t.status))
          .map(t => ({
            taskId: t.taskId,
            status: t.status,
            assigneeId: t.assigneeId,
            result: t.completionResult,
          })),
      };
      ```
   h. **Signal message** (human-readable for LLM):
      - Satisfied: `"Group {groupId} policy satisfied ({policyType}). {completed}/{total} tasks completed."`
      - Unsatisfiable: `"Task {taskId} failed in group {groupId}. Group state: {completed} completed, {failed} failed, {running} running. Policy: {policyType} (no longer satisfiable)."`
      - Settled: `"All tasks in group {groupId} have reached terminal state. Final: {completed} completed, {failed} failed, {cancelled} cancelled."`
   i. Send signal via `executor.signal(group.delegator_conversation_id, signal)`.
   j. Write `completion_result` on the triggering task (same pattern as existing per-task handler -- write the group signal as completion_result on the individual task row).

4. **Important:** When a task has a `group_id`, the dispatcher MUST NOT send per-task `task_completion`/`task_failure` signals to the delegator. The group evaluation subsumes that (Pitfall 2 from research).

- Settled transition: all terminal after policy evaluation -> group_settled signal
- Concurrent evaluation: second evaluation after group is already satisfied -> no duplicate signal
