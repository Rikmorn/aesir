# Phase 22.1 Plan 01: Refactor @aesir/common to Pure Library Summary

**One-liner:** Removed env validation from @aesir/common to unblock Docker container startup

## Overview

Refactored @aesir/common to pure library pattern by deleting the config folder and removing import-time environment validation. This unblocks Docker container startup where integration services were failing due to cascading validation failures when importing common utilities.

**Problem:** Integration packages import @aesir/common for error types, logging, and ID utilities. This triggered env validation even though integrations have their own environment configuration, causing containers to fail on startup with validation errors.

**Solution:** Removed all config-related code from @aesir/common. The logger factory already accepted optional config with process.env defaults (pure pattern). ID utilities were renamed from db/ to utils/ for clarity.

## Decisions Made

1. **Delete config folder entirely**
   - Rationale: Common library should not own environment validation - services should
   - Alternative considered: Keep config but make it lazy via Proxy (attempted in Phase 22, insufficient)
   - Chosen approach: Remove config completely, push validation to consuming packages

2. **Rename db/ to utils/**
   - Rationale: Folder contains pure utilities (nanoid wrappers), not database logic
   - Alternative: Keep misleading "db" name
   - Chosen approach: Rename for semantic clarity

3. **Logger already pure - no changes needed**
   - Rationale: createLogger() already follows pure library pattern
   - Alternative: None needed
   - Verification: Accepts optional config, defaults to process.env, no validation

## Lessons Learned

1. **Lazy validation insufficient for deep import chains**
   - Proxy-based lazy validation attempted in Phase 22
   - Failed because module-level code (db connections) still triggered validation
   - Lesson: True pure library requires zero module-level side effects

2. **Misleading folder names create confusion**
   - db/ folder contained no database code (just nanoid wrappers)
   - Developers would expect database connections in db/
   - Lesson: Folder names should reflect actual content, not historical context

3. **Logger was already correct**
   - createLogger() already followed dependency injection pattern
   - No changes needed - demonstrates correct library design from Phase 12
   - Lesson: Review existing code before assuming changes needed
