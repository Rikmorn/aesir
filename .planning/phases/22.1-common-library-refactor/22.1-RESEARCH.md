# Phase 22.1: Common Library Refactor - Research

**Researched:** 2026-01-24
**Domain:** TypeScript library architecture, dependency injection patterns, monorepo shared packages
**Confidence:** HIGH

## Summary

This phase refactors @aesir/common from a library with import-time side effects (environment validation, global state) to a pure library pattern where all dependencies are passed as function arguments. The core architectural principle is "functional core, imperative shell" — the library provides pure utilities (core), while services own their environment configuration and pass values to library functions (shell).

Current problem: Importing @aesir/common triggers lazy environment validation via Proxy objects, which causes cascading failures in Docker containers and requires complex vi.mock patterns in tests. Services already have their own config files (packages/integrations/*/src/types/config.ts) but still trigger common's validation through transitive imports.

The refactor follows established TypeScript patterns from 2025:
- Factory functions with explicit options objects for dependency injection
- No module-level side effects or global state
- Services validate environment at boot time (fail-fast, eager validation)
- Libraries accept pre-validated configuration as arguments
- TypeScript project references for clean package boundaries in monorepos

**Primary recommendation:** Delete common/src/config/ entirely, refactor logger to `createLogger(opts?)` with sensible defaults, move integration-specific errors to their packages, and update all consumers in a big-bang migration with compilation-time verification.

### Pattern 1: Factory Function with Optional Dependencies
**What:** Export factory functions that accept options with sensible defaults from process.env
**When to use:** Logger, utilities that need configuration but should work with minimal setup

**Example:**
```typescript
// packages/common/src/logging/pino-logger.ts
export interface CreateLoggerOptions {
  service?: string;
  component?: string;
  level?: string;
  correlationId?: string;
}

export function createLogger(options: CreateLoggerOptions = {}): Logger {
  const {
    service = process.env.SERVICE_NAME ?? "aesir",
    component,
    level = process.env.LOG_LEVEL ?? "info",
    correlationId,
  } = options;

  // No validation, just use defaults
  return pino({
    level,
    base: {
      service,
      ...(component && { component }),
      ...(correlationId && { correlationId }),
    },
    // ... rest of config
  });
}
```

**Why this works:**
- Services can pass explicit values: `createLogger({ service: config.service.name, level: config.logging.level })`
- Tests can pass minimal config: `createLogger({ level: 'silent' })`
- No environment validation at import time
- Defaults from process.env for backwards compatibility

### Pattern 2: Service-Level Eager Configuration
**What:** Single config.ts file per service with eager validation at module load
**When to use:** All services (integrations, agents) that run as independent processes

**Example:**
```typescript
// packages/integrations/linear/src/config.ts
import dotenvFlow from "dotenv-flow";
import { z } from "zod";

// Load env files immediately (not lazy)
dotenvFlow.config({ silent: true, default_node_env: "development" });

const linearEnvSchema = z.object({
  PORT: z.coerce.number().default(3001),
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  LINEAR_CLIENT_ID: z.string().min(1),
  LINEAR_CLIENT_SECRET: z.string().min(1),
  // ... all env vars for this service
});

// Validate immediately (fail-fast at boot)
const parsed = linearEnvSchema.safeParse(process.env);
if (!parsed.success) {
  console.error("Linear environment validation failed:", parsed.error.format());
  process.exit(1);
}

export const env = parsed.data;
export const config = {
  server: { port: env.PORT, nodeEnv: env.NODE_ENV },
  linear: { clientId: env.LINEAR_CLIENT_ID, clientSecret: env.LINEAR_CLIENT_SECRET },
  // ... typed config object
} as const;
```

**Why this works:**
- Eager validation at boot — service crashes immediately if env vars missing
- Single source of truth for service configuration
- No Proxy objects — just plain validated data
- Clear error messages listing ALL missing vars at once

### Pattern 3: Type Re-exports for Clean Abstraction
**What:** Re-export third-party types from common to shield consumers from implementation details
**When to use:** Types that appear in common's public API

**Example:**
```typescript
// packages/common/src/logging/types.ts
import type { Logger } from "pino";

// Re-export for consumers
export type { Logger, Logger as PinoLogger };

export interface CreateLoggerOptions {
  service?: string;
  component?: string;
  level?: string;
}
```

**Why this works:**
- Consumers import from @aesir/common, not from pino directly
- Future logger implementation changes don't break consumers
- Type-only imports have zero runtime cost

### Anti-Patterns to Avoid

- **Lazy validation via Proxy:** Module-level Proxy objects that validate on property access create cascading failures. Services can't import utilities without triggering full env validation.

- **Global config objects:** Module-level `export const config = buildConfig()` creates hidden dependencies and makes testing require vi.mock. Pass config explicitly to functions.

- **Mixed lazy/eager loading:** Half-lazy (Proxy) + half-eager (db clients) creates confusion and unpredictable failures. Be consistent: libraries are eager (load immediately), services validate at boot.

- **Environment validation in libraries:** Libraries shouldn't know about environment variables. Accept pre-validated config as function arguments.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| DI container | Custom service registry with decorators | Factory functions with options objects | Decorators require reflect-metadata polyfill, add build complexity; factory functions are simpler and equally testable |
| Environment validation | Custom env parser | Zod schemas with safeParse | Zod provides detailed error messages, type inference, and is already adopted across the codebase |
| Logger factory | Custom logger builder | pino with createLogger(opts?) | Pino is already in use, battle-tested, high-performance; factory pattern is native to Node.js/TypeScript |
| ID generation | uuid or custom nanoid wrapper | nanoid with prefix util | nanoid is already a dependency, 21-character IDs are sufficient; prefix pattern is established |

**Key insight:** The TypeScript/Node.js ecosystem has standardized on factory functions (not DI containers) for library-level dependency injection. Factory functions are simpler, require no decorators, work naturally with TypeScript's type system, and are easier to test.

## Common Pitfalls

### Pitfall 1: Breaking Changes Hidden by Type Compatibility
**What goes wrong:** Removing exports from @aesir/common causes runtime errors in production if TypeScript compilation succeeds but runtime imports fail.

**Why it happens:** TypeScript validates types at compile time, but dynamic imports or conditional code paths may not be checked. Integration packages re-export from common, creating transitive dependencies.

**How to avoid:**
- Run full build across all packages: `pnpm build` from monorepo root
- Run all unit tests: `pnpm test:fast` (no Docker required)
- Start all Docker containers: `docker compose up` (verifies runtime imports)
- Audit integration package index.ts files for re-exports that depend on removed common exports

**Warning signs:**
- Build succeeds but Docker containers fail with "module not found"
- Tests pass locally but fail in CI/Docker
- Runtime errors about missing exports despite TypeScript compilation success

### Pitfall 2: Forgetting to Update Mock Patterns
**What goes wrong:** Tests use vi.mock("@aesir/common", () => ({ ... })) to prevent config validation. After refactor, mocks may export wrong interface or unnecessary mocked functions.

**Why it happens:** 160 files import from @aesir/common, many with vi.mock. Mock implementations need to match new factory signatures.

**How to avoid:**
- After refactor, remove vi.mock for @aesir/common from test files where no longer needed (if library has no side effects, mocking isn't required)
- Update remaining mocks to match new factory signatures: `createLogger: vi.fn(() => mockLogger)`
- Use Grep to find all vi.mock patterns: `grep -r 'vi.mock.*@aesir/common' packages/`
- Run test suite after each mock update to verify

**Warning signs:**
- Tests fail with "X is not a function" after refactor
- Tests expect mocked config object but now get function
- Type errors in test files that were previously masked

### Pitfall 3: Docker Environment Variable Mismatches
**What goes wrong:** docker-compose.yml passes environment variables that don't match service config schemas, causing validation failures at container startup.

**Why it happens:** Config schemas evolve independently from docker-compose.yml. Variables get renamed, defaults change, or new required vars are added.

**How to avoid:**
- Maintain alignment between .env (source of truth), docker-compose.yml (container env), and service config.ts (validation schema)
- Use consistent naming: DB_HOST in .env, DB_HOST in docker-compose.yml, DB_HOST in schema
- Test container startup locally: `docker compose up [service-name]`
- Check health endpoints after startup: `curl http://localhost:3001/health`

**Warning signs:**
- Container exits immediately after startup
- Logs show "environment validation failed"
- Different behavior between `pnpm dev` (local) and Docker

### Pitfall 4: Runtime Dependencies vs DevDependencies
**What goes wrong:** Library moves dependencies to devDependencies, causing "module not found" in containers despite working locally.

**Why it happens:** Local development has devDependencies installed, but Docker builds with `--production` flag or `pnpm deploy` which excludes devDependencies. Past issues: nanoid, dotenv-flow not available in containers.

**How to avoid:**
- Runtime dependencies (imported in src/) go in dependencies
- Build-time only (TypeScript, Vitest) go in devDependencies
- Check each library in common: if it appears in src/ imports, it's a runtime dependency
- After updating package.json, rebuild Docker image: `docker compose build [service-name]`
- Verify with `docker compose up [service-name]` — container must start successfully

**Warning signs:**
- Build succeeds locally but Docker image fails to start
- Error: "Cannot find module 'pino'" or similar in container logs
- Works with `pnpm dev` but fails with `pnpm build && node dist/main.js`

### Logger Factory (Pure Function with Defaults)
```typescript
// packages/common/src/logging/pino-logger.ts
import type { Logger } from "pino";
import pino from "pino";

export interface CreateLoggerOptions {
  service?: string;
  component?: string;
  level?: string;
  correlationId?: string;
  parentCorrelationId?: string;
  rootCorrelationId?: string;
}

export function createLogger(options: CreateLoggerOptions = {}): Logger {
  const {
    service = process.env.SERVICE_NAME ?? "aesir",
    component,
    level = process.env.LOG_LEVEL ?? "info",
    correlationId,
    parentCorrelationId,
    rootCorrelationId,
  } = options;

  return pino({
    level,
    base: {
      service,
      ...(component && { component }),
      ...(correlationId && { correlationId }),
      ...(parentCorrelationId && { parentCorrelationId }),
      ...(rootCorrelationId && { rootCorrelationId }),
    },
    timestamp: () => {
      const now = new Date();
      return `,"timestamp":"${now.toISOString()}","time":${now.getTime()}`;
    },
    formatters: {
      level: (label) => ({ level: label }),
    },
  });
}

// Service usage with explicit config
import { createLogger } from "@aesir/common";
import { config } from "./config.js";

const logger = createLogger({
  service: "linear-integration",
  component: "integrations:linear",
  level: config.logging.level,
});
```

### Service Entry Point (Dependency Injection)
```typescript
// packages/integrations/linear/src/main.ts
import { createPinoLogger, createHttpLogger } from "@aesir/common";
import express from "express";
import { db } from "./db/client.js";
import { config } from "./config.js"; // Validates at import time
import { createRoutes } from "./api/routes.js";

// Config already validated (or process exited)
const logger = createPinoLogger({
  component: "integrations:linear",
  level: config.logging.level,
});

async function main() {
  const app = express();

  app.use(express.raw({ type: "application/json" }));
  app.use(createHttpLogger({ logger }));

  const routes = createRoutes({ logger });
  app.use("/", routes);

  app.listen(config.server.port, () => {
    logger.info({ port: config.server.port }, "Linear service started");
  });
}

main().catch((err) => {
  logger.error({ err }, "Failed to start");
  process.exit(1);
});
```

### Integration-Specific Error (Moved from Common)
```typescript
// packages/integrations/linear/src/errors.ts
import { AppError, type ErrorMetadata, type RecoveryHint } from "@aesir/common";

export type LinearErrorCode =
  | "INT_LINEAR_API"
  | "INT_LINEAR_WEBHOOK"
  | "INT_LINEAR_TOKEN"
  | "INT_LINEAR_OAUTH";

export class LinearError extends AppError {
  readonly code: LinearErrorCode;

  constructor(
    code: LinearErrorCode,
    message: string,
    options?: {
      cause?: Error;
      metadata?: ErrorMetadata;
      recovery?: RecoveryHint;
    },
  ) {
    super(message, options);
    this.code = code;
    this.name = "LinearError";
  }

  get httpStatus(): number {
    switch (this.code) {
      case "INT_LINEAR_WEBHOOK":
      case "INT_LINEAR_TOKEN":
        return 401;
      case "INT_LINEAR_OAUTH":
        return 400;
      default:
        return 500;
    }
  }
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Global config singleton | Factory functions with explicit deps | TypeScript ecosystem 2023-2025 | Better testability, no hidden dependencies |
| Lazy Proxy validation | Eager validation at service boot | This refactor (2026) | Fail-fast errors, simpler debugging, no cascading failures |
| Module-level side effects | Pure libraries, impure services | Functional programming best practices 2024-2025 | Libraries are side-effect-free, services own state |
| DI containers with decorators | Factory functions with options | TypeScript community shift 2024-2025 | No reflect-metadata, simpler build, better tree-shaking |

**Deprecated/outdated:**
- Lazy validation via Proxy: Causes cascading failures, hard to debug, replaced by eager validation in services
- Config folder in libraries: Libraries shouldn't validate environment, services should
- Integration errors in common: Each integration owns its error types, common provides base classes only
- vi.mock for @aesir/common in every test: Only needed for side effects; pure libraries don't need mocking

## Open Questions

Things that couldn't be fully resolved:

1. **Should agent-config.ts stay in common or move to agents?**
   - What we know: Contains AgentConfigSchema, devAgentConfig, validation utils
   - What we know: Used only by agents package, not platform or integrations
   - What's unclear: Is it a cross-layer contract (like state/) or agent-specific?
   - Recommendation: Move to agents package — it's agent configuration, not a shared contract. Platform doesn't need to know agent config schema.

2. **Should db/ids.ts be renamed to utils/ids.ts?**
   - What we know: Currently in common/src/db/index.ts, exports createId utility
   - What we know: No database-specific logic, just nanoid with prefix pattern
   - What's unclear: Does "db" folder imply database operations, causing confusion?
   - Recommendation: Rename to utils/ids.ts — it's a pure utility, not database-specific

3. **How many test mocks can be removed vs updated?**
   - What we know: 160 files import from @aesir/common, many with vi.mock
   - What we know: Pure libraries don't need mocking for side effects
   - What's unclear: How many mocks are for config validation vs other reasons (spying, stubbing API calls)?
   - Recommendation: Grep all vi.mock patterns, categorize (config vs other), remove config mocks, update others. Defer detailed audit to planning phase.
