# Phase 58.1: Task Schema and Service - Context

**Gathered:** 2026-02-06
**Status:** Ready for planning

<domain>
## Phase Boundary

The task and handoff data model exists in PostgreSQL with a validated service layer, enabling the tool and routing layers to be built on top. This phase also includes the prerequisite ToolContext.taskId → sandboxId rename across the codebase.

Scope: migration (drop legacy + create new), TaskService with shape validation, ToolContext rename, createId additions. Agent tools, routing changes, correlation tables, and prompt updates are separate phases.

</domain>

<decisions>
## Implementation Decisions

### Validation boundary
- **Service validates shape** (data integrity): metadata is valid JSONB under 10KB, handoff context has required summary (max 2000 chars, ~4KB total), title is non-empty, type fields are valid enums. Implemented as Zod schemas that reject structurally invalid data.
- **Tools validate business logic** (workflow rules, Phase 58.2): status transitions, circular delegation, max depth/subtask limits. These require context the service doesn't have.
- **Reasoning:** The service is the single writer to the database. Shape validation at the service layer guarantees data integrity regardless of caller (tools, tests, migration helpers, future admin API). Business logic at the tool layer keeps the service simple and reusable.

### Plan structure
- **Two plans:** Plan 1 is the ToolContext rename (prerequisite). Plan 2 is schema migration + TaskService + createId additions.
- **Plan 1 (rename):** Mechanical `taskId → sandboxId` across ~37 files (framework types, worker-loop, codebase tool factories, spawn-agent, router tools, tests). Also rename `taskId` → `correlationRef` in `query-conversations.ts` router tool. Isolated commit, own blast radius.
- **Plan 2 (schema/service):** Single migration file (DROP legacy → CREATE new → ALTER conversations), TaskService, createId.task() and createId.handoff() in @aesir/types.
- **Reasoning:** The rename is a prerequisite, not a peer. Having two meanings of `taskId` coexisting during a plan is error-prone. Clean commit boundary: "rename taskId → sandboxId" then "add task schema and service."

### Migration strategy
- **Single migration file:** DROP `tasks`, `context_snapshots`, `execution_traces` unconditionally, then CREATE `agents.tasks` + `agents.task_handoffs`, then ALTER `agents.conversations` to add `task_id`. Atomic, simpler to reason about.
- Remove legacy table definitions from `schema.drizzle.ts` in the same plan.

### createId placement
- `createId.task()` and `createId.handoff()` additions go in Plan 2 (schema/service), not Plan 1 (rename). They live in `packages/types/src/utils/ids.ts` — different package and file from the ToolContext rename. Introduced alongside their first consumer (TaskService.create() and addHandoff()).

### Claude's Discretion
- Test approach for the rename pass (snapshot tests vs manual verification vs typecheck-driven)
- TaskService internal implementation details (query patterns, error handling strategy)
- Exact Zod schema definitions for task create/update params (following spec field definitions)
- Whether to add TaskService integration tests with testcontainers or unit tests with mocks (or both)

</decisions>

## Specific Ideas

- "The service is the single writer to the database. Shape validation at the service layer guarantees data integrity regardless of the caller."
- "A future admin API could call service.update() to force-cancel a task without going through the tool's transition checks."
- "Adding createId entries in the rename plan means they sit unused until the next plan lands. Adding them in the schema/service plan means they're introduced alongside their first consumer."
