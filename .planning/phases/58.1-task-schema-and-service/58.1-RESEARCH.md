# Phase 58.1: Task Schema and Service - Research

**Researched:** 2026-02-06
**Domain:** PostgreSQL schema migration, Drizzle ORM, service layer, codebase rename
**Confidence:** HIGH

## Summary

This phase introduces the `agents.tasks` and `agents.task_handoffs` tables, a TaskService CRUD layer with Zod shape validation, adds `createId.task()` and `createId.handoff()` to `@aesir/types`, and renames the existing `ToolContext.taskId` (sandbox container ID) to `sandboxId` across the agents package. The spec (`2.5-agentic-conversations.md` Phase 3) provides complete SQL schemas, service method signatures, and status enum values, so no design research is needed -- the research focus is on codebase patterns, rename scope, migration mechanics, and pitfall identification.

The codebase has well-established patterns for all aspects of this phase: factory functions with options objects, Drizzle ORM schemas with companion `schema.drizzle.ts`, hand-written SQL migrations, and Zod validation. The primary risk is the rename (Plan 1) touching files across multiple domains with different `taskId` meanings -- careful scoping prevents unintended changes to Slack integration, platform logging, and test utility code where `taskId` means "Linear issue identifier," not "sandbox container ID."

**Primary recommendation:** Execute as two sequential plans. Plan 1: mechanical rename of `ToolContext.taskId` to `sandboxId` scoped to 20 files in `packages/agents/src`. Plan 2: migration + schema + service + createId additions.

### Anti-Patterns to Avoid
- **DO NOT use drizzle-kit generate for this migration.** The project writes migrations by hand. drizzle-kit generate would try to diff the schema.drizzle.ts and might produce unwanted DROP/ALTER statements.
- **DO NOT add a Postgres trigger for `updated_at` on tasks.** The spec explicitly states `updated_at` is application-level in TaskService, not a trigger. This is different from the conversations table which does use a trigger (see migration 0000).
- **DO NOT rename `taskId` in platform, Slack integration, or test-utils packages.** Those use `taskId` to mean "Linear issue identifier" -- completely different concept from the sandbox container ID being renamed.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| ID generation | Custom UUID or incrementing IDs | `createId.task()` / `createId.handoff()` | Consistent prefix pattern, collision resistant |
| Input validation | Manual field checks | Zod schemas with `.parse()` / `.safeParse()` | Automatic type inference, consistent error messages |
| DB queries | Raw SQL strings | Drizzle ORM query builder | Type-safe, composable, consistent with codebase |
| JSON size validation | `JSON.stringify().length` alone | Zod `.refine()` with `Buffer.byteLength()` | Handles multi-byte chars correctly |

**Key insight:** Every pattern needed already exists in the codebase. The service is a composition of existing patterns, not novel engineering.

## Common Pitfalls

### Pitfall 1: Rename Scope Creep
**What goes wrong:** Renaming `taskId` to `sandboxId` catches files outside the intended scope -- Slack integration (`taskId` = Linear issue ID), platform logging (`taskId` in TraceContext), test-utils (workflow state `taskId`).
**Why it happens:** Global find-and-replace without understanding the semantic difference.
**How to avoid:** Scope Plan 1 rename ONLY to files where `taskId` means "sandbox container ID":
- `packages/agents/src/framework/types.ts` (ToolContext interface)
- `packages/agents/src/framework/worker-loop.ts` (sandbox setup)
- `packages/agents/src/framework/tool-factories.ts` (codebase adapter)
- `packages/agents/src/shared/tools/types.ts` (CodebaseToolDeps interface)
- `packages/agents/src/shared/tools/codebase/*.ts` (5 tool files)
- `packages/agents/src/shared/tools/coordination/spawn-agent.ts`
- Corresponding test files
- Router: `query-conversations.ts` (`taskId` param -> `correlationRef`)
- Router: `system-prompt.ts` (prompt text references `taskId`)
**Warning signs:** Changes to files in `packages/integrations/`, `packages/platform/src/logging/`, or `packages/test-utils/`.

### Pitfall 2: schema.drizzle.ts Sync
**What goes wrong:** Adding new tables to `schema.ts` but forgetting `schema.drizzle.ts`, or vice versa. Or removing legacy tables from `schema.drizzle.ts` but not `schema.ts`.
**Why it happens:** The project maintains two schema files (runtime vs drizzle-kit).
**How to avoid:** Both files must be updated in lockstep:
- `schema.ts`: Remove nothing (legacy tables aren't there). Add `tasks`, `taskHandoffs` with type exports.
- `schema.drizzle.ts`: Remove `contextSnapshots`, `tasks` (old), `executionTraces`. Add new `tasks`, `taskHandoffs` (matching `schema.ts` but without external deps).
**Warning signs:** `drizzle-kit generate` produces unexpected diff. Typecheck fails on missing table references.

### Pitfall 3: Migration Ordering with Foreign Keys
**What goes wrong:** The migration tries to ALTER `conversations` to add `task_id` FK before the `tasks` table is created.
**Why it happens:** SQL statements in wrong order.
**How to avoid:** Order: (1) DROP legacy tables, (2) CREATE `tasks`, (3) CREATE `task_handoffs` (references tasks), (4) ALTER `conversations` ADD `task_id` (references tasks), (5) CREATE indexes.

### Pitfall 4: Self-Referential FK on tasks.parent_id
**What goes wrong:** Drizzle ORM self-referential foreign keys can be tricky. In the SQL migration, it's straightforward: `parent_id TEXT REFERENCES agents.tasks(id)`. In the Drizzle schema definition, self-reference requires a function call.
**Why it happens:** Drizzle needs the table reference to exist before it can be used.
**How to avoid:** Use Drizzle's self-referential pattern:
```typescript
parent_id: text("parent_id").references(() => tasks.id),
```
In the hand-written SQL, just use `REFERENCES agents.tasks(id)` directly.

### Pitfall 5: JSONB Size Validation
**What goes wrong:** Using `JSON.stringify(obj).length` to check 10KB metadata limit doesn't account for multi-byte characters.
**Why it happens:** JavaScript string length !== byte length.
**How to avoid:** Use `Buffer.byteLength(JSON.stringify(metadata), 'utf-8') <= 10240` in the Zod `.refine()`.

### Pitfall 6: Null task_id Backward Compatibility
**What goes wrong:** New code that accesses `conv.task_id` without null checks breaks existing conversations.
**Why it happens:** `task_id` is nullable on conversations. All existing rows will have `task_id = null`.
**How to avoid:** The Drizzle schema must declare `task_id` as nullable. The new `ToolContext.taskId` (Phase 58.1 TASK-22) is set from `conv.task_id ?? undefined` in the worker loop. All downstream code must handle `undefined`.

### Migration SQL (verified from spec + existing migration patterns)

```sql
-- 0005_add_task_tables.sql
-- Phase 58.1: Task primitive schema
-- DROP legacy tables, CREATE new tables, ALTER conversations

-- 1. Drop legacy tables (no runtime usage, different schema from v2.5)
DROP TABLE IF EXISTS agents.execution_traces;
--> statement-breakpoint
DROP TABLE IF EXISTS agents.context_snapshots;
--> statement-breakpoint
DROP TABLE IF EXISTS agents.tasks;
--> statement-breakpoint

-- 2. Create tasks table
CREATE TABLE agents.tasks (
  id            TEXT PRIMARY KEY,
  parent_id     TEXT REFERENCES agents.tasks(id),
  creator_type  TEXT NOT NULL CHECK (creator_type IN ('agent', 'human')),
  creator_id    TEXT NOT NULL,
  assignee_type TEXT NOT NULL CHECK (assignee_type IN ('agent', 'human')),
  assignee_id   TEXT NOT NULL,
  status        TEXT NOT NULL DEFAULT 'created'
                CHECK (status IN ('created', 'active', 'paused', 'completed', 'cancelled')),
  title         TEXT NOT NULL,
  objective     TEXT,
  metadata      JSONB DEFAULT '{}',
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  completed_at  TIMESTAMPTZ
);
--> statement-breakpoint

CREATE INDEX idx_tasks_assignee ON agents.tasks(assignee_type, assignee_id, status);
--> statement-breakpoint
CREATE INDEX idx_tasks_parent ON agents.tasks(parent_id) WHERE parent_id IS NOT NULL;
--> statement-breakpoint
CREATE INDEX idx_tasks_status ON agents.tasks(status) WHERE status IN ('created', 'active', 'paused');
--> statement-breakpoint

-- 3. Create task_handoffs table
CREATE TABLE agents.task_handoffs (
  id                TEXT PRIMARY KEY,
  task_id           TEXT NOT NULL REFERENCES agents.tasks(id),
  conversation_id   TEXT NOT NULL REFERENCES agents.conversations(id),
  handoff_type      TEXT NOT NULL CHECK (handoff_type IN ('completion', 'pause', 'delegation', 'escalation')),
  context           JSONB NOT NULL,
  author_type       TEXT NOT NULL CHECK (author_type IN ('agent', 'human')),
  author_id         TEXT NOT NULL,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
--> statement-breakpoint

CREATE INDEX idx_handoffs_task ON agents.task_handoffs(task_id, created_at);
--> statement-breakpoint

-- 4. Add task_id FK to conversations
ALTER TABLE agents.conversations
  ADD COLUMN task_id TEXT REFERENCES agents.tasks(id);
--> statement-breakpoint

CREATE INDEX idx_conversations_task ON agents.conversations(task_id)
  WHERE task_id IS NOT NULL;
```

### Zod Validation Schemas (TaskService)

```typescript
// Handoff context schema (from spec TASK-07)
const HandoffContextSchema = z.object({
  summary: z.string().min(1).max(2000),
  key_decisions: z.array(z.string()).optional(),
  artifacts: z.record(z.unknown()).optional(),
  open_questions: z.array(z.string()).optional(),

  (ctx) => Buffer.byteLength(JSON.stringify(ctx), 'utf-8') <= 4096,
  { message: "Handoff context must be under 4KB" }
);

// Task metadata schema (from spec TASK-08)
const TaskMetadataSchema = z.record(z.unknown()).refine(
  (meta) => Buffer.byteLength(JSON.stringify(meta), 'utf-8') <= 10240,
  { message: "Task metadata must be under 10KB" }
);

// Create task params
const CreateTaskParamsSchema = z.object({
  parentId: z.string().optional(),
  creatorType: z.enum(['agent', 'human']),
  creatorId: z.string().min(1),
  assigneeType: z.enum(['agent', 'human']),
  assigneeId: z.string().min(1),
  status: z.enum(['created', 'active', 'paused', 'completed', 'cancelled']).default('active'),
  title: z.string().min(1),
  objective: z.string().optional(),
  metadata: TaskMetadataSchema.optional().default({}),
```

### TaskService Query Pattern

```typescript
// Using Drizzle ORM (consistent with codebase):
async create(params) {
  const validated = CreateTaskParamsSchema.parse(params);
  const id = createId.task();
  const now = new Date();

  const [task] = await db
    .insert(tasks)
    .values({
      id,
      parent_id: validated.parentId ?? null,
      creator_type: validated.creatorType,
      creator_id: validated.creatorId,
      assignee_type: validated.assigneeType,
      assignee_id: validated.assigneeId,
      status: validated.status,
      title: validated.title,
      objective: validated.objective ?? null,
      metadata: validated.metadata,
      created_at: now,
      updated_at: now,
    })
    .returning();

  return task;
}

async update(taskId, fields) {
  const validated = UpdateTaskParamsSchema.parse(fields);
  const now = new Date();

  const [updated] = await db
    .update(tasks)
    .set({
      ...validated,
      updated_at: now,
      ...(validated.status === 'completed' && { completed_at: now }),
    })
    .where(eq(tasks.id, taskId))
    .returning();

  if (!updated) throw new Error(`Task not found: ${taskId}`);
  return updated;
}
```

## Testing Recommendations (Claude's Discretion)

### Plan 1 (Rename): Typecheck-Driven Verification

**Recommendation:** Use `pnpm run typecheck` as the primary verification, supplemented by running existing tests.

**Reasoning:**
- The rename is purely mechanical (no logic changes). TypeScript's type system catches every missed reference.
- All existing tests should pass unchanged (behavior is identical, just field names differ).
- Running `pnpm run typecheck` after the rename catches every remaining reference to the old `taskId` field on `ToolContext` and `CodebaseToolDeps`.
- No snapshot tests needed -- this adds maintenance burden for a one-time change.

**Verification steps:**
1. Rename across scoped files
2. `pnpm run typecheck` -- must pass with zero errors
3. `pnpm test:fast` -- existing unit tests must pass
4. Manual review of `query-conversations.ts` and `system-prompt.ts` for the `correlationRef` rename (prompt text is not type-checked)

### Plan 2 (Schema/Service): Unit Tests with Mocks

**Recommendation:** Unit tests with mocked DB for TaskService, verifying Zod validation and query construction. Defer integration tests with testcontainers to Phase 58.2 when the tools are built.

**Reasoning:**
- TaskService is a thin CRUD layer. The value of integration tests is lower here than for the tools (which have workflow logic).
- Unit tests with mocked `db` can verify: Zod rejects invalid inputs, correct Drizzle queries are constructed, `updated_at` is set application-side, `completed_at` is set when status transitions to completed.
- Migration correctness is verified by running `pnpm --filter @aesir/agents db:migrate` against a real database (manual, or in CI).

**Test cases for TaskService:**
- `create()`: validates params via Zod, generates `task_` prefixed ID, sets `updated_at`
- `create()`: rejects empty title, invalid creator_type, metadata > 10KB
- `update()`: sets `updated_at`, sets `completed_at` when status = completed
- `addHandoff()`: validates context via Zod, rejects missing summary, enforces 4KB limit
- `addHandoff()`: rejects summary > 2000 chars
- `getLatestHandoff()`: returns most recent by `created_at`
- `listByAssignee()`: filters by assignee_type + assignee_id + optional status
