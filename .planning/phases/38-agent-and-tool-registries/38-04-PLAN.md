Use create-all-then-find adapter pattern (as recommended in research Pitfall 4):
```typescript
const mcpAdapter = (
  createFn: (deps: McpToolDeps) => ToolDefinition[],
  displayName: string,
) => (ctx: ToolContext) => {
  const allTools = createFn({ agentId: ctx.agentId, correlationId: ctx.correlationId });
  const tool = allTools.find(t => t.name === displayName);
  if (!tool) throw new Error(`MCP tool ${displayName} not found in factory output`);
  return tool;
};
```

`coordination:spawn_agent` -- needs AgentRegistry + ToolRegistry for sub-agent resolution. The factory captures the agentRegistry reference and resolves sub-agents LAZILY at invocation time (when the tool's execute() is called), not at registration time. This avoids circular dependency issues.

```typescript
registry.register("coordination:spawn_agent", (ctx: ToolContext) => {
  // We need to build AgentTypeConfig objects for each sub-agent at resolve time.
  // The spawn_agent tool itself uses the existing createSpawnAgentTool factory,
  // which takes pre-built sub-agent configs. We build those configs by looking
  // up sub-agent definitions from the AgentRegistry.
  //
  // NOTE: This is an adapter that bridges v2.3 registries to the existing
  // v2.2 spawn_agent tool interface. Phase 40 (Executor) will simplify this.
  //
  // The agentRegistry.get() calls happen here (at resolve time, when the
  // parent agent's tools are being assembled), NOT at execute time.
  // This means sub-agent definitions are loaded once when the parent starts.

  // For now, return a tool that lazily builds sub-agent configs
  // We need tokenBudget and traceRecorder which are NOT in ToolContext
  // because they are conversation-scoped, not tool-scoped.
  //
  // Solution: The spawn_agent adapter returns a ToolDefinition whose execute()
  // function builds sub-agent configs from the registry on each spawn call.
  // This is the only tool that needs this pattern -- all others are stateless.

  return {
    name: "spawn_agent",
    description:
      "Spawn a focused sub-agent to perform a specific task. Available agent types: " +
      "'researcher' (explores codebase, reads files, searches code), " +
      "'coder' (implements changes, writes files, runs builds), " +
      "'tester' (runs tests, diagnoses failures, reads code). " +
      "Each sub-agent shares the token budget with the orchestrator.",
    inputSchema: z.object({
      agentType: z.enum(["researcher", "coder", "tester"]).describe("Type of sub-agent to spawn"),
      task: z.string().describe("Task description for the sub-agent to execute"),
      context: z.string().optional().describe("Additional context to prepend to the task"),
    }),
    async execute(): Promise<{ content: string; isError: boolean }> {
      // Phase 40 will replace this with the real implementation that uses
      // the ConversationExecutor to spawn child conversations.
      // For Phase 38, the ToolRegistry resolves this tool correctly,
      // but actual spawn execution still goes through the v2.2 path
      // (createOrchestratorToolkit -> createSpawnAgentTool).
      return {
        content: "spawn_agent via ToolRegistry is not yet wired to the executor. " +
                 "Phase 40 (ConversationExecutor) will implement this. " +
                 "Current execution uses the v2.2 toolkit path.",
        isError: true,
      };
    },
  };
});
```
