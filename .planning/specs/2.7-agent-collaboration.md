# Milestone v2.7: Agent Collaboration

**Status:** Planning
**Scope:** Multi-agent collaboration — agents delegate work to each other and to humans through tasks, backed by shared memory and a directory of capabilities. Linear gets first-class agent identity via Agent SDK.

---

## Phase 70: Linear Agent SDK Migration

**Goal**: The Linear integration uses Linear's native Agent SDK — agent activities replace comments, `actor=app` gives the agent its own identity, and the echo problem is eliminated by design.

**Depends on**: v2.6 complete

**Context**: Currently the agent communicates via `create_comment` using the installing user's OAuth token. This means agent comments appear as the user, echo filtering relies on `LINEAR_BOT_USER_ID` matching (brittle), and we miss Linear's first-class agent UX (activity types, session state, mention/assignment support). Linear's Agent SDK solves all three.

**References**:
- [Getting Started – Linear Agents](https://linear.app/developers/agents)
- [Agent Interaction – Linear Developers](https://linear.app/developers/agent-interaction)
- [OAuth Actor Authorization](https://linear.app/developers/oauth-actor-authorization)

### Requirements

| ID | Requirement |
|---|---|
| LSDK-01 | OAuth re-authorization with `actor=app` — agent gets its own workspace identity (name, icon), not the installing user's |
| LSDK-02 | New scopes `app:assignable` + `app:mentionable` — agent can be delegated issues and @mentioned |
| LSDK-03 | Agent activity MCP tools replace `create_comment` — `create_agent_activity` with typed content (`thought`, `response`, `elicitation`, `action`, `error`) |
| LSDK-04 | `agentSessionId` tracked from `agent_session.created` webhook through replyContext — denormalizer uses session ID for outbound activities |
| LSDK-05 | Communication tool to activity type mapping: `reply` → `response`, `ask` → `elicitation`, reasoning blocks → `thought` |
| LSDK-06 | Inbound `agent_session.prompted` events replace `comment.created` for user follow-ups during active agent sessions |
| LSDK-07 | Echo filter (`LINEAR_BOT_USER_ID`) removed — agent activities and user prompts are different types, no filtering needed |

### Success Criteria

1. The agent appears in Linear's mention menu and can be assigned issues directly, with its own name and avatar (not the installing user's)
2. When the dev-agent replies via `communication:reply` with a Linear replyContext, the denormalizer calls `createAgentActivity` with type `response` (not `create_comment`)
3. When a user sends a follow-up message on an agent session, it arrives as `agent_session.prompted` — adapter extracts the prompt, router signals the active conversation
4. Agent session state is visible in Linear UI (active/complete/error) based on agent activity emissions
5. No echo filtering code exists for Linear — agent activities and user prompts are structurally distinct

### Open Design Questions

1. **ReplyContext shape** — `agentSessionId` needs to be in replyContext alongside `issueId`. The session ID comes from the `created` webhook but the agent needs it for every outbound message. Store in replyContext or conversation row?
2. **Activity type classification** — `reply→response`, `ask→elicitation` is clean. Should `thought` activities be automatic (from `<reasoning>` blocks) or explicit (agent tool call)? Linear shows thoughts as ephemeral status updates.
3. **Product-agent** — Triggered from Slack, creates issues. No agent session. Still needs `create_comment` for issue comments, or just doesn't communicate via Linear?
4. **Backward compatibility** — Support both `create_comment` and `createAgentActivity` during migration, or cut over?
5. **Session lifecycle** — Agent should update session state (active → complete/error). Map to conversation lifecycle events?

### Estimated Plans

| Plan | Scope |
|---|---|
| 70-01 | OAuth `actor=app` re-auth + scopes + agent identity verification |
| 70-02 | Agent activity MCP tools + client SDK wrappers + permission seeding |
| 70-03 | Adapter + denormalizer + replyContext update (session ID tracking, activity type mapping, prompted events) |
| 70-04 | Remove echo filter + update tests + validate end-to-end |

|---|---|---|

| Client | `linear/src/client/factory.ts` | Expose agent activity methods |

## Phase 71: Shared Memory

**Goal**: Agents can store, classify, and query knowledge that persists across conversations — reducing redundant exploration and enabling context accumulation across the swarm.

**Depends on**: v2.6 complete

**Context**: Each agent conversation is isolated. When an agent discovers something (codebase structure, architecture decisions, constraints), that knowledge dies with the conversation. Task handoffs carry some context, but there's no persistent, queryable knowledge store. This means agents in a delegation chain repeatedly re-discover the same things, wasting token budget on redundant exploration. Shared memory provides the institutional knowledge that human teams build naturally through docs, wikis, and conversation history.

### Requirements

| ID | Requirement |
|---|---|
| MEM-01 | Knowledge classification system — entries are typed (e.g., `discovery`, `architecture_decision`, `constraint`, `thought`) with metadata (confidence, expiry, author agent, scope) |
| MEM-02 | Private agent memory (notepad) — working memory that persists across an agent's conversation turns but is not shared with other agents |
| MEM-03 | Shared knowledge store — classified entries accessible by all agents, queryable by topic/type/relevance |
| MEM-04 | MCP tools for memory operations — `knowledge:store`, `knowledge:query`, `knowledge:update` exposed as standard agent tools |
| MEM-05 | Scope and permissions — user-configurable policies controlling what knowledge is shared, what stays private, and what expires. Tradeoffs documented so users can make informed choices |
| MEM-06 | Storage abstraction — the classification determines the backend. Vector store for semantic search, structured DB for discrete facts, document store for long-form content. Agents interact through a unified tool interface regardless of backend |
| MEM-07 | Knowledge lifecycle — entries can expire, be superseded, or be explicitly invalidated. Stale facts don't poison future agent decisions |

### Success Criteria

1. An agent stores a discovery ("auth middleware uses JWT, located at src/middleware/auth.ts") and a subsequent agent in a different conversation queries "what do we know about auth?" and retrieves it
2. Private notepad entries are only visible to the authoring agent's conversations — other agents cannot query them
3. Knowledge entries carry classification metadata (type, confidence, expiry, author) that policies can act on
4. User can configure scope policies (e.g., "all discoveries are shared", "thoughts stay private") without code changes
5. Expired or invalidated knowledge is excluded from query results

### Open Design Questions

1. **Storage backends** — Vector DB (pgvector? dedicated service?) for semantic queries, Postgres for structured facts, or a unified store with multiple indexes? Start with one and expand, or design multi-backend from day one?
2. **Knowledge granularity** — Per-workspace? Per-project? Per-agent-type? A discovery about "the auth system" might be relevant to dev-agent but noise for product-agent.
3. **Conflict resolution** — Two agents store contradictory facts about the same topic. Last-write-wins? Confidence-based? Flag for human review?
4. **Curation mechanism** — Beyond expiry, should there be active curation (agent or human reviews and prunes)? Or is passive decay sufficient for v1?
5. **Classification taxonomy** — Fixed set of types or extensible? Too few types and everything is a `discovery`; too many and agents miscategorize.

### Estimated Plans

| Plan | Scope |
|---|---|
| 71-01 | Knowledge schema design + classification taxonomy + storage layer (Postgres-first, vector search via pgvector) |
| 71-02 | MCP tools (`knowledge:store`, `knowledge:query`, `knowledge:update`) + permission checks |
| 71-03 | Private notepad (agent-scoped memory) + scope/permission configuration |
| 71-04 | Agent prompt updates — teach agents when and how to store/query knowledge |

## Phase 72: Entity Directory

**Goal**: Agents can discover other agents and humans by capability — enabling informed delegation decisions based on who exists in the system and what they can do.

**Depends on**: Phase 70 (Linear Agent SDK — agent identity must be resolved before directory exposes agents)

**Context**: For agents to delegate work, they need to know who can help. Currently, agent definitions exist as YAML files on disk and humans exist only as implicit participants in Slack channels. There's no queryable registry that an agent can search to answer "who can implement code changes?" or "who can approve this design decision?" The directory provides service discovery for the agent swarm.

### Requirements

| ID | Requirement |
|---|---|
| DIR-01 | Entity table in database — stores agents and humans with type, name, declared capabilities (natural language), and reachability info |
| DIR-02 | Agent seeding from YAML — `pnpm seed:directory` reads agent definitions, extracts `id`, `name`, `description`, and new `capabilities` field, seeds to directory table |
| DIR-03 | Human entries — manually configured (seed script or admin UI). Includes name, role, capabilities, and reachVia (channel type + target, e.g., `{ channel: "slack", target: "#aesir-dev" }`) |
| DIR-04 | Capability-based query tool — `directory:find` accepts a capability description ("implement code changes", "approve architecture decisions") and returns matching entities ranked by relevance |
| DIR-05 | Entity detail tool — `directory:get` returns full profile for a specific entity (capabilities, reachability, type) |
| DIR-06 | Capabilities declared in definition.yaml — new `capabilities` field (list of natural language strings) describing what the agent can do at an intent level, not tool level |

### Success Criteria

1. An agent calls `directory:find` with "implement code changes and open pull requests" and receives dev-agent as the top result
2. An agent calls `directory:find` with "approve design decisions" and receives human entries with appropriate Slack reachability
3. Agent definitions include a `capabilities` field that is seeded to the directory table via `pnpm seed:directory`
4. Human entries exist in the directory with reachVia pointing to Slack channels
5. Directory queries return both agents and humans — the delegating agent chooses based on capability match, not entity type

### Open Design Questions

1. **Capability matching** — Exact text match, keyword search, or semantic similarity (vector search)? Semantic is more flexible but adds complexity. Keyword + description search may be sufficient for v1.
2. **Availability/capacity** — Should the directory reflect whether an agent is currently busy? Or assume all agents are always available? For v1, always-available is simpler.
3. **Human reachVia extensibility** — Start with Slack only (user's constraint), but the schema should accommodate Linear, email, etc. later. `reachVia` as a typed JSON field?
4. **Directory staleness** — Agents change over time (new capabilities, deprecated ones). Re-seed on deploy? Or watch for YAML changes?

### Estimated Plans

| Plan | Scope |
|---|---|
| 72-01 | Directory schema + entity table + seed script (agents from YAML, humans from config) |
| 72-02 | MCP tools (`directory:find`, `directory:get`) + capability matching logic |
| 72-03 | Agent definition.yaml `capabilities` field + prompt updates for directory usage |

## Phase 73: Task Delegation

**Goal**: Agents can delegate work to other agents or humans through tasks, with a negotiation handshake that gives the delegator agency over whether to wait, pivot, or escalate.

**Depends on**: Phase 72 (Entity Directory — agents need to discover who to delegate to)

**Context**: Currently, work flows through external systems: product-agent creates a Linear ticket, a human assigns it, dev-agent picks it up via webhook. This works but requires human intervention at every handoff. Task delegation generalizes this — an agent can send a task to any entity (agent or human) from the directory, the task materializes appropriately based on the recipient type, and a negotiation handshake ensures the delegator maintains agency over the work.

The delegation mechanism extracts the protocol that tickets already encode (deadline, priority, assignee, status, back-and-forth) and makes it medium-agnostic. Whether the team wants full ticket transparency or invisible internal handoffs is a prompt-level policy, not an architectural choice.

### Requirements

| ID | Requirement |
|---|---|
| DEL-01 | `task:delegate` tool — creates a task targeting an entity from the directory, with description, expectations (priority, estimated effort), and context from shared memory |
| DEL-02 | Task tree structure — delegated tasks carry `parentTaskId`, forming a tree from root task through all subtasks. Enables tracing the full delegation chain |
| DEL-03 | Negotiation handshake — target entity responds to delegation with accept (+ estimate), reject (+ reason), or counter-propose. Delegator decides: proceed, cancel, or try someone else |
| DEL-04 | Handshake abstraction — the negotiation protocol is a strategy that can be swapped. v1: simple accept/reject with estimate. Interface supports richer strategies later (counter-propose, redirect, partial accept) |
| DEL-05 | Materialization layer — task delivery adapts to recipient type. Agent → internal conversation start/signal. Human → Slack message (v1), with schema supporting Linear ticket, email, etc. later |
| DEL-06 | Materialization as policy — whether delegation creates an external artifact (Linear ticket) or stays internal is a prompt-level decision, not hardcoded. Teams configure their preferred transparency |
| DEL-07 | Delegation judgment guidance — agent prompts include criteria for when delegation is worth the overhead vs. doing the work directly. Prevents over-delegation / management-layer anti-pattern |

### Success Criteria

1. Product-agent discovers dev-agent via directory, delegates a task ("implement this feature"), dev-agent accepts with an estimate, and work begins in a new conversation linked as a subtask
2. An agent delegates to a human — the task materializes as a Slack message in the human's channel with context and expectations
3. A delegated-to agent rejects a task with a reason ("this requires database access, I don't have that capability") and the delegator pivots to another entity
4. Task tree is queryable — given a root task, all subtasks and their conversations are retrievable
5. The same delegation flow works with materialization as a Linear ticket (prompt-configured) or as an internal handoff — no code change required

### Open Design Questions

1. **Internal materialization mechanics** — Agent-to-agent delegation without external artifacts. Does the delegating agent call `start()` directly (via a tool), or does the system handle it? The tool creates the task, the materialization layer calls `start()` with the task as context?
2. **Context passing** — The task description is the brief. Should it also include a reference to relevant shared memory entries, or does the target agent query memory independently?
3. **Parallel delegation** — Can an agent delegate to multiple entities simultaneously (fan-out)? If so, how does it handle partial completions?
4. **Delegation depth limits** — For v1, scope rules (product-agent → dev-agent, not reverse). But the system should track depth for future cycle detection.
5. **Human response format** — When a human receives a delegated task via Slack, how do they accept/reject? Slack buttons (like existing approval flow)? Free-text reply?

### Estimated Plans

| Plan | Scope |
|---|---|
| 73-01 | Task tree structure (`parentTaskId`) + tree query tools |
| 73-02 | `task:delegate` tool + materialization layer (internal channel for agents, Slack for humans) |
| 73-03 | Negotiation handshake v1 (accept/reject with estimate) + strategy abstraction interface |
| 73-04 | Agent prompt updates — delegation judgment, handshake behavior, context passing |

## Phase 74: Completion Signaling

**Goal**: When a delegated task completes (or fails), the delegating agent is notified and can resume work — closing the collaboration loop.

**Depends on**: Phase 73 (Task Delegation — signals need tasks to signal about)

**Context**: This is the hardest part of the collaboration system. The delegator pauses via `wait_for` while the target works. When the target finishes, a signal must route back to the delegator's waiting conversation with results. Multiple completion sources exist (agent reports done, PR merged, timeout exceeded) and edge cases are numerous (partial completion, target needs clarification, delegator's conversation expired). The existing signal infrastructure (`wait_for`, `signal()`, domain-typed signals) provides the foundation, but task-lifecycle-driven signaling is new.

### Requirements

| ID | Requirement |
|---|---|
| SIG-01 | Task completion signal — when a delegated task is marked complete, the system fires a signal to the delegating conversation with task results and completion summary |
| SIG-02 | Task failure signal — when a delegated task fails, the delegating agent receives a failure signal with reason, enabling retry with a different entity or escalation |
| SIG-03 | Callback routing — delegated tasks carry `callbackConversationId` so the system knows which conversation to signal on completion |
| SIG-04 | Multiple completion sources — completion can be triggered by: agent marking task done, external event (PR merged), or timeout. All route through the same signal mechanism |
| SIG-05 | Clarification signal — target agent can signal back to the delegator requesting more information. Delegator wakes, responds, pauses again. Bidirectional conversation mediated by tasks |
| SIG-06 | Expectation-based timeout — delegator sets expectations during handshake ("need this in 10 minutes"). If the estimate passes without completion, delegator receives a timeout signal and decides: keep waiting, cancel, or escalate |
| SIG-07 | Orphan handling — if the delegating conversation is no longer active (errored, garbage-collected), completion signals are logged but not lost. Dashboard shows orphaned completions |

### Success Criteria

1. Dev-agent completes a delegated task → product-agent's waiting conversation resumes with the completion results
2. Dev-agent fails → product-agent receives a failure signal, queries directory for alternatives, and re-delegates
3. Dev-agent needs clarification → signals back to product-agent, which wakes, answers via the task, and pauses again
4. A delegated task exceeds its estimated time → delegator receives a timeout signal and decides to keep waiting or cancel
5. Completion signals for conversations that no longer exist are logged in agent_events and visible in the dashboard

### Open Design Questions

1. **Signal payload shape** — What does a completion signal carry? Just "done + summary" or structured results (artifacts produced, files changed, PR URL)?
2. **Partial completion** — Target agent made progress but can't finish. Cancel and return partial results? Or hand off to someone else with accumulated context?
3. **Cascading failures** — A → B → C delegation chain. C fails. B handles it (retries with D). Does A know about C's failure, or only B's eventual resolution? Probably only B's — each level manages its own subtree.
4. **Resume context** — When the delegator wakes up after a long wait, how much context does it need to re-establish? History manager may have compacted. Shared memory helps, but the signal payload should be self-contained enough to resume.

### Estimated Plans

| Plan | Scope |
|---|---|
| 74-01 | Callback routing infrastructure — `callbackConversationId` on tasks + signal dispatch on task state changes |
| 74-02 | Completion/failure/timeout signals + integration with existing `wait_for` and signal infrastructure |
| 74-03 | Clarification signal (bidirectional) + orphan handling |
| 74-04 | Dashboard — task tree visualization, delegation graph, signal tracing |

## Phase 75: Delegation Graph Observability

**Goal**: The dashboard provides clear visibility into multi-agent collaboration — task trees, delegation chains, signal flow, and cross-conversation tracing.

**Depends on**: Phase 74 (Completion Signaling — the full delegation lifecycle must exist before observability can visualize it)

**Context**: Single-agent debugging is reading one conversation log. Multi-agent debugging requires tracing across conversations, understanding handoffs, and finding where context was lost or decisions went wrong. This is distributed systems observability applied to agent collaboration. The task tree (from Phase 73) provides the data structure; this phase provides the visualization and tooling to make it useful.

### Requirements

| ID | Requirement |
|---|---|
| OBS-01 | Task tree view — given a root task, render the full delegation tree with subtasks, their status, assigned entity, and linked conversations |
| OBS-02 | Delegation timeline — chronological view of delegation events (delegated, accepted, completed, failed) across the task tree |
| OBS-03 | Cross-conversation tracing — click through from a subtask to its conversation, see the handoff context, and trace signals between conversations |
| OBS-04 | Signal flow visualization — show signals sent between conversations (completion, failure, clarification) with timestamps and payloads |
| OBS-05 | Health indicators — surface problematic patterns: orphaned completions, timed-out delegations, rejection chains, excessive delegation depth |

### Success Criteria

1. A root task with 3 levels of delegation renders as an interactive tree with status at each node
2. Clicking a subtask navigates to its conversation detail view
3. Signals between conversations are visible as edges in the delegation graph
4. Timed-out or failed delegations are highlighted for quick diagnosis
5. The delegation timeline shows the full chronological flow of a multi-agent work item

### Estimated Plans

| Plan | Scope |
|---|---|
| 75-01 | Task tree API endpoints + tree query optimization |
| 75-02 | Dashboard task tree view + delegation timeline component |
| 75-03 | Cross-conversation trace view + signal flow visualization |
| 75-04 | Health indicators + problematic pattern detection |

## Phase 76: QA Agent + Validation Workflow

**Goal**: A lightweight QA orchestrator agent exercises the full collaboration system end-to-end — proving directory discovery, task delegation, negotiation handshake, completion signaling, shared memory, and delegation graph observability work together in a real multi-agent workflow.

**Depends on**: Phase 75 (Delegation Graph Observability — all collaboration infrastructure must be in place)

**Context**: The collaboration infrastructure (Phases 71–75) is general-purpose, but validating it with only the existing product-agent → dev-agent pipeline tests a two-node linear flow. The interesting failure modes — fan-out delegation, feedback loops, competing subtasks, delegation depth, shared memory across unrelated conversations — only emerge with three or more participants. The QA agent is not a production-grade test system — it's a validation vehicle that creates a triangular workflow exercising every collaboration primitive.

### The Validation Workflow

```
Product-agent ──delegates──→ Dev-agent ──delegates──→ QA-agent
                                 ↑                        │
                                 └──delegates fix back────┘
```

1. Product-agent receives a feature request, delegates implementation to dev-agent (directory query, handshake, materialization)
2. Dev-agent implements and delegates verification to QA-agent (second-level delegation, task tree grows)
3. QA-agent runs tests, checks PR against requirements
4. **Pass**: QA-agent signals completion → dev-agent resumes → signals completion → product-agent resumes
5. **Fail**: QA-agent delegates a fix back to dev-agent (feedback loop, third-level delegation) → dev-agent fixes → re-delegates to QA → pass → completion chain unwinds

This single workflow exercises: directory queries (3 lookups), delegation handshake (3+ negotiations), materialization (internal), completion signaling (success + failure + re-delegation), clarification signals (QA asks dev for context), shared memory (QA stores test results, dev queries known failures), and a task tree 3 levels deep.

### Requirements

| ID | Requirement |
|---|---|
| QA-01 | QA agent definition — orchestrator-level agent with `capabilities` declared in definition.yaml, registered in entity directory |
| QA-02 | Core tools — run test suite, check PR diff, review changes against requirements (from delegated task context or shared memory) |
| QA-03 | Collaboration tools — `directory:find`, `directory:get`, `task:delegate`, `knowledge:store`, `knowledge:query`, plus standard communication tools (reply/ask/notify) |
| QA-04 | Delegation acceptance — QA agent participates in negotiation handshake (accepts verification tasks with time estimates, rejects tasks outside its capability) |
| QA-05 | Feedback loop — when tests fail, QA agent delegates a fix task back to dev-agent with failure details, test output, and relevant knowledge entries. Waits for completion signal |
| QA-06 | Knowledge contribution — QA agent stores test results, discovered regressions, and known-failure patterns in shared memory for future QA runs and dev-agent reference |
| QA-07 | Validation test suite — integration tests that run the full triangular workflow end-to-end, asserting: task tree structure, signal delivery, knowledge entries, delegation graph |

### Success Criteria

1. The full product → dev → QA → (fix) → QA → complete workflow runs end-to-end with correct task tree structure
2. QA agent appears in directory and is discoverable by dev-agent via capability query ("verify code changes and run tests")
3. QA agent negotiates handshake — accepts with estimate when given a PR to review, rejects when given tasks outside its capability
4. Failed tests trigger a delegation back to dev-agent — the feedback loop completes and the task tree shows the re-delegation
5. Knowledge entries from QA runs are queryable by subsequent agents ("what test failures have we seen in the auth module?")
6. The delegation graph in the dashboard renders the full 3-level tree with all signals visible

### Open Design Questions

1. **Test execution environment** — Does QA agent run tests in the same dev container as dev-agent, or does it need its own sandbox? Shared container is simpler for v1, separate container is more realistic.
2. **Requirements source** — QA agent checks "against requirements." Where do these come from? The delegated task description? Shared memory? The original Linear ticket? All three?
3. **Retry limits** — How many fail → fix → retest cycles before QA agent escalates to a human? Prompt-guided judgment or hard limit?
4. **Scope for v2.8** — This agent is a validation vehicle. What does a production QA agent look like? Continuous test monitoring, regression detection, test coverage analysis? Document the expansion path.

### Estimated Plans

| Plan | Scope |
|---|---|
| 76-01 | QA agent definition (definition.yaml + prompt.md + capabilities) + directory seeding |
| 76-02 | Core QA tools (run tests, check PR, review against requirements) |
| 76-03 | Collaboration wiring — delegation acceptance, feedback loop, knowledge contribution |
| 76-04 | End-to-end validation test suite — triangular workflow integration tests |

## Design Constraints

These apply across all phases:

**Graceful degradation** — Collaboration enhances, isolation still works. If the directory is unreachable, agents continue solo. If completion signaling fails, delegators eventually timeout rather than hang forever. If the knowledge store is down, agents work without shared context (higher token cost, not a hard failure). Each collaboration primitive is best-effort — agents should catalog failures in knowledge for future reference and fail cleanly when collaboration is truly impossible.
