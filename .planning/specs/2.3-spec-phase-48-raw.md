# Phase 48: Sub-Agent Spawning (spawn_agent)

**Goal**: Wire the `spawn_agent` coordination tool to the ConversationExecutor so the dev-agent can delegate work to sub-agents (researcher, coder, tester) that run as child conversations with shared token budgets and sandbox access.

## Problem

The dev-agent is designed as an orchestrator that delegates implementation work to focused sub-agents. Its prompt explicitly states: "You do NOT have write_file or run_command directly. Delegate code changes to the coder sub-agent." However, `spawn_agent` is a placeholder that always returns an error:

```typescript
// tool-factories.ts:237-271
async execute(): Promise<{ content: string; isError: boolean }> {
  return {
    content: "spawn_agent via ToolRegistry is not yet wired to the executor.",
    isError: true,
  };
},
```

This was intentionally deferred during Phase 40 (ConversationExecutor). Without it, the dev-agent can see the codebase but cannot make changes, create branches, or run tests. During E2E testing, the agent correctly identified a one-line fix in `src/pages/Home.tsx` but had to escalate to a human because it couldn't execute the change.

## What Already Exists

The infrastructure for sub-agent spawning is largely built. This phase wires the pieces together.

### Database Schema (Phase 37)
- `conversations.parent_conversation_id` column exists with index (`idx_conversations_parent`)
- `agent_events.parent_instance_id` column exists for hierarchy tracking
- Status lifecycle: `queued` → `running` → `completed`/`failed`/`waiting`
- Deterministic IDs: `{agentDefinitionId}-{correlationKey}`

### Agent Registry (Phase 38)
- `AgentRegistry.get(id)` loads definition from `definitions/{id}/definition.yaml` + `prompt.md`
- Sub-agent definitions exist and are validated:
  - `researcher`: read_file, search_codebase, list_directory, run_command (Haiku, 30 iterations)
  - `coder`: read_file, write_file, search_codebase, run_command (Haiku, 40 iterations)
  - `tester`: read_file, search_codebase, run_command (Haiku, 20 iterations)
- `definition.subAgents` maps role names to agent definition IDs (e.g., `coder: coder`)

### Token Budget (Phase 28)
- `TokenBudget` is a mutable object with `remaining`, `deduct()`, `isExhausted()`, `isReserveOnly()`
- Passed by reference — all deductions visible to parent immediately
- Sub-agent YAML `tokenBudget` is standalone; executor should override with shared budget
- Reserve mode (5000 tokens) allows graceful wrap-up

### Agent Loop (Phase 28)
- `runAgentLoop(options)` returns `AgentLoopResult` with `messages`, `status`, `tokenCount`, `output`
- Handles rate limiting (429 retries), token budget checks, abort signals
- Tool execution is synchronous within the loop — tools run one at a time

### ConversationExecutor (Phase 40)
- `start()` creates conversation rows with `parent_conversation_id` support
- Worker loop claims with `FOR UPDATE SKIP LOCKED`
- Heartbeats detect stale claims
- Ownership verified after loop before persisting results

### Sandbox Wiring (Phase 47)
- `setupSandbox()` spawns container and clones repo keyed by `taskId = conv.id`
- Sub-agents need the SAME container as the parent (shared filesystem)
- `ToolContext.containerManager` + `ToolContext.taskId` wire sandbox to codebase tools

### wait_for Pattern (Phase 40)
- Mutable state flag pattern: tool mutates state, executor checks after loop
- Tool returns confirmation so LLM sees success and generates clean end_turn
- Reference implementation for how spawn_agent should integrate

## Requirements

### SPAWN-01: Tool Implementation
The `spawn_agent` tool must accept `agentType` (researcher/coder/tester), `task` (string), and optional `context` (string). It must resolve the agent type against the parent's `subAgents` mapping in the definition YAML, run the sub-agent's loop to completion, and return the sub-agent's output to the parent agent.

### SPAWN-02: Shared Token Budget
Sub-agents must share the parent's `TokenBudget` by reference. All token deductions in sub-agents are immediately visible to the parent. If the budget is exhausted during a sub-agent run, the sub-agent's loop exits gracefully via reserve mode, and the parent sees the depletion.

### SPAWN-03: Shared Sandbox
Sub-agents must use the same dev container as the parent. The parent's `ToolContext.containerManager` and `ToolContext.taskId` must be passed to the sub-agent's tool resolution. The sub-agent operates on the same filesystem (repo already cloned by parent's `setupSandbox`).

### SPAWN-04: Sequential Execution
Sub-agents run synchronously within the parent's agent loop. When `spawn_agent` is called, the parent's loop blocks until the sub-agent completes. No parallel sub-agent execution. (This aligns with the existing "out of scope" decision in REQUIREMENTS.md.)

### SPAWN-05: Result Passing
The sub-agent's output (final text response) must be returned to the parent as the tool result. The parent agent sees the sub-agent's work product and can act on it (e.g., commit the coder's changes, analyze the tester's results).

### SPAWN-06: Error Handling
If a sub-agent fails (error, max iterations, token exhaustion), the spawn_agent tool must return an error result with diagnostic information. The parent agent decides how to proceed (retry with different instructions, try a different approach, or escalate).

### SPAWN-07: Event Tracking
Sub-agent execution must be tracked in the event log with `parent_instance_id` linking child events to the parent's instance. This enables observability of the full execution hierarchy.

### SPAWN-08: Definition Validation
If the parent agent's definition specifies a `subAgents` mapping, all referenced agent IDs must exist in the registry. Fail fast at conversation start (not at spawn time) if a referenced sub-agent definition is missing.

## Design

### Execution Model: In-Process (Not via ConversationExecutor)

The sub-agent runs as a nested `runAgentLoop()` call **within the parent's worker loop execution**, not as a separate conversation claimed by the worker pool.

**Rationale:**
- Sub-agents are synchronous from the parent's perspective — the parent blocks until the sub-agent finishes
- Creating a separate conversation would require the parent to `wait_for` completion and poll/signal — adding unnecessary complexity
- The worker loop already has the sandbox, token budget, and tool context — passing these to a nested loop is straightforward
- Sub-agents don't need persistence (they don't pause, resume, or receive signals) — they run to completion
- This matches the original v2.2 design (`createSpawnAgentTool` called `runAgentLoop` directly)

**Tradeoff:** Sub-agent messages are NOT independently persisted as separate conversations. The sub-agent's execution is tracked via events (SPAWN-07) and its output is captured in the parent's tool result. If independent persistence of sub-agent conversations is needed later, the tool can be refactored to use `ConversationExecutor.start()` + polling.

### Tool Factory Pattern

Replace the placeholder in `tool-factories.ts` with a real factory that receives dependencies via `ToolContext`. The factory needs:

1. **AgentRegistry** — to load sub-agent definitions (prompt, model, tools, limits)
2. **ToolRegistry** — to resolve the sub-agent's tool set
3. **TokenBudget** — shared mutable budget from the parent
4. **ToolContext** — container manager, task ID, logger (for sandbox sharing)
5. **EventLog** — to record sub-agent events with parent_instance_id
6. **Parent definition** — to look up the `subAgents` role-to-ID mapping

Since `ToolContext` currently only carries `agentId`, `correlationId`, `logger`, `containerManager`, and `taskId`, additional dependencies must be provided. Two approaches:

**Option A: Extend ToolContext** — Add optional fields for agentRegistry, toolRegistry, tokenBudget, eventLog, parentDefinition. The worker loop populates them when the agent has `coordination:spawn_agent` in its tool list.

**Option B: Closure capture in factory registration** — The tool factory in `tool-factories.ts` captures the registries and budget at registration time. The `ToolContext` is used only for per-invocation context (container, logger).

**Recommended: Option B (closure capture).** Keeps ToolContext focused. The `registerSpawnAgent()` function accepts deps at setup time and returns a factory. The worker loop calls this registration with the conversation-specific deps (budget, event log) before resolving tools.

### Token Budget Override

The sub-agent definition YAML specifies `tokenBudget: 100000` (standalone value). When spawned by a parent, this is ignored — the parent's shared `TokenBudget` object is passed directly. The sub-agent's `maxIterations` from the YAML IS respected (prevents runaway sub-agents).

### Sandbox Sharing

The sub-agent's `ToolContext` uses the SAME `containerManager` and `taskId` as the parent. This means codebase tools in the sub-agent operate on the same container and filesystem. No additional container spawn needed.

### History Management

Sub-agents get their own fresh message history (they start with a system prompt + task brief as the first user message). The parent's history config does NOT apply. The sub-agent's history config from its own YAML definition IS applied if the conversation grows long enough (unlikely for focused tasks).

### Abort Signal Propagation

The parent's abort signal (from graceful shutdown) must be passed to the sub-agent loop. If the service is shutting down, both parent and child should exit cleanly.

## Implementation Sketch

### spawn-agent.ts

```typescript
interface SpawnAgentDeps {
  agentRegistry: AgentRegistry;
  toolRegistry: ToolRegistry;
  tokenBudget: TokenBudget;
  eventLog: EventLog;
  parentDefinition: AgentDefinition;
  parentInstanceId: string;
  abortSignal?: AbortSignal;
}

function createSpawnAgentTool(deps: SpawnAgentDeps, ctx: ToolContext): ToolDefinition {
  return {
    name: "spawn_agent",
    description: "...",
    inputSchema: z.object({
      agentType: z.enum(["researcher", "coder", "tester"]),
      task: z.string(),
      context: z.string().optional(),
    }),
    async execute(input): Promise<{ content: string; isError: boolean }> {
      // 1. Resolve agentType → definition ID via parentDefinition.subAgents
      const agentId = deps.parentDefinition.subAgents?.[input.agentType];
      if (!agentId) return { content: `Unknown agent type: ${input.agentType}`, isError: true };

      // 2. Load sub-agent definition from registry
      const definition = deps.agentRegistry.get(agentId);
      if (!definition) return { content: `Agent definition not found: ${agentId}`, isError: true };

      // 3. Build sub-agent ToolContext (shared sandbox)
      const subCtx: ToolContext = {
        agentId: definition.id,
        correlationId: ctx.correlationId,
        logger: ctx.logger.child({ subAgent: definition.id }),
        containerManager: ctx.containerManager,
        taskId: ctx.taskId,
      };

      // 4. Resolve sub-agent tools
      const tools = deps.toolRegistry.resolve(definition.tools, subCtx);

      // 5. Build initial message
      const initialMessage = input.context
        ? `${input.context}\n\n${input.task}`
        : input.task;

      // 6. Record sub-agent start event
      const subInstanceId = `inst_${nanoid(12)}`;
      deps.eventLog.append({ type: "agent.started", parentInstanceId: deps.parentInstanceId, ... });

      // 7. Run sub-agent loop
      const result = await runAgentLoop({
        model: definition.model,
        systemPrompt: definition.systemPrompt,
        tools,
        initialMessage,
        maxIterations: definition.maxIterations,
        tokenBudget: deps.tokenBudget, // SHARED reference
        abortSignal: deps.abortSignal,
      });

      // 8. Record sub-agent completion event
      deps.eventLog.append({ type: "agent.completed", ... });

      // 9. Return result to parent
      if (result.status === "error" || result.status === "aborted") {
        return { content: `Sub-agent ${input.agentType} failed: ${result.output}`, isError: true };
      }

      return { content: result.output, isError: false };
    },
  };
}
```

## Design Decisions

| Decision | Choice | Reasoning |
|----------|--------|-----------|
| Execution model | In-process nested loop | Synchronous, no persistence overhead, matches v2.2 design intent |
| Persistence | Events only (no child conversation rows) | Sub-agents are ephemeral; event hierarchy sufficient for observability |
| Token budget | Shared by reference | Parent's budget object passed directly; all deductions visible |
| Sandbox | Shared container + taskId | Same filesystem, no extra container spawn |
| History | Fresh per sub-agent | Sub-agents start clean; parent history is irrelevant to focused tasks |
| Agent types | Restricted to definition.subAgents | Parent declares which roles it can spawn; prevents arbitrary agent spawning |
| Parallel execution | Not supported | Sequential only; matches existing out-of-scope decision |

## Open Questions

1. **Should sub-agent messages be persisted?** Current design: no (events only). If debugging requires message-level inspection, consider writing sub-agent messages to a separate field on the parent conversation or to a child conversation row.

2. **Should the tool registry support conversation-scoped overrides?** The spawn_agent factory needs per-conversation deps (budget, event log instance). This may require a small extension to ToolRegistry's resolve pattern.

3. **maxIterations for sub-agents**: Use the value from the sub-agent's YAML definition, or allow the parent to specify via the tool input? Current design: YAML value. The parent controls scope via the task brief, not iteration limits.
