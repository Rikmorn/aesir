# v2.3 Spec: Unified Agent Framework

## Goal

Replace per-agent services, Temporal workflow state machines, and fragmented persistence with a unified agent framework where agents are declarative config, conversations are the execution primitive, and a single event log provides ground truth. Deliver a system where adding a new agent type requires zero infrastructure changes — just a new agent definition.

## Why This Matters

v2.2 proved the agent-first principle: LLMs make control flow decisions, not hardcoded graphs. But v2.2 left the orchestration layer unchanged — Temporal workflows still encode phase machines (`pre_approval → awaiting_approval → post_approval → ...`) that fight the agent for control. Every time the agent does something the workflow didn't anticipate (autonomous completion, skipped approval), the workflow breaks and requires patching.

v2.3 finishes the architectural shift that v2.2 started. The agent loop becomes the *only* state machine. Infrastructure handles durability, signals, and timeouts — nothing else.

## Problem Statement

### Three Stores, Three Problems

v2.2 shipped with three disconnected persistence mechanisms:

1. **`execution_traces`** — Observability log. Buffered in memory, flushed after each Temporal activity. Records tool calls but **not tool results** (noted in `trace-recorder.ts` line 15: "tool_result traces are NOT recorded in this version"). Purpose: post-hoc debugging.

2. **`tasks`** — Structured state. PR number, branch name, approval status. Written **imperatively by Temporal activities** after the agent loop completes. The activity scans the agent's trace to find PR info (`parsePrInfoFromTrace(result)`) then writes it to the task store. If the agent creates a PR in an unexpected phase, the parsing misses it.

3. **`context_snapshots`** — LLM-generated summaries written at activity boundaries. Exist solely because Temporal splits execution into separate activities that lose conversation context. The agent that resumes after approval is a different agent with a summary of what the previous one did — lossy by definition.

### Brittle Workflow Logic

The Temporal workflow encodes a decision tree that the agent should own:

```typescript
// orchestrator-workflow.ts — workflow decides, not agent
if (preResult.humanInputRequest === null) {
  // Agent completed autonomously — skip approval
} else {
  // Wait for approval signal
  await wf.condition(() => approval !== null, timeout);
}
```

This is v2.1's `routeByPhase()` switch statement wearing a Temporal costume. Each new agent behavior requires a matching workflow branch. The v2.2 patch for autonomous completion, the v2.3 notes about tool side-effects — these are symptoms of a workflow that fights the agent for control.

### Per-Agent Services

Dev agent runs on port 3004, product agent on port 3005. Separate `main.ts`, separate `worker.ts`, separate Dockerfile, separate Temporal task queue. Adding a new agent type requires duplicating ~400 lines of boilerplate (HTTP server setup, Temporal worker bootstrap, graceful shutdown, health checks).

The two agents share ~90% of their infrastructure. The differences are: system prompt, tool selection, token budget, and max iterations. These are configuration, not separate services.

### Context Loss at Boundaries

Each Temporal activity invocation starts a fresh `runAgentLoop()` with a new conversation. The agent that researched the codebase and planned the implementation is gone — replaced by a new agent that reads a summary. Critical details (specific file paths, error messages, architectural decisions) are the first casualties of summarization.

## Architecture Overview

```
External Events (Slack, Linear, GitHub webhooks)
        |
        v
Single Agent Service (HTTP)
        |
        v
Event Router (resolves event → conversation)
        |
        +--> New event: executor.start(agentDefinitionId, message)
        |
        +--> Signal for paused conversation: executor.signal(conversationId, signal)
        |
        v
Conversation Executor (abstraction over durability + signal routing)
        |
        +--> Loads AgentDefinition from registry
        +--> Resolves tools from ToolRegistry
        +--> Manages conversation persistence
        +--> Runs agent loop (pause/resume with full history)
        |
        v
Agent Loop (runAgentLoop — unchanged from v2.2)
        |
        +--> Tools execute → EventLog records events in real-time
        +--> Agent reasons → decides next action
        +--> Agent calls wait_for → conversation pauses
        +--> Agent stops calling tools → conversation completes
        |
        v
Event Log (unified ground truth, abstracts backing store)
        |
        +--> Session Projection (fast reads: status, artifacts)
        +--> Observability (full trace with tool results)
        +--> History for resume (conversation messages)
```

## What Changes vs. v2.2

| Component | v2.2 (Current) | v2.3 (Target) |
|-----------|----------------|---------------|
| Agent definition | Code (orchestrator functions, toolkit factories, system prompts as constants) | Declarative config (data — persistable in DB, files, or API) |
| Deployment | Separate services per agent type (dev-agent:3004, product-agent:3005) | Single agent service with agent registry |
| Orchestration | Temporal workflows with phase machines per agent type | ConversationExecutor — generic pause/resume for all agents |
| Persistence | 3 stores (execution_traces, tasks, context_snapshots) | Unified event log + session projection |
| Context across pauses | LLM-generated summaries at activity boundaries | Full conversation history (compacted, not summarized from scratch) |
| Adding new agent type | New service, worker, main.ts, Dockerfile, Temporal workflow, task queue | New AgentDefinition in registry |
| Tool result tracking | Not recorded (noted as gap in trace-recorder.ts) | Real-time events with tool results and optional artifact extraction |
| State inference | Parse agent output for sentinels, scan trace for PR info | Event log records ground truth as tools execute |

## What Stays the Same

- **`runAgentLoop()`** — The core agent loop runtime is unchanged. Same Anthropic SDK tool-use loop, same `AgentLoopOptions`/`AgentLoopResult` interface, same callbacks.
- **MCP layer** — All integration tools (Linear, GitHub, Slack) via MCP HTTP protocol. Same endpoints, same headers, same rate limiting.
- **Integration packages** — `@aesir/integration-linear`, `@aesir/integration-github`, `@aesir/integration-slack` unchanged.
- **Platform layer** — `@aesir/platform` (config, logging, db, sandbox).
- **Dev containers** — `DevContainerManager`, `DevContainerGit`, `DevContainerCleanup` unchanged.
- **Tool definitions** — Same `ToolDefinition` interface with Zod schemas. Tool implementations unchanged.

## Detailed Requirements

### 1. Agent Definition

The foundational data model. An agent is defined by declarative configuration, not code. Agent definitions are data — persistable in a database, file system, or API — enabling runtime creation, external management, and version-controlled evolution.

**Schema:**

```typescript
interface AgentDefinition {
  // --- Identity ---
  id: string;                    // "dev-agent", "product-agent", "researcher"
  name: string;                  // "Development Agent"
  description: string;           // Used for routing decisions + documentation
  version: string;               // Explicit commit — e.g., "1.0.0" or "3"

  // --- Behavior ---
  systemPrompt: string;          // The primary control surface. Static string.
  model: string;                 // "claude-sonnet-4-20250514"
  temperature?: number;          // Default: 0

  // --- Capabilities ---
  tools: string[];               // References resolved at runtime by ToolRegistry
                                 // e.g., ["linear:get_issue", "github:create_pr"]

  // --- Delegation ---
  subAgents?: Record<string, string>;  // role → agentDefinitionId
                                       // e.g., { "researcher": "researcher-v1" }

  // --- Guardrails ---
  maxIterations: number;
  tokenBudget: number;

  // --- Conversation History ---
  history: {
    pruneThreshold: number;        // Token count to trigger tool output pruning
    protectedMessages: number;     // Recent messages to never touch
    summaryThreshold: number;      // Token count to trigger structured summarization
    summaryModel: string;          // Model for summarization
  };

  // --- Event Routing ---
  triggers?: Array<{
    event: string;                 // Event type that starts this agent
  }>;
}
```

**Invocation is separate from definition:**

```typescript
interface AgentInvocation {
  agentDefinitionId: string;     // Which agent to run
  message: string;               // What to tell it (caller constructs this)
  context?: string;              // Metadata (slack context, linear team ID, etc.)
  conversationId?: string;       // For multi-turn history lookup
}
```

**Design decisions:**

- **Tools are references, not implementations.** The definition says `"linear:get_issue"` — a string. The `ToolRegistry` resolves this to the actual `ToolDefinition` with its `execute` function at runtime. The current code already does name-based filtering (`["linear_get_issue", ...].includes(t.name)`); this formalizes the pattern.

- **Tool references are individual, not wildcards.** `"linear:get_issue"` not `"linear:*"`. Principle of least privilege — each tool is explicitly granted. Easier to audit, easier to validate against real-world usage.

- **The caller builds the initial message, not the definition.** The agent definition describes personality and capabilities. The invocation provides the task. Same pattern as Claude Code's Task tool: the agent definition is the Markdown file, the `prompt` parameter is the task. No template engines, no conditional logic in data.

- **Sub-agents are references to other agent definitions.** Instead of embedding `{ systemPrompt, tools, maxIterations, model }` inside the parent's code, sub-agents reference definitions by ID. The researcher can be reused across parent agents and updated independently.

- **Version is an explicit commit.** Allows draft/work-in-progress changes that don't go live until intentionally versioned. Running agents stay pinned to the version they started with. Rollback is deliberate — deploy version N-1, not "undo the last 3 field edits."

- **No runtime dependencies in the definition.** The definition doesn't mention `containerManager`, `db`, or `logger`. The framework infers runtime needs from tool references — if you reference `codebase:read_file`, it knows a container is needed. Keeps definitions pure data.

**Sub-agent model:**

Sub-agents are normal agent definitions. Same schema, same runtime, same `runAgentLoop()`. Spawning is controlled by:

1. Does the agent have `coordination:spawn_agent` in its `tools` list? If not, it can't spawn.
2. What does its `subAgents` map contain? This scopes which definitions it can invoke.

Recursive spawning is supported. A researcher could spawn a coder to build a one-off analysis tool. The framework enforces a configurable max depth as a guardrail, and the shared token budget from the root agent provides a natural economic constraint.

```
Orchestrator (depth 0, budget: 500k)
  └── Researcher (depth 1, budget: shared)
        └── Coder (depth 2, budget: shared)
              └── (depth 3 — framework blocks spawn if max depth reached)
```

**What maps from v2.2 to v2.3:**

| v2.2 | v2.3 AgentDefinition |
|------|---------------------|
| `ORCHESTRATOR_SYSTEM_PROMPT` constant | `systemPrompt` field |
| `createOrchestratorToolkit()` factory | `tools: ["linear:get_issue", "github:create_pr", ...]` |
| `maxIterations ?? 100` in orchestrator.ts | `maxIterations: 100` |
| `maxTokenBudget ?? 500_000` in orchestrator.ts | `tokenBudget: 500000` |
| `subAgentConfigs` in toolkits.ts | `subAgents: { researcher: "researcher-v1", ... }` |
| `"claude-haiku-4-5-20251001"` in sub-agent config | `model` field on researcher definition |

### 2. Event Log

The unified ground truth, replacing `execution_traces`, `tasks`, and `context_snapshots` with a single event stream. Events are written when things happen — not reconstructed afterward.

**Event schema:**

```typescript
interface AgentEvent {
  id: string;
  conversationId: string;          // Groups all events for one agent session
  agentDefinitionId: string;
  agentDefinitionVersion: string;
  agentInstanceId: string;         // Unique per invocation (sub-agents get their own)
  parentInstanceId: string | null; // For sub-agent correlation
  sequence: number;                // Monotonic within conversation

  type: AgentEventType;
  payload: Record<string, unknown>; // Event-specific data

  timestamp: string;
  tokenCount: { input: number; output: number } | null;
  durationMs: number | null;
}

type AgentEventType =
  // Tool lifecycle
  | "tool.called"
  | "tool.succeeded"
  | "tool.failed"

  // LLM interaction
  | "llm.response"

  // Agent lifecycle
  | "agent.started"
  | "agent.completed"
  | "agent.paused"
  | "agent.resumed"

  // Sub-agent lifecycle
  | "agent.spawned"
  | "agent.child_completed"

  // External signals
  | "signal.received";
```

**EventLog interface (abstracts backing store):**

```typescript
interface EventLog {
  /** Append an event. Fire-and-forget from caller's perspective. */
  append(event: AgentEvent): void;

  /** Query events for a conversation */
  query(conversationId: string, opts?: EventQueryOpts): Promise<AgentEvent[]>;

  /** Subscribe to events in real-time (for projections, external consumers) */
  subscribe(filter: EventFilter, handler: (event: AgentEvent) => void): Unsubscribe;

  /** Lifecycle */
  flush(): Promise<void>;
  close(): Promise<void>;
}

interface EventQueryOpts {
  afterSequence?: number;
  types?: AgentEventType[];
  agentInstanceId?: string;
  limit?: number;
}

interface EventFilter {
  conversationId?: string;
  types?: AgentEventType[];
}
```

**Design decisions:**

- **`append` is void, not async.** The caller never waits for persistence. The implementation handles buffering, batching, and flushing internally. For Postgres: buffer N events, batch-insert every K milliseconds. For Kafka: produce to topic asynchronously. The agent loop is never blocked on event I/O.

- **`subscribe` enables reactive projections.** The session projection subscribes to events and updates state. Additional projections (metrics, billing, external webhooks) can subscribe without modifying the event log implementation.

- **`flush` is explicit.** For graceful shutdown or when persistence must be guaranteed before proceeding. The framework calls this at lifecycle points; agents never need to.

- **Postgres implementation for local dev.** Batch inserts with configurable buffer size and flush interval. `LISTEN/NOTIFY` or polling for subscriptions. Swap to Kafka/SQS when production scale demands it — the interface is unchanged.

**Artifact extraction from tool results:**

Tools can declare significant output via an extended `ToolResult`:

```typescript
interface ToolResult {
  content: string;           // Text fed back to the LLM (unchanged)
  isError?: boolean;
  data?: unknown;            // Structured result — tool decides shape and content
}
```

The tool registry maps tools to artifact keys:

```typescript
// Tool registry entry
artifact?: {
  key: string;               // "github:pr" — storage key in session projection
};
```

When a `tool.succeeded` event is written for a tool that has artifact config AND the result includes `data`, the data is stored in the session projection under the configured key. No field extraction logic, no JSON path parsing, no assumptions about result format. The tool knows its own output.

**Session projection (fast reads):**

```typescript
interface AgentSession {
  conversationId: string;
  agentDefinitionId: string;
  status: "running" | "paused" | "completed" | "failed";

  lastEventType: AgentEventType;
  lastEventAt: string;

  // Materialized from tool.succeeded events with artifact config
  artifacts: Record<string, unknown>;
  // e.g., { "github:pr": { number: 47, url: "..." }, "github:branch": "feature/aes-42" }
}
```

Updated reactively by subscribing to the event log. Replaces the `tasks` table's structured fields (`pr_number`, `branch_name`, `approval_status`).

**What this replaces:**

| v2.2 | v2.3 Event Log |
|------|---------------|
| `execution_traces` (buffered, flushed after activity, no tool results) | `agent_events` (real-time, includes tool.succeeded with results) |
| `tasks` (imperatively updated by Temporal activities) | `agent_sessions` projection (reactively updated from events) |
| `context_snapshots` (LLM summaries at activity boundaries) | Conversation history (framework-managed, topic 5) |
| `parsePrInfoFromTrace(result)` | Exists in event log — `tool.succeeded` for `github:create_pull_request` |
| Sentinel parsing from agent output | Agent calls `wait_for` tool — explicit, not inferred |

### 3. Execution Model

The core change: **the agent loop is the state machine**. No workflow encodes phase transitions. The agent runs, pauses when it needs to wait for something external, and resumes with its full conversation history when the signal arrives.

**The conversation primitive:**

```typescript
interface Conversation {
  id: string;                          // Stable across pauses/resumes
  agentDefinitionId: string;
  agentDefinitionVersion: string;

  // The full message history (Anthropic API format)
  messages: Message[];                 // user/assistant turns with tool calls and results

  // Current state
  status: "running" | "paused" | "completed" | "failed";

  // What we're waiting for (when paused)
  pendingWait?: {
    type: string;                      // "approval", "user_reply", "pr_review", etc.
    metadata: Record<string, unknown>; // Channel, timeout config, etc.
  };

  // Signals that arrived before/during execution
  queuedSignals: Signal[];

  createdAt: string;
  updatedAt: string;
}
```

The conversation's `messages` array is the Anthropic API message format — `user` and `assistant` turns, including `tool_use` and `tool_result` blocks. This is the agent's complete memory.

**ConversationExecutor interface:**

```typescript
interface ConversationExecutor {
  /** Start a new agent conversation */
  start(params: StartConversationParams): Promise<string>;

  /** Resume a paused conversation with a signal */
  signal(conversationId: string, signal: Signal): Promise<void>;

  /** Query conversation state */
  get(conversationId: string): Promise<Conversation | null>;

  /** Cancel a running or paused conversation */
  cancel(conversationId: string, reason: string): Promise<void>;

  /** List conversations (filtered) */
  list(filter: ConversationFilter): Promise<ConversationSummary[]>;

  /** Lifecycle */
  close(): Promise<void>;
}

interface StartConversationParams {
  agentDefinitionId: string;
  message: string;
  context?: string;
  conversationId?: string;         // Caller-controlled deterministic ID
  parentConversationId?: string;
  timeouts?: TimeoutConfig;
}

interface Signal {
  type: string;                  // "approval", "user_reply", "pr_merged", etc.
  data: Record<string, unknown>;
  source: string;                // "slack:webhook", "github:webhook", "internal:scheduler"
}

interface TimeoutConfig {
  waitTimeout?: string;          // Max pause duration before auto-wake ("72h", "7d")
  totalTimeout?: string;         // Max conversation duration before forced termination ("14d")
}

interface ConversationFilter {
  status?: Conversation["status"];
  agentDefinitionId?: string;
  pausedWaitingFor?: string;
}
```

**Design decisions:**

- **`start` is async and returns immediately.** It enqueues the agent loop to run — doesn't block until completion. The caller (webhook handler) gets back a `conversationId` and returns 200 to the webhook source.

- **`start` with a deterministic `conversationId` is idempotent.** If a conversation with that ID already exists and is running/paused, return the existing ID. No error, no duplicate. Replaces Temporal's `WorkflowExecutionAlreadyStartedError` handling.

- **`signal` is idempotent.** Duplicate signals (webhook retries) are no-ops. Deduplication by signal source + data.

- **Sub-agents don't go through the executor.** When `spawn_agent` fires, it runs the sub-agent inline (same process, separate conversation). The executor only manages top-level conversations — the ones that need durability across pauses.

- **`cancel` handles recovery.** When things go wrong, cancel and start fresh. Clean slate, no corrupted state. The event log preserves the full history of the cancelled conversation for debugging.

**How pause/resume works:**

```
Agent loop running:
  → Agent calls wait_for({ type: "approval", timeout: "72h" })
  → Framework records tool result in conversation history
  → Framework writes agent.paused event to event log
  → Framework persists conversation to storage
  → Framework sets up signal listener + timeout
  → Agent loop completes normally (not suspended in-thread)

Time passes (hours, days)...

External signal arrives (Slack button click):
  → Framework writes signal.received event
  → Framework loads conversation from storage
  → Framework appends signal as new user message to history
  → Framework applies history compaction if needed
  → Framework writes agent.resumed event
  → runAgentLoop() called with full history — agent sees everything
      it did before the pause, plus the signal
```

The agent never loses context. No summaries, no context snapshots, no re-reading the issue from scratch.

**Full flow with all components connected:**

```
1. GitHub webhook arrives at HTTP server
     |
2. Event router resolves: "this is a PR review for conversation conv_abc"
     |
3. executor.signal("conv_abc", { type: "pr_review", data: { ... } })
     |
4. Executor loads conversation conv_abc from storage
   - status: "paused", pendingWait: { type: "pr_review" }
     |
5. Executor appends signal as user message to conversation.messages
     |
6. EventLog.append({ type: "signal.received", ... })
   EventLog.append({ type: "agent.resumed", ... })
     |
7. Executor resolves AgentDefinition from registry (by id + version)
     |
8. Executor resolves tools from ToolRegistry (by definition.tools)
     |
9. Framework applies history compaction if needed (definition.history config)
     |
10. runAgentLoop({
      systemPrompt: definition.systemPrompt,
      tools: resolvedTools,
      messages: conversation.messages,
    })
     |
11. Agent runs:
    - Sees its full prior conversation + the new signal
    - Calls tools -> EventLog records tool.called/tool.succeeded
    - Reasons, acts, decides next step
    - Either completes OR calls wait_for to pause again
     |
12. If completed: agent.completed event, conversation status: "completed"
    If paused: agent.paused event, conversation status: "paused", timeout set
```

**What replaces Temporal:**

The `ConversationExecutor` interface abstracts the infrastructure. It needs to handle:

| Concern | What It Does |
|---------|-------------|
| Durable persistence | Save conversation to storage, survive restarts |
| Signal routing | Route incoming webhooks/events to the right paused conversation |
| Timeout enforcement | Wake up a paused conversation after N hours if no signal |
| At-least-once execution | If agent loop crashes mid-run, detect and restart |
| Concurrency control | Only one agent loop runs per conversation at a time |

The backing implementation is a deployment decision:

- **Local dev:** Postgres-backed (conversations in a table, signal matching via queries, pg_cron or polling for timeouts)
- **AWS production:** SQS for job queue, EventBridge for signal routing, DynamoDB/RDS for conversation persistence, EventBridge Scheduler for timeouts

The interface is the same regardless of backing store.

**Framework-level config:**

```typescript
interface AgentFrameworkConfig {
  maxSpawnDepth: number;        // Default: 3 — max recursive sub-agent depth
  // Additional runtime guardrails added as needed
}
```

### 4. History Management

Full conversation history is the agent's memory. But conversations with tool calls and results can grow beyond the context window. History management is a **framework concern** — every agent gets it, configured via the `history` field on `AgentDefinition`.

**Three-phase strategy, applied in order (each phase is cheaper than the next):**

#### Phase 1: Tool Output Pruning (default, always active)

Tool outputs are the biggest context hog. A single `read_file` or `search_codebase` result can be thousands of tokens, while the agent's reasoning about it is a few sentences.

When conversation exceeds `pruneThreshold`:
- Protect the last `protectedMessages` messages (verbatim, untouched)
- For older messages: keep assistant reasoning, replace tool results with short descriptors
- Deduplicate: if the same file was read multiple times, keep only the most recent read
- Head+tail preservation for large tool results: keep first ~500 tokens + last ~1500 tokens, truncate middle

This alone handles most cases. The bulk of tokens in a dev agent conversation come from raw file contents and command output — the agent's decisions about them are compact.

**Evidence:** JetBrains research (NeurIPS 2025) found that observation masking (preserving reasoning, replacing tool outputs) **matched** LLM summarization quality, was cheaper (no summarization API calls, 7% savings), and was faster. Summarization actually caused agents to run 13-15% longer because summaries obscured stopping signals.

#### Phase 2: Structured Anchored Summarization (escalation)

When Phase 1 isn't enough (conversation still exceeds `summaryThreshold` after pruning), generate a structured summary of the oldest section:

```
## Goal
Implement /healthz endpoint (AES-42)

## Progress
- Research complete: found existing /health pattern in integration services
- Plan approved: add /healthz to dev-agent main.ts with DB check
- Implementation done: coder created api/health.ts + tests

## Artifacts
- Branch: feature/aes-42-healthz
- PR: #47 (https://github.com/...)
- Files modified: main.ts, api/health.ts, api/health.test.ts

## Current State
- Tests passing (3/3)
- Waiting for PR review feedback

## Next Steps
- Address review comments when they arrive
```

Key properties:
- **Anchored, not regenerated.** Updated incrementally — new information merged into the existing structure. This resists "summaries of summaries" drift that every research paper identifies as the primary failure mode.
- **Artifact section populated from event log projection.** File paths and PR numbers can't be lost to summarization — they come from ground truth, not the LLM's memory.
- **Explicit sections** (goal, progress, artifacts, state, next steps). Factory.ai's research found that structured summaries preserve critical details (file paths, error messages) better than freeform ones.

#### Phase 3: Agent-Managed Memory (future evolution)

Not for v2.3 implementation, but the architecture supports it. Add `memory:save` and `memory:search` tools to the tool registry. The agent proactively saves important findings to an archive and retrieves them when needed.

This aligns with the agent-first principle — the agent decides what to remember, not the infrastructure. MemGPT/Letta demonstrates the pattern. It becomes a natural tool addition — no framework changes needed.

**History config on AgentDefinition:**

```typescript
history: {
  pruneThreshold: number;        // Token count to trigger Phase 1 (e.g., 80000)
  protectedMessages: number;     // Recent messages to never touch (e.g., 20)
  summaryThreshold: number;      // Token count to trigger Phase 2 after pruning
  summaryModel: string;          // Model for Phase 2 (e.g., "claude-haiku-4-5")
}
```

**What this replaces:**

| v2.2 | v2.3 History Management |
|------|------------------------|
| `compactConversationHistory()` in product-agent only | Framework-level, all agents get it via config |
| `context_snapshots` table + `ContextManager` | Unnecessary — conversation history IS the context |
| Summary regenerated from scratch each time | Anchored structured summary, updated incrementally |
| No tool output pruning | Phase 1 pruning as default strategy |

### 5. Agent Registry + Single Service

The runtime infrastructure that replaces per-agent services with a single service backed by registries. Four components: Agent Registry, Tool Registry, Event Router, and Single Service.

#### Agent Registry

Stores and resolves `AgentDefinition` objects. Lazy-loaded from definition files on first access, cached in memory. File modification detected via mtime check — no file watcher complexity.

```typescript
interface AgentRegistry {
  get(id: string, version?: string): Promise<AgentDefinition | null>;
  list(): Promise<AgentDefinition[]>;
}
```

When `version` is omitted, returns the latest. When specified, returns that exact version (for conversations pinned to the version they started with).

**Backing store:** File-based for v2.3. Agent definitions live in a `definitions/` directory within the agents package, one directory per agent:

```
packages/agents/definitions/
  dev-agent/
    definition.yaml
    prompt.md
  product-agent/
    definition.yaml
    prompt.md
  researcher/
    definition.yaml
    prompt.md
  coder/
    definition.yaml
    prompt.md
  tester/
    definition.yaml
    prompt.md
```

The registry reads the definition file (config) and prompt file (system prompt), assembles the `AgentDefinition`. The interface supports database backing later — agents and framework interact with the interface, never the file system directly.

**Lazy loading:** Definitions are read from disk on first `get()` call and cached. No startup cost for definitions that aren't used. New definition files are picked up on next access without restart.

#### Tool Registry

Resolves string tool references from agent definitions to actual `ToolDefinition` implementations. Uses factory functions because tools need per-invocation runtime context (container manager, agent ID, correlation ID).

```typescript
interface ToolRegistry {
  register(ref: string, factory: ToolFactory): void;
  resolve(toolRefs: string[], context: ToolContext): ToolDefinition[];
}

type ToolFactory = (context: ToolContext) => ToolDefinition;

interface ToolContext {
  agentId: string;
  correlationId: string;
  containerManager?: DevContainerManager;
  taskId?: string;
  logger: PinoLogger;
}
```

Tool factories are registered at startup by namespace:

```typescript
toolRegistry.register("codebase:read_file", (ctx) => createReadFileTool(ctx));
toolRegistry.register("codebase:write_file", (ctx) => createWriteFileTool(ctx));
toolRegistry.register("linear:get_issue", (ctx) => createLinearGetIssueTool(ctx));
// ...
```

When the executor starts a conversation, it calls `toolRegistry.resolve(definition.tools, context)` and gets back `ToolDefinition[]`. The registry handles which context fields each tool needs — the caller provides the full context, each factory takes what it needs.

**Namespace convention:** `integration:tool_name` maps to existing tool names with a prefix. `codebase:read_file`, `linear:get_issue`, `github:create_pr`, `slack:send_message`, `coordination:spawn_agent`, `coordination:wait_for`.

#### Event Router

Maps incoming events to actions: start a conversation, signal a paused conversation, or ignore.

```typescript
interface EventRouter {
  handle(event: IncomingEvent): Promise<RouteResult>;
}

type RouteResult =
  | { action: "start"; agentDefinitionId: string; message: string; context?: string; conversationId: string }
  | { action: "signal"; conversationId: string; signal: Signal }
  | { action: "ignore"; reason: string };
```

**Start rules** are declarative — defined on `AgentDefinition` via the `triggers` field. The router loads triggers from all registered definitions. When an event matches a trigger, the router knows which agent to start.

**Signal matching** is code — each integration puts correlation data in different places (Slack in action payloads, GitHub in branch names, Linear in issue IDs). The router uses event-type-specific resolver functions to extract the conversation ID and construct the signal.

**Smart router adaptation:** The existing smart router module (`packages/agents/src/router/`) provides fast-path deterministic rules and slow-path LLM classification for ambiguous events. This module is adapted (not rewritten) — `workflowClient` calls become `executor` calls, "workflow" becomes "conversation" in prompts and tool names. The fast-path/slow-path architecture is preserved.

#### Single Service

One HTTP server, one port, one process. Replaces `packages/agents/src/dev-agent/main.ts` (port 3004), `packages/agents/src/product-agent/main.ts` (port 3005), and `packages/agents/src/router/main.ts`.

### 6. Signal Handling

How external events find paused conversations and resume them. The event system is generalized — events can come from external integrations (Slack, GitHub, Linear) or internal systems (schedulers, other conversations). The framework treats all events uniformly.

#### Unified Event Shape

```typescript
interface IncomingEvent {
  type: string;                      // Freeform — "slack.app_mention.created", "internal.timeout"
  data: Record<string, unknown>;     // Event-specific payload
  source: string;                    // Origin — "slack:webhook", "github:webhook", "internal:scheduler"
  correlationKey?: string;           // For conversation ID resolution
  deduplicationId?: string;          // For idempotency
  message?: string;                    // Human-readable description for agent context on resume
}
```

No enums, no predefined event types. Any source can emit events. Adding a new event type requires: (1) something emits an `IncomingEvent`, (2) an agent definition has a trigger or an agent calls `wait_for` with that type. No framework changes, no signal definitions, no handler functions.

#### Adapters

Each event source is an adapter that transforms raw payloads into `IncomingEvent`:

```
Slack webhook payload  → adapter → IncomingEvent { type: "approval", ... }
GitHub webhook payload → adapter → IncomingEvent { type: "pr_merged", ... }
Timeout fires          → adapter → IncomingEvent { type: "wait_timeout", ... }
Agent completes        → adapter → IncomingEvent { type: "agent.completed", ... }
```

**Adapters normalize to domain language.** The Slack adapter maps `block_actions.approve` → type `"approval"`. The GitHub adapter maps `pull_request.merged` → type `"pr_merged"`. Agents think in domain terms (`"approval"`, `"pr_merged"`, `"user_reply"`), never in integration-specific event names. This keeps agent prompts clean and integration-agnostic.

Adding a new integration (e.g., Jira webhooks): write an adapter. The router, executor, and agents don't change.

#### Signal Routing

**Deterministic conversation IDs** constructed from event data:

- Dev agent conversations: `dev-agent-{issueId}`
- Product agent conversations: `product-agent-{threadTs}`

Both the start event and subsequent signals carry the same correlation key. The event router reconstructs the conversation ID using the same formula. No database lookups for signal routing.

**Type matching:** When a signal arrives, the executor checks `pendingWait.type` on the target conversation. A conversation waiting for `"approval"` won't be woken by `"pr_merged"`. Mismatched signals are logged and rejected.

#### Signal Queueing

Three conversation states when a signal arrives:

1. **Paused, waiting for matching type** — normal case. Resume with signal appended as user message.

2. **Paused, waiting for different type** — mismatch. Reject, log for debugging.

3. **Running or not yet paused** — signal is **queued** on the conversation record. When the agent next calls `wait_for`, the executor checks queued signals before suspending. If a matching signal is already queued, the conversation resumes immediately without ever visibly pausing.

This eliminates the product agent's retry-with-backoff hack for the race condition where a thread reply arrives before the workflow starts. No timing-dependent retries, no `sleep(500ms)`. The signal is stored, the conversation picks it up when ready.

#### Deduplication

Three layers:

1. **Webhook delivery dedup** — HTTP layer. `WebhookIdempotencyService.checkAndRecord(provider, deliveryId)`. Unchanged from v2.2.

2. **Conversation start dedup** — `executor.start()` with a deterministic conversation ID is idempotent. If conversation exists and is running/paused, return existing ID. No error, no duplicate.

3. **Signal dedup** — signals carry source + delivery ID. The executor tracks delivered signal IDs on the conversation. Duplicate signals are no-ops.

#### End-to-End Flow

```
POST /events receives webhook
    |
    v
1. Webhook dedup (idempotency check by delivery ID)
    |
    v
2. Adapter transforms raw payload → IncomingEvent (domain language)
    |
    v
3. Event router:
    a. Check start rules (from agent definitions) → executor.start()
    b. Resolve conversation ID from correlation key
    c. Conversation paused with matching wait? → executor.signal()
    d. Conversation running? → queue signal
    e. No match → ignore (log)
    |
    v
4. Return 200 to webhook source (non-blocking)
```

#### What This Replaces

| v2.2 | v2.3 |
|------|------|
| `defineSignal<[PlanApprovalPayload]>` (Temporal signal definition) | String type `"approval"` on `IncomingEvent` |

## Appendix A: Design Rationale & Research

This appendix captures the reasoning, industry research, and key debates behind the design decisions. It serves as context for future discussions and implementation.

### A.1 Why Temporal Is Being Replaced

Temporal was introduced in v2.1 as the durability layer for long-running agent workflows. It provided signal-based flow control, approval gates, timeouts, and crash recovery. In v2.2, the agent loop replaced LangGraph's fixed node graphs, but Temporal workflows remained as the orchestration layer.

**The fundamental mismatch:** Temporal workflows are deterministic state machines. They encode a phase graph (`setup → pre_approval → awaiting_approval → post_approval → ...`) that assumes a specific sequence of events. The agent, by design, doesn't think in phases — it thinks in goals and tools. When the agent's actual behavior doesn't match the expected phase sequence, the workflow breaks.

**Specific failures observed:**

1. **Autonomous completion bug (v2.2):** The dev agent completed a simple task (README update) during pre-approval by creating a PR directly without calling `request_human_input`. The workflow unconditionally entered `awaiting_approval` and waited for a signal that would never arrive. Fix required adding `if (humanInputRequest === null)` branch — the workflow reverse-engineering what the agent did.

2. **Data tracking by inference:** The workflow doesn't know what happened during the agent loop. It infers state from sentinel markers in agent output (`parsePrInfoFromTrace(result)`), task store queries after activity completion, and activity return values. Each new agent behavior requires a matching inference path.

3. **Context loss at activity boundaries:** Each Temporal activity invocation starts a fresh `runAgentLoop()`. The agent that researched the codebase is gone — replaced by a new agent reading an LLM-generated summary. Critical details (file paths, error messages, architectural decisions) are lost in summarization.

4. **Recovery difficulty:** When something goes wrong mid-workflow, Temporal's replay semantics make it hard to skip ahead or inject corrections. The practical answer is always: terminate and restart the workflow, losing all prior work.

**The realization:** These problems are symptoms of Temporal being used as the agent's brain rather than as infrastructure. The v2.2 design principles ("agent-first problem solving", "prompt engineering over code engineering") logically lead to removing the workflow state machine entirely. The agent loop IS the state machine. Temporal's useful features (durability, signals, timeouts) can be provided by a simpler abstraction.

### A.2 Industry Research: How Agent Frameworks Handle Spawning & Deployment

Research conducted across major agent frameworks (2025-2026) revealed a strong consensus:

**Every major framework treats agents as parameterized instances of the same runtime, not separate services.**

| Framework | Agent = | Deployment | Spawning |
|-----------|---------|------------|----------|
| Claude Code | Markdown file (YAML frontmatter + prompt) | Single process | Function call, in-process (up to 7 concurrent) |
| OpenAI Agents SDK | `Agent(name, instructions, tools, handoffs)` | Single process | Handoff tool invocation with full conversation history |
| CrewAI | `Agent(role, goal, tools)` + YAML config | Single process | Task delegation via Crew orchestration |
| LangGraph | Graph node with state + tools | Single process (shared checkpointer) | Graph routing (deterministic or LLM-driven) |
| Microsoft Agent Framework | Component with role + tools + orchestration pattern | Single or distributed | Pattern-based (Magentic, handoff, group chat) |

**Key patterns identified:**

1. **Agents are config, not services.** Claude Code uses Markdown files. OpenAI uses simple code objects. CrewAI uses YAML + Python decorators. None deploy separate services per agent type.

2. **Spawning is function-call model.** Sub-agents run in-process (same runtime, fresh context). Not HTTP calls, not separate containers. Claude Code explicitly prevents sub-agents from spawning further sub-agents (but OpenAI allows handoff chains).

3. **Communication is via message/state passing.** Shared conversation history (OpenAI), shared TypedDict state (LangGraph), task results (CrewAI). No shared memory, no race conditions by design.

4. **Same runtime, different config.** All frameworks parameterize by: system prompt/instructions, tool set, model selection, and permission modes. The runtime is identical.

**Implications for Aesir:** The current separate services (dev-agent:3004, product-agent:3005) are an outlier compared to industry practice. A single service with an agent registry is the standard pattern.

### A.3 Agent Definition: Key Design Debates

**Code objects vs declarative data:**

The initial question was whether agent definitions should be TypeScript objects (OpenAI style) or declarative data (Claude Code Markdown style). The deciding factor was **persistence**: code objects are tied to the codebase, while data (JSON/YAML in DB, files, or API) can be managed externally — enabling runtime creation, version-controlled evolution, multi-tenant definitions, and admin tooling without redeployment.

The compromise: tool **implementations** live in code (they have runtime dependencies), but tool **selection** is data (the definition references tools by name, the registry resolves implementations).

**Tool granularity:**

Three options were considered:
- Option A: Individual tools — `["linear:get_issue", "linear:update_issue_status"]` (explicit, auditable)
- Option B: Wildcards — `["linear:*"]` (convenient, less precise)
- Option C: Both with deny lists — `["linear:*", "!linear:delete_issue"]` (flexible, complex)

Decision: **Option A (individual)** for now. Principle of least privilege, easier to validate with real-world usage. Wildcards can be added later as a convenience without changing the schema.

**Sub-agent recursion:**

The current v2.2 architecture deliberately prevents sub-agents from spawning (they don't have the `spawn_agent` tool). The question was whether to keep this restriction.

Decision: **Allow recursion, controlled by config.** A researcher spawning a coder to build a one-off analysis tool is a genuinely useful emergent behavior. The controls are: (1) `spawn_agent` must be in the agent's tool list, (2) `subAgents` map scopes which definitions are available, (3) framework enforces max depth, (4) shared token budget from root provides economic constraint.

**Artifact extraction:**

The initial proposal used declarative field extraction: `artifact: { key: "github:pr", fields: ["number", "url"] }`. This was challenged because it assumes results are always JSON with simple, predictable paths.

Decision: **The tool declares its own significant output via `data` field on `ToolResult`.** The tool knows its own output format. The registry config just maps tool → artifact key. No JSON path parsing, no format assumptions. The tool puts whatever it considers significant in `data`, and the framework stores it.

### A.4 History Compaction: Research Findings

Comprehensive research across 12+ systems and academic papers identified five fundamental approaches to conversation history management:

**1. Tool Output Pruning (Claude Code, OpenCode, Cline, JetBrains)**
Strip old tool results while keeping agent reasoning. Highest impact, lowest cost. A single `read_file` result can be thousands of tokens; the agent's reasoning about it is a few sentences.
- Claude Code: Two-phase — clear old tool results first, then full summarization if needed
- OpenCode: Head+tail preservation — keep first 500 tokens + last 1500, truncate middle. `PRUNE_PROTECT` (40K recent tokens always protected)
- Cline: Middle-out truncation + dedup file reads + priority-based preservation
- **JetBrains (NeurIPS 2025): Observation masking matched LLM summarization quality, was 7% cheaper, and was faster. Summarization caused agents to run 13-15% longer because summaries obscured stopping signals.**

**2. Sliding Window + Summary (LangChain, Google ADK, Aesir v2.2 product agent)**
Keep recent N messages verbatim, summarize older. Universal failure mode: summaries of summaries degrade with each compression.

**3. Structured Anchored Summarization (Factory.ai, OpenAI Agents SDK)**
Maintain persistent structured document with explicit sections. New info merged incrementally rather than re-summarizing from scratch. Factory.ai found: all approaches lose **file paths and artifact references first** — structured summaries resist this better than freeform.

**4. Encrypted/Opaque Compression (OpenAI `/responses/compact`)**
99.3% token reduction. But black box — can't inspect, debug, or port across providers. Not suitable for a multi-provider architecture.

**5. Agent-Managed Memory (MemGPT/Letta)**
OS-inspired virtual memory. Agent manages its own memory via tools: `save_to_archive`, `search_archive`, `update_working_memory`. Full conversation in recall store, agent curates what's in-context. Aligns with agent-first principle but adds cost (extra LLM calls for memory management).

**Decision for Aesir:** Three-phase strategy. Phase 1 (tool output pruning) as default — backed by JetBrains evidence. Phase 2 (structured anchored summarization) as escalation — artifact section populated from event log projection so ground truth can't be lost. Phase 3 (agent-managed memory) as future evolution — natural tool addition, no framework changes.

**Key research insight:** The compaction trigger point matters as much as the technique. Community consensus across Claude Code, Cline, and OpenCode: **70-80% context capacity** is the right auto-compact trigger, not 95%. Compacting too late leaves insufficient reasoning room for the model.

### A.5 Event Log: Why Three Stores Converge

v2.2 shipped three persistence mechanisms that serve overlapping purposes:

1. **`execution_traces`** — Records tool calls but NOT tool results (acknowledged as a gap in the code: "tool_result traces are NOT recorded in this version"). Buffered in memory, flushed after each Temporal activity completes. Purpose: post-hoc debugging.

2. **`tasks`** — Structured state updated imperatively by Temporal activities. PR info extracted by scanning agent traces after completion (`parsePrInfoFromTrace`). If the agent creates a PR in an unexpected phase, the parsing misses it.

3. **`context_snapshots`** — LLM-generated summaries at activity boundaries. Exist solely because Temporal splits execution into separate activities that lose context.

The event log converges these because:
- Events are written **when things happen** (real-time), not reconstructed afterward
- Events include **tool results** (closing the `execution_traces` gap)
- The session projection replaces `tasks` with **reactively updated state** from events
- Conversation history replaces `context_snapshots` entirely

The backing store is abstracted behind the `EventLog` interface. Postgres handles local dev. Kafka, SQS, or similar handle production scale. The agents and framework interact with the interface, never the backing store directly. AWS services (SQS for job queue, EventBridge for signal routing, EventBridge Scheduler for timeouts) are available for production but out of scope for v2.3 implementation.

### A.6 Smart Router: Why Adapt, Not Rewrite

The smart router module (`packages/agents/src/router/`) is the largest Temporal consumer in the codebase — it imports `Client` from `@temporalio/client` and uses `workflow.start()`, `workflow.getHandle().signal()`, and `workflow.list()` across fast-path rules, slow-path LLM classification, and router tools.

However, the router's architecture maps directly to v2.3's Event Router:

| Router component | v2.2 (Temporal) | v2.3 (Executor) |
|------------------|-----------------|-----------------|
| Fast-path rules | 10 event types → `workflow.start()` / `handle.signal()` | Same rules → `executor.start()` / `executor.signal()` |
| Slow-path LLM | Agentic loop with `start_workflow` / `signal_workflow` tools | Same loop with `start_conversation` / `signal_conversation` tools |
| `RouterDeps.workflowClient` | `Client` from `@temporalio/client` | `ConversationExecutor` |
| `send_message` tool | MCP-based (no Temporal) | Unchanged |

The fast-path/slow-path architecture is sound — deterministic rules handle unambiguous events with zero latency, LLM classification handles edge cases. Only the execution layer (how it starts and signals) changes. The business logic, rule set, system prompt, and LLM routing survive intact.

The classification module (`packages/agents/src/dev-agent/classification/`) is already deprecated (inline comment: "This module is legacy — comment classification now routes through the smart router"). It has no Temporal dependencies and can be deleted.

### A.7 Generalized Event System

The v2.2 signal system requires ceremony to add new signal types: `defineSignal<[Payload]>` in signals.ts, a sender function in signal-handler.ts, routing logic in events.ts, and payload type definitions. Six distinct signals exist, each with their own typed payload and dedicated handler.

The v2.3 generalization collapses this to a single `IncomingEvent` shape with a freeform `type` string. The key insight is that **agents speak domain language, not integration language**. An agent doesn't care whether an approval came from a Slack button click or a Linear comment — it just knows it received an `"approval"` signal.

This separation of concerns is enforced by **adapters**: integration-specific code that transforms raw webhook payloads into domain-language events. The adapter is the only code that knows about Slack's `block_actions` payload structure or GitHub's `pull_request` event schema. Everything downstream — the router, executor, and agent — operates on normalized domain events.

The pattern also enables internal events (timeouts, agent completion, health checks) to flow through the same pipe. A timeout is just `IncomingEvent { type: "wait_timeout", source: "internal:scheduler" }`. No special handling, no separate code path.

### A.8 Spec Completion Status

All seven topics are settled:

1. **Agent Definition** — Declarative config as data, tool references by name, sub-agent references by ID, explicit versioning
2. **Event Log** — Unified ground truth replacing three stores, `EventLog` interface abstracts backing store
3. **Execution Model** — `ConversationExecutor` replaces Temporal, conversations as execution primitive, `wait_for` tool for pause/resume

### B.1 The `wait_for` Tool

The tool that lets agents pause conversations and wait for external signals. Referenced throughout Topics 3 and 6 but defined here in full.

```typescript
const waitForTool: ToolDefinition = {
  name: "wait_for",
  description:
    "Pause this conversation and wait for an external signal before continuing. " +
    "Use when you need: human approval for a plan, user reply in a conversation, " +
    "PR review feedback, CI results, or any external input. " +
    "The conversation will resume automatically when the signal arrives or the timeout expires.",
  parameters: z.object({
    type: z.string().describe(
      "What to wait for. Must match the signal type that will wake this conversation. " +
      "Common types: 'approval', 'user_reply', 'pr_review', 'pr_merged', 'escalation_resolved'."
    ),
    reason: z.string().describe(
      "Why you are pausing. Logged for observability and included in timeout notifications. " +
      "E.g., 'Waiting for human approval of implementation plan before proceeding.'"
    ),
    timeout: z.string().optional().describe(
      "Max time to wait before auto-waking with a timeout signal. " +
      "Format: '<number><unit>' where unit is h (hours) or d (days). " +
      "E.g., '72h', '7d'. Defaults to framework config if not specified."
    ),
    metadata: z.record(z.unknown()).optional().describe(
      "Additional context stored with the pause. " +
      "E.g., { channel: 'C123', threadTs: '1234.5678' } for Slack notifications."
    ),
  }),
};
```

**Behavior:**

1. Framework intercepts this tool call (it's not a normal tool — it controls the loop).
2. Tool result returned to the agent: `{ content: "Conversation paused. Waiting for: {type}. Reason: {reason}." }`
3. Framework writes `agent.paused` event to event log.
4. Framework sets `conversation.status = "paused"` and `conversation.pendingWait = { type, metadata }`.
5. Framework persists conversation to storage.
6. Framework registers timeout (if specified or default exists).
7. Agent loop exits normally (returns `AgentLoopResult`).

**On timeout:** The framework creates a signal `{ type: "wait_timeout", data: { originalWaitType: type, reason }, source: "internal:scheduler" }` and delivers it like any other signal. The agent decides what to do — escalate, retry, or complete.

### B.4 Signal-to-Message Format

When a signal resumes a paused conversation, the framework constructs a user message from the signal and appends it to `conversation.messages`. This is what the agent sees when its loop restarts.

**The `IncomingEvent.message` field is the primary source.** Adapters construct a human-readable message when creating the event. The framework uses this directly as the user message content.

**Adapter message examples:**

| Signal Type | Adapter Message |
|-------------|----------------|
| `approval` (approved) | `"Plan approved by John Smith. Feedback: 'Looks good, proceed with the implementation.'"` |
| `approval` (rejected) | `"Plan rejected by Jane Doe. Feedback: 'Need more test coverage for the auth module.'"` |
| `user_reply` | `"User reply: We also need to handle the edge case where the token expires mid-request."` |
| `pr_merged` | `"PR #47 (feature/aes-42-healthz) was merged into main."` |
| `pr_review` | `"PR review from @reviewer on PR #47: 'Consider using a connection pool instead of creating a new connection per request.'"` |
| `escalation_resolved` (retry) | `"Escalation resolved: retry. Guidance: 'Try using the v2 API endpoint instead — the v1 endpoint was deprecated last month.'"` |
| `wait_timeout` | `"Wait timeout: you have been paused for 72h waiting for 'approval'. No signal was received. Decide whether to escalate, retry, or complete."` |

**Fallback:** If `IncomingEvent.message` is not set, the framework constructs a generic message: `"Signal received: {type}. Data: {JSON.stringify(data)}"`. This should be rare — adapters should always provide a message.

**Format in conversation history:** The signal message is appended as a standard `user` role message in the Anthropic API format:

```typescript
conversation.messages.push({
  role: "user",
  content: event.message ?? `Signal received: ${signal.type}. Data: ${JSON.stringify(signal.data)}`,
});
```

The agent sees it as a normal user message and responds naturally. No special parsing, no XML tags, no structured format the agent needs to decode.

### B.5 Conversation ID Construction

Conversation IDs are **deterministic** — constructed from the triggering event's correlation data. The construction formula is owned by the **event router's resolver functions**, not by adapters or agent definitions.

**Current formulas:**

| Agent | Formula | Correlation Source |
|-------|---------|-------------------|
| dev-agent | `dev-agent-{issueId}` | `issueId` from Linear `agent_session.created` event |
| product-agent | `product-agent-{threadTs}` | `threadTs` from Slack `app_mention.created` event |

**How it flows:**

1. **Start event:** Adapter emits `IncomingEvent` with `correlationKey` set to the raw identifier (e.g., `"ABC-123"` or `"1234567890.123456"`).
2. **Event router:** Matches start rule → determines `agentDefinitionId` → constructs `conversationId` using the formula `{agentDefinitionId}-{correlationKey}`.
3. **Signal event:** Adapter emits `IncomingEvent` with same `correlationKey`. Router reconstructs the same `conversationId` using the same formula.

**The formula `{agentDefinitionId}-{correlationKey}` is the default.** It works for all current cases. If a future agent needs a different formula (e.g., composite keys), the router's resolver function can be extended per agent type.

**Why the router owns this, not the adapter:** The adapter normalizes payloads but shouldn't know about conversation ID structure. The router knows which agent handles which event and how to construct identifiers. The adapter just provides the raw correlation data.
