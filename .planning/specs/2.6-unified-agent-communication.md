# 2.6: Unified Agent Communication (Domain-Language I/O)

## Problem

Agents currently interact with integrations through channel-specific tools (`slack:send_message`, `slack:reply_to_thread`, `linear:create_comment`, `github:create_pull_request`, etc.). This creates several issues:

1. **Complexity scales as O(agents x integrations)** — every new channel means updating every agent's tool list and prompt guidance.
2. **Agents reason about channels instead of intent** — the dev-agent has hardcoded Slack escalation behavior rather than thinking "I need to reply to this feedback."
3. **Reply routing is disconnected from signal origin** — an approval signal looks identical regardless of whether it came from Slack, Linear, or GitHub. The agent can't "reply where the conversation is happening" because it doesn't know where that is.
4. **Asymmetry with inbound** — inbound events are already normalized through adapters into domain-language signals (approval, pr_review, user_reply). Outbound communication has no equivalent abstraction.

## Design Principle

**Classify by intent, reply by origin.**

The semantic meaning of a signal (approval, feedback, question) is independent of the channel it arrived on. What matters is: (a) classifying the intent correctly, and (b) replying back on the same channel the human used. The agent should reason in domain language, and the infrastructure handles channel translation in both directions.

A comment on a PR is about the PR and should be handled by dev-agent. A comment on a Linear issue is task-level and doesn't matter if it came from Linear, Slack, or even GitHub as a random comment challenging the design. What matters is replying back to the same channel.

## Current State (What Exists Today)

### Inbound: Normalizers (Working Well)

Inbound events are already normalized through adapters (`packages/agents/src/adapters/`) into domain-language signals:

```
Slack webhook  → adaptSlackEvent()  → { type: "approval", data: { approved: true }, source: "slack:webhook" }
Linear webhook → adaptLinearEvent() → { type: "approval", data: { approved: true }, source: "linear:webhook" }
GitHub webhook → adaptGitHubEvent() → { type: "pr_review", data: { ... }, source: "github:webhook" }
```

The `IncomingEvent` type (`packages/agents/src/adapters/types.ts`):

```typescript
// Current schema
export const IncomingEventSchema = z.object({
  type: z.string().min(1),       // Domain event type (e.g., "approval", "thread_reply")
  data: z.record(z.unknown()),   // Event-specific payload
  source: z.string().min(1),     // Origin (e.g., "slack:webhook")
  correlationKey: z.string().optional(),
  deduplicationId: z.string().optional(),
  message: z.string().optional(),
  taskId: z.string().optional(),
});
```

The `source` field tells us where the event came from, but this information is **not propagated** to the agent in a structured way. By the time the signal reaches the agent, it's been stringified into a user message:

```typescript
// conversation-executor.ts — signal becomes a user message
const signalContent = signal.message ??
  `Signal received: ${signal.type}. Data: ${JSON.stringify(signal.data ?? {})}`;
```

The agent sees text like `"Signal received: approval. Data: {"approved":true}"` — no structured `replyContext`.

### Communication Gaps in Current State

1. **No Linear comment tool exposed to agents** — `create_comment` exists in the Linear integration MCP server (`packages/integrations/linear/src/mcp/tools/issues.ts`) but is NOT registered in `linear-tools.ts` and NOT listed in the MCP server's tool list. Neither agent can comment on Linear issues.

2. **Product-agent can't reply to threads** — has `slack:send_message` but NOT `slack:reply_to_thread`. When it responds, it sends a new top-level message rather than continuing the thread.

3. **Dev-agent communication is Slack-only** — approval requests, escalations, and status updates all go to Slack. The agent has no way to communicate on Linear issues or GitHub PRs even if the signal originated there.

4. **No GitHub comment capability** — no tool exists for agents to reply to PR reviews or add PR comments.

### How Tools Execute Today

Tools are created via factory functions that receive a `ToolContext`:

```typescript
// packages/agents/src/framework/types.ts
export interface ToolContext {
  agentId: string;         // e.g., "dev-agent"
  correlationId: string;   // Conversation ID
  taskId?: string;         // v2.5 task primitive
  logger: PinoLogger;
  containerManager?: DevContainerManager;
  sandboxId?: string;
  spawnDeps?: SpawnAgentDeps;
}
```

Integration tools use the `mcpAdapter()` bridge which extracts `McpToolDeps` from `ToolContext`:

```typescript
// packages/agents/src/shared/tools/integration/mcp-wrapper.ts
export interface McpToolDeps {
  agentId: string;
  correlationId: string;
  taskId?: string;
}
```

Each tool call goes through MCP HTTP:
```typescript
// packages/agents/src/shared/mcp/client.ts
callMcpTool({ integration: "slack", tool: "send_message", params, agentId, correlationId })
  → POST http://slack-integration:3003/mcp/tools/send_message
```

**Key limitation:** `ToolContext` has no knowledge of the conversation's active signal, reply context, or originating channel. The agent must hardcode channel details (Slack channel IDs, thread timestamps) because there's no infrastructure to propagate this context.

### Signal Flow (Current)

```
1. Slack thread reply arrives
2. Normalizer: adaptSlackEvent() → IncomingEvent { type: "thread_reply", data: { text, threadTs, channelId }, source: "slack:webhook" }
3. Router: slow-path classifies → signal_conversation({ signalType: "user_reply", message: text })
4. Executor: signal becomes user message → "Signal received: user_reply. Data: {}"
5. Agent: sees text, reasons, calls slack:send_message(channel, text) ← HARDCODED channel
```

The agent has to know it's Slack and know the channel ID. If the same semantic signal came from Linear, the agent would still try to reply on Slack.

## Proposed Architecture: Symmetric Normalization

### Inbound (exists, extend with replyContext)

```
Slack webhook  → normalizer → { type: "approval", replyContext: { channel: "slack", ... }, data: { approved: true } }
Linear comment → normalizer → { type: "approval", replyContext: { channel: "linear", ... }, data: { approved: true } }
GitHub review  → normalizer → { type: "pr_review", replyContext: { channel: "github", ... }, data: { ... } }
```

### Agent Layer (domain language only)

Agent sees domain signals → reasons about intent → emits domain actions.
Never touches integration-specific details.

### Outbound (proposed)

```
Agent calls reply(replyContext, message)  → denormalizer → Slack reply_to_thread / Linear create_comment / GitHub PR comment
Agent calls ask(replyContext, question)   → denormalizer → Slack approval buttons / Linear comment with instructions
Agent calls notify(target, message)       → denormalizer → Slack channel post / Linear issue comment
```

## Detailed Design

### 1. replyContext Type

```typescript
// packages/agents/src/shared/communication/types.ts
// Domain types shared across adapters, framework, tools, and router.
// Lives outside shared/tools/ to avoid circular imports (adapters create
// ReplyContext, framework passes it, tools consume it — no layer owns it).

/**
 * Channel-specific addressing for message delivery.
 * Attached by inbound normalizers, passed through signals, consumed by outbound denormalizers.
 * Also used for notify() targets and defaultNotifyTarget in agent definitions.
 *
 * The semantic difference between reply and notify lives in the tool choice,
 * not the type. ReplyContext is just an address — where to deliver the message.
 */
export type ReplyContext =
  | {
      channel: "slack";
      teamId: string;
      channelId: string;
      threadTs?: string;  // Present for thread replies, absent for channel-level notifications
    }
  | {
      channel: "linear";
      issueId: string;
    }
  | {
      channel: "github";
      owner: string;
      repo: string;
      prNumber: number;
      commentId?: number;  // For replying to specific review comments (deferred — PR-level comments only in v2.6)
    };

/**
 * Content type for outbound messages.
 * Agent provides content in a neutral format; denormalizer translates.
 *
 * Future: add `semantic` field ("status_update" | "escalation" | "completion")
 * when format translation lands (FMT-01/FMT-02). Unused in v2.6.
 */
export interface MessageContent {
  text: string;                         // Markdown body — primary content
  options?: Array<{                     // For ask() — interactive options
    label: string;
    value: string;
    style?: "primary" | "danger";
  }>;
}
```

### 2. Inbound: Extend Normalizers with replyContext

Every adapter output that has enough data to construct a replyContext should include one — not just events where a human explicitly communicated. Adapters normalize data; they don't classify intent. The agent decides whether to use the replyContext. The only events without replyContext are those with no originating channel (e.g., internal timeout signals).

The existing adapters need to attach `replyContext` to `IncomingEvent.data`:

**Changes to `packages/agents/src/adapters/types.ts`:**

```typescript
export const IncomingEventSchema = z.object({
  type: z.string().min(1),
  data: z.record(z.unknown()),
  source: z.string().min(1),
  correlationKey: z.string().optional(),
  deduplicationId: z.string().optional(),
  message: z.string().optional(),
  taskId: z.string().optional(),
  replyContext: ReplyContextSchema.optional(),  // NEW: propagated through signal
});
```

**Changes to `packages/agents/src/adapters/slack.ts`** (example):

```typescript
case "slack.message.created": {
  const threadTs = payload.threadTs as string | undefined;
  if (!threadTs) {
    return { action: "ignore" as const, reason: "..." };
  }
  return {
    type: "thread_reply",
    data: { text: payload.text, userId: payload.user, channelId: payload.channel, threadTs },
    source: "slack:webhook",
    correlationKey: threadTs,
    deduplicationId: event.correlationId,
    message: payload.text as string,
    replyContext: {                            // NEW
      channel: "slack",
      teamId: payload.teamId as string,
      channelId: payload.channel as string,
      threadTs,
    },
  };
}
```

Similar changes in `adaptLinearEvent()` and `adaptGitHubEvent()`.

### 3. Signal Pipeline: Propagate replyContext

**Changes to `packages/agents/src/framework/types.ts`:**

```typescript
export const SignalSchema = z.object({
  type: z.string().min(1),
  data: z.record(z.unknown()).optional(),
  message: z.string().optional(),
  source: z.string().optional(),
  deduplicationId: z.string().optional(),
  replyContext: ReplyContextSchema.optional(),  // NEW
});
```

**Changes to signal delivery in `conversation-executor.ts`:**

When the signal is injected into the conversation as a user message, the `replyContext` must be included in a structured way the agent can pass back:

```typescript
// Current: signal becomes plain text
const signalContent = signal.message ?? `Signal received: ${signal.type}. Data: ${JSON.stringify(signal.data ?? {})}`;

// Proposed: signal includes replyContext as structured data
const signalContent = buildSignalMessage(signal);
// e.g., "Signal received: user_reply\nMessage: looks good ship it\n\n<reply_context>{\"channel\":\"slack\",\"channelId\":\"C123\",\"threadTs\":\"1234567890.000000\",\"teamId\":\"T789\"}</reply_context>"
```

The `<reply_context>` tag makes the context available to the LLM without requiring it to parse or understand the structure — it just passes it through to `reply()`.

**Changes to conversation start in `conversation-executor.ts`:**

The `start()` path also needs replyContext. When a conversation is created from an IncomingEvent (e.g., Slack app mention, Linear issue assignment), the originating channel's replyContext should be stored on the conversation row immediately — not deferred until the first signal. Without this, agents that complete without pausing have no way to reply to the originating channel.

```typescript
// packages/agents/src/framework/types.ts — extend StartConversationParams
export interface StartConversationParams {
  agentDefinitionId: string;
  correlationKey: string;
  initialMessage: string;
  context?: string;
  parentConversationId?: string;
  taskId?: string;
  replyContext?: ReplyContext;  // NEW: from the IncomingEvent that triggered start()
}
```

The router propagates `replyContext` from `IncomingEvent` into both `start()` and `signal()` calls. The executor stores it on the conversation row at creation time. The initial message includes a `<reply_context>` tag so the agent can reply from turn one.

### 4. Outbound: Unified Communication Tools

Three new tools registered in the `communication` namespace:

**`communication:reply`** — Respond to whoever is talking to you

```typescript
// packages/agents/src/shared/tools/communication/reply.ts

export function createReplyTool(deps: CommunicationToolDeps): ToolDefinition {
  return {
    name: "reply",
    description: "Reply to a human message. Pass the replyContext from the signal that triggered this response. The message will be delivered to the same channel the human used (Slack thread, Linear issue comment, or GitHub PR comment).",
    inputSchema: z.object({
      replyContext: ReplyContextSchema,       // Opaque to the agent — just pass it through
      message: z.string().min(1),             // Markdown body
    }),
    async execute(input): Promise<ToolResult> {
      const { replyContext, message } = parsed;
      const result = await denormalize({ action: "reply", replyContext, content: { text: message } }, deps);
      return { content: JSON.stringify(result) };
    },
  };
}
```

**`communication:ask`** — Request input from a human with structured options


### 5. Outbound Denormalizer

The denormalizer dispatches outbound actions to the correct integration MCP tool:

```typescript
// packages/agents/src/shared/tools/communication/denormalizer.ts

export interface DenormalizeAction {
  action: "reply" | "ask" | "notify";
  replyContext: ReplyContext;
  content: MessageContent;
}

export async function denormalize(action: DenormalizeAction, deps: CommunicationToolDeps): Promise<DenormalizeResult> {
  const { replyContext, content } = action;

  switch (replyContext.channel) {
    case "slack":
      return denormalizeSlack(action, replyContext, deps);
    case "linear":
      return denormalizeLinear(action, replyContext, deps);
    case "github":
      return denormalizeGitHub(action, replyContext, deps);
    default:
      throw new Error(`Unknown channel: ${(replyContext as ReplyContext).channel}`);
  }
}
```

**Slack denormalizer:**

```typescript
async function denormalizeSlack(action: DenormalizeAction, ctx: SlackReplyContext, deps: CommunicationToolDeps) {
  if (action.action === "ask" && action.content.options?.length) {
    // Use send_approval_request for interactive buttons
    return callMcpTool({
      integration: "slack",
      tool: "send_approval_request",
      params: {
        channel: ctx.channelId,
        ...(ctx.threadTs && { threadTs: ctx.threadTs }),
        text: action.content.text,
        options: action.content.options,
        taskIdentifier: deps.taskId,     // For correlating button clicks
      },
      agentId: deps.agentId,
      correlationId: deps.correlationId,
    });
  }

  // threadTs present → reply in thread; absent → post to channel
  const tool = ctx.threadTs ? "reply_to_thread" : "send_message";
  return callMcpTool({
    integration: "slack",
    tool,
    params: {
      channel: ctx.channelId,
      ...(ctx.threadTs && { threadTs: ctx.threadTs }),
      text: action.content.text,
    },
    agentId: deps.agentId,
    correlationId: deps.correlationId,
  });
}
```

**Linear denormalizer:**

```typescript
async function denormalizeLinear(action: DenormalizeAction, ctx: LinearReplyContext, deps: CommunicationToolDeps) {
  if (action.action === "ask" && action.content.options?.length) {
    // No buttons on Linear — render options as text instructions
    const optionsList = action.content.options.map(o => `- **${o.label}**: reply "${o.value}"`).join("\n");
    const body = `${action.content.text}\n\n${optionsList}`;
    return callMcpTool({
      integration: "linear",
      tool: "create_comment",
      params: { issueId: ctx.issueId, body },
      agentId: deps.agentId,
      correlationId: deps.correlationId,
    });
  }

  return callMcpTool({
    integration: "linear",
    tool: "create_comment",
    params: { issueId: ctx.issueId, body: action.content.text },
    agentId: deps.agentId,
    correlationId: deps.correlationId,
  });
}
```

**GitHub denormalizer:**

```typescript
async function denormalizeGitHub(action: DenormalizeAction, ctx: GitHubReplyContext, deps: CommunicationToolDeps) {
  // Reply as PR comment
  return callMcpTool({
    integration: "github",
    tool: "create_pr_comment",   // New MCP tool needed
    params: {
      owner: ctx.owner,
      repo: ctx.repo,
      prNumber: ctx.prNumber,
      body: action.content.text,
      ...(ctx.commentId && { inReplyTo: ctx.commentId }),
    },
    agentId: deps.agentId,
    correlationId: deps.correlationId,
  });
}
```

## Communication Channels by Semantic Level

The dev-agent interacts across three channels, each at a different semantic level:

| Channel | Semantic Level | Role |
|---------|---------------|------|
| **Linear** | Task-level (the *what*) | Approvals, questions, feedback, scope discussion |
| **GitHub** | Solution-level (the *how*) | PR reviews, code feedback, merge/close signals |
| **Slack** | Meta-level (the *hey*) | Escalation reminders, unanswered question nudges |

The agent doesn't decide which channel to use based on hardcoded rules. It responds where the conversation is happening (via replyContext) and uses `notify()` for meta-level broadcasts when no existing conversation context exists.

## Full Round-Trip Examples

### Example 1: Linear Comment Approval

```
1. Human comments "looks good, ship it" on Linear issue AT-123
2. Linear webhook → linear-integration → POST /events (NormalizedEvent)
3. adaptLinearEvent() → IncomingEvent:
   {
     type: "comment_created",
     data: { text: "looks good, ship it", issueId: "uuid-abc", authorName: "Roberto" },
     source: "linear:webhook",
     replyContext: { channel: "linear", issueId: "uuid-abc" },     // NEW
     correlationKey: "uuid-abc",
   }
4. Router slow-path → classifies as "approval" → signal_conversation:
   {
     conversationId: "dev-agent-uuid-abc",
     signalType: "approval",
     payload: { approved: true, approverName: "Roberto", source: "linear" },
     replyContext: { channel: "linear", issueId: "uuid-abc" },     // NEW: propagated
   }
5. Executor delivers signal to waiting conversation:
   "Signal received: approval. Approved: yes, by Roberto.
    <reply_context>{"channel":"linear","issueId":"uuid-abc"}</reply_context>"
6. Agent resumes, decides to proceed, calls:
   communication:reply({ replyContext: { channel: "linear", issueId: "uuid-abc" }, message: "Starting implementation..." })
7. Denormalizer → callMcpTool({ integration: "linear", tool: "create_comment", params: { issueId: "uuid-abc", body: "Starting implementation..." } })
8. Comment appears on the Linear issue — same channel the human used
```

1. **Expose `create_comment` tool** — already implemented in `src/mcp/tools/issues.ts` but not registered in the MCP server tool list. Needs to be added to the handler and the agents-side `linear-tools.ts`.

### GitHub Integration (`packages/integrations/github/`)

1. **Add `create_pr_comment` tool** — new MCP tool for adding PR-level comments. Uses Octokit's `issues.createComment` (PRs are issues in GitHub's API). This posts a conversational comment in the PR timeline — NOT `pulls.createReview`, which carries review workflow semantics (approved/changes requested) and is inappropriate for agent replies. Inline review comment replies (`pulls.createReplyForReviewComment`) deferred — see `commentId` on ReplyContext.

### Slack Integration (`packages/integrations/slack/`)

1. **No changes needed** — `send_message`, `reply_to_thread`, and `send_approval_request` already cover all outbound patterns. The denormalizer calls the right one based on action type.

- The `replyContext` field is optional everywhere — signals without it still work (agent falls back to `notify()`)

## Relationship to Existing Work

- **v2.5 domain-language signals** — already abstracts inbound event semantics. This extends the same principle outbound.
- **Adapter pipeline** (`packages/agents/src/adapters/`) — inbound normalizers exist. Outbound denormalizers are the symmetric counterpart.
- **MCP layer** — outbound denormalizers call integration MCP tools internally, preserving the HTTP boundary between agents and integrations.
- **Router** — continues to handle inbound classification. Outbound routing is handled by the denormalizer dispatcher, not the router.
- **Tool registry** (`packages/agents/src/framework/tool-registry.ts`) — new `communication:*` namespace follows existing registration patterns.
- **mcpAdapter pattern** (`packages/agents/src/framework/tool-factories.ts`) — `communicationAdapter` follows the same ToolContext → deps extraction.

## Open Questions

1. **How should the agent access replyContext from signals?** Options: (a) XML tags in the signal message (simple, LLM-friendly), (b) structured tool_result content block, (c) injected as a system message with the reply context. Option (a) is simplest and aligns with existing prompt patterns.

2. **~~Should notify() require explicit target or use conversation metadata?~~** Resolved: notify() takes an explicit `ReplyContext` target. Agent definitions support an optional `defaultNotifyTarget` (ReplyContext) for fallback routing. Start with agent YAML, move to workspace config when multi-workspace support matters.

3. **How does this interact with the product-agent?** Product-agent is Slack-native today. It benefits from this abstraction if/when it gains Linear or other channel support. In the short term, all its replyContexts will be Slack.

4. **Should replyContext support multiple targets?** e.g., "reply on GitHub AND update Linear." Current design uses separate `reply()` calls — agent decides when multi-channel is appropriate. Could add a convenience `replyAll()` later if the pattern is common.

5. **~~Where do default channel preferences live?~~** Resolved: `defaultNotifyTarget` in agent definition YAML (a `ReplyContext` value). Move to workspace-level config when multi-tenancy matters.
