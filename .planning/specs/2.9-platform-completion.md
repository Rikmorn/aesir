# Milestone v2.9: Platform Completion

**Status:** Planning
**Scope:** Complete every collaboration capability agents will need before domain modeling begins. When v2.9 ships, the platform is feature-complete — all future work is agent intelligence, not infrastructure. Every mechanism for negotiation, parallel work, scheduling, discovery, and persistent identity is in place.

**Predecessor:** v2.8 (Agent Resilience & Observability) — stabilizes existing system
**Successor:** v3.0 (Domain Modeling) — deep role analysis and agent design

---

## Phase 1: Richer Negotiation

**Goal**: The delegation handshake supports counter-proposals and mid-task clarification — agents can negotiate scope and ask follow-up questions during work, not just accept or reject.

**Depends on**: v2.8 complete

**Context**: v2.7 shipped accept/reject handshake (DEL-03/04). Two capabilities were deferred:

1. **Counter-propose (ADEL-01)**: Agent responds with modified scope, timeline, or approach instead of flat accept/reject. The strategy interface exists from v2.7 — this is a new strategy implementation, not a refactor.
2. **Bidirectional clarification (ASIG-01)**: Target agent signals delegator mid-task requesting more information. Multi-type `wait_for` (SIG-08) ships the infrastructure; this adds the signal type and coordination tools.

### Requirements

| ID | Requirement |
|---|---|
| NEG-01 | Counter-propose response type — target responds with modified scope, timeline, or approach. Delegator sees the modification and decides: accept modified version, reject and cancel, or try someone else. No counter-counter-proposals — if the delegator disagrees with the modification, they reject and re-delegate with refined scope (fresh negotiation, not extended handshake). All delegation response signals (rejection, counter-proposal, counter-proposal-rejected) carry the original task summary, responding agent ID, and reason — enough context for the delegator to reason about next steps without history lookup |
| NEG-02 | Counter-propose as handshake strategy — new strategy implementation alongside existing accept/reject. Same `task:respond` tool with additional response type. Counter-proposing puts the target conversation into a `wait_for` state — the target does not begin work until the delegator explicitly accepts the modified scope. If rejected, the target's conversation terminates without doing work |
| NEG-03 | Clarification signal type — `task_clarification` signal from target to delegator with question and optional structured options |
| NEG-04 | `task:clarify` tool — target agent sends a clarification request back to the delegating conversation. Implicitly enters `wait_for` — the target pauses until the delegator responds (same pattern as counter-propose) |
| NEG-05 | Clarification response — delegator answers via signal back to target. Target's conversation resumes with the answer in context |
| NEG-06 | Multi-round support — clarification can go back and forth within a single delegation, bounded by the task timeout. Clarification wait time counts toward the task timeout (total delegation duration is what matters, not individual round-trip time) |
| NEG-07 | Prompt guidance — agents default to accommodating: prefer accepting or counter-proposing over rejecting. Counter-propose to honestly scope what they can deliver ("I can do X but not Y"). Reserve rejection for genuine capability mismatches. Use clarification when missing information would significantly affect the outcome; proceed with assumptions when the risk is low |

### Success Criteria

1. An agent counter-proposes a delegation ("I can implement this but need the API spec first") and the delegator accepts the modification
2. A target agent requests clarification mid-task and the delegator provides additional context, allowing the target to continue
3. Multiple clarification rounds work within a single delegation without deadlock
4. Counter-propose and clarification compose correctly with existing timeout and completion signaling

### Open Design Questions

1. **Counter-propose format** — Free-text modification description, or structured fields (modified_scope, modified_timeline)? Probably free-text with optional structured metadata — the agent reasons about the modification in natural language.
2. ~~**Clarification timeout** — Resolved: clarification wait time counts toward the task timeout (NEG-06). Total delegation duration is what matters. Pausing the clock would remove pressure for efficient round-trips and create a gaming vector (CRITICAL-1 in PITFALLS.md).~~

## Phase 2: Parallel Delegation

**Goal**: Agents can delegate to multiple entities simultaneously and define completion policies for the group — enabling fan-out workflows like parallel research, independent feature implementation, and concurrent reviews.

**Depends on**: Phase 1 (richer negotiation enables more sophisticated delegation patterns)

**Context**: v2.7 supports sequential delegation only (ASIG-02 deferred). Real workflows need fan-out: research from multiple sources, parallel implementation of independent features, concurrent reviews. The complexity is in partial completion handling — what happens when 2 of 3 complete and one fails?

### Requirements

| ID | Requirement |
|---|---|
| PAR-01 | Task groups — `task:delegate_group` creates multiple delegations as a named group with a shared completion policy |
| PAR-02 | Completion policies — `all_required` (wait for all), `any_sufficient` (first success unblocks delegator), `majority` (N of M). Defined at group creation |
| PAR-03 | Partial completion handling — when policy is `all_required` and one task fails, delegator receives immediate notification and decides: wait for others, cancel remaining, or accept partial results |
| PAR-04 | Group status tool — `task:group_status` returns aggregated group state (how many complete, pending, failed) |
| PAR-05 | Signal aggregation — completion signals from group members are collected. Delegator is signaled when the group's completion policy is satisfied |
| PAR-06 | Group cancellation — delegator can cancel all remaining tasks in a group (e.g., after `any_sufficient` is met, cancel the rest) |
| PAR-07 | Budget-aware group design — group data model accommodates future tree budget distribution (Phase 4). Phase 2 uses per-conversation budgets; Phase 4 retrofits tree-level allocation into groups |

### Success Criteria

1. An agent delegates research to 3 agents with `any_sufficient` policy and resumes when the first returns results
2. An agent delegates implementation of 3 independent features with `all_required` and waits for all to complete
3. When one task in an `all_required` group fails, the delegator receives immediate notification and can cancel remaining tasks
4. `task:group_status` accurately reflects the state of all tasks in the group

### Open Design Questions

1. **Group vs individual handshake** — Does each delegation in a group go through its own handshake, or is there a group-level acceptance? Probably individual — each agent decides independently whether to accept.
2. **`any_sufficient` cancellation** — When `any_sufficient` is met, should remaining tasks auto-cancel or continue running? Probably agent decides — signal the delegator, who can cancel explicitly if they want.

## Phase 3: Transparent Materialization

**Goal**: Task delegation can optionally create external artifacts (Linear tickets) for auditability and human visibility — the same delegation flow produces an internal handoff or a visible ticket based on prompt-level policy.

**Depends on**: v2.8 complete

**Context**: v2.7 delegation is internal-only — tasks create conversations but no external artifacts. For teams that want visibility into agent-to-agent work through their existing tools, delegated tasks should optionally materialize as Linear tickets (ADEL-02/03). The materialization interface exists from v2.7 with a single implementation path (internal). This adds the transparent path.

### Requirements

| ID | Requirement |
|---|---|
| MAT-01 | Materialization policy parameter — `task:delegate` accepts an optional `materialization` parameter: `internal` (default, current behavior) or `transparent` |
| MAT-02 | Linear materialization — transparent mode creates a Linear issue with task description, priority, assignee (agent), and a link/reference back to the internal task |
| MAT-03 | Bidirectional sync — status changes on the materialized artifact (Linear issue updated) sync to task status. Task completion updates the Linear issue |
| MAT-04 | Materialization as prompt guidance — the decision to use internal vs transparent is agent judgment. Prompt guidance describes when transparency is valuable (e.g., "use transparent materialization when humans need to track this work") |
| MAT-05 | Materialization interface — extensible dispatch for future targets (Slack thread, GitHub issue) without changing the delegation tool |
| MAT-06 | Correlation tracking — materialized artifacts are tracked in the integration correlation layer so incoming webhooks route correctly back to the task |

### Success Criteria

1. An agent delegates with `materialization: "transparent"` and a Linear ticket is created with the task description and agent assignee
2. When the delegated agent completes the task, the Linear ticket is automatically updated to done
3. The same delegation flow works with `materialization: "internal"` (default) — no external artifact, identical to v2.7 behavior
4. Webhook events from the materialized Linear ticket route correctly to the delegated task's conversation

### Open Design Questions

1. **Which integrations first** — Linear is the obvious first target. GitHub issues as a second materialization target? Probably defer to when there's a real use case.
2. **Sync conflict** — If a human modifies the materialized Linear ticket (changes status, edits description), how does that affect the internal task? Probably: status changes sync as signals, description changes are informational only.

## Phase 4: Tree-Level Token Budgets

**Goal**: Token budget enforcement spans the entire delegation tree, preventing delegation chains from consuming unbounded resources while giving operators visibility into total cost.

**Depends on**: Phase 2 (parallel delegation creates the most risk for budget overruns)

**Context**: v2.7 enforces token budgets per-conversation. A delegation chain (A → B → C) has independent budgets. If each conversation allocates its own budget, the total tree consumption is unpredictable. ASIG-03 from v2.7 deferred work. With parallel delegation (Phase 2), this becomes more critical — a fan-out of 5 parallel tasks could each allocate full budgets.

### Requirements

| ID | Requirement |
|---|---|
| BUD-01 | Tree budget allocation — root task sets a total token budget for the entire delegation tree via `task:delegate` parameter |
| BUD-02 | Budget propagation — delegated tasks inherit a portion of the remaining tree budget, not an independent allocation. The delegating agent can specify allocation or accept default (equal split of remaining) |
| BUD-03 | Budget tracking — real-time token usage aggregated across all conversations in the tree, queryable via `task:tree_budget` tool |
| BUD-04 | Budget exhaustion signal — when tree budget is approaching exhaustion, active conversations receive a warning signal. Hard exhaustion stops all conversations in the tree |
| BUD-05 | Budget visibility in dashboard — token usage per tree level, per conversation, and total. Visual representation in the task tree view |
| BUD-06 | Backward compatibility — conversations without a tree budget continue using per-conversation budgets (existing behavior) |

### Success Criteria

1. A delegation tree with a 200k token budget stops all conversations when the total is reached, regardless of individual conversation usage
2. Budget allocation is visible in the dashboard across the tree hierarchy
3. A conversation without a tree budget works exactly as it does in v2.7

### Open Design Questions

1. **Allocation strategy** — Equal split? Proportional to estimated effort? Agent-decided? Probably agent-decided with equal-split default — the agent has context about relative complexity.
2. **Warning threshold** — At what percentage should conversations receive a "budget running low" warning? 80%? Configurable? Probably 80% default, configurable per tree.

## Phase 5: Scheduled Agent Execution

**Goal**: Agents can be triggered on a schedule (cron-like), enabling periodic work like backlog grooming, monitoring checks, and proactive task creation — breaking the purely reactive event-driven model.

**Depends on**: v2.8 complete

**Context**: The current model is purely reactive: external event → EventRouter → conversation. But domain-expert agents (v3.0) need periodic execution: PO grooms the backlog weekly, monitoring agent checks metrics daily, QA runs regression suites on schedule. No mechanism exists for time-based triggers. pg-boss (already used for timeout scheduling) provides the foundation. The Proactive Task Creation expansion path depends on this capability.

### Requirements

| ID | Requirement |
|---|---|
| SCH-01 | Schedule trigger type — agents declare `schedule` triggers in definition.yaml alongside event triggers |
| SCH-02 | Cron expression support — standard cron syntax (e.g., `"0 9 * * MON"` for Monday 9am). Validated at definition load time |
| SCH-03 | Schedule registration — on startup, worker loop registers pg-boss scheduled jobs for all agents with schedule triggers |
| SCH-04 | Synthetic event — when a schedule fires, pg-boss job creates a synthetic `IncomingEvent` with type `schedule.triggered` and metadata (schedule name, last run time, last run outcome). EventRouter processes it like any other trigger |
| SCH-05 | Overlap prevention — configurable per-schedule: `skip` (drop if previous run still active) or `queue` (wait for completion then start). Default: `skip` |
| SCH-06 | Schedule context injection — scheduled conversations receive context about why they were triggered: schedule name, last run timestamp, last run outcome summary, time since last run |
| SCH-07 | Manual trigger — API endpoint and dashboard button to manually fire a scheduled agent (for testing and ad-hoc execution) |
| SCH-08 | Schedule visibility in dashboard — active schedules, next run time, last run status, run history |

### Success Criteria

1. An agent with `schedule: "0 9 * * MON"` starts a new conversation every Monday at 9am with schedule context
2. If the previous scheduled run is still active when the next fires, the new run is skipped (with a logged event)
3. Manual trigger from dashboard starts the agent immediately with schedule context
4. Schedule status and history are visible in the dashboard

### Open Design Questions

1. **Timezone** — Cron expressions need a timezone. Default to UTC? Server timezone? Configurable per-schedule? Probably UTC default with optional `timezone` field.
2. **Definition.yaml format** — Probably a `schedules` array alongside `triggers`:
   ```yaml
   schedules:
     - name: weekly-grooming
       cron: "0 9 * * MON"
       overlap: skip
       timezone: UTC
   ```
3. **Schedule vs trigger coexistence** — An agent can have both event triggers and schedules. Same agent, different conversation types. The schedule context tells the agent why it was started.

## Phase 6: Sub-Agent Discovery

**Goal**: Orchestrators select sub-agents by capability description rather than hardcoded YAML references — enabling dynamic sub-agent selection as the sub-agent pool grows in v3.0.

**Depends on**: v2.8 complete

**Context**: Sub-agents are currently hardcoded in the orchestrator's `subAgents` YAML map. This works with 3 sub-agents (coder, researcher, tester) but v3.0 will introduce many more per role. Each new sub-agent requires YAML changes and prompt updates to every orchestrator that might use it. The entity directory provides the pattern (capability-based discovery) but sub-agents are excluded from the directory (they're internal workers, not peers). This phase creates a parallel discovery mechanism for sub-agents.

### Requirements

| ID | Requirement |
|---|---|
| DISC-01 | Sub-agent capabilities field — sub-agent definitions include `capabilities` (same format as orchestrator capabilities in directory) |
| DISC-02 | Sub-agent registry — internal registry of sub-agents queryable by capability, separate from the entity directory |
| DISC-03 | Capability-based spawn — `coordination:spawn_agent` accepts either a hardcoded agent ID (backward compatible) or a `capability` parameter that resolves to the best-matching sub-agent |
| DISC-04 | Registry seeding — sub-agent capabilities seeded from YAML at startup, alongside orchestrator directory seeding |
| DISC-05 | Semantic matching — reuse pgvector embedding pipeline from knowledge/directory for capability matching |
| DISC-06 | Orchestrator prompt simplification — orchestrators describe the capability they need ("I need code written" vs "spawn coder"). Prompt guidance teaches capability-based reasoning |
| DISC-07 | Fallback behavior — if no sub-agent matches the capability query, return empty result. Agent decides: do the work itself, try a different capability description, or signal inability |

### Success Criteria

1. An orchestrator calls `spawn_agent` with `capability: "write production-quality code"` and the registry resolves to the coder sub-agent
2. Adding a new sub-agent (e.g., "migration-planner") requires only the new sub-agent's definition.yaml — no changes to orchestrator definitions or prompts
3. Existing hardcoded `spawn_agent(agentId: "coder")` calls continue to work unchanged
4. The registry returns relevant matches even with imprecise capability descriptions

### Open Design Questions

1. **Registry storage** — Same `entity_directory` table with a `tier: 'sub-agent'` discriminator, or separate table? Separate table is cleaner conceptually (different lifecycle, different visibility), same table is simpler operationally (shared embedding pipeline).
2. **Scoping** — Should orchestrators only discover sub-agents listed in their `subAgents` YAML? Or any sub-agent in the system? Probably any — the YAML list becomes optional (backward compat), and discovery is open. The agent's judgment determines what's appropriate.
3. **Multiple matches** — When multiple sub-agents match a capability, return ranked list? Or just the best match? Probably best match — the orchestrator doesn't need to choose between sub-agents, just describe what it needs.

## Phase 7: Persistent Agent Identity

**Goal**: Agents maintain coherent, evolving understanding across conversations through structured identity documents — not scattered knowledge entries but maintained mental models that represent what the agent knows about its domain.

**Depends on**: v2.8 complete (knowledge system stabilized)

**Context**: Knowledge entries are atoms: individual facts with types and expiry. But domain-expert agents (v3.0) need something fundamentally different — maintained documents that represent ongoing understanding. A product agent's product brief, a dev agent's architectural model, a QA agent's quality baseline. These aren't individual facts — they're structured documents the agent reads at conversation start and updates at conversation end. Without this, agents rediscover context every conversation. Knowing 50 individual facts isn't the same as having a coherent mental model.

### Requirements

| ID | Requirement |
|---|---|
| IDN-01 | Identity document table — structured, versioned documents scoped to an agent role (not a conversation). Schema: agent_id, document_type, content (text), version, updated_at, token_count |
| IDN-02 | Document types — extensible set: `product_brief`, `architectural_model`, `stakeholder_map`, `domain_knowledge`, `working_context`, `learned_preferences`. New types addable without schema change |
| IDN-03 | Context injection — relevant identity documents injected into the system prompt at conversation start. The agent begins every conversation with its accumulated understanding |
| IDN-04 | `identity:update` tool — agents update their identity documents at conversation end (or mid-conversation for important discoveries). Appends a new version; old versions retained |
| IDN-05 | `identity:read` tool — agents can explicitly read their identity documents (beyond the auto-injected version at start) for refresh during long conversations |
| IDN-06 | Document versioning — every update creates a new version. Full history retained for audit and rollback |
| IDN-07 | Size management — identity documents have configurable token limits per type. When approaching the limit, the agent is prompted to summarize/compress before the next update |
| IDN-08 | Dashboard visibility — identity documents viewable and version-comparable in the dashboard. Operators can see how an agent's understanding evolved over time |
| IDN-09 | Graceful degradation — if identity documents fail to load, conversation starts without them (higher context cost, not a hard failure) |

### Success Criteria

1. A product-agent that has worked on 10 conversations has a `product_brief` document that reflects accumulated understanding, not just the last conversation
2. A new conversation for the same agent starts with its identity documents injected, and the agent demonstrates awareness of prior context without explicit knowledge queries
3. An operator can view the evolution of an agent's identity document over time in the dashboard, comparing versions
4. Identity documents survive independently of conversation lifecycle — they persist even when all conversations are complete

### Open Design Questions

1. **Injection scope** — Inject all identity documents at conversation start, or only relevant ones? For v1, inject all — the agent's identity is its identity. If token cost becomes a problem, add selective injection later.
2. **Update trigger** — Should the agent be explicitly prompted to update identity documents at conversation end, or is it purely agent-initiated? Probably both — system prompt guidance says "update your identity documents when you learn something significant", plus the executor could inject a reminder before conversation completion.
3. **Relationship to knowledge entries** — Identity documents are the agent's maintained understanding. Knowledge entries are shared facts for the swarm. An agent might store a discovery as a knowledge entry (shared) AND update its architectural model identity document (personal). Both are valid — different purposes.
4. **Multi-agent identity** — If two instances of dev-agent run simultaneously, they share identity documents. Conflict resolution? Last-write-wins with version history is probably sufficient for v1 — identity updates are infrequent (conversation end, not every tool call).

## Phase 8: Knowledge Retrieval Enhancement

**Goal**: The knowledge retrieval pipeline becomes a pluggable abstraction with per-agent configuration, and long conversations preserve knowledge before context compaction — setting the foundation for v3.0 domain-expert agents to declare retrieval strategies tailored to their workload.

**Depends on**: v2.8 complete (knowledge system stabilized)

**Context**: v2.7 shipped the knowledge system with pure pgvector cosine similarity search. All agents get the same retrieval pipeline regardless of domain. Competitive research (OpenClaw) revealed that different agent roles benefit from different retrieval strategies: keyword-heavy for exact tokens (function names, error codes), semantic-heavy with temporal decay for evolving priorities, diversity-optimized for broad coverage. Rather than implementing specific strategies before v3.0 role analysis reveals which ones matter, this phase creates the pluggable pipeline and per-agent configuration — the seams v3.0 fills with concrete implementations.

Separately, the history compaction system (Haiku summarization) can discard context without giving agents a chance to persist important knowledge. Pre-compaction flush addresses this gap.

### Requirements

| ID | Requirement |
|---|---|
| KR-01 | Retrieval strategy abstraction — pluggable pipeline interface that accepts a query and agent config, returns ranked results. Current vector search refactored as the default strategy implementation |
| KR-02 | Per-agent retrieval config in definition.yaml — agents declare retrieval preferences (strategy selection, weights, feature flags) in their definition. Schema designed against known strategy interfaces: vector, keyword, temporal decay, diversity |
| KR-03 | Strategy registry — strategies registered by name, resolved at query time from agent config. New strategies addable without changing the pipeline code |
| KR-04 | Score fusion interface — when multiple strategies are enabled, scores are combined via configurable weights. Designed for hybrid retrieval (e.g., vector + keyword) even though only vector ships initially |
| KR-05 | Pre-compaction knowledge flush — before history compaction, inject a turn prompting the agent to persist important knowledge via `store_knowledge`. Uses existing auto-supersede deduplication |
| KR-06 | Flush safeguards — flush count tracking prevents double-flushing. Flush is skipped if agent has no knowledge tools. Agent responds with a sentinel if nothing to store |
| KR-07 | Backward compatibility — agents without retrieval config in YAML use the current vector-only pipeline with existing behavior. No changes to existing agent definitions required |
| KR-08 | Config validation — retrieval config validated at definition load time via Zod. Invalid strategy references or weight configurations fail fast at startup |

### Success Criteria

1. Current vector search works identically when no retrieval config is specified in the agent definition
2. An agent definition can declare retrieval preferences and the pipeline routes through the configured strategy
3. A new retrieval strategy can be added by implementing the strategy interface and registering it — no pipeline code changes required
4. Before history compaction, the agent is prompted to store knowledge, and stored entries survive compaction
5. Pre-compaction flush is skipped cleanly for agents without knowledge tools

### Open Design Questions

1. **Config schema shape** — Flat weights (`vector_weight: 0.7, keyword_weight: 0.3`) or nested strategy blocks (`strategies: [{ type: "vector", weight: 0.7 }]`)? Nested is more extensible but heavier for v1 where only one strategy exists.
2. **Flush prompt content** — How directive should the flush prompt be? "Store anything important" vs "Review the conversation for discoveries, decisions, and context that should persist beyond this conversation." The latter gives the agent judgment criteria rather than a vague instruction.
3. **Flush tool restriction** — During the flush turn, should the agent only have access to `store_knowledge` (prevent side effects) or its full tool set? Restricted is safer — the flush is a focused operation, not a general agent turn.

## Design Constraints

- Nothing ships until the milestone is complete — all 8 phases land together. Phases can assume later phases will exist; no need for intermediate shippability.
- All capabilities must be additive — v2.7's existing delegation, knowledge, and directory systems continue working unchanged
- Each phase should be independently valuable — if v2.9 is interrupted, completed phases are still useful
- Backward compatibility with hardcoded patterns (sub-agent YAML, accept/reject handshake, per-conversation budgets) while enabling dynamic alternatives
- New tools follow existing namespace conventions: `task:*` for delegation, `coordination:*` for sub-agents, `identity:*` for identity documents
- Phases 7 and 8 both inject agent turns at lifecycle boundaries (identity update before completion, knowledge flush before compaction). Whichever is built first should establish the general lifecycle hook mechanism so the other plugs into it rather than duplicating the pattern
- Do not deepen per-agent external identities — no new per-agent bot users, no agent-specific integration configurations. Unified external identity is a v3.0 target (see design vision)

## Dependency Graph

```
Phase 1: Richer Negotiation ──→ Phase 2: Parallel Delegation ──→ Phase 4: Tree-Level Token Budgets

Phase 3: Transparent Materialization (independent)

Phase 5: Scheduled Agent Execution (independent)

Phase 6: Sub-Agent Discovery (independent)

Phase 7: Persistent Agent Identity (independent)

Phase 8: Knowledge Retrieval Enhancement (independent)
```

Phase 1 → 2 → 4 is sequential (each builds on the previous). Phases 3, 5, 6, 7, and 8 are independent of each other and of the negotiation chain — they can run in any order or in parallel with the sequential chain.
