# Milestone v3.0: Domain Modeling

**Status:** Vision
**Scope:** Transform agents from generic task processors into domain-expert professionals. Deep role analysis drives agent architecture, sub-agent design, tool requirements, and prompt engineering. Every agent should perform its role the way a world-class professional would — understanding context, making judgment calls, and producing high-quality artifacts.

**Predecessor:** v2.9 (Platform Completion) — all infrastructure capabilities in place
**Successor:** v3.1 (Human Collaboration) — formal human-agent collaboration protocols

---

## Philosophy

v2.2 through v2.9 built the stage. v3.0 builds the actors.

The shift is fundamental. Previous milestones asked "what capabilities does the platform need?" v3.0 asks "what does a world-class Product Owner actually do, and how do we build an agent that does it?"

This means:

- **Role analysis before architecture** — understand the domain deeply before writing any code. Map real-world workflows, identify decision points, catalog the artifacts professionals produce.
- **Tool-driven capability** — agents are only as capable as their tools allow. An agent that "should analyze dependencies" but has no dependency analysis tool will hallucinate or fail. Tool design is the primary engineering work.
- **Prompt-driven intelligence** — the system prompt is where domain expertise lives. Identity documents (v2.9) provide persistent context; the prompt defines how the agent thinks, reasons, and judges. This is the primary design work.
- **Iterate from real usage** — dogfood agents against real tasks. Observe where they make bad decisions, where they lack context, where they need tools they don't have. The feedback loop from real work is faster than abstract design.
- **Leverage the full platform** — every mechanism from v2.2–v2.9 is available: delegation, knowledge, directory, scheduling, identity documents, parallel delegation, sub-agent discovery. Agents should use them naturally, not as afterthoughts.

---

## Approach

For each agent role:

1. **Role Analysis** — What does this professional do? What decisions do they make? What artifacts do they produce? What do they need to know? Who do they talk to? What are their boundaries?

2. **Workflow Mapping** — Break the role into discrete workflows (e.g., PO: discovery, prioritization, specification, stakeholder management). Each workflow has inputs, outputs, decision points, and collaboration needs.

3. **Architecture Design** — Which workflows are the orchestrator's responsibility vs. sub-agent work? What tools does each need? What identity documents should the agent maintain? What schedules should it run on?

4. **Implementation** — Build sub-agents, tools, prompts. Leverage sub-agent discovery (v2.9) so new sub-agents are automatically available to orchestrators.

5. **Validation** — Run against real-world scenarios. Measure quality of decisions, not just completion. Iterate on prompts, tools, and architecture based on observed behavior.

## Agent Roles

### Product Agent

**Current state:** Requirement gatherer that creates Linear issues from Slack conversations. Knows nothing about the product, users, business context, or strategic priorities.

**Target state:** A domain-expert Product Owner that understands the product, users, and business. Capable of the full PO workflow:

- **Discovery** — monitors support channels, analyzes usage patterns, synthesizes user feedback, identifies problems worth solving. Not waiting for someone to ask — proactively surfacing opportunities.
- **Prioritization** — maintains a ranked backlog based on impact, effort, strategic alignment, and dependencies. Can articulate why item A is above item B. Queries dev-agent for technical cost estimates.
- **Specification** — turns vague ideas into structured requirements with acceptance criteria, edge cases, scope boundaries, and success metrics. Knows when a spec is ready for implementation and when it needs more discovery.
- **Stakeholder management** — communicates progress, manages expectations, negotiates scope. Knows when to push back ("that's a 3-week feature, not a quick fix") and when to accommodate.
- **Product knowledge** — maintains deep, persistent understanding of the product domain via identity documents. Knows why feature X exists, what user segment Y cares about, what the competitive landscape looks like, what tech debt constrains.

**Potential sub-agents:**
- `spec-writer` — takes rough notes/discussion and produces structured requirement documents
- `discovery-researcher` — monitors channels, analyzes data, produces insight summaries
- `market-analyst` — researches competitive landscape and industry trends
- `user-research-synthesizer` — aggregates and patterns user feedback

**Tool needs:**
- Support channel monitoring (Slack history search, ticket pattern analysis)
- Backlog management (Linear queries with filtering, batch operations, priority reordering)
- Product brief maintenance (identity documents)
- Analytics integration (usage data, feature adoption metrics) — future integration
- Stakeholder communication (reply/ask/notify already exist)

**Identity documents:**
- `product_brief` — what the product is, who uses it, core value proposition, roadmap context
- `stakeholder_map` — key people, their interests, communication preferences
- `domain_knowledge` — accumulated understanding of the problem space

**Scheduled work:**
- Weekly backlog grooming (review, re-prioritize, close stale items)
- Support channel synthesis (periodic analysis of recent support patterns)

### Dev Agent

**Current state:** Receives ticket, writes code, opens PR. No investigation, no risk assessment, no architectural judgment.

**Target state:** A senior developer that investigates before committing, identifies risks proactively, and makes architectural decisions:

- **Investigation** — explores codebase, understands existing patterns, identifies risks before writing code. Spawns researcher for deep dives. Checks shared memory for prior discoveries about this area.
- **Implementation** — writes production-quality code with appropriate tests and documentation. Delegates to coder sub-agent with clear context. Reviews sub-agent output before committing.
- **Review** — reviews code changes (own and others') with domain context. Identifies issues beyond style — architectural concerns, security implications, performance risks, missing edge cases.
- **Architecture** — proposes improvements when patterns emerge. Raises tech debt concerns proactively. Stores architectural decisions in shared knowledge.
- **Scope management** — pushes back when requirements are unclear or scope is too large. Asks product-agent for clarification via delegation rather than guessing.

**Potential sub-agents:**
- `coder` — existing, but should evolve to produce higher-quality output
- `researcher` — existing, but should be deeper (dependency analysis, impact assessment)
- `tester` — existing, but should be smarter about what to test
- `code-reviewer` — reviews diffs with domain context and architectural awareness
- `dependency-analyzer` — analyzes dependency trees, identifies risks, suggests updates
- `migration-planner` — plans data/API migrations with rollback strategies
- `security-reviewer` — identifies security implications of code changes

**Tool needs:**
- Deeper codebase analysis (AST-level search, dependency graphs, call hierarchy)
- Git history analysis (who changed this, when, why — blame + log integration)
- Performance profiling (basic benchmarking before/after changes)
- Security scanning (dependency vulnerabilities, common patterns)
- Test coverage analysis (what's tested, what isn't, where are the gaps)

**Identity documents:**
- `architectural_model` — how the codebase is structured, key patterns, where the dragons are
- `domain_knowledge` — accumulated understanding of the codebase and its conventions
- `learned_preferences` — what approaches work well in this codebase, common pitfalls

### QA Agent

**Current state:** Runs tests, checks PR diff against delegation brief. Thin validation vehicle from v2.7.

**Target state:** A quality engineer that understands risk and designs test strategies:

- **Risk assessment** — analyzes what changed and determines appropriate testing depth. Not everything needs full e2e — a typo fix needs a smoke test, an auth change needs comprehensive security testing.
- **Test strategy** — selects testing approach based on change characteristics. Unit, integration, e2e, manual verification, performance testing — each has its place.
- **Regression detection** — identifies patterns in test failures across time. "This module has failed 3 times in the last week" is actionable insight.
- **Non-functional validation** — performance implications (did the change add N+1 queries?), security surface (did we expose a new endpoint?), accessibility.
- **Quality reporting** — communicates quality status to stakeholders with context, not just pass/fail. "Tests pass but I noticed the response time doubled" is more valuable than "all green."

**Potential sub-agents:**
- `regression-analyst` — analyzes historical test data for patterns
- `performance-tester` — runs benchmarks, identifies performance regressions
- `security-scanner` — focused security analysis of changes

**Tool needs:**
- Test runner integration (run specific test suites, parse output, extract coverage)
- Coverage analysis (what's covered, what isn't, coverage diff for the change)
- Performance benchmarking (before/after comparison)
- Historical test data (past failures, flaky tests, common failure patterns)

**Identity documents:**
- `quality_baseline` — what the test suite covers, known flaky areas, historical failure patterns
- `domain_knowledge` — understanding of which areas are risk-prone and why

### New Roles (candidates for v3.0 or future)

**Docs Agent** — maintains documentation as code changes. Identifies stale docs, writes API docs, ensures README freshness. Triggered by PR merges that change public interfaces. Could be a sub-agent of dev-agent or a standalone orchestrator.

**DevOps/Deploy Agent** — manages deployment pipelines, environment health, release management. Monitors CI status, manages release branches, coordinates deployment windows. Needs: CI/CD integration tools, environment health checks, deployment automation.

**Security Agent** — monitors dependencies for vulnerabilities, scans for security anti-patterns, reviews access patterns. Scheduled execution for periodic audits, triggered by dependency updates. Needs: vulnerability database access, SAST tools, dependency analysis.

**Support Agent** — triages incoming support requests, identifies known issues, routes to appropriate teams or agents. Monitors support channels, matches problems to existing documentation or known bugs. Needs: support channel integration, documentation search, issue matching.

The decision on which new roles to implement should be driven by real workflow gaps, not speculation. Each role is a significant investment in design, tools, and validation.

## Domain Action Primitives

As agents are built for their domains, patterns will emerge where integration-specific tools can be unified into domain-language primitives. The decision to unify should be data-driven:

**Unify when:** The interface is genuinely isomorphic across integrations. Communication worked because text + destination is universal — `reply()` maps cleanly to Slack, Linear, email.

**Keep separate when:** Integration-specific capabilities would be lost in abstraction. Linear cycles vs Jira sprints have different semantics. GitHub draft PRs vs GitLab merge request approvals have different workflows. Forcing these into `code:create_review` loses important capabilities.

**The approach:** As v3.0 agents are built, catalog every action tool they use. After each role is implemented, analyze the tool surface for genuine isomorphism. Build domain primitives only where the abstraction is clean and lossless. Accept that some tools will remain integration-specific — that's a feature, not a bug.

## Cross-Session Learning

With persistent agent identity (v2.9) providing the storage, v3.0 adds the feedback loop:

- **Task outcomes** are recorded: success/failure, duration, token usage, quality assessment, what worked, what didn't
- **Patterns are surfaced**: "tasks in the auth module tend to need more research", "PRs over 500 lines get more review comments"
- **Identity documents are updated**: learned preferences and strategies accumulate in the agent's identity. The agent gets better at its job over time.
- **Prompt context adapts**: identity documents at conversation start include accumulated wisdom from past work

This is emergent — it develops as agents handle real tasks, not as upfront design. The first iteration will be simple: agents are encouraged (via prompt guidance) to update their `learned_preferences` identity document when they discover something useful. Automated pattern detection comes later if manual accumulation proves insufficient.

---

## Validation Approach

Domain modeling doesn't have a test suite in the traditional sense. Validation is:

1. **Real task execution** — give the agent real work and observe outcomes. Does the PO write good specs? Does the dev write good code? Does QA catch real bugs?
2. **Decision quality assessment** — not just "did it complete" but "did it make good decisions?" LLM-as-judge evaluation of agent reasoning and output quality.
3. **Workflow completeness** — can the agent handle the full workflow for its role, or does it fall back to "I don't know" on certain activities?
4. **Collaboration effectiveness** — do agents collaborate well? Does the PO give dev clear enough requirements? Does dev give QA enough context? Does the feedback loop actually improve outcomes?
5. **Iterative refinement** — each real task is a learning opportunity. What went wrong? What was missing? Fix the prompt, add the tool, update the identity document, try again.
