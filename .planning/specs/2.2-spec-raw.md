# v2.2 Agentic Architecture — Milestone Specification

## Goal

Replace the rigid LangGraph state machine architecture with an agentic tool-use loop where LLMs make control flow decisions. Agents reason about what to do, use tools to act, observe results, and adapt — instead of following a predetermined graph of nodes. Deliver a working end-to-end flow: Slack message → product agent gathers requirements → Linear issue → dev agent orchestrator researches, plans, gets approval, implements → PR ready for merge.

## Why This Matters

This is the architectural shift that makes Aesir's agents actually intelligent. v2.1 proved the plumbing works (events, integrations, containers, workflows). v2.2 replaces the brains. Every future capability — new agent types, cross-agent collaboration, multi-repo support — depends on agents that can reason, not agents that follow flowcharts.

## Problem Statement

The current agent architecture (shipped in v2.1) uses LangGraph to define fixed node-and-edge graphs that every task walks through identically. A README edit and a complex feature follow the same 8+ node pipeline through 16 hardcoded phases (`DevAgentPhaseSchema` in `packages/agents/src/dev-agent/workflow/state.ts`). The LLM generates content (plans, code) but never decides what to do next — `routeByPhase()` in `graph.ts` decides that via a switch statement mapping phases to nodes.

**Specific failures observed in v2.1 E2E testing:**
- Dev agent runs tests on documentation-only changes because the graph always routes through the verify node
- Agent gets stuck using the wrong package manager — the test-fix loop in `execute.ts` (lines 237-273) retries identically 3 times without LLM reasoning about the error. There's a TODO: "In future, use LLM to analyze and fix"
- Simple tasks require human approval of multi-step plans because there's no complexity-aware routing
- The execute node processes plan steps sequentially with no ability to reorder, skip, or adapt
- Classification responses outside expected patterns (approve/reject/guidance/question/abort/unclear) break the flow

**Root cause:** The architecture is a state machine that uses an LLM, not an LLM agent that has structure. Control flow is hardcoded in the graph topology and the 16-value `DevAgentPhase` enum, not emergent from reasoning.

**Additional technical limitation:** All LLM usage currently goes through `@langchain/anthropic` (`ChatAnthropic`) for text completion only. No LLM tool-use/function-calling exists anywhere in the codebase. The MCP integration layer (HTTP calls to integration services) is completely separate from LLM invocations — the LLM can't "see" or decide to use tools.

## End-to-End Flow: The Target Experience

This is the primary success scenario. Everything in this spec serves this flow.

### Scenario: "Add a health check endpoint to the API"

**Step 1: Feature Request (Slack → Product Agent)**
```
User posts in #product-requests:
  "@aesir we need a /healthz endpoint that returns service status
   including DB connectivity and uptime"
```

**Step 2: Smart Router**
```
Router receives: slack.app_mention.created
Router reasons: "New mention in product channel, not in existing thread.
  This is a feature request — route to product agent."
→ Starts Temporal workflow: product-agent-{threadTs}
```

**Step 3: Product Agent (agentic loop)**
```
Agent reads message, reasons:
  "This is a clear, specific request. I have: what (health endpoint),
   why (service status monitoring), acceptance criteria (DB check, uptime).
   This is complete enough to create an issue."

→ tool: search_issues({ query: "health check endpoint" })
  Result: No duplicates found

Agent reasons: "No duplicates. I'll draft the issue and confirm."

→ tool: send_message({
    channel: "C_product_requests",
    thread_ts: "1706...",
    text: "I'll create a task for this. Here's what I have:

      **Add /healthz endpoint with service status**
      - GET /healthz returns { status, db, uptime }
      - Checks PostgreSQL connectivity
      - Returns 200 if healthy, 503 if degraded

      Priority: Medium

      Does this look right, or should I adjust anything?"
  })

→ Temporal signal wait (user reply)

User replies: "looks good, go ahead"

Agent reasons: "User confirmed. Create the issue."

→ tool: create_issue({
    title: "Add /healthz endpoint with service status",
    description: "...",
    priority: "medium",
    labels: ["enhancement"]
  })
  Result: { id: "ABC-123", identifier: "AES-42" }

→ tool: send_message({
    thread_ts: "...",
    text: "Created AES-42. I've assigned it to the dev agent."
  })

Agent: done. Phase = "complete".
```

**Step 4: Event Handoff**
```
Linear webhook fires: linear.agent_session.created (issue AES-42 assigned to agent)
Smart router: "Linear issue assigned to agent → start dev agent workflow"
→ Starts Temporal workflow: dev-agent-AES-42
```

**Step 5: Dev Agent Orchestrator — Research & Plan (Temporal Activity 1)**
```
Orchestrator reads issue via MCP:
→ tool: get_issue({ issueId: "AES-42" })
  Result: { title: "Add /healthz endpoint...", description: "..." }

Orchestrator reasons: "I need to understand the existing codebase structure
  before planning. Let me spawn a researcher."

→ tool: spawn_agent("researcher", {
    task: "Research how to add a /healthz endpoint to the API",
    context: {
      issueTitle: "Add /healthz endpoint with service status",
      issueDescription: "...",
      repoStructure: "Express-based services, see packages/*/src/main.ts"
    }
  })

  Researcher agent (fresh context, focused):
    → read_file("package.json") — identifies project structure
    → list_directory("packages/") — sees service layout
    → search_codebase("health") — finds existing health checks
    → read_file("packages/integrations/linear/src/main.ts") — sees health pattern
    → read_file("packages/integrations/github/src/main.ts") — confirms pattern
    → read_file("packages/platform/src/db/connection.ts") — understands DB setup

    Returns: {
      summary: "All integration services have GET /health returning
        { status: 'ok', service: name }. Pattern is in main.ts of each.
        DB connection is via drizzle-orm with postgres.js driver.
        No existing /healthz — only simple /health without DB check.",
      relevantFiles: ["packages/integrations/linear/src/main.ts", ...],
      patterns: ["Express app with app.get('/health', ...)"],
      conventions: "Health checks return JSON, use service name identifier"
    }

Orchestrator receives research, reasons:
  "Clear pattern exists. Small change — add a /healthz route alongside /health.
   Need DB connectivity check. I'll plan this myself, no need for complex breakdown."

Orchestrator produces plan:
  "1. Add /healthz handler to dev-agent main.ts (packages/agents/src/dev-agent/main.ts)
   2. Add DB connectivity check using existing drizzle connection
   3. Return { status, db: { connected, latencyMs }, uptime: process.uptime() }
   4. Add test for the endpoint

   This is a straightforward change. Tests needed: unit test for handler logic."

→ tool: request_approval({
    channel: "C_dev_agent_slack",
    plan: "...",
    issueId: "AES-42",
    complexity: "low"
  })
```

**Step 6: Human Approval (Temporal Signal Wait)**
```
Slack message appears with plan + Approve/Reject buttons.
Human clicks Approve.

→ Temporal signal: planApprovalSignal({ approved: true })
→ Cross-channel sync: Linear comment posted with approval
```

**Step 7: Dev Agent Orchestrator — Execution (Temporal Activity 2)**
```
Orchestrator loads context summary from DB (what was researched, what was planned).

Orchestrator reasons: "Plan approved. This is a small feature, I'll spawn
  a coder with the plan and relevant file context."

→ tool: spawn_agent("coder", {
    task: "Implement /healthz endpoint",
    plan: [...steps from plan],

      "packages/agents/src/dev-agent/main.ts": "...(contents)...",

  Coder agent (fresh context):
    → read_file("packages/agents/src/dev-agent/main.ts") — reads current code

    → write_file("packages/agents/src/dev-agent/api/health.test.ts", new) — adds tests

      filesChanged: ["main.ts", "api/health.ts", "api/health.test.ts"],
      summary: "Added /healthz endpoint with DB connectivity check and uptime.
        Extracted to separate handler file following existing patterns.
        Added unit tests with mocked DB."
    }

Orchestrator receives result, reasons:
  "Coder done. Files changed include a test file. Let me run the tests."

→ tool: spawn_agent("tester", {
    task: "Run tests for the health endpoint changes",
    changedFiles: ["api/health.ts", "api/health.test.ts"],
    projectInfo: { packageManager: "pnpm", testRunner: "vitest" }
  })

  Tester agent (fresh context):
    → run_command("pnpm test packages/agents/src/dev-agent/api/health.test.ts")
    → Result: 3 tests passed

    Returns: { passed: true, output: "3 tests passed", failures: [] }

Orchestrator reasons: "Tests pass. Create the PR."

→ tool: create_branch({ branch: "feature/aes-42-healthz-endpoint", from: "main" })
→ tool: create_commit({
    files: [...changed files],
    message: "feat: add /healthz endpoint with DB connectivity check\n\nCloses AES-42"
  })
→ tool: create_pull_request({
    title: "feat: add /healthz endpoint with DB connectivity check",
    body: "## Summary\n- Adds GET /healthz...\n\nCloses AES-42",
    branch: "feature/aes-42-healthz-endpoint"
  })
  Result: { number: 47, url: "https://github.com/org/repo/pull/47" }

→ tool: update_issue_status({ issueId: "AES-42", status: "In Review" })
→ tool: send_message({
    channel: "C_dev_agent_slack",
    text: "PR #47 created for AES-42: https://github.com/org/repo/pull/47"
  })

Orchestrator: done. Returns { prNumber: 47, prUrl: "..." }
```

**Step 8: PR Completion (Temporal Signal Wait)**
```
Human reviews PR, merges.
GitHub webhook: github.pull_request.merged
→ Temporal signal: prCompletionSignal({ merged: true })

Completion activity:
  → update_issue_status("AES-42", "Done")
  → send_message("PR #47 merged. AES-42 complete.")
  → stop_container(containerId)
```

**Total: Slack message → merged PR, with human in the loop only for approval.**

## Architecture Overview

```
External Events (Slack, Linear, GitHub webhooks)
        │
        ▼
Smart Router (LLM-based classifier — lightweight agentic loop)
        │
        ├── Product Agent (agentic loop + Temporal for conversation durability)
        │       └── Creates Linear issues → event-driven handoff to dev agent
        │
        └── Dev Agent Orchestrator (agentic loop + Temporal for approval gates)
                ├── Spawns Researcher agent (fresh context, read-only tools)
                ├── Spawns Coder agent (fresh context, read+write tools)
                └── Spawns Tester agent (fresh context, run+read tools)

All agents share:
  - Agentic tool-use loop runtime (LLM + tools, no fixed graph)
  - Temporal workflows for durability, signals, timeouts
  - Context summaries persisted to PostgreSQL at boundaries
  - Execution traces for every tool call
  - Guardrails (iteration limits, cost budgets, sandbox enforcement)
```

## What Changes vs. v2.1

| Component | v2.1 (Current) | v2.2 (Target) |
|-----------|----------------|---------------|
| LLM SDK | `@langchain/anthropic` (text completion only) | `@anthropic-ai/sdk` (native tool-use/function-calling) |
| Agent logic | LangGraph fixed node graphs (13 nodes dev, 6 nodes product) | Agentic tool-use loops |
| Control flow | `routeByPhase()` switch statement + 16-phase enum | LLM decides next action each iteration |
| Event routing | Hardcoded event-type → handler in `events.ts` | LLM-based smart router |
| Dev agent | Single graph, all context in one window | Orchestrator + focused sub-agents with separate context |
| Product agent | 6 fixed nodes (classify→analyze→clarify→confirm→create→notify) | Single agentic loop, adapts to input clarity |
| State | LangGraph `PostgresSaver` checkpoints (serialized graph state) | Semantic context summaries (LLM-generated JSONB) |
| Error recovery | 3 blind retries in `execute.ts` → escalate | LLM reads error, diagnoses, fixes or tries different approach |
| Test decisions | Always runs (verify node) unless hardcoded docs-only skip | LLM decides if/how to test based on task reasoning |
| Classification | `withStructuredOutput` on `ChatAnthropic` for approval intents | Subsumed by smart router (same LLM reasoning, broader scope) |
| Dependencies | `@langchain/langgraph`, `@langchain/langgraph-checkpoint-postgres`, `@langchain/core`, `@langchain/anthropic` | `@anthropic-ai/sdk` (direct), keep `@temporalio/*` |

## Detailed Requirements

### 1. Agentic Tool-Use Loop Runtime

The core execution primitive replacing LangGraph. This is the foundation everything else builds on.

**What it is:** A function that takes a system prompt, a set of tool definitions, and an initial message — then loops: send to LLM → LLM responds with tool calls → execute tools → feed results back → repeat until LLM says done or guardrail limit hit.

**Implementation approach:** Use Anthropic's native tool-use API (`@anthropic-ai/sdk`) directly. The current `@langchain/anthropic` wrapper adds complexity without value for tool-use loops. The Anthropic SDK's `messages.create()` with `tools` parameter is purpose-built for this pattern.

**Interface:**
```typescript
interface AgentLoopOptions {
  systemPrompt: string;
  tools: ToolDefinition[];       // Zod schemas → Anthropic tool format
  initialMessage: string;        // The task to accomplish
  context?: string;              // Additional context (e.g., previous phase summary)
  model?: string;                // Default: claude-sonnet-4-20250514
  maxIterations?: number;        // Default: 50
  maxTokenBudget?: number;       // Total input+output tokens allowed
  onToolCall?: (call: ToolCall) => void;    // For tracing
  onResponse?: (response: LLMResponse) => void; // For tracing
  abortSignal?: AbortSignal;     // For cancellation
}

interface AgentLoopResult {
  status: "completed" | "max_iterations" | "max_tokens" | "aborted" | "error";
  output: string;                // Final LLM message
  structuredOutput?: unknown;    // If final message includes structured data
  toolCallCount: number;
  tokenCount: { input: number; output: number };
  trace: TraceStep[];           // Full execution history
}

interface ToolDefinition {
  name: string;
  description: string;
  inputSchema: ZodSchema;       // Zod schema, converted to JSON Schema for Anthropic
  execute: (input: unknown) => Promise<ToolResult>;
}

interface ToolResult {
  content: string;              // Text result fed back to LLM
  isError?: boolean;            // If true, LLM sees this as an error to reason about
}
```

**Behaviour:**
- Each iteration: send conversation history to LLM → receive response
- If response contains `tool_use` blocks → execute each tool → append results → next iteration
- If response contains only text (no tool calls) → agent is done, return result
- If iteration/token limit hit → return with `max_iterations`/`max_tokens` status and last state
- All tool calls and LLM responses recorded in trace

**Why not LangChain:** The current codebase uses `@langchain/anthropic` v0.3.0 for text completion. LangChain adds an abstraction layer over the Anthropic API that doesn't add value for tool-use loops and makes debugging harder. The Anthropic SDK's tool-use is well-documented, type-safe, and purpose-built. This also removes the `@langchain/core`, `@langchain/langgraph`, and `@langchain/langgraph-checkpoint-postgres` dependencies.

### 2. Agent Tool Library

Tools available to agents. Each tool is a `ToolDefinition` with a Zod input schema and an `execute` function.

**Codebase tools** (execute inside dev container via `DevContainerManager`):
- `read_file(path)` → file contents (or error if not found)
- `write_file(path, content)` → success/failure
- `search_codebase(pattern, glob?)` → matching lines with file paths
- `list_directory(path)` → directory listing
- `run_command(command)` → stdout + stderr + exit code

These tools wrap the existing `DevContainerManager` and `DevContainerGit` services. The container is already set up with the cloned repo, Node.js, pnpm, git, and gh CLI (Phase 24 infrastructure).

**Git tools** (via existing GitHub MCP):
- `create_branch(branch, from)` → success
- `create_commit(files, message)` → commit SHA
- `create_pull_request(title, body, branch)` → PR number + URL
- `get_pull_request(number)` → PR details
- `merge_pull_request(number)` → success/failure

**Integration tools** (via existing MCP layer, wrapped as `ToolDefinition`):
- Linear: `get_issue`, `create_issue`, `update_issue_status`, `list_teams`, `list_labels`
- GitHub: `get_repository`, `get_file_contents`, `list_files` (and git tools above)
- Slack: `send_message`, `reply_to_thread`, `send_approval_request`, `get_message`, `list_channels`

These call `callMcpTool()` from `packages/agents/src/shared/mcp/client.ts` internally — the MCP HTTP layer is unchanged. The tool definitions just wrap MCP calls with Zod schemas so the LLM can invoke them via native tool-use.

**Agent coordination tools** (orchestrator only):
- `spawn_agent(type, brief)` → agent result (runs a nested agentic loop with focused context and tools)
- `request_human_input(channel, message)` → signals Temporal to wait, returns when human responds

**Search/research tools** (optional, future):
- `web_search(query)` → search results
- `fetch_url(url)` → page content

### 3. Smart Router

Replaces the hardcoded event-type → handler mapping currently in `packages/agents/src/dev-agent/api/events.ts` and `packages/agents/src/product-agent/api/events.ts`.

**What it replaces:**
```typescript
// Current: hardcoded switch in dev-agent events.ts
switch (event.type) {
  case "linear.agent_session.created": → startWorkflow()
  case "linear.comment.created": → classifyAndSignal()
  case "slack.block_actions.approved": → signalApproval()
  // ...
}

// Current: hardcoded switch in product-agent events.ts
switch (event.type) {
  case "slack.app_mention.created": → startWorkflow()
  case "slack.message.created": → signalReply()
}
```

**What it becomes:** A lightweight agentic loop that receives events and reasons about routing.

**Router context (system prompt includes):**
- Available agent types and their purposes
- How to check for running workflows (Temporal client query)
- Signal types each workflow accepts
- Channel/source conventions (which Slack channels map to which agent)

**Router tools:**
- `query_running_workflows(taskId?)` → list of active workflow IDs and their current state
- `start_workflow(agentType, input)` → workflow ID
- `signal_workflow(workflowId, signal, payload)` → success
- `send_message(channel, text)` → for clarification

**Router decisions (currently hardcoded, now LLM-reasoned):**
- `slack.app_mention.created` → Is this a product request or a direct dev command? Context: channel, message content, user
- `linear.comment.created` → What's the intent? (Currently uses separate `classifyApprovalIntent()` with Claude — this gets folded into the router's reasoning)
- `slack.block_actions.*` → Which workflow to signal and with what payload
- `github.pull_request.*` → Which dev-agent workflow to signal
- `slack.message.created` in thread → Is this a reply to product agent, or a cancellation? (Currently checks hardcoded cancel phrases like "nevermind", "cancel", "nvm")

**Existing classification absorbed:** The approval intent classifier in `packages/agents/src/dev-agent/classification/approval.ts` (which already uses Claude with structured output) gets absorbed into the router. Same capability, unified system.

### 4. Dev Agent Orchestrator

Replaces the 13-node LangGraph graph defined in `packages/agents/src/dev-agent/workflow/graph.ts` and all nodes in `packages/agents/src/dev-agent/workflow/nodes/`.

**Orchestrator system prompt includes:**
- Agent identity and purpose ("You are a dev agent that implements Linear issues by writing code, running tests, and creating PRs")
- The issue details (title, description, acceptance criteria)
- Project conventions detected from prior research or codebase analysis
- Constraints ("You must get human approval before creating a PR", "All code runs in a sandboxed container", "You cannot merge your own PRs")
- Available tools and when to use them
- Sub-agent types and when to spawn them vs. do work directly

**Orchestrator tools:**
- Lightweight codebase tools: `read_file`, `search_codebase`, `list_directory` (enough to understand the task, not full implementation)
- `spawn_agent(type, brief)` — spawns researcher, coder, or tester with focused context
- Integration tools: `get_issue`, `update_issue_status`, `send_message`, `request_approval`
- Git tools: `create_branch`, `create_commit`, `create_pull_request`

**Sub-agents:**

| Agent | Purpose | Tools | Context |
|-------|---------|-------|---------|
| Researcher | Deep codebase exploration | `read_file`, `search_codebase`, `list_directory`, `run_command` | Task description, repo root |
| Coder | Implement changes | `read_file`, `write_file`, `search_codebase`, `run_command` | Plan, relevant files, conventions |
| Tester | Run and diagnose tests | `read_file`, `run_command`, `search_codebase` | Changed files, project info (package manager, test runner) |

**The orchestrator decides (things the graph currently hardcodes):**
- Whether research is needed: simple README → skip, complex feature → spawn researcher
- Plan granularity: trivial change → brief plan, complex change → detailed plan
- Whether to request approval: configurable per complexity/policy
- How to handle test failures: read error → diagnose → spawn coder with fix instructions vs. spawn tester for deeper analysis
- When to escalate: after reasoning about repeated failures, not after a fixed retry count
- Whether to create separate files vs. modify existing ones
- What test approach fits: unit tests, integration tests, or no tests for docs-only

**Temporal integration (replaces current activities):**

Current 9 activities in `worker.ts`:
```
runDevAgentGraphActivity → runs full LangGraph graph
continueAfterApprovalActivity → runs LangGraph from execute phase
handlePRFeedbackActivity → runs LangGraph for feedback
handleRePlanActivity → runs LangGraph for re-planning
stopContainerActivity → stops dev container
sendReminderActivity → sends Slack reminder
updateSlackApprovalActivity → updates Slack message
syncApprovalToLinearActivity → posts approval to Linear
completeTaskActivity → final cleanup
```

New activities:
```
runOrchestratorPreApproval → agentic loop: research + plan → returns plan
runOrchestratorPostApproval → agentic loop: execute + test + PR → returns PR details
handleOrchestratorFeedback → agentic loop: address PR feedback → returns updated files
stopContainerActivity → unchanged
sendReminderActivity → unchanged (or folded into orchestrator tools)
updateSlackApprovalActivity → folded into orchestrator tools
syncApprovalToLinearActivity → folded into orchestrator tools
completeTaskActivity → simplified, orchestrator handles most via tools
```

**Temporal workflow structure simplifies:**
```
1. Setup container (existing infrastructure)
2. Run pre-approval orchestrator loop → plan
3. Wait for approval signal (existing pattern, 24h/48h timeouts)
4. Run post-approval orchestrator loop → PR
5. Wait for PR completion signal (existing pattern, 7-day timeout)
6. On feedback signal → run feedback orchestrator loop → updated PR
7. Complete (update Linear, notify Slack, cleanup container)
```

The signal types (`planApprovalSignal`, `prFeedbackSignal`, `prCompletionSignal`, `escalationResolvedSignal`) stay the same. The workflow state machine simplifies because most transitions are now handled inside the agentic loop rather than as separate Temporal activities.

### 5. Product Agent

Replaces the 6-node LangGraph graph in `packages/agents/src/product-agent/workflow/graph.ts` and nodes in `packages/agents/src/product-agent/workflow/nodes/`.

**Current fixed pipeline:**
```
classify → analyzeRequirements → generateClarification → confirm → createTasks → notify
```

Every conversation walks all 6 nodes regardless of input clarity.

**New: single agentic loop** that adapts to the conversation:

**System prompt includes:**
- Agent identity ("You are a product agent that gathers requirements from Slack conversations and creates well-structured Linear issues")
- Full thread history (all messages in the conversation)
- Guidelines for good issues (vertical slices, clear acceptance criteria, appropriate sizing)
- When to ask clarifying questions vs. proceed
- How to detect cancellation intent

**Tools:**
- `send_message(channel, thread_ts, text)` — post in Slack thread
- `search_issues(query)` — check for duplicates in Linear
- `create_issue(title, description, priority, labels)` — create Linear issue
- `get_issue(issueId)` — read issue details (for context)

**Behaviour:**
- Clear request with all details → create issue immediately (1-2 tool calls, no forced clarification)
- Vague request → ask one focused question, wait for reply, continue
- User says "nevermind"/"cancel" → acknowledge and close (LLM recognizes intent, no hardcoded phrase list)
- Multi-issue request → create multiple issues, one at a time with confirmation
- Duplicate detection → tell user "this looks similar to AES-34, should I update that instead?"

**Temporal integration (same pattern as current):**
- Multi-turn conversation loop with `userReplySignal` waits between turns
- `cancelConversationSignal` for cancellation
- Same timeout handling (24h reminder, 72h total)
- Activity runs the agentic loop for one turn, returns response + phase indicator
- Current `maxIterations = 20` for conversation turns remains sensible

### 6. Context Management

Replaces LangGraph's `PostgresSaver` checkpoint persistence (which serializes the full graph state including all 16+ fields of `DevAgentState` at every node transition).

**New database table: `agents.context_snapshots`**

```sql
CREATE TABLE agents.context_snapshots (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  task_id TEXT NOT NULL,                    -- e.g., "AES-42"
  workflow_id TEXT NOT NULL,                -- Temporal workflow ID
  agent_type TEXT NOT NULL,                 -- "dev-orchestrator", "product", "researcher", etc.
  stage TEXT NOT NULL,                      -- "post-research", "post-approval", "post-execution"

  -- Semantic context (LLM-generated, flexible)
  summary TEXT NOT NULL,                    -- Natural language summary of work done
  completed_actions JSONB DEFAULT '[]',     -- What's been accomplished
  pending_intent TEXT,                      -- What the agent was about to do next
  known_issues JSONB DEFAULT '[]',          -- Problems encountered
  project_context JSONB DEFAULT '{}',       -- Detected: package manager, test runner, framework
  key_files JSONB DEFAULT '[]',             -- Important file paths
  research_findings JSONB,                  -- Structured research output (if applicable)
  plan JSONB,                               -- Approved plan (if applicable)

  -- Metadata
  tool_call_count INTEGER NOT NULL DEFAULT 0,
  token_count JSONB DEFAULT '{}',           -- { input, output }
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_context_snapshots_task ON agents.context_snapshots(task_id);
CREATE INDEX idx_context_snapshots_workflow ON agents.context_snapshots(workflow_id);
```

**New/updated table: `agents.tasks`**

For critical data that must be exact (not LLM-summarized):

```sql
CREATE TABLE agents.tasks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  task_id TEXT NOT NULL UNIQUE,             -- e.g., "AES-42"
  issue_id TEXT,                            -- Linear issue ID
  issue_identifier TEXT,                    -- e.g., "AES-42"
  agent_type TEXT NOT NULL,                 -- "dev" or "product"
  workflow_id TEXT,                         -- Temporal workflow ID
  status TEXT NOT NULL DEFAULT 'pending',   -- pending, researching, planning, approved, executing, complete, failed

  -- Critical structured data (not JSONB)
  container_id TEXT,
  branch_name TEXT,
  pr_number INTEGER,
  pr_url TEXT,
  approval_status TEXT DEFAULT 'pending',   -- pending, approved, rejected
  approval_feedback TEXT,

  -- Error tracking
  error TEXT,
  escalation_reason TEXT,

  -- Slack context
  slack_channel TEXT,
  slack_message_ts TEXT,                    -- For updating approval messages

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**When context is written:**
- End of each Temporal activity (orchestrator summarizes its work)
- Before spawning a sub-agent (orchestrator produces a focused brief)
- On error/escalation (capture full state for debugging/resumption)

**When context is read:**
- Start of post-approval activity (system prompt includes: "Here's what was decided before approval: {summary}")
- When orchestrator briefs a sub-agent (sub-agent gets only relevant context, not full history)
- When resuming after crash/restart (Temporal replays, activity reads latest snapshot)

**What this replaces:**
- `PostgresSaver` and `@langchain/langgraph-checkpoint-postgres` dependency
- `DevAgentState` Zod schema with 16 fixed fields
- `ProductAgentState` Zod schema
- `DevAgentPhaseSchema` enum (16 phases)
- `ProductAgentPhaseSchema` enum

### 7. Execution Tracing

Every tool call, LLM reasoning step, and sub-agent spawn logged for debugging and observability.

**Extends existing `observability.execution_events` table** (from `@aesir/observability`):

```sql
CREATE TABLE agents.execution_traces (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  task_id TEXT NOT NULL,
  workflow_id TEXT NOT NULL,
  agent_type TEXT NOT NULL,                 -- "dev-orchestrator", "researcher", "coder", etc.
  agent_instance_id TEXT NOT NULL,          -- Unique per agent invocation (for sub-agents)
  parent_agent_instance_id TEXT,            -- If this is a sub-agent, who spawned it
  step_number INTEGER NOT NULL,             -- Sequential within agent instance

  type TEXT NOT NULL,                       -- "tool_call", "tool_result", "llm_response", "agent_spawn", "agent_complete"
  tool_name TEXT,                           -- Which tool (null for LLM responses)
  input JSONB,                              -- Tool params or spawn context
  output JSONB,                             -- Tool result or agent result

  -- Cost tracking
  token_count_input INTEGER,
  token_count_output INTEGER,
  duration_ms INTEGER,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_execution_traces_task ON agents.execution_traces(task_id);
CREATE INDEX idx_execution_traces_instance ON agents.execution_traces(agent_instance_id);
```

**Tracing is automatic:** The agentic loop runtime calls `onToolCall` and `onResponse` callbacks on every step, which write to this table. No manual instrumentation in agent code.

### 8. Guardrails

Explicit safety boundaries replacing the implicit constraints of the graph topology.

| Guardrail | Value | Rationale |
|-----------|-------|-----------|
| Max tool calls per sub-agent | 50 | Prevent runaway loops in focused agents |
| Max tool calls per orchestrator | 100 | Orchestrator does less direct work, more delegation |
| Max tool calls for smart router | 10 | Router should decide quickly |
| Max token budget per task | Configurable (default: 500K) | Cost control across all agent invocations |
| Activity timeout | 30 min (dev), 5 min (product) | Existing Temporal timeouts, keep as-is |
| Sandbox enforcement | All `run_command` via `DevContainerManager` | No host access, existing infrastructure |
| Tool permissions | MCP permission tables (existing) | Agents can only use allowed MCP tools |
| No self-merge | Agents cannot call `merge_pull_request` | Human merges only |
| Escalation | 3 distinct approaches failed (not 3 identical retries) | LLM must try different approach each time |
| Container isolation | Existing Docker sandbox with network restrictions | Code execution cannot reach host |

**Configuration:** Guardrails configurable via environment variables or a config table, not hardcoded. The current `AgentConfig` in `packages/agents/src/shared/config/agent-config.ts` can be extended:

```typescript
interface AgentConfig {
  name: string;
  model: string;                    // Default: claude-sonnet-4-20250514
  temperature: number;              // Default: 0
  maxIterations: number;            // Default: 50 (was 10 for LangGraph)
  maxTokenBudget: number;           // New: total tokens per task
  orchestratorMaxIterations: number; // New: for orchestrator specifically
  routerMaxIterations: number;       // New: for router specifically
  requireApproval: boolean;          // New: can be disabled for trivial tasks
}
```

## Success Criteria

1. **End-to-end flow works:** Slack message → product agent → Linear issue → dev agent → approved PR — the full scenario described above
2. **README edit without tests:** Dev agent completes a docs-only change in under 10 tool calls, no test execution, no unnecessary research
3. **Simple feature with tests:** Dev agent implements a function, writes appropriate tests, runs them with the correct package manager (pnpm), creates PR
4. **Test failure recovery:** When tests fail, agent reads the error, diagnoses the cause (wrong command, missing dependency, actual code bug), and fixes it — not blind retry
5. **Product agent adapts to clarity:** Clear request → issue in 1-2 turns. Vague request → asks questions. No forced clarification pipeline.
6. **Smart router replaces hardcoded event handling:** All current event types routed correctly by LLM reasoning
7. **Context survives Temporal boundaries:** Agent resumes after approval wait with full understanding of what was researched and planned
8. **Sub-agents get focused context:** Coder agent gets plan + relevant files, not full research history. Researcher gets task description, not code changes.
9. **All tool calls traced:** Every step queryable in `agents.execution_traces` with correlation across sub-agents
10. **Guardrails enforced:** Loops terminate at limits. Commands execute only in sandbox. Cost tracked per task.
11. **No LangGraph dependency:** `@langchain/*` packages removed from agents, replaced with `@anthropic-ai/sdk`

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| LLM makes poor control flow decisions (wrong tool, wrong order) | Agent produces broken output or spins | Guardrails (iteration + cost limits), escalation with diagnosis, execution traces for debugging, system prompts with clear constraints |
| Context summaries lose critical information at boundaries | Agent resumes with incomplete understanding | Explicit DB columns for critical data (PR number, branch, issue ID). JSONB only for semantic context. Test boundary transitions specifically. |
| Higher LLM cost per task | More API calls than fixed graph | Cost budgets per task. Simple tasks should use fewer calls (5-10 vs. current 8 fixed nodes). Monitor and tune. Net cost may decrease for simple tasks. |
| Harder to debug than deterministic graph | "Why did it do that?" is harder to answer | Comprehensive execution tracing with parent/child agent correlation. Every step logged with reasoning + tool calls. |
| Sub-agent context transfer lossy | Coder doesn't understand what researcher found | Orchestrator produces structured briefs. Sub-agents can request additional context via `read_file`/`search_codebase`. |
| Anthropic SDK migration introduces bugs | Existing functionality breaks | Phase 1 builds the runtime independently. Phases 3-4 replace agents one at a time. Phase 8 validates E2E. |
| Smart router misclassifies events | Wrong agent gets triggered, or signal goes to wrong workflow | Router has tools to query running workflows. Fallback: if agent can't handle, it says so. Router can be conservative (ask for clarification on ambiguous input). |
| Prompt engineering is hard to get right | Agents behave unpredictably | Iterative prompt development with execution traces. Start with verbose, constrained prompts. Relax as confidence grows. |

## Out of Scope for v2.2

- **Cross-agent collaboration** — dev agent asking product agent to clarify mid-task. Architecture supports it (both are Temporal workflows that can receive signals), not wired in this milestone.
- **Multi-LLM support** — using GPT-4 or other models for certain agents. The `AgentConfig.model` field supports it, but v2.2 uses Claude throughout.
- **New agent types** (QA, reviewer, docs) — architecture supports adding them. v2.2 delivers dev + product.
- **Production deployment** (CI/CD, monitoring, alerting) — deferred to subsequent milestone. Get agents smart first, deploy later.
- **Web search / internet research tools** — can be added as tools later without architectural change. Not in v2.2 scope.
- **UI for observing agent execution** — traces stored in DB, queryable via SQL. UI is a separate concern.
- **Codebase indexing / RAG** — agents explore via `read_file`/`search_codebase` tools. No vector DB or embedding pipeline.
- **Multi-repo support** — agents work on a single configured repo. Multi-repo is a future enhancement.
