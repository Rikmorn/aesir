# v2.5 — Agentic Conversations

## Summary

Give agents continuity across interactions through a task primitive that groups conversations, enable conversation reopening for follow-up events, and rewrite orchestrator prompts to be goal-oriented instead of procedural.

See also: `.planning/specs/2.5-design-vision.md` for architectural rationale, expansion paths, and design philosophy behind these changes.

## Phase 1: Prompt Rewrites

Rewrite product-agent and dev-agent prompts simultaneously, following the Prompt Authoring Guide (`packages/agents/definitions/PROMPT_GUIDE.md`).

**What changes:**
- Remove state machines and if/then branching trees
- Replace with goal-oriented prompts and judgment criteria
- Remove prescriptive tool sequences; let agents reason about tool use
- Reduce directive density (MUST/ALWAYS/NEVER) to genuine safety boundaries
- Both agents rewritten in parallel (no production risk)

**Techniques applied:**
- **Constitutional constraints**: Replace positive procedures with negative boundaries. Instead of "search then draft then confirm," use "never create an issue without checking for duplicates" and "never create an issue the user hasn't confirmed."
- **Few-shot examples with reasoning**: Replace if/then branches with 3-5 examples showing input → reasoning → action. The agent learns the reasoning pattern and generalizes to novel inputs. Use abstract reasoning, not literal tool call syntax — decouples examples from tool schemas so they don't go stale when tools change.
- **Selective chain-of-thought**: Orchestrator agents (product, dev) externalize reasoning in `<reasoning>` blocks before significant decisions. Stored in event log for observability. Worker agents (coder, researcher, tester) skip this — they just execute.
- **Clean prompt structure**: Consistent section separation across all agents — identity, constraints, examples, tools, context. Instructions (stable) are clearly separated from context (per-conversation).
- **Structured output only at framework boundaries**: Phase tags and handoff structures remain. Everything else is natural language.

**Pitfall mitigations:**
- **Regression prevention**: Before rewriting, create a traceability matrix for each agent: old if/then rule → failure it originally prevented → new constraint or example that covers it. Manually test 5-6 key scenarios per agent before and after (clear request, vague request, duplicate found, tool failure, etc.). Full prompt eval tooling (promptfoo, shadow mode) is explicitly deferred — net improvement over state machines doesn't require perfect regression coverage.
- **Constraint conflicts**: Keep constitutional constraints to 5-7 per agent. Add an explicit priority ordering: safety > correctness > efficiency. Include one few-shot example that demonstrates resolving a constraint tension.
- **Rollback path**: Prompts are in git. If behavior regresses, revert prompt.md and investigate.

**Deliverables:**
- Rewritten `definitions/product-agent/prompt.md`
- Rewritten `definitions/dev-agent/prompt.md`
- Both following PROMPT_GUIDE.md structure: identity → constraints → examples → tools → context
- Traceability matrix per agent (old rule → why it exists → new coverage)

## Phase 2: Conversation Reopening

Allow completed/failed conversations to receive signals and re-enter the work loop.

**Changes:**
- Executor handles signals on conversations in `completed` or `failed` status
- Signal transitions conversation back to `queued` with the signal payload available
- Agent receives full prior history plus the signal context on resume
- Dashboard: add retry/reopen action to conversation detail view

**World-state injection (required):**
When a conversation is reopened, the agent's prior history is factual about what *happened* but potentially wrong about the *current state of the world*. A PR may have been merged, an issue status may have changed, a branch may have been deleted. The agent will act confidently on stale information unless told otherwise.

Mitigation: inject a `<world_state>` context block when reopening. Additionally, add a constitutional constraint to reopened prompts: "When resuming a previous conversation, verify the current state of any artifacts you previously created before acting on them."

**Reopen signal payload:**
The reopen signal carries a single required field: `reason: string` (non-empty). No structured delta — the only consumer is the LLM (via the `<world_state>` block), and it reasons on natural language. Structured fields can be added later as backward-compatible optional additions if a programmatic consumer emerges.

The `reason` describes what changed for completed conversations ("PR #42 received a review with changes requested") or why retrying for failed conversations ("Transient infra issue resolved, retry"). The dashboard should prompt for a meaningful reason — a text field with placeholder like "What changed?" rather than a bare reopen button.

The `<world_state>` block is injected as a **user message** appended to the conversation history — not a system prompt modification. This creates a clear boundary between the previous run and the reopened run, forces the agent to explicitly acknowledge and respond to the context, and is visible in the event log. The constitutional constraint in the agent's base prompt ("verify current state of artifacts") provides the persistent reminder across iterations.

```xml
<world_state>
This conversation was reopened. Context: {reason}

The world may have changed since you last acted. Verify the current state of
any artifacts you previously created before taking new actions.
</world_state>
```

**API design:**
Single endpoint `POST /conversations/:id/reopen` handles both completed and failed conversations. The behavior is identical in both cases (transition to queued, inject world_state, resume with full history), and the agent already knows whether it previously completed or failed from its own conversation history. The dashboard renders different labels ("Retry" on failed, "Reopen" on completed) but calls the same endpoint. Rejects non-terminal conversations with 400. Emits a single `agent.reopened` event type (previous status available as event metadata).

**Execution limits:**
Iteration count, token budget, and retry count all reset to agent defaults on reopen. A reopened conversation is a new run with prior context — the agent needs a full budget to verify state, reason about changes, and act. Reopen is separate from the executor's automatic retry mechanism: retries are immediate/automatic within a single run, reopens are deliberate human actions across runs. `reopen_count` tracks reopens; retry count tracks automatic retries within a run. Per-run limits (`maxIterations`, `tokenBudget`) still cap each individual run. No special "reopen budget" config.

**Scope boundaries:**
- Only `reopen` signal type triggers this — other signals on terminal conversations are still ignored
- No automatic reopening — must be triggered by an explicit signal (manual via dashboard, or from event routing in Phase 3)

**Pitfall mitigations:**
- **History explosion**: Reopened conversations accumulate messages across runs. Use the handoff (Phase 3) as the primary context-passing mechanism. Track `reopen_count` on the conversation for observability. Defer the multi-reopen warning UX until real usage data shows how often conversations get reopened — the threshold and UX can be added to the dashboard later without schema changes. The API endpoint does not enforce a reopen limit; any future warning is dashboard-only (soft, not a hard block).
- **Signal dedup array growth**: Cap `delivered_signal_ids` at 100 entries with FIFO eviction on insert — when adding entry #101, drop the oldest. Oldest signals are least likely to be re-delivered (webhook retries happen within minutes). Single JSONB operation, no background jobs or lifecycle hooks.

## Phase 3: Task Primitive

Introduce the task as a first-class entity that groups related conversations.

### Task Bootstrapping

When an event-triggered conversation starts and no task exists yet, the **agent** creates the task as its first action via `create_task`. Task creation is optional — conversations without tasks continue to work (backward-compatible). The framework does not auto-create tasks; this keeps it agent-first.

The prompt guides agents to create a task when starting meaningful work, but doesn't mandate it for every conversation. Quick single-turn interactions (status checks, simple queries) don't need tasks.

### Schema

**tasks:**
```sql
CREATE TABLE agents.tasks (
  id            TEXT PRIMARY KEY,  -- createId.task() -> "task_<nanoid>"
  parent_id     TEXT REFERENCES agents.tasks(id),

  creator_type  TEXT NOT NULL CHECK (creator_type IN ('agent', 'human')),
  creator_id    TEXT NOT NULL,
  assignee_type TEXT NOT NULL CHECK (assignee_type IN ('agent', 'human')),
  assignee_id   TEXT NOT NULL,

  status        TEXT NOT NULL DEFAULT 'created'
                CHECK (status IN ('created', 'active', 'paused', 'completed', 'cancelled')),

  title         TEXT NOT NULL,
  objective     TEXT,
  metadata      JSONB DEFAULT '{}',

  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  completed_at  TIMESTAMPTZ
);

CREATE INDEX idx_tasks_assignee ON agents.tasks(assignee_type, assignee_id, status);
CREATE INDEX idx_tasks_parent ON agents.tasks(parent_id) WHERE parent_id IS NOT NULL;
CREATE INDEX idx_tasks_status ON agents.tasks(status) WHERE status IN ('created', 'active', 'paused');
```

Task IDs use the existing `createId` pattern (`task_<nanoid>`) — consistent with every other table in Aesir, no collision across environments. External human-readable identifiers (Linear's AES-42) are the user-facing reference; task IDs are internal plumbing. Add `task` and `handoff` entries to the `createId` object in `packages/types/src/utils/ids.ts`: `task: () => task_${nanoid()}` and `handoff: () => ho_${nanoid()}`.

**task_handoffs:**
```sql
CREATE TABLE agents.task_handoffs (
  id                TEXT PRIMARY KEY,  -- createId.handoff() -> "ho_<nanoid>"
  task_id           TEXT NOT NULL REFERENCES agents.tasks(id),
  conversation_id   TEXT NOT NULL REFERENCES agents.conversations(id),

  handoff_type      TEXT NOT NULL CHECK (handoff_type IN ('completion', 'pause', 'delegation', 'escalation')),
  context           JSONB NOT NULL,

  author_type       TEXT NOT NULL CHECK (author_type IN ('agent', 'human')),
  author_id         TEXT NOT NULL,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_handoffs_task ON agents.task_handoffs(task_id, created_at);
```

Handoff `context` is structured JSONB with a required `summary` field. The `complete_task` and `handoff_task` tools enforce this via Zod validation: `{ summary: string (required, max 2000 chars), key_decisions?: string[], artifacts?: object, open_questions?: string[], next_steps?: string }`. Size capped at ~4KB per handoff — agents needing to pass more context reference artifacts or use `get_task_context` for full history.

**conversations (addition):**
```sql
ALTER TABLE agents.conversations
  ADD COLUMN task_id TEXT REFERENCES agents.tasks(id);

CREATE INDEX idx_conversations_task ON agents.conversations(task_id)
  WHERE task_id IS NOT NULL;
```

### TaskService

Factory function following the existing `create{Service}` pattern (options object, fail-fast validation, interface return type, `health()` + `close()` lifecycle methods). Methods:

- `create(params)` → task — insert new task with Zod-validated fields
- `get(taskId)` → task | null — single task lookup
- `update(taskId, fields)` → task — update status, metadata, assignee, etc.
- `addHandoff(params)` → handoff — insert handoff with Zod-validated context (summary required, ~4KB cap)
- `getHandoffs(taskId, opts?)` → handoffs[] — all handoffs for a task, ordered by created_at
- `getLatestHandoff(taskId)` → handoff | null — most recent handoff (used by worker loop for `<task_context>` injection)
- `listByAssignee(assigneeType, assigneeId, filters?)` → tasks[] — query by assignee with optional status/limit filters
- `listByParent(parentId, filters?)` → tasks[] — query child tasks of a parent with optional status/limit filters
- `linkConversation(taskId, conversationId)` → void — UPDATE conversations SET task_id WHERE id (used by create_task tool)

The service layer validates data shape (Zod schemas, size limits) but not business logic. Shape validation — metadata under 10KB, handoff context has required `summary` (max 2000 chars, ~4KB total), title non-empty, valid enum values — lives in the service because it's the single writer to the database and must guarantee data integrity regardless of caller. Business logic — status transition rules, circular delegation prevention, depth/subtask limits — lives in the tool layer (Phase 58.2) where the agent interacts, because tools have workflow context the service doesn't need to know about.

**Valid task status transitions** (enforced by tools, not the service):
```
created → active
active → paused, completed, cancelled
paused → active, cancelled
completed → (terminal)
cancelled → (terminal)
```
No `created → completed` shortcut — a task must be active before it can complete. Both `completed` and `cancelled` are terminal and immutable. Task reopening is not a v2.5 concept; conversation reopening operates at a different layer.

In v2.5, `create_task` sets status to `active` immediately — agents always create tasks they're about to work on, so a separate activation step is friction with no benefit. The `created` state exists in the schema for future use (human-created tasks awaiting agent pickup, queued tasks from external systems) but is not used by any v2.5 tool.

`updated_at` is set at the application level in TaskService (not a Postgres trigger) — keeps the data layer portable and avoids coupling to Postgres-specific features while the long-term storage choice isn't settled.

### Integration Correlation Tables

Each integration maintains a correlation table mapping external artifacts to tasks:

```sql
CREATE TABLE {integration}.task_correlations (
  external_type   TEXT NOT NULL,
  external_ref    TEXT NOT NULL,
  task_id         TEXT NOT NULL,  -- plain TEXT, no FK to agents.tasks
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (external_type, external_ref)
);
```

`task_id` is a plain TEXT column, not a foreign key. Integration packages are independent and don't reference the agents schema. Orphaned correlations (task deleted) are harmless — the routing layer finds no matching task and falls through to normal routing. This also supports future scaling where integrations have separate state stores.

- **Outgoing**: When an agent creates an artifact via MCP, the integration records the correlation (e.g., PR #42 → task T123). Agent passes task_id as MCP call context.
- **Incoming**: When a webhook arrives, the integration looks up the correlation and attaches the task reference before forwarding to the agent service.

**MCP header propagation:** Add `taskId?: string` to `McpCallOptions` and `McpToolDeps`. The MCP client sends `X-Task-ID` header when present. The `mcpAdapter` in `tool-factories.ts` extracts `taskId` from ToolContext alongside `agentId` and `correlationId`. Since `create_task` mutates `ctx.taskId` mid-run, MCP calls after task creation automatically include the header; calls before task creation send no header (correct — no task to correlate yet).

**Correlation-triggering operations:** Each integration's MCP handler checks: is `X-Task-ID` present AND is this a correlatable operation? If yes, INSERT INTO task_correlations (fire-and-forget, catch and log failures). The initial set (expected to evolve based on real usage):

- **Linear**: `create_issue` → `("issue", issueId)`, `create_comment` → `("comment", commentId)`
- **GitHub**: `create_pull_request` → `("pull_request", "owner/repo#number")`, `create_branch` → `("branch", "owner/repo:branchName")`, `create_commit` → `("commit", "owner/repo@sha")`
- **Slack**: `send_message` → `("thread", "channelId:threadTs")`, `send_approval_request` → `("approval", "channelId:messageTs")`

Read operations (`get_*`, `list_*`, `search_*`) and update operations (`update_issue_status`, `merge_pull_request`, `reply_to_thread`) do not record correlations — the entity is either already correlated from creation or is not an addressable artifact.

**Incoming correlation lookup:** Add `taskId?: string` to both `NormalizedEvent` (in `@aesir/types`) and `IncomingEvent` (in `adapters/types.ts`). The integration performs the correlation lookup when processing an incoming webhook: extract the artifact reference from the webhook payload (e.g., issue ID, PR number, thread timestamp), query `task_correlations`, and set `taskId` on the `NormalizedEvent` before POSTing to the agent service. The adapter preserves `taskId` into `IncomingEvent`. This keeps the lookup in the integration layer where the webhook payload parsing already happens.

### Agent Tools

Six tools registered under the `task:` namespace:
- `create_task` — create a task (with optional parent_id for subtasks)
- `complete_task` — mark task completed with a completion handoff
- `pause_task` — pause task with a pause handoff
- `handoff_task` — write a delegation or escalation handoff (no status change)
- `list_tasks` — query tasks by assignee (default: self) or by parent_id for subtasks, with optional status filter
- `get_task_context` — retrieve task metadata (title, status, assignee, created_at) and all handoffs ordered by date

**Orchestrator vs worker agents:** Task tools are added to **orchestrator agents only** (product-agent, dev-agent) — agents with triggers, subAgents, and coordination tools that make strategic decisions. **Worker agents** (coder, researcher, tester) do NOT get task tools. Workers are spawned by orchestrators, execute focused tasks, and return results. They share the parent's conversation context (`correlationId`), so task lifecycle operations from a worker would conflict with the orchestrator's task state (e.g., `create_task` would overwrite the parent conversation's task link, `complete_task` could mark the orchestrator's task done mid-run). When a worker hits issues, it returns to the orchestrator, which has the full task context to decide next steps (retry, delegate, escalate).

**Tool LLM-facing input schemas:** All task tools auto-fill `authorType`/`creatorType` (`"agent"`), `authorId`/`creatorId` (`ctx.agentId`), and `conversationId` (`ctx.correlationId`). Status-changing tools (`complete_task`, `pause_task`) and `handoff_task` default `taskId` to `ctx.taskId` (current conversation's task) but accept an explicit `taskId` to operate on subtasks.

- **`create_task`**: `{ title: string, objective?: string, assigneeType: "agent" | "human", assigneeId: string, parentId?: string, metadata?: object }`. Auto-fills creator and status (`"active"`). No default for assignee.
- **`complete_task`**: `{ taskId?: string, summary: string, key_decisions?: string[], artifacts?: object, next_steps?: string }`. Transitions active → completed + completion handoff.
- **`pause_task`**: `{ taskId?: string, summary: string, open_questions?: string[], next_steps?: string }`. Transitions active → paused + pause handoff.
- **`handoff_task`**: `{ taskId?: string, handoffType: "delegation" | "escalation", summary: string, key_decisions?: string[], artifacts?: object, open_questions?: string[], next_steps?: string }`. Records handoff only, no status change.
- **`list_tasks`**: `{ parentId?: string, status?: string, limit?: number }`. Without `parentId`, lists tasks assigned to the calling agent. With `parentId`, lists subtasks of that parent. Returns summary rows per task: `id`, `title`, `status`, `assignee`, `createdAt`, plus `lastHandoffSummary` truncated at 200 chars (enough to triage without blowing token budget). Call `get_task_context` for full detail on a specific task.
- **`get_task_context`**: `{ taskId?: string }`. Defaults to `ctx.taskId`. Returns task metadata (title, status, assignee, createdAt) followed by all handoffs in flat chronological order. Each handoff entry includes timestamp, type, author, and all context fields (summary, key_decisions, artifacts, open_questions, next_steps). Chronological order preserves the task narrative — the agent reads top-to-bottom to understand what happened and acts on the latest state.

**Tool result format:** All task tool results use plain text, not JSON. `ToolResult.content` is already a string — JSON would be stringified into it anyway, adding ~30% token overhead (braces, quotes, commas) for zero benefit since the only consumer is the LLM. Consistent with existing tools (`spawn_agent`, `wait_for`, codebase tools). Structured read tools use labeled text format (e.g., `Task: task_abc123\nStatus: active\n...`) which is both more token-efficient and easier for the LLM to scan than equivalent JSON. Write tools (`create_task`, `complete_task`, `pause_task`, `handoff_task`) return minimal confirmation: task ID + new status + linkage note (for `create_task`). The LLM just provided the input fields — echoing them back is pure token waste. Read tools (`list_tasks`, `get_task_context`) return richer output since their purpose is fetching information the LLM doesn't have.

**Tool error handling:** Invalid operations (bad status transitions, depth limit, circular delegation, subtask cap) return `{ content: "...", isError: true }` — never throw. Consistent with `spawn_agent` error pattern. Error messages include the current state and valid transitions so the LLM can self-correct: e.g., `Cannot complete task_abc123: status is "paused". Valid transitions from paused: active, cancelled.` This applies to all status-changing tools and guard failures.

**Tool injection pattern:** TaskService is injected into task tool factories via closure, following the existing adapter pattern in `tool-factories.ts`. `RegisterAllToolsOptions` receives a `taskService` field (alongside `agentRegistry`). A `taskAdapter` closure captures TaskService and passes both TaskService and ToolContext to each tool factory at resolve time — same pattern as `codebaseAdapter` (containerManager) and `mcpAdapter` (agentId/correlationId).

**Conversation-task linking:** `create_task` conditionally links the current conversation to the new task based on whether a task is already associated. When `ctx.taskId` is undefined (no task yet): link the conversation via `TaskService.linkConversation(taskId, conversationId)` and mutate `ctx.taskId = newTaskId` so subsequent tools see the task (MCP calls include `X-Task-ID` header). When `ctx.taskId` is already set: just create the task in the database and return the ID — no linking, no ctx mutation. This supports the natural orchestrator flow: first `create_task` establishes the orchestrator's own task (linked), subsequent `create_task(parentId: ctx.taskId)` calls create subtasks for delegation without disturbing the conversation's task association. Erroring would block subtask creation. Overwriting would silently lose the original task link. The conversation ID is available via `ctx.correlationId` (set to `conv.id` by the worker loop). No ToolContext interface change needed — `taskId` is already `string | undefined`.

**Task context injection:** When `conv.task_id` is present and a handoff exists, the worker loop injects a `<task_context>` block. Format is XML tags (consistent with `<workspace_context>`, `<slack_context>`). Content: task metadata (title, status, assignee) + most recent full handoff (all fields: summary, key_decisions, artifacts, open_questions, next_steps), truncated at 4000 chars total. A "Call get_task_context for full history" pointer is included only when the handoff was truncated or multiple handoffs exist — if there's a single untruncated handoff, the agent already has everything and the pointer would be noise. Full handoff is included rather than summary-only because the structured fields (key_decisions, open_questions, next_steps) are the most valuable context for preventing wasted work — summary-only would force an immediate `get_task_context` call in most cases. If task_id exists but no handoffs yet, inject a minimal task reference (title, objective, status, assignee) without handoff content — ensures every conversation with a task_id knows what task it belongs to, including new conversations routed to the task via Phase 58.4 before the first handoff is written. The worker loop calls `taskService.getLatestHandoff(conv.task_id)` to fetch the handoff; TaskService is available via the same options object that provides it to `registerAllTools`.

**Context block ordering and injection points:** Context blocks use two injection points depending on conversation lifecycle. For **new conversations**, blocks are prepended to the initial user message in broad-to-specific order: `<workspace_context>` (where am I?) → `<task_context>` (what happened before?) → event content (what triggered this run?). For **reopened conversations**, the original first message is deep in history and can't be modified. Fresh `<task_context>` is injected alongside the `<world_state>` message (the reopen boundary from Phase 57): `<world_state>` → `<task_context>` → reopen signal. This gives the agent a clean "here's what's new" boundary with both the reopen reason and fresh task handoffs (which may have been added by other conversations while this one was terminal). `<task_context>` is always fetched fresh at run start — its content is current, only the injection location differs.

### Event Routing Changes

```
Event arrives at integration layer
  → Integration looks up task_correlations, attaches taskId if found
  → Forward to agent service (POST /events)

Agent service routeEvent():
  → Adapter pipeline: NormalizedEvent → IncomingEvent (preserves taskId)
  → Has taskId? → Task-routing branch (early exit, skips EventRouter)
      → Acquire advisory lock on taskId
      → Find active conversation for task
      → Active/waiting/queued conversation exists? → deliver as signal
      → No active conversation? → create new conversation in task
  → No taskId? → Existing EventRouter.handle() (fast-path/slow-path unchanged)
```

**Task-routing implementation:** The task branch is an early-exit in `routeEvent()`, inserted between the adapter pipeline and `EventRouter.handle()`. When `incomingEvent.taskId` is present, the event is routed entirely through the task path — no EventRouter involvement. When absent, existing routing logic runs unchanged.

**Active conversation lookup:** Add `findActiveForTask(taskId): Promise<ConversationInfo | null>` to `ConversationExecutor`. Queries conversations with `task_id = ? AND status IN ('running', 'waiting', 'queued')` ordered by `created_at DESC LIMIT 1`. Called by the router within the advisory lock transaction.

When routing to an existing task:
- If the task has an active/waiting/queued conversation: deliver as signal (serialized via advisory lock)
- If no active conversation: create new conversation in task via `executor.start()` with `taskId` param, worker loop handles `<task_context>` injection from most recent handoff

**New conversation within a task:** Add `taskId?: string` to `StartConversationParams`. When present, `start()` sets `conversations.task_id` on INSERT. The `correlationKey` for task-scoped conversations is `${taskId}:${event.deduplicationId || event.type}` — includes task ID plus an event-specific component so `start()` creates a new conversation rather than returning a completed one. The router determines `agentDefinitionId` from the task's `assignee_id` (which is an agent definition ID when `assignee_type = "agent"`).

### Concurrency

Events for the same task are serialized. Second event queued as signal, delivered when active conversation completes or pauses. One problem at a time.

Task-level serialization uses PostgreSQL advisory locks (`pg_advisory_xact_lock(hashtext(task_id))`) — separate lock space from conversation-level `SKIP LOCKED`, preventing deadlock between the two locking mechanisms. Canonical lock order: task first, then conversation. The routing transaction is short (SELECT + routing decision); actual conversation creation/signal delivery happens outside the transaction.

### CorrelationKey and Task-Scoped Conversations

The existing `start()` is idempotent via `correlationKey`. With tasks, a task may need multiple sequential conversations (the previous one completed, a new event triggers a fresh conversation in the same task). The `correlationKey` for task-scoped conversations must include the task ID plus a distinguishing factor (e.g., the triggering event ID) so that `start()` creates a new conversation rather than returning the completed one.

### Pitfall Mitigations

- **Schema collision**: `schema.drizzle.ts` contains legacy tables (`tasks`, `context_snapshots`, `execution_traces`) from v1/v2 retained to prevent destructive migrations. The migration should DROP all three unconditionally — they use different schemas (`atask_` prefix, workflow/container/PR fields) and are not used by any runtime code. Remove their definitions from `schema.drizzle.ts` as well. Then CREATE the new `agents.tasks` and `agents.task_handoffs` tables.
- **Metadata bloat**: Validate `tasks.metadata` with Zod on write, enforce a 10KB size limit at the application layer. Metadata is for task-level attributes (tags, priority overrides), not accumulated conversation data — use handoffs for that.
- **Backward compatibility**: All code paths that touch `task_id` must handle null (existing conversations have no task). Add a `hasTask` helper. Prompts must degrade gracefully: "If operating within a task, use task tools for context. If no task is available, operate as before." Dashboard shows "No task associated" for taskless conversations.
- **Circular delegation**: `create_task` tool checks the parent chain and rejects if the same `assignee_id + assignee_type` combination appears more than once in the ancestry. Max 10 subtasks per parent task.
- **ToolContext.taskId collision**: The existing `ToolContext.taskId` field is used for sandbox container identification, not tasks. Rename to `sandboxId` before adding the v2.5 `taskId` field. Affects ~37 files (framework types, worker-loop, codebase tool factories, spawn-agent, router tools, and their tests). Additionally, `query-conversations.ts` in the router uses a local `taskId` parameter for pattern-matching conversation IDs by correlation key — rename to `correlationRef` in the same pass to avoid confusion with the new v2.5 `taskId`. The new `ToolContext.taskId` is set unconditionally from `conv.task_id ?? undefined` in the worker loop (outside the sandbox conditional block) — available to all tools, not just codebase tools. Task tools need it to know the conversation's task; integration tools need it in Phase 58.3 for the `X-Task-ID` MCP header.

## Phase 4: Prompt Evolution

Update all agent prompts to leverage the task lifecycle:
- Agents think in terms of tasks, not conversations
- Agents write handoffs at conversation boundaries (prompt guidance + examples)
- Agents can delegate subtasks to other agents or create tasks for humans
- Agents can query for related tasks and incorporate context
- Handoff examples added to few-shot sections

**Pitfall mitigations:**
- **Telephone game effect**: Through delegation chains, handoff content degrades as each agent summarizes at a lossy level of abstraction. Mitigation: structured handoff schema (required fields survive compression better than free text), `get_task_context` returns all handoffs (not just the most recent), and prompt guidance tells agents to call `get_task_context` when the latest handoff references prior work.
- **Bad handoffs**: Agents may write handoffs that are too long, miss key info, or hallucinate context. Mitigation: the `complete_task` and `handoff_task` tools enforce the structured schema with size limits. Include good handoff examples in few-shot sections — bad examples are an anti-pattern in prompts (models anchor on in-context patterns regardless of "don't do this" framing). A good example with the right level of detail teaches by demonstration.

## Expansion Constraints

Architectural guardrails — must not be violated without revisiting `2.5-design-vision.md`.

1. **Bidirectional assignment.** Never assume assignees are agents. The `assignee_type` field exists for this reason.
2. **Task hierarchies.** Don't assume tasks are flat. `parent_id` enables subtask trees.
3. **Handoff strategies will grow.** Don't pattern-match on `handoff_type` in framework code. The type is metadata for the receiving agent.
4. **Event routing checks for existing tasks.** Don't skip the task lookup for "simple" events.
5. **Agents author handoffs.** Don't auto-generate handoff content. The agent decides what matters.
6. **Task completion is agent-decided.** Don't auto-complete on external signals (PR merged, issue closed).
7. **Tasks are not artifact wrappers.** A task references external artifacts but is not defined by them.

## Resolved Decisions

- **Stale task cleanup**: Framework flags inactive tasks via scheduled job, agent decides what to do (follow up, discard, retry). Mechanism: timeout signal, similar to existing `wait_for` timeouts.
- **Context pressure**: Only deliver most recent handoff by default; older ones available via `get_task_context` tool. Handoff context capped at ~4KB with structured schema. Auto-injected `<task_context>` block in worker loop truncates at 4000 chars; pointer to `get_task_context` included only when truncated or multiple handoffs exist (conditional, not always).
- **Circular delegation**: Depth limit on `parent_id` chains (max 5 levels). `create_task` tool checks ancestry for delegation cycles (A → B → A) and rejects. Self-decomposition (A → A) is allowed — consecutive same-assignee is task breakdown, not circular delegation. Max 10 subtasks per parent.
- **Task bootstrapping**: Agent creates the task as its first action via `create_task`. Framework does not auto-create tasks. Task creation is optional — quick single-turn interactions don't need tasks.
- **CorrelationKey with tasks**: Task-scoped conversations use a correlationKey that includes both task ID and triggering event ID, so `start()` creates new conversations within a task instead of returning completed ones.
- **Task IDs**: Use existing `createId` pattern (`task_<nanoid>`). External human-readable identifiers (Linear's AES-42) serve as user-facing references.
- **Reopen signal payload**: Single required field `reason: string` (non-empty). No structured delta — the LLM is the only consumer and reasons on natural language. Structured fields can be added as backward-compatible optional additions if a programmatic consumer emerges post-v2.5.
- **Reopen API**: Single `POST /conversations/:id/reopen` endpoint for both completed and failed conversations. Behavior is identical (transition to queued, inject world_state, resume). Dashboard renders different labels ("Retry" vs "Reopen") but calls the same endpoint. One `agent.reopened` event type with previous status as metadata.
- **World-state injection mechanism**: Injected as a user message appended to conversation history, not a system prompt modification. Creates a clear history boundary, forces explicit agent acknowledgment, and is observable in the event log.
- **Multi-reopen threshold**: Track `reopen_count` on conversation. Defer warning UX until usage data exists. API never enforces a limit; any future warning is dashboard-only soft suggestion, not a hard block.
- **Execution limits on reopen**: Reset `maxIterations`, `tokenBudget`, and retry count to agent defaults. Reopened conversation is a new run — continuing from the old budget makes the reopen useless if the original run consumed most of it.
- **Legacy tables**: DROP `tasks`, `context_snapshots`, `execution_traces` unconditionally in the migration. Remove from `schema.drizzle.ts`. Different schema from v2.5 tasks, no runtime usage, no production data.
- **TaskService methods**: `create`, `get`, `update`, `addHandoff`, `getHandoffs`, `getLatestHandoff`, `listByAssignee`, `listByParent`, `linkConversation`. Service validates data shape (Zod schemas, size limits) as the single database writer; business logic (status transitions, hierarchy rules) lives in tools (Phase 58.2).
- **Task status transitions**: `created → active`, `active → paused/completed/cancelled`, `paused → active/cancelled`. Both `completed` and `cancelled` are terminal. No `created → completed` shortcut.
- **Task initial status**: `create_task` sets status to `active` immediately. `created` state exists in schema for future use but is not used by v2.5 tools.
- **updated_at strategy**: Application-level in TaskService, not a Postgres trigger. Keeps data layer portable while long-term storage choice isn't settled.
- **ToolContext.taskId availability**: Set unconditionally from `conv.task_id` in worker loop, available to all tools. Separate from `sandboxId` (conditional, sandbox-only).
- **Task tool injection**: TaskService injected via closure in `registerAllTools` (same adapter pattern as codebase/MCP tools). `RegisterAllToolsOptions` gets a `taskService` field.
- **Conversation-task linking**: Conditional — `create_task` links and mutates `ctx.taskId` only when `ctx.taskId` is undefined (first task). When a task already exists, creates the task without linking or mutating ctx. Supports orchestrator flow: first call establishes own task, subsequent calls create subtasks for delegation.
- **Task context injection**: Worker loop injects `<task_context>` XML block whenever `conv.task_id` is present. With handoffs: task metadata + most recent full handoff (all structured fields), truncated at 4000 chars. Without handoffs: minimal task reference (title, objective, status, assignee). Always injected — ensures every conversation knows its task regardless of handoff state.
- **Context block injection points**: New conversations: prepend to initial user message in order `<workspace_context>` → `<task_context>` → event content. Reopened conversations: inject alongside `<world_state>` message (reopen boundary) as `<world_state>` → `<task_context>`. Task context is always fetched fresh; only the injection location differs.
- **Task tools on orchestrators only**: product-agent and dev-agent get task tools. Worker agents (coder, researcher, tester) do not — they share the parent's conversation context, so task lifecycle operations would conflict with the orchestrator's task state.
- **handoff_task is status-free**: `handoff_task` records a delegation or escalation handoff without changing task status. The orchestrator composes sequences: `handoff_task` + `pause_task` for "escalate and wait", `handoff_task` + `create_task` for "delegate a subtask." `complete_task` and `pause_task` are the tools that atomically change status + record a handoff.
- **get_task_context returns**: Task metadata (title, status, assignee, created_at) + all handoffs ordered by date. No conversation messages — handoffs are the context-passing mechanism.
- **list_tasks query modes**: Without `parentId`, lists tasks assigned to the calling agent. With `parentId`, lists subtasks. Both support optional status/limit filters. TaskService gets `listByParent` method.
- **Correlation table task_id**: Plain TEXT, no FK to agents.tasks. Integration packages are independent and shouldn't reference the agents schema. Orphaned correlations are harmless. Supports future scaling where integrations have separate state stores.
- **Correlation-triggering operations**: Only operations that create addressable entities: Linear (`create_issue`, `create_comment`), GitHub (`create_pull_request`, `create_branch`, `create_commit`), Slack (`send_message`, `send_approval_request`). Expected to evolve based on real usage.
- **Correlation duplicate handling**: `ON CONFLICT (external_type, external_ref) DO NOTHING` — first task to create an artifact owns the correlation. Re-correlation to a different task is silently ignored. This is consistent with the one-to-one MVP constraint (PK on external_type + external_ref). If many-to-many correlation is needed later (monorepo PRs spanning tasks), this changes to an upsert or a junction table.
- **Incoming taskId propagation**: `taskId?: string` added to both `NormalizedEvent` (@aesir/types) and `IncomingEvent` (adapters/types.ts). Integration performs correlation lookup on incoming webhooks and sets taskId before forwarding.
- **Task-routing placement**: Early-exit branch in `routeEvent()` between adapter pipeline and `EventRouter.handle()`. Events with `taskId` bypass EventRouter entirely.
- **Active conversation lookup**: `findActiveForTask(taskId)` added to `ConversationExecutor`. Queries `status IN ('running', 'waiting', 'queued')` for a given task_id.
- **Task-scoped conversation creation**: `taskId?: string` added to `StartConversationParams`. `start()` sets `task_id` on INSERT. CorrelationKey: `${taskId}:${event.deduplicationId || event.type}`. Router derives `agentDefinitionId` from task's `assignee_id`.
- **Tool result format**: Plain text, not JSON. `ToolResult.content` is a string — JSON adds ~30% token overhead for zero benefit since the only consumer is the LLM. Write tools return minimal confirmation (task ID + status + side-effects). Read tools use labeled text format for structured data. Consistent with existing tools.
- **get_task_context output structure**: Flat chronological — task metadata header followed by all handoffs in creation order. Preserves the task narrative (created → worked on → paused → delegated → completed). Grouping by type would break temporal context the agent needs for reasoning.
- **Tool error handling**: Invalid operations return `{ content, isError: true }` with current state and valid transitions — never throw. Consistent with `spawn_agent` pattern. LLM can self-correct without guessing.
- **Task-routed signal types**: Domain-specific (`pr_review`, `approval`, `pr_merged`, etc.), not a generic `task_event`. Task routing changes where the event goes, not what the event is. Preserves existing `wait_for` matching semantics.
- **Task-routed signal payload**: Identical to non-task-routed signals — no task metadata enrichment. The agent already receives task context via `<task_context>` injection in the worker loop. Task routing is a delivery mechanism, not a payload transformation.
- **Human/no-agent assignee routing**: When `task.assignee_type !== "agent"`, fall through to EventRouter. There's no agent definition to load — this is a precondition failure, not a judgment call for the agent.
- **Terminal task status routing**: Route to the task regardless of task status (completed, cancelled). The agent receives `<task_context>` with the current status and decides how to handle the follow-up. Framework does not filter on task status — agent-first.
- **Advisory lock failure handling**: Fall through to EventRouter, log warning. Event delivery is not blocked by transient DB issues. Normal lock contention (another event being routed for the same task) waits — that's the serialization guarantee.
- **Task lookup failure handling**: Strip `taskId` from the event and fall through to EventRouter. An orphaned taskId pointing to a nonexistent or unreachable task is misleading downstream — fall through should behave as if no correlation existed.
- **Prompt evolution scope — orchestrators only**: "All agent prompts" in EVOL-03 means orchestrator prompts only (product-agent, dev-agent). Workers (coder, researcher, tester) don't have task tools and don't need task lifecycle awareness.
- **Prompt evolution — section placement**: Task lifecycle additions follow the existing prompt structure: `<domain_knowledge>` for task concepts and handoff guidance; `<examples>` for 1-2 new few-shot examples showing task lifecycle in action; `<tools>` for task tool descriptions. No changes to `<identity>` (rewritten in Phase 56) or `<constraints>` (task creation is judgment, not a safety boundary).
- **Prompt evolution — existing examples retained**: Phase 56 examples are retained unchanged. Phase 59 adds 1-2 new examples per orchestrator that demonstrate task lifecycle (creating a task, writing a handoff, delegating a subtask). Existing examples show core reasoning; new examples show task-aware reasoning.
- **Prompt evolution — graceful degradation**: A single note in `<domain_knowledge>`, not a constraint. Agents are told that if no `<task_context>` is present, their core capabilities work the same way. Avoids a MUST/ALWAYS directive for contextual awareness.
- **Prompt evolution — cross-agent delegation deferred**: Cross-agent delegation via `create_task` is not an expected v2.5 workflow for product-agent. Product-agent creates Linear issues that trigger dev-agent via webhooks — task correlation links the artifacts. Prompt guidance mentions delegation as a capability but examples focus on the current issue-creation workflow. Full agent delegation and orchestration is a separate milestone.
- **Hierarchy enforcement location**: Guardrails (depth limit, subtask cap, circular delegation) are added as guard checks in the existing `create_task` tool factory, before the `TaskService.create()` call. No separate utility or middleware — same file, same function, additional validation.
- **Circular delegation detection**: Iteratively walks the parent chain via `TaskService.get()`, bounded at 5 iterations by the depth limit. Detects delegation cycles, not self-decomposition: reject when the new task's assignee appears in the parent chain with a different assignee between them (A → B → A is circular, A → A is self-decomposition). Implementation: track whether a different assignee has been seen during the walk; if yes and the current assignee matches, reject. DB errors during the walk reject the creation (fail safe — don't allow a task you can't validate).
- **Task depth computation**: Computed by walking the parent chain, not stored as a column. The walk is bounded at 5 iterations. No `depth` column avoids consistency issues if tasks are ever reparented. In practice, most tasks are 1-2 levels deep.
- **Subtask limit enforcement**: Enforced by counting existing children via `TaskService.listByParent(parentId)` before insert. No database-level constraint — task creation is serialized per-task via advisory locks in the routing layer, and `create_task` calls within a single agent loop are sequential.
- **Hierarchy limits as constants**: Max depth 5, max subtasks per parent 10. Constants in the `create_task` tool code, not configurable per-agent. System-wide safety limits, not behavioral preferences.
- **Hierarchy violation error format**: Follows the existing `{ content, isError: true }` pattern. Messages include the limit hit, current state, and what the agent can do. E.g., "Cannot create subtask: parent task_abc123 already has 10 subtasks (maximum)." "Cannot create task: would exceed maximum depth of 5 levels." "Cannot create task: circular delegation — dev-agent delegates to product-agent which delegates back to dev-agent."
- **Product-agent task creation trigger**: Create a task when the conversation will produce artifacts (Linear issues, approval threads), not at every conversation start. Judgment-based on artifact commitment — "Will this conversation produce something that needs follow-up?" — not input classification (SIMPLE/COMPLEX). Pure information queries (status checks, listing issues) don't need tasks. Late task creation is fine: `create_task` retroactively links the existing conversation via `linkConversation()`.
- **Dev-agent task creation trigger**: Always create a task. The trigger (`linear.agent_session.created`) guarantees substantive work — there are no informational dev-agent conversations. Early creation maximizes MCP correlation coverage for artifact-creating calls (`create_branch`, `create_commit`, `create_pull_request`).
- **Task title convention**: No explicit prompt guidance. The agent naturally derives titles from triggering context (Linear issue title, user request summary). Don't prescribe copying external artifact titles verbatim — the agent's reframing can be more precise. Few-shot examples demonstrate good titles implicitly.
- **Task objective field**: Mentioned in `<domain_knowledge>` prompt guidance. The objective captures intent/why behind the work (not just what). Persists across conversations via `<task_context>` injection, preventing the telephone game effect through handoff chains. More valuable for dev-agent (captures why behind a Linear issue) than product-agent (objective overlaps with title for broad engagements), but the field is optional and the agent decides.
- **Dev-agent handoff content**: Taught via few-shot examples, not a checklist in `<domain_knowledge>`. Priority order for completion handoffs: (1) artifacts — PR URL, branch, key files changed (the "where to look"), (2) key decisions — approach chosen, tradeoffs made, constraints discovered (prevents revisiting or contradicting past work), (3) known limitations — intentional omissions, fragile areas, coverage gaps (prevents wasted investigation on known issues). Exclude step-by-step logs, file diffs, and tool call sequences — those belong to conversation history and the PR itself. The structured handoff schema (`summary`, `artifacts`, `key_decisions`, `open_questions`) maps directly to these priorities.
- **Product-agent handoff content**: Different emphasis — intent and agreements, not implementation. Priority order: (1) what was agreed with the human — decisions made during the conversation (prevents re-asking or contradicting), (2) the gap between ask and scope — the delta between what the user wanted and what was scoped into issues (prevents confusing "intentionally deferred" with "forgotten"), (3) artifacts created — Linear issue IDs, Slack threads, (4) open threads — deferred scope, "let's revisit" items. Exclude conversation back-and-forth, search steps, and message wording.
- **No bad examples in prompts**: Good handoff examples only. Bad examples are an anti-pattern — LLMs anchor on in-context patterns regardless of "don't do this" framing. A good example with the right detail level teaches by demonstration. If a specific failure pattern recurs in practice, add a targeted constraint reactively, not a preemptive bad example.
- **spawn_agent vs create_task(parentId)**: In v2.5, `spawn_agent` remains the mechanism for dev-agent → worker delegation (coder, researcher, tester). These are synchronous operations within a single conversation — no independent lifecycle, no follow-up routing, no handoffs needed. `create_task(parentId)` is for asynchronous work that needs independent tracking across conversations, which is a v2.6 cross-agent delegation pattern. Dev-agent prompt examples show `create_task` for its own task (no `parentId`) and `spawn_agent` for sub-agent work. Subtask creation via `parentId` works if used but is not the expected v2.5 pattern.
- **Task context on conversation start**: Agents rely on the injected `<task_context>` block, not a proactive `get_task_context` call. The block already includes task metadata + most recent full handoff, fetched fresh. A "call get_task_context for full history" pointer is included only when truncated or multiple handoffs exist — the agent calls the tool reactively when told there's more, not proactively on every start. No prompt guidance to "always check task context first" — that's a prescriptive tool sequence for information already in context.
- **Existing task lookup on new conversations**: No prescriptive `list_tasks` search on startup. For correlated follow-ups (same Slack thread, same PR), the correlation layer attaches `taskId` and routing handles it. For uncorrelated follow-ups (new thread referencing old work), the agent has `list_tasks` and can reason about when to use it — no prompt guidance needed, this is native LLM judgment. Known gap: new thread about old topic bypasses correlation. If frequent in practice, the fix is better correlation (e.g., user-level task affinity), not a prompt workaround.

## Scope Decisions

What's in v2.5, what's explicitly deferred, and why.

### In Scope

| Decision | Reasoning |
|----------|-----------|
| Prompt rewrites with traceability matrix | Net improvement over state machines. Manual scenario testing is sufficient — full eval tooling is disproportionate to the risk. |
| World-state injection on reopen | Must ship with Phase 2. Without it, reopened conversations act on stale context and erode trust. Non-negotiable. |
| Task primitive with structured handoffs | Core milestone capability. Zod validation and size limits on metadata/handoffs prevent the worst bloat without over-engineering. |
| Integration correlation (happy path) | Outgoing MCP correlation recording + incoming webhook lookup. Fire-and-forget on the recording side — missing correlations fall through to slow-path routing. |
| Advisory locks for task serialization | Solves the deadlock risk cleanly. Well-understood Postgres pattern. |
| ToolContext.taskId rename to sandboxId | Prerequisite for task primitive. Mechanical change, do it in the same phase. |

### Explicitly Deferred (Not v2.5)

| Decision | Reasoning |
|----------|-----------|
| Prompt evaluation tooling (promptfoo, shadow mode) | Building eval infrastructure is a milestone unto itself. Manual traceability matrix + scenario testing covers the v2.5 rewrite. Revisit when prompt changes become more frequent. |
| Integration correlation edge cases (Slack thread forking, GitHub force push, Linear status noise) | Low-frequency edge cases. Route to slow path as known limitations. Document them, monitor correlation miss rate, add handling in a later milestone if it proves to be a real problem. |
| Agent → human task notification | Schema supports it (polymorphic assignee). Delivery mechanism (Slack DM, Linear assignment) is future work. |
| Cross-agent task discovery | Requires task history to accumulate before it's useful. |
| Task analytics / cross-session learning | Aggregating patterns across completed tasks is post-v2.5. |
| Proactive task creation | Agents identifying work without event triggers needs a scheduling mechanism. |
| Many-to-many artifact correlation | Current one-to-one model (PK on external_type + external_ref) is an MVP constraint. Monitor for cases where it's insufficient (monorepo PRs fixing multiple issues). |
| Optimistic correlation / reconciliation job | The fire-and-forget model is sufficient for v2.5. If orphaned artifacts become a pattern (MCP succeeds but correlation recording fails), add the reconciliation job. |
| Handoff quality evaluation (LLM-as-judge) | Novel territory with no production validation. Structured schema + size limits are the v2.5 safeguard. Evaluate handoff quality from real usage before building automated evaluation. |
| Conversation reopening history reset | Keep full history on reopen for v2.5. If multi-reopen conversations become a token budget problem, add handoff-only context mode later. |

## Verification Checklist

Items that appear complete after implementing but have hidden failure modes. Use as a gate after each phase.

- [ ] **Prompt rewrites**: Traceability matrix complete — every removed if/then rule has an identified replacement. Key scenarios tested manually before and after.
- [ ] **Conversation reopening**: Tested with actual external state changes between conversation runs (not just "reopen with same state"). Signal payload carries delta information, not just "reopen."
- [ ] **Task schema migration**: Tested against a database with the legacy `tasks` table present, not just a fresh database.
- [ ] **Task serialization**: Tested with 10+ concurrent events targeting the same task. No deadlock errors in Postgres logs.
- [ ] **Integration correlation**: Tested the failure path (artifact created successfully, correlation recording fails). Webhook for that artifact routes via slow path, not silently lost.
- [ ] **Handoff chains**: Tested with 3+ chained handoffs. Information from the first handoff is retrievable via `get_task_context` at the end of the chain.
- [ ] **Backward compatibility**: Existing conversations (null task_id) survive the migration unchanged. Dashboard, routing, and agent tools all handle the null case.
- [ ] **Event routing latency**: Correlation lookup doesn't regress event routing p95 latency. Measured, not assumed.
