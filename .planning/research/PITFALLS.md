# Domain Pitfalls: Unified Agent Communication (v2.6)

**Domain:** Communication abstraction layer over multi-integration agent platform
**Researched:** 2026-02-08
**Overall confidence:** HIGH (based on deep codebase analysis of the full signal pipeline end-to-end)

---

## Critical Pitfalls

Mistakes that cause rewrites, data loss, or silent misbehavior across the signal pipeline.

---

### CRITICAL-1: replyContext Lost During History Compaction

**What goes wrong:** The replyContext is embedded in a signal's user message as an XML-tagged block (`<reply_context>{"channel":"slack",...}</reply_context>`). The history manager's Phase 2 summarization replaces old messages with a summary generated by Haiku. If the signal message containing the replyContext falls outside the `protectedMessages` boundary (default 20 messages for dev-agent, 10 for product-agent), the summarization LLM will either drop it entirely or paraphrase it -- destroying the structured JSON that the agent needs to pass through to `communication:reply`.

**Why it happens:** The history manager (`history-manager.ts`) has no concept of "this user message contains structured data that must survive intact." It treats all user messages as natural language eligible for summarization. With `protectedMessages: 20` and long conversations (100 max iterations for dev-agent), a signal received early in a conversation will eventually be summarized away. The agent then has no replyContext to pass to `communication:reply`.

**Consequences:**
- Agent tries to reply but has no valid replyContext -- tool call fails with Zod validation error
- Agent fabricates a replyContext from reasoning (e.g., guessing a Slack channel ID) -- message goes to the wrong channel or fails silently
- Agent falls back to `communication:notify` with a hardcoded target, breaking the "reply where the conversation is happening" principle

**Prevention:**
- Store the most recent replyContext on the conversation row (new JSONB column or in `pending_wait` metadata), not just in the message text
- When the signal is delivered, persist the replyContext as structured data alongside the conversation
- On resume, populate the replyContext into ToolContext so `communication:reply` reads it from infrastructure, not from the message history
- Alternative: add a replyContext preservation rule to the history manager that extracts and protects `<reply_context>` blocks during Phase 1 pruning (similar to how `<summary>` blocks are detected via `containsSummary()`)

**Detection:** Agent calls `communication:reply` with an empty, malformed, or hallucinated replyContext. Monitor for Zod validation failures on the replyContext schema and MCP 404/400 errors from integration endpoints.

**Phase to address:** Phase 1 (Foundation) -- this is infrastructure, not something to defer. The replyContext persistence mechanism must be designed before the tools consume it.

### CRITICAL-2: Signal Message Format Creates Fragile LLM Passthrough Contract

**What goes wrong:** The spec proposes embedding replyContext in the signal message as an XML tag:

```
Signal received: approval. Approved: yes, by Roberto.
<reply_context>{"channel":"linear","issueId":"uuid-abc"}</reply_context>
```

The agent must extract the JSON from between the tags and pass it verbatim to `communication:reply`. This is a fragile contract because:

1. The LLM may "helpfully" modify the JSON (reformat, add fields, change quotes, normalize values)
2. The LLM may extract only part of the replyContext (e.g., just the channel field)
3. Multiple signals in a conversation mean multiple `<reply_context>` blocks -- the agent must use the most recent, not an earlier one
4. The model may merge fields from different replyContext blocks across signals
5. String values like `threadTs: "1234567890.000000"` may be truncated to `"1234567890"` (loses Slack precision)

**Why it happens:** LLMs treat all input as malleable text. Asking an LLM to pass structured data through unchanged fights against its core behavior of interpreting and reformulating. The model genuinely tries to be helpful by "fixing" the JSON.

**Consequences:**
- `channel` changed from `"slack"` to `"Slack"` -- Zod enum validation fails
- `threadTs` truncated -- Slack API returns "thread_not_found"
- `issueId` rewritten from UUID to human-readable format -- Linear API returns 404
- Agent uses replyContext from signal 2 turns ago instead of the most recent one

**Prevention -- the architectural decision:**

| Approach | Pros | Cons |
|----------|------|------|
| **LLM passthrough** (spec's current design) | No ToolContext changes; agent has full control; can modify replyContext intentionally | Fragile; replyContext mutated, lost in compaction, or used from wrong signal |
| **Infrastructure-level** (recommended) | Robust; survives compaction; impossible to mutate; no prompt burden | Agent can't override reply target; requires ToolContext + worker loop changes |

**Recommendation:** Use infrastructure-level for `communication:reply` (reply to the most recent signal's origin) and require explicit target only for `communication:notify` (broadcast to a specific channel). This eliminates the highest-risk pitfalls while preserving flexibility where it's actually needed.

If the LLM-passthrough approach is kept despite this recommendation:
- Make the tool's `replyContext` field accept a JSON string and parse server-side with lenient normalization
- Add `.passthrough()` to the Zod replyContext schema so extra fields don't cause failures
- Add explicit prompt examples showing the exact copy-paste pattern
- Log and diff every replyContext received vs. the one in the originating signal

**Phase to address:** Phase 1 (Foundation) -- this is the most consequential architectural decision in the milestone. Decide LLM passthrough vs. infrastructure-level before building anything.

### CRITICAL-3: Router Doesn't Propagate replyContext Through Any of Three Routing Paths

**What goes wrong:** replyContext must be threaded through THREE separate code paths that construct signals from events. All three currently drop it:

**1. Fast-path EventRouter** (`event-router.ts`, lines 125-131):
```typescript
const signal: Signal = {
  type: event.type,
  data: event.data,
  message: event.message,
  source: event.source,
  deduplicationId: event.deduplicationId,
  // replyContext: event.replyContext  <-- MISSING
};
```

**2. Slow-path signal_conversation tool** (`signal-conversation.ts`): The tool's input schema has no `replyContext` field. The router LLM (Haiku) classifies the event and calls `signal_conversation` but cannot pass replyContext because the schema doesn't accept it.

**3. Task-aware routing** (`router.ts`, lines 87-93): `routeViaTask()` constructs a signal without replyContext.

Missing any one of these three breaks the chain for events routed through that path.

**Why it happens:** The `SignalSchema` in `types.ts` doesn't have a `replyContext` field. Adding `replyContext` to `IncomingEventSchema` doesn't automatically propagate it through existing code that destructures specific fields into Signal objects.

**Consequences:**
- All fast-path signals (Slack button clicks, PR merged/closed) arrive at the agent without replyContext
- All slow-path signals (Linear comments, Slack thread replies, PR reviews) arrive without replyContext
- All task-routed signals arrive without replyContext
- The agent has `communication:reply` but nothing to reply TO

**Prevention:**
1. Add `replyContext` to `SignalSchema` in `types.ts`
2. Add `replyContext` to `signal_conversation` tool's input schema
3. Update the router system prompt to instruct the LLM to propagate replyContext
4. Create a shared helper `buildSignalFromEvent(event: IncomingEvent): Signal` used by all three paths
5. Update the executor's signal delivery to include replyContext in the user message (or persist it infrastructure-level per CRITICAL-2)
6. Write a test for each routing path that verifies replyContext survives from adapter to agent

**Phase to address:** Phase 1 (Foundation) -- extend schemas and all three routing paths together. Do not address them in separate phases.

### CRITICAL-4: Simultaneous Prompt and Tool Changes Break Agent Behavior

**What goes wrong:** The migration replaces `slack:send_message` and `slack:send_approval_request` with `communication:reply`, `communication:ask`, and `communication:notify` in agent definitions. This requires changes to both `definition.yaml` (tool list) and `prompt.md` (behavioral guidance) simultaneously.

Failure scenarios:

1. **Tools removed, prompt not updated:** Agent prompt says "send a Slack notification" but `slack:send_message` is gone. Agent tries to call a non-existent tool, gets an error, retries with variations, exhausts iterations.

2. **Prompt updated, tools not available:** Agent prompt says "use communication:reply" but `communication:*` tools aren't registered in `tool-factories.ts` yet. `toolRegistry.resolve()` throws with "missing refs" error on conversation start.

3. **Both changed but prompt guidance insufficient:** Agent has `communication:reply` but the prompt doesn't explain replyContext. Agent fabricates arguments or calls the tool with wrong parameters.

**Why it happens:** YAML definitions and prompt.md are loaded from disk by the AgentRegistry with mtime-based caching. Both files must be coherent at any given time. The tool registry must have all referenced tools registered before any conversation tries to resolve them.

**Consequences:**
- Conversation fails immediately on tool resolution ("tool not found" error in `toolRegistry.resolve()`)
- Agent wastes tokens attempting workarounds
- In-flight conversations break if agent definitions are changed during execution (stale recovery re-enqueues with new definition)

**Prevention:**
- Phase the rollout: (1) register `communication:*` tools in tool-factories.ts, (2) add `communication:*` to agent definition.yaml ALONGSIDE existing Slack tools (both available), (3) update prompts to prefer `communication:*`, (4) remove Slack tools from agent definitions only after validation
- Keep Slack tools in the global registry even after removing them from agent definitions -- the router still uses `slack:send_message` for alerts
- Never remove old tools from agent definitions until the new tools are proven end-to-end
- Add a startup validation: for each agent definition, verify all tool refs resolve in the registry. Fail fast with a clear error.

**Phase to address:** Phase 2 creates tools, Phase 3 migrates agents. The spec already has this phasing -- do NOT collapse these phases into one.

### CRITICAL-5: MCP Tools Don't Exist Yet for Linear and GitHub Communication

**What goes wrong:** The denormalizer calls:
- `linear:create_comment` -- exists in the Linear integration package code but is NOT registered in the MCP server tool list and NOT in the agent-side `linear-tools.ts`
- `github:create_pr_comment` -- does not exist at all. No implementation, no MCP handler, no tool wrapper.

If the denormalizer calls a non-existent MCP tool, the HTTP POST to the integration returns 404. The `communication:reply` tool returns an error. The agent sees "reply failed" but has no fallback.

**Why it happens:** The communication abstraction depends on integration-level capabilities that were never needed before. Agents never replied on Linear or GitHub -- all outbound was through Slack. "Exposing" the Linear tool requires: MCP handler registration, permission seeding. "Creating" the GitHub tool requires: Octokit implementation, MCP handler, permission seeding, agent-side wrapper.

**Consequences:**
- `communication:reply` returns an error when `replyContext.channel` is "linear" or "github"
- The channel-agnostic abstraction only works for Slack, defeating its purpose
- Agent enters error handling for what should be a normal operation

**Prevention:**
- Build and validate MCP tools BEFORE building the denormalizer that calls them
- For each new MCP tool, the checklist is: (1) integration-side implementation, (2) MCP handler registration, (3) permission seed script update, (4) run seed script, (5) agent-side tool wrapper for the denormalizer to call via `callMcpTool`
- Write integration tests that call each MCP tool directly (HTTP to the integration service) before wiring the denormalizer
- For GitHub `create_pr_comment`: use Octokit's `issues.createComment` (PR comments are issue comments in GitHub's API) or `pulls.createReviewComment` for inline comments

**Phase to address:** Phase 2, first sub-phase. The denormalizer is only as useful as the endpoints it calls.

### MAJOR-1: Capability Asymmetry Creates Divergent Signal Flows

**What goes wrong:** When the agent calls `communication:ask` with options (approval buttons):
- **Slack denormalizer** renders buttons via `send_approval_request`. Button click fires `slack.block_actions.approved` which fast-paths to an `approval` signal.
- **Linear denormalizer** renders options as text: "Reply 'approve' or 'reject'". Human reply fires `linear.comment.created` which goes to the slow-path router for Haiku classification.
- **GitHub denormalizer** renders options as text. Human PR comment fires a PR event, also slow-path.

The signal flow is different even though the semantic intent is identical:
- Slack approval: fast-path, immediate, type-matched resume
- Linear approval: slow-path, Haiku classification, potential misclassification, higher latency

The agent calls `wait_for(type: "approval")`. From Slack, it receives a clean `approval` signal. From Linear, it might receive `user_reply` or `issue_comment` depending on how the router classifies the response. If the signal type doesn't match the `wait_for` type, the signal is **rejected** (conversation-executor.ts, lines 365-376).

**Consequences:**
- Linear/GitHub approval responses rejected due to type mismatch with `wait_for`
- Agent stays paused indefinitely waiting for an `approval` signal that will never arrive
- User posted "approve" on the Linear issue but the agent doesn't respond

**Prevention:**
- Ensure the router's Linear comment classification path generates `approval` signals (not `user_reply`) when the comment is a response to an agent's `ask()` prompt
- Consider broadening `wait_for` to accept multiple signal types or removing type matching entirely (any signal resumes)
- Document the asymmetry in agent prompts so the agent expects different response paths
- Test the full round-trip for each channel: ask on Slack (button response), ask on Linear (text response), ask on GitHub (PR comment response)

**Phase to address:** Phase 1 (router prompt updates) and Phase 3 (agent prompt guidance).

### MAJOR-2: notify() Target Requires Information the Agent Doesn't Have

**What goes wrong:** `communication:notify` requires an explicit target: `{ channel: "slack", teamId: "T789", channelId: "C-alerts" }`. The agent must know the Slack team ID and channel ID.

For dev-agent conversations started via Linear (`linear.agent_session.created`, `source: "linear:webhook"`), there is no `<slack_context>` in the initial message. The enrichment function (`enrichment.ts`, lines 64-73) only adds `<slack_context>` for `source === "slack:webhook"` events.

The dev-agent currently uses hardcoded Slack channel references in its prompt and environment. With the abstraction layer, the prompt says "use notify() for escalations" but the agent has no `NotifyTarget` to construct.

**Consequences:**
- Agent tries to call `communication:notify` without a valid target -- Zod validation error
- Agent fabricates a Slack channel ID -- message goes to wrong channel or API returns error
- Escalation notifications silently fail, leaving the human unaware of blockers

**Prevention:**
- Add a `defaultNotifyTarget` to the agent definition YAML or workspace configuration
- Inject this target into the conversation's initial message or into ToolContext
- Alternative: have the denormalizer accept a "default" target that routes to a configured notification channel
- In the short term, keep the Slack channel ID in the dev-agent prompt as a literal fallback

**Phase to address:** Phase 3 (Agent Migration) -- design the default target mechanism when updating prompts.

### MAJOR-3: Product-Agent Prompt Deeply Assumes Slack-Specific Communication

**What goes wrong:** The product-agent prompt has deep Slack assumptions:

- **Line 15:** "Communicate with the user only through slack_send_message -- text output is internal reasoning only, never user-facing."
- **Lines 117-122:** "Your initial message includes a <slack_context> block... use as the 'channel' parameter in slack_send_message calls."
- **Line 130:** "Send messages: Communicate with the user via Slack (your only channel for user-facing communication)."

Simply replacing `slack:send_message` with `communication:reply` in the YAML without rewriting these prompt sections creates conflicting instructions. The prompt says "communicate through slack_send_message" but the tool doesn't exist.

**Consequences:**
- Agent attempts to call `slack_send_message` (the LLM sees display names) after the tool is removed
- Agent becomes confused by contradictory instructions and may stop communicating entirely
- Tool call errors consume iterations and token budget

**Prevention:**
- Rewrite the product-agent prompt holistically, not just find-and-replace tool names
- Replace `<slack_context>` extraction guidance with replyContext guidance
- Replace "channel parameter in slack_send_message" with "pass replyContext from the signal to communication:reply"
- Test the rewritten prompt with actual conversation scenarios

**Phase to address:** Phase 3 (Agent Migration) -- prompt rewrite is the core work of this phase.

### MAJOR-4: Linear Comment Routing Gap for Terminal Conversations

**What goes wrong:** The router system prompt has detailed "query status -> reopen if completed" routing for Slack thread replies, but only 4 lines for Linear comments:

```
For Linear comments (linear.comment.created):
1. Extract issueId
2. Derive conversationId: dev-agent-{issueId}
3. Classify intent
4. signal_conversation
```

This misses the reopen flow. If a Linear comment arrives for a completed dev-agent conversation, the router calls `signal_conversation` which returns `rejected` (terminal state, conversation-executor.ts lines 462-467). The comment is silently dropped. The human posted feedback on a Linear issue and got no response.

With the communication abstraction promoting Linear as a first-class channel, this gap is amplified. Users will comment on Linear issues expecting responses.

**Consequences:**
- Linear comments for completed conversations silently dropped
- Human gets no response to their feedback
- Trust in the system erodes

**Prevention:**
- Add the same "query_conversations -> check status -> reopen if terminal" flow to the Linear comment section of the router system prompt
- Test: create a dev-agent conversation, let it complete, post a comment on the Linear issue. Verify the conversation reopens and the agent replies on Linear.

**Phase to address:** Phase 1 or Phase 3 -- router prompt update.

### MODERATE-1: Slack send_approval_request Needs taskIdentifier for Callback Correlation

**What goes wrong:** The Slack denormalizer for `ask()` with options calls `send_approval_request` which requires a `taskIdentifier` field. This is how Slack button callbacks correlate back to the conversation -- the `block_actions.approved` event carries `taskIdentifier` as the correlation key (slack.ts adapter, line 39: `const taskId = payload.taskIdentifier as string`).

Currently, the dev-agent provides taskIdentifier explicitly. With the abstraction, the agent calls `communication:ask` without knowing about Slack internals. The denormalizer must derive the `taskIdentifier`.

The full callback path: `send_approval_request(taskIdentifier: X)` -> button click -> `slack.block_actions.approved` -> adapter extracts `correlationKey: X` -> fast-path EventRouter -> signal to `dev-agent-X`. So `taskIdentifier` must equal the correlation key (Linear issue UUID), which is embedded in the conversation ID (`dev-agent-{issueId}`).

**Prevention:**
- Extract the correlation key from the conversation ID: parse out the part after the agent prefix
- Better: store the original correlation key on the conversation row and expose via ToolContext
- Or use the `taskId` from the v2.5 task primitive if available
- Trace the full callback round-trip in a test before deploying

**Phase to address:** Phase 2 (Outbound Denormalizer).

---

### MODERATE-2: GitHub PR Review Events Have No correlationKey

**What goes wrong:** The GitHub adapter (github.ts, lines 73-93) handles PR review events but has: "No correlationKey -- PR reviews don't include branchName, always goes to slow_path." The slow-path router must figure out which conversation to signal.

With the communication abstraction adding replyContext, the adapter needs to attach `replyContext: { channel: "github", owner, repo, prNumber }`. But since there's no correlationKey, the router can't derive the conversation ID deterministically.

**Prevention:**
- Update the GitHub adapter to include PR number and repo info in the correlation pipeline
- Use task routing: if the PR is linked to a task, task routing finds the active conversation regardless of correlationKey
- Add PR-specific routing logic to the router system prompt: "For PR reviews, query conversations with the PR number to find the associated dev-agent conversation"

**Phase to address:** Phase 1 (Foundation) -- update GitHub adapter alongside Linear and Slack adapters.

### MODERATE-3: Fast-Path EventRouter Signal Construction Doesn't Copy replyContext

**What goes wrong:** Even after adding `replyContext` to `IncomingEventSchema` and updating all adapters to populate it, the fast-path EventRouter (`event-router.ts`) constructs signals by manually copying specific fields (lines 125-131). It doesn't include `replyContext` because the field didn't exist when the code was written.

This is separate from CRITICAL-3 (which is about the overall propagation gap) -- this specific pitfall is about the most easily missed code path because the EventRouter is synchronous and pure, so it's easy to think "I already updated the adapters, signals should work."

**Prevention:**
- Use a shared `buildSignalFromEvent()` helper instead of manual field copying
- Add a TypeScript type assertion or exhaustive mapping to ensure all IncomingEvent fields are considered

**Phase to address:** Phase 1 (Foundation).

### MODERATE-4: Denormalizer Error Messages Don't Identify Which Channel Failed

**What goes wrong:** When the denormalizer's MCP call fails (e.g., Linear API rate limited, GitHub 500), the `communication:reply` tool returns an error. Current integration tools surface integration-specific errors ("linear_get_issue error: Rate limited"). The communication tool abstracts the integration away -- the agent sees "Reply failed" but doesn't know if it's Slack, Linear, or GitHub failing.

**Prevention:**
- Include the channel name in error messages: "Reply failed (linear): Rate limited"
- Return structured error data: `{ channel: "linear", retryable: true, error: "Rate limited" }`
- Add prompt guidance: "If reply() fails, retry once. If it fails again, try notify() on a different channel."

**Phase to address:** Phase 2 (Outbound Denormalizer).

---

### MODERATE-5: Tool Name Collision in History Manager Classification

**What goes wrong:** The history manager's `classifyTool` function (history-manager.ts, lines 214-244) classifies tools by name prefix: `linear_`, `github_`, `slack_` are "integration" tier. New communication tools will have display names like `communication_reply`, `communication_ask`, `communication_notify`. These don't match any tier and fall into "unknown" -- left untouched during pruning. Communication tool results won't benefit from Phase 1 compaction.

**Prevention:**
- Add `communication_` prefix to the integration tier in `classifyTool()`
- Communication tool results ("comment created successfully") are good candidates for minimal descriptors

**Phase to address:** Phase 4 (Cleanup).

---

### MODERATE-6: Backward Compatibility During Rolling Deployment

**What goes wrong:** During deployment, old worker instances have old agent definitions (with `slack:send_message`), new instances have new definitions (with `communication:reply`). A conversation started on an old worker may be resumed on a new worker after stale recovery.

The `agent_definition_version` is recorded at creation time (currently "1"). The AgentRegistry loads from disk by agent ID -- version is informational. Changing the YAML without bumping version means the same version string maps to different definitions before/after deployment.

**Prevention:**
- Bump agent definition version when changing tool lists ("1" -> "2")
- Accept that in-flight conversations will use the new definition on resume (this is current behavior)
- Test: create a conversation with old tools, deploy new definitions, resume. Verify no crash.
- Ensure new prompts handle conversation history that references old Slack tools

**Phase to address:** Phase 3 (Agent Migration).

## Architectural Decision: LLM Passthrough vs. Infrastructure-Level replyContext

This is the most consequential design decision in the milestone. The spec proposes LLM passthrough (agent extracts `<reply_context>` from signal message, passes to tool). The alternative is infrastructure-level storage.

**LLM Passthrough (spec's current approach):**
```
Signal message -> Agent sees <reply_context>JSON</reply_context> -> Agent passes JSON to communication:reply
```
- Fragile: LLM may mutate, lose, or misattribute the JSON (CRITICAL-1, CRITICAL-2)
- Lost on history compaction (CRITICAL-1)
- Requires prompt training for every agent
- Every signal handling path must embed it in the message text

**Infrastructure-Level (recommended alternative):**
```
Signal arrives -> Executor stores replyContext on conversation row -> Worker loop populates ToolContext.replyContext -> communication:reply reads from ToolContext
```
- Robust: survives compaction, impossible to mutate, no prompt burden
- Requires changes to: conversation schema (new column), Signal delivery, worker loop ToolContext construction
- Agent cannot override reply target (acceptable for reply; notify still takes explicit target)
- Most recent replyContext always available without parsing message history

**Recommendation:** Infrastructure-level for `communication:reply` and `communication:ask` (the common case: reply where the conversation is happening). Explicit target parameter only for `communication:notify` (the uncommon case: broadcast to a specific channel). The agent decides WHAT to say; the infrastructure decides WHERE to send it.

This eliminates CRITICAL-1, CRITICAL-2, and significantly simplifies CRITICAL-3 (only need to persist replyContext, not thread it through message text).
