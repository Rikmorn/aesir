  <action>
    **QueryKnowledgeParamsSchema changes:**
    Add two optional fields:
    ```typescript
    mode: z.enum(['semantic', 'exact', 'combined']).optional().default('semantic'),
    metadata: z.record(z.unknown()).optional(),
    ```

    **StoreKnowledgeParamsSchema changes:**
    Add optional metadata field:
    ```typescript
    metadata: z.record(z.unknown()).optional(),
    ```

    **query() method changes:**
    Refactor the existing query logic to handle 3 modes:

    1. **`semantic` (default -- existing behavior unchanged):** Current embedding-based cosine similarity search. No change to existing logic. If `metadata` filter is provided in semantic mode, add it as an additional WHERE condition (JSONB containment `@>`).

    2. **`exact` mode:** Skip embedding entirely. Build WHERE clause from base conditions + metadata containment. Order by `created_at DESC`. This mode works even without an embedding service available.
       ```typescript
       if (validated.metadata) {
         baseConditions.push(
           sql`${knowledgeEntries.metadata} @> ${JSON.stringify(validated.metadata)}::jsonb`
         );
       }
       ```
       Select and return rows ordered by created_at DESC, limited by limit.

    3. **`combined` mode:** Filter by metadata first (WHERE clause with `@>` containment), then rank by semantic similarity within matches. If embedding fails, fall back to metadata-only ordering by created_at.

    **store() method changes:**
    Pass `metadata` through to `insertEntry()`. Update `insertEntry()` to accept and insert optional metadata (defaulting to `{}`).

    **KnowledgeQueryResult type changes:**
    Add optional `metadata` field so query results include the metadata:
    ```typescript
    metadata?: Record<string, unknown>;
    ```

    **Backward compatibility:** The `mode` field defaults to `'semantic'` and `metadata` is optional. Existing callers pass neither -- they get identical behavior. The `query` field remains required even in exact mode (the query string acts as a label/context for logging, not for search).

    Actually, reconsider: in exact mode, the query string is not used for search. But it's already required by the schema. Keep it required for backward compatibility and use it only for logging in exact mode. The semantic query is only performed when mode is 'semantic' or 'combined'.
  </action>
