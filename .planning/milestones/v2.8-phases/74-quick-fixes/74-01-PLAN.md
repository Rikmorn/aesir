  <action>
    In `get-task-context.ts`, change the no-taskId branch (lines 43-49) from returning `isError: true` to returning an informational message without the error flag.

    Current code:
    ```typescript
    const taskId = parsed.data.taskId ?? ctx.taskId;
    if (!taskId) {
      return {
        content: "No task ID provided and no task associated with this conversation.",
        isError: true,
      };
    }
    ```

    Replace with:
    ```typescript
    const taskId = parsed.data.taskId ?? ctx.taskId;
    if (!taskId) {
      return {
        content: "No active tasks found for this conversation.",
      };
    }
    ```

    Per the locked decision: "Empty result, not null, not an error." The `isError: true` flag causes the LLM to treat "no tasks" as a failure, leading to retries or error escalation. Removing it lets the agent reason about the empty state naturally.

    Then create or update `get-task-context.test.ts` with a unit test. Follow the existing test patterns in the `task/` directory (see `create-task.test.ts` for mock helpers). The test needs:

    1. A test that verifies: when `ctx.taskId` is undefined and no `taskId` input is provided, the tool returns `{ content: "No active tasks found for this conversation." }` with `isError` being undefined/falsy.
    2. A test that verifies: when a valid `taskId` is provided (either via input or ctx), the tool works normally (returns task metadata). Mock `taskService.get()` to return a task object and `taskService.getHandoffs()` to return an empty array.

    Create the test file with the same structure as `create-task.test.ts`: mock `TaskService` with all methods as `vi.fn()`, create a mock `ToolContext` with agentId, correlationId, logger.
  </action>

    ```typescript
    const SpawnAgentInputSchema = z.object({
      agentType: z
        .string()
        .min(1)
        .describe("Role of sub-agent to spawn (must match a key in the agent's subAgents mapping)"),
      task: z.string().describe("Task description for the sub-agent to execute"),
      context: z
        .string()
        .optional()
        .describe("Additional context to prepend to the task"),
    });
    ```

    2. **Update the tool description** (lines 57-61). The current description hardcodes "researcher/coder/tester" which is misleading after the schema change:
    ```typescript
    description:
      "Spawn a focused sub-agent to perform a specific task. " +
      "The agent type must match a role defined in this agent's subAgents mapping. " +
      "Each sub-agent shares the token budget with the orchestrator.",
    ```

    The existing `subAgents` mapping check at lines 84-93 already validates the role and returns a descriptive error listing available roles. The Zod enum was a redundant, overly-restrictive guard.

    Then in `spawn-agent.test.ts`, add a new test case that exercises a custom agentType:

    ```typescript
    it("accepts custom agentType matching subAgents mapping", async () => {
      const childDef = createMockDefinition({
        id: "test-subagent-child",
        name: "Test SubAgent Child",
      });
      const deps = createMockSpawnDeps({
        parentDefinition: createMockParentDefinition({
          subAgents: { worker: "test-subagent-child" },

        agentType: "worker",
        task: "perform test work",

      expect(result.isError).toBe(false);
      expect(deps.agentRegistry.get).toHaveBeenCalledWith("test-subagent-child");
    });
    ```

    This test proves that roles like "worker" (used by test-subagent-parent) are now accepted. Verify all existing spawn-agent tests still pass -- the existing tests use "coder" and "researcher" which are valid strings under the new schema.
