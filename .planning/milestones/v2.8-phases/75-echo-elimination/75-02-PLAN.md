    ```typescript
      email: z.string().optional(),

    }).optional(),
    ```

    Add `actorType` to the payload:
    ```typescript
    payload: {
      // ... existing fields
      actorType: payload.actor?.type,  // NEW: for echo detection
    },
    ```

    **3. AgentSessionPayload (webhooks/types.ts):**
    The AgentSessionPayload type doesn't have actor info today. Add an optional `actor` field:
    ```typescript
    actor?: {
      type?: string;
    };
    ```

    **4. normalizeAgentSessionEvent (dispatcher/normalize.ts):**
    Accept the optional actor type and include in payload:
    ```typescript
    payload: {
      // ... existing fields
      actorType: payload.actor?.type,  // NEW: for echo detection
    },
    ```

    **5. Webhook handler (api/webhooks.ts):**
    For Comment events: `actorType` flows automatically because `parseCommentPayload` already parses the actor object -- no change needed if the schema captures it.

    For AgentSession events: The raw `basicPayload` parsed from JSON needs the actor field threaded through. After `parseAgentSessionPayload(rawBody)`, the validated payload needs to include the actor. Update the AgentSessionPayload Zod schema or the basic parse to extract `actor.type` from the raw JSON:
    - Parse `basicPayload.actor?.type` from the raw JSON
    - Pass it through to the normalize function by setting it on the payload object before normalization

    **IMPORTANT:** AgentSession events from Linear are from the Linear platform triggering a session, not from a user or bot. The actor.type on these may be undefined. That's fine -- the adapter will treat missing actorType as "not a bot" (fail-open).

    **Backward compatibility:** All new fields are optional. Existing payloads without actor.type will have `actorType: undefined` in the normalized payload, which is safe.

    **GitHub -- Thread sender into normalize functions:**

    **1. normalizePRReviewEvent (dispatcher/normalize.ts):**
    Add optional `sender` parameter and include in payload:
    ```typescript
    export function normalizePRReviewEvent(
      payload: PRReviewPayload,
      deliveryId: string,
      sender?: { login: string; type?: string },  // NEW
    ): NormalizedEvent {
      return {
        // ... existing fields
        payload: {
          // ... existing fields
          ...(sender && { sender }),  // NEW: for echo detection
        },
      };
    }
    ```

    **2. normalizePRClosedEvent (dispatcher/normalize.ts):**
    Same pattern -- add optional sender parameter and spread into payload.

    **3. normalizePRMergedEvent (dispatcher/normalize.ts):**
    Same pattern (unused today but keep consistent).

    **4. Webhook handler (api/webhooks.ts):**
    Extract `sender` from the parsed payload and pass to normalize functions.
    For PR reviews: `payload` is `PRReviewPayload`. The `WebhookPayloadBase` type includes `sender?: { login: string; id: number }`. Cast the raw payload to access sender:
    ```typescript
    const rawPayload = JSON.parse(rawBody) as { sender?: { login: string; type?: string } };
    const normalizedEvent = normalizePRReviewEvent(payload, deliveryId, rawPayload.sender);
    ```
    For PR closed: Same approach -- extract sender from the raw parsed JSON and pass to `normalizePRClosedEvent`.

    **Slack -- Thread api_app_id into normalize functions:**

    **1. normalizeMessageEvent (dispatcher/normalize.ts):**
    Add `apiAppId` to the NormalizedEvent payload. The `SlackEventPayload` already has `raw` which contains the parsed event. For Events API events, the `BaseEventSchema` has `api_app_id`.
    Read it from `payload.raw`:
    ```typescript
    payload: {
      // ... existing fields
      ...('api_app_id' in payload.raw && payload.raw.api_app_id && { apiAppId: payload.raw.api_app_id }),
    },
    ```

    **2. normalizeAppMentionEvent (dispatcher/normalize.ts):**
    Same pattern -- include `apiAppId` from `payload.raw.api_app_id`.

    **3. Slack main.ts -- no changes needed for Events API events.** The `normalizeEvent` function already captures the raw event object, and the normalize functions will now extract `api_app_id` from it.

    **4. Slack block_actions (main.ts):** Block actions are already user-initiated (button clicks) per research. The normalized events dispatched for block_actions don't go through `normalizeSlackEvent` -- they're manually constructed in the action handlers. No `apiAppId` needed for these.

    **Backward compatibility:** All new fields are optional. Existing payloads without sender/apiAppId will have undefined values, which is safe.
