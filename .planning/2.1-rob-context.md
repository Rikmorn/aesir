## v2.1 Focus: Agent Intelligence

### Background

v2.0 Foundation (Phases 10-22) established the platform infrastructure. MVP was validated but painful to test/setup — hence the cleanup effort. The agents themselves are basic ("fairly dumb") — plumbing works, intelligence doesn't.

v2.1 shifts focus entirely to agent capabilities. Infrastructure is good enough.

### Approach

**Don't:**
- Build abstract "memory systems" or "reasoning modules"
- Over-plan the milestone upfront
- Do workflow walkthroughs of current agent (it's too basic to learn from)

**Do:**
- Pick real projects as test cases
- Define what success looks like for specific tasks
- Build capability, test on real work, see what breaks
- Let phases emerge from actual gaps

### v2.1 Structure

**Phase 23:** Agent can take a Linear issue and produce a working PR for a simple, well-defined task (first test project)

**Phase 24+:** Based on what Phase 23 reveals — might be context retrieval, code quality, knowing when to ask for help, etc.

Plan Phase 23 in detail. Let it inform the rest.

### Discussion Focus When Starting v2.1

1. **Pick the first project** — What's a real task? What does success look like?
2. **Minimum viable intelligence** — What does agent need to do for this project?
3. **Iteration approach** — Build, test on real project, fix what breaks

## Agent Workflow Pattern

The discuss → research → plan → execute → verify pattern produces good results (GSD uses it). Implement as single-agent state machine first. Multi-agent coordination is a later optimization.

```
Agent State Machine:
┌─────────┐
│ Discuss │ ← Clarify issue, ask questions if ambiguous
└────┬────┘
     ▼
┌──────────┐
│ Research │ ← Find relevant code, understand context
└────┬─────┘
     ▼
┌──────┐
│ Plan │ ← Outline approach, identify files to change
└───┬──┘
    ▼
┌─────────┐
│ Execute │ ← Write code, create commits
└────┬────┘
     ▼
┌────────┐
│ Verify │ ← Run tests, self-review, check requirements met
└────┬───┘
     ▼
  [Done or loop back]
```

Each phase produces artifacts. Human can approve between phases or let it run.

## Core Vocabulary

### Agent
The overall system that takes a task and produces an outcome. Has identity, memory, and capabilities.

### Workflow
A defined sequence of phases to accomplish a type of task. Different task types might use different workflows.

```
"Feature Workflow" = discuss → research → plan → execute → verify
"Bug Fix Workflow" = research → execute → verify (simpler)
```

### Phase
A bounded step in a workflow with:
- **Entry criteria**: What must be true to start
- **Goal**: What this phase accomplishes
- **Inputs**: What it receives from previous phase
- **Outputs**: Artifacts it produces
- **Exit criteria**: What must be true to proceed

### Artifact
A concrete output from a phase. Not ephemeral thoughts — persisted, observable, referenceable.

```
Research Phase → Context Artifact (relevant files, patterns found)
Plan Phase → Plan Artifact (approach, files to change, steps)
Execute Phase → Code Artifact (commits, PR)
Verify Phase → Verification Artifact (test results, checklist)
```

### Checkpoint
A point between phases where:
- Artifacts are persisted
- Agent can pause/resume
- Human can review/approve/reject
- Workflow can branch (retry phase, skip phase, abort)

### Context
Information the agent carries through the workflow:
- **Task context**: The original request, requirements
- **Accumulated context**: What's been learned (from research, from failures)
- **Codebase context**: Relevant code snippets, patterns

### Tool
An atomic capability the agent can invoke. Tools don't have phases — they do one thing.

```
Tools: read_file, search_code, create_branch, run_tests, ask_human
```

### Phase vs Tool (Important Distinction)
- **Tool**: Single action, no internal state, immediate result
- **Phase**: Multi-step process, has artifacts, has entry/exit criteria

```
"Search for authentication code" = Tool (grep/search)
"Research how auth works in this codebase" = Phase (multiple searches, reading, synthesizing)
```

## Phase Definitions

### 1. Discuss Phase
**Goal:** Ensure requirements are clear and unambiguous

**Entry criteria:** Task received (Linear issue, Slack message, etc.)

**What it does:**
- Parse the request
- Identify ambiguities or missing information
- Ask clarifying questions (or make stated assumptions)
- Confirm scope boundaries

**Artifact:** `ClarifiedTask`
```typescript
{
  originalRequest: string;
  interpretation: string;      // Agent's understanding
  assumptions: string[];       // What agent assumed
  clarifications: string[];    // Answers received from human
  scope: {
    includes: string[];
    excludes: string[];
  };
  acceptanceCriteria: string[]; // How to know it's done
}
```

**Exit criteria:** Agent can state what it's building and how to verify success

---

### 2. Research Phase
**Goal:** Gather context needed to plan the work

**Entry criteria:** ClarifiedTask artifact exists

**What it does:**
- Find relevant code (search, read files)
- Understand existing patterns
- Identify dependencies and constraints
- Note potential risks or unknowns

**Artifact:** `ResearchContext`
```typescript
{
  relevantFiles: {
    path: string;
    why: string;           // Why this file matters
    keySnippets: string[]; // Important code sections
  }[];
  patterns: {
    name: string;
    example: string;
    shouldFollow: boolean;
  }[];
  dependencies: string[];   // What this work touches
  risks: string[];          // Potential issues spotted
  unknowns: string[];       // Things agent couldn't determine
}
```

**Exit criteria:** Agent knows where to make changes and what patterns to follow

---

### 3. Plan Phase
**Goal:** Define the approach before writing code

**Entry criteria:** ResearchContext artifact exists

**What it does:**
- Break work into steps
- Identify files to create/modify
- Sequence the changes
- Define verification approach

**Artifact:** `ExecutionPlan`
```typescript
{
  approach: string;         // High-level strategy
  steps: {
    order: number;
    description: string;
    files: string[];        // Files this step touches
    verification: string;   // How to verify this step worked
  }[];
  testStrategy: string;     // How to test the whole thing
  rollbackPlan: string;     // If it fails, how to recover
}
```

**Exit criteria:** Agent can describe exactly what it will do without ambiguity

---

### 4. Execute Phase
**Goal:** Implement the plan

**Entry criteria:** ExecutionPlan artifact exists

**What it does:**
- Create branch
- Make changes per plan steps
- Commit incrementally
- Run tests as it goes

**Artifact:** `Implementation`
```typescript
{
  branch: string;
  commits: {
    sha: string;
    message: string;
    stepNumber: number;     // Which plan step this fulfills
  }[];
  filesChanged: string[];
  testResults: {
    passed: boolean;
    output: string;
  };
}
```

**Exit criteria:** Code changes committed, tests pass (or failures noted)

---

### 5. Verify Phase
**Goal:** Confirm work meets requirements

**Entry criteria:** Implementation artifact exists

**What it does:**
- Compare output against acceptance criteria
- Self-review code quality
- Check for regressions
- Prepare PR or report issues

**Artifact:** `Verification`
```typescript
{
  criteriaResults: {
    criterion: string;
    met: boolean;
    evidence: string;
  }[];
  selfReview: {
    issues: string[];       // Problems agent spotted
    suggestions: string[];  // Improvements it would make
  };
  status: 'ready' | 'needs_work' | 'blocked';
  prUrl?: string;           // If ready, the PR
  blockers?: string[];      // If blocked, why
}
```

**Exit criteria:** PR created, or clear report of what's incomplete

## Vocabulary Cheat Sheet

| Term | Meaning |
|------|---------|
| **Workflow** | Full sequence of phases for a task type |
| **Phase** | Bounded step with entry/exit criteria and artifact |
| **Artifact** | Persisted output from a phase |
| **Checkpoint** | Pause point between phases for human review |
| **Context** | Information accumulated through the workflow |
| **Tool** | Atomic action (read, write, search, test) |
| **Entry criteria** | What must be true to start a phase |
| **Exit criteria** | What must be true to complete a phase |

## Example Usage in v2.1 Discussions

When starting v2.1, you can say:

> "For Phase 23, I want to implement the core **workflow** with all five **phases**. Each phase produces its **artifact**. We'll have **checkpoints** after discuss and plan phases for human approval. The **verify phase** should loop back to execute if criteria aren't met."

This is precise enough to build from without ambiguity.

## Future Considerations (Not v2.1)

- **Multi-agent coordination**: Separate agents for each phase (like GSD's researcher/planner/executor). Adds complexity but enables parallelization and specialization. Consider for v2.2+.
- **Workflow variants**: Different workflows for different task types (feature vs bug vs refactor).
- **Learning from feedback**: Agent improves based on PR review comments. Requires feedback loop infrastructure.
