# v2.1 Milestone Brief: Agents That Ship

**Captured:** 2026-01-25
**Purpose:** Reference for v2.1 milestone planning

---

## Objective

By the end of v2.1, both agents work end-to-end:
- **Product-agent** takes conversations/requests and produces well-defined Linear issues
- **Dev-agent** takes those issues and produces mergeable PRs

The agents work like junior coworkers - they ask good questions, do thorough research, plan before acting, and produce quality output.

---

## Success Criteria (End-to-End)

**The milestone is complete when:**

1. **Full loop works:** Human describes feature in Slack → product-agent creates Linear issue → dev-agent produces PR → human reviews and merges

2. **Product-agent can:**
   - Receive feature request via Slack
   - Ask clarifying questions to refine scope
   - Create well-structured Linear issue with acceptance criteria
   - Issue is clear enough for dev-agent to execute

3. **Dev-agent can:**
   - Receive Linear issue via webhook
   - Spin up dev container with cloned repo
   - Research codebase naturally (grep, find, read files)
   - Plan implementation and get approval
   - Write code, run tests, commit - all in container
   - Push and create PR

4. **Both agents:**
   - Communicate status via Slack
   - Ask for help when stuck (not silently fail)
   - Handle feedback loops (clarifications, revisions)

**The bar:** Output quality matches "competent junior developer" - not perfect, but reasonable and reviewable.

---

## Lessons from v2.0 (Embedded)

| Lesson | How v2.1 Addresses It |
|--------|----------------------|
| "Infrastructure phases must include consumer migration" | Every phase that builds infrastructure MUST include wiring it to actual usage |
| "Verify end-to-end, not just deliverables" | Each phase includes E2E verification checkpoint |
| "Pure library pattern" | Already fixed in v2.0; maintain this |
| "Gap phases appeared late" | Define success criteria upfront; phases work backward from E2E goal |

**v2.1 Rule:** No phase is complete until its output is verified working in the full flow.

## Agent Distinction

### Product Agent

**Role:** Product manager. "What should we build and why?"

**Trigger:** Slack message (feature request, bug report, question)

**Workflow:**
```
Slack message
     ↓
┌─────────────┐
│   Listen    │ ← Receive message, determine if actionable
└──────┬──────┘
       ↓
┌─────────────┐
│  Interpret  │ ← Understand what's being asked, identify gaps
└──────┬──────┘
       ↓
┌─────────────┐
│   Discuss   │ ← Ask clarifying questions via Slack thread
└──────┬──────┘
       ↓
┌─────────────┐
│   Refine    │ ← Break down scope, define acceptance criteria
└──────┬──────┘
       ↓
┌─────────────┐
│   Create    │ ← Create Linear issue(s)
└──────┬──────┘
       ↓
┌─────────────┐
│   Notify    │ ← Confirm in Slack with issue link
└─────────────┘
```

**Key behaviors:**
- Asks "why" and "for whom"
- Breaks large requests into shippable increments
- Writes issues that dev-agent can execute without ambiguity
- Confirms understanding before creating issues
- Does NOT write code

**Output artifact:** Linear issue with:
- Clear problem statement (what and why)
- Defined scope (in/out)
- Acceptance criteria (testable)
- Context links (related issues, docs)

---

### Dev Agent

**Role:** Developer. "How do we build it?"

**Trigger:** Linear issue webhook (issue created/updated with right label/status)

**Execution model:** Works inside a **persistent dev container** with cloned repo - like a real developer with shell access.

**Workflow:**
```
Linear issue
     ↓
┌─────────────┐
│   Setup     │ ← Spawn dev container, clone repo, create branch
└──────┬──────┘
       ↓
┌─────────────┐
│   Discuss   │ ← Clarify technical ambiguities (if needed)
└──────┬──────┘
       ↓
┌─────────────┐
│  Research   │ ← Explore codebase via shell (grep, find, cat)
└──────┬──────┘
       ↓
┌─────────────┐
│    Plan     │ ← Design implementation, get human approval
└──────┬──────┘
       ↓
┌─────────────┐
│   Execute   │ ← Write files, run tests, commit (in container)
└──────┬──────┘
       ↓
┌─────────────┐
│   Verify    │ ← Full test suite, self-review, push branch
└──────┬──────┘
       ↓
┌─────────────┐
│   Submit    │ ← Create PR via API
└──────┬──────┘
       ↓
┌─────────────┐
│  Feedback   │ ← Respond to PR review (container still alive)
└─────────────┘
```

**Key behaviors:**
- Works in a real environment (not API calls per file)
- Explores codebase naturally (grep, find, ripgrep)
- Runs tests as it goes (fast feedback)
- Commits incrementally (good git history)
- Container persists for feedback loop

**Output artifact:** Mergeable PR with:
- Clear title and description
- Links to Linear issue
- Passing tests
- Atomic commits with clear messages

### The Handoff

```
┌──────────────────┐                    ┌──────────────────┐
│   Product Agent  │                    │    Dev Agent     │
│                  │                    │                  │
│  Slack message   │                    │  Linear issue    │
│       ↓          │                    │       ↓          │
│  Clarification   │                    │  Spawn container │
│       ↓          │                    │       ↓          │
│  Linear issue ───┼───── webhook ─────▶│  Research + Plan │
│                  │                    │       ↓          │
│                  │◀─── notification ──│  Execute + PR    │
│                  │                    │                  │
└──────────────────┘                    └──────────────────┘
```

**Contract:**

Product-agent produces issues with:
- Problem statement (what, why, for whom)
- Scope boundaries (in/out)
- Acceptance criteria (how to verify)
- Context (related issues, docs, conversations)

Dev-agent expects:
- Unambiguous requirements (or permission to ask)
- Testable acceptance criteria
- Access to relevant context

### Event Flow Architecture

**Webhook Flow:**
```
External Service → Cloudflare Tunnel → nginx:80 → Integration Service
                                                         │
                                                         ▼
                                              ┌─────────────────────┐
                                              │  1. Verify signature │
                                              │  2. Check idempotency│
                                              │  3. Parse payload    │
                                              │  4. Normalize event  │
                                              │  5. Dispatch         │
                                              └──────────┬──────────┘
                                                         │
                                                         ▼
                                              ┌─────────────────────┐
                                              │  Event Dispatcher   │
                                              │                     │
                                              │  Routes by type:    │
                                              │  • linear.* → agent │
                                              │  • github.* → agent │
                                              │  • slack.* → agent  │
                                              └──────────┬──────────┘
                                                         │
                                                         ▼
                                                   Agent /events
```

**Normalized Event Schema:**
```typescript
interface NormalizedEvent {
  id: string;                    // Unique event ID
  type: string;                  // e.g., "linear.issue.created"
  source: "linear" | "github" | "slack";
  timestamp: string;             // ISO 8601
  correlationId: string;         // For log correlation
  payload: LinearEventPayload | GitHubEventPayload | SlackEventPayload;
}
```

**Dispatcher Routing Config:**
```typescript
// Linear Integration routing
{
  routes: {
    "linear.issue.created": {
      target: "http://dev-agent:3004/events",
      mode: "async",
      filter: { labels: ["agent-ready"] }
    },
    "linear.comment.created": {
      target: "http://dev-agent:3004/events",
      mode: "sync"
    }
  }
}

// Slack Integration routing
{
  routes: {
    "slack.message.created": {
      target: "http://product-agent:3005/events",
      mode: "async",
      filter: { channelId: "${SLACK_CHANNEL_ID}" }
    },
    "slack.approval.clicked": {
      target: "dynamic",  // Based on correlatedAgentId
      mode: "sync"
    }
  }
}
```

│     ─────────────────────────────────────────────────────────────────────      │

│     If fails → LangGraph analyzes error, fixes, retries                        │
│     If passes → commit:                                                        │
│                                                                                │

│                                                                                │
│  5. VERIFY (full test suite)                                                   │
│     ─────────────────────────────────────────────────────────────────────      │

│     exec: pnpm typecheck                         # Type check                  │
│                                                                                │
│     If fails → back to EXECUTE to fix                                          │

│                                                                                │
│     exec: git push -u origin feature/{issueId}                                 │
│                                                                                │
│                                                                                │
│  6. FEEDBACK (container stays alive)                                           │
│     ─────────────────────────────────────────────────────────────────────      │
│     PR review received → GitHub webhook → dev-agent                            │
│     Agent resumes in SAME container (code still there)                         │
│                                                                                │
│     exec: git pull                                                             │
│     # ... make fixes based on review feedback ...                              │
│     exec: git commit -m "fix: address review feedback"                         │
│     exec: git push                                                             │
│                                                                                │
│                                                                                │
│  7. CLEANUP (task completes or timeout)                                        │
│     ─────────────────────────────────────────────────────────────────────      │
│     docker rm -f dev-container-{taskId}                                        │
│                                                                                │
│     Container lifetime:                                                        │
│     • Lives until PR merged/closed                                             │
│     • Or timeout (e.g., 24 hours of inactivity)                                │
│     • Or explicit cleanup on task completion                                   │
│                                                                                │

## Plan Approval: Dual-Channel Approach

### Why Both Linear and Slack?

| Channel | Strength | Weakness |
|---------|----------|----------|
| **Linear** | Context stays with issue, traceable history, permanent record | Might miss if not watching |
| **Slack** | Real-time notification, quick response | Context split from issue |

**Solution:** Post plan to **both**, accept approval from **either**.

### Good Discussion (Product Agent)

**Does:**
- Parses request to understand what's being asked
- Identifies ambiguities ("should this handle edge case X?")
- Makes explicit assumptions when reasonable
- Asks focused questions via Slack (not vague)
- Confirms scope boundaries

**Doesn't:**
- Ask obvious questions answered in the message
- Start creating issues without understanding
- Make silent assumptions about important decisions

### Good Research (Dev Agent)

**Does:**
- Finds relevant files (understands relationships)
- Identifies existing patterns
- Notes dependencies
- Flags risks
- Admits unknowns

**Doesn't:**
- Grep for one keyword and call it done
- Miss obviously related code
- Ignore existing patterns

### Good Code (Dev Agent)

**Does:**
- Follows existing patterns (naming, structure)
- Writes code that passes linting and type checks
- Includes appropriate error handling
- Makes atomic commits with clear messages
- Runs tests and ensures they pass

**Doesn't:**
- Invent new patterns when existing ones work
- Write code that breaks existing tests
- Make massive commits with unrelated changes

### Good PRs (Dev Agent)

**Does:**
- Clear title that summarizes the change
- Description explains what, why, how to test
- Links to Linear issue
- Reasonable commit history
- Passes CI checks

**Doesn't:**
- Submit PRs with failing tests
- Write vague descriptions
- Include unrelated changes

## Suggested Phase Structure

Based on v2.0 lessons: **every phase includes E2E verification**.

| Phase | Focus | E2E Verification |
|-------|-------|------------------|
| **23** | Webhook → Integration → Dispatcher plumbing | Webhook arrives, event dispatches to agent /events |
| **24** | Dev container infrastructure | Container spawns, agent can exec commands, cleanup works |
| **25** | Product-agent workflow (Slack → Linear) | Message in Slack → issue in Linear with correct content |
| **26** | Dev-agent workflow (Linear → PR) | Issue in Linear → PR in GitHub with working code |
| **27** | Human-in-the-loop (approvals, feedback) | Approval resumes workflow; PR feedback triggers revision |
| **28+** | Quality gaps | Based on what breaks in 25-27 |

**Critical:** Phases 25-27 each verify their complete loop works, not just "code is written."
